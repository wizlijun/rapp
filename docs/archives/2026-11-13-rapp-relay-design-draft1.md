| G2 | relay 被攻破以后，数据不被劫持：拿到 relay 的人不能冒充设备，也不能插进已有的连接 | 用户已定，U63 |
| G3 | 没有经过统一认证的，访问不到 | 用户已定，U62 |
| G4 | 不消耗额外资源，流畅，轻量 | 用户已定，U63 |
| G5 | relay 与业务无关，是纯技术方案 | 用户已定，U64 |
| G6 | 选最成熟的做法，不自己发明 | 用户已定，U64 |
| G7 | 生产级：可靠，能长期无人值守地跑 | 用户已定，U71 |
| G8 | 架构将来能扩成 SaaS；初期是单节点、个人部署 | 用户已定，U71 |

不做（第一版）：

- Docker 镜像以外的发布形式；在 macOS、Windows 主机上跑 relay。

- 多节点、多地区。
- 账号、计费、网页管理界面。
- TCP 备用入口；给不是 rapp 设备的客户端（比如外部小屏）用的入口。§10 留了位置。
- 对 relay 隐藏"谁在什么时候连了谁"。relay 是牵线的，这些它必然知道（§2.3）。

不能出现的结果（做成了也算失败）：

- relay 的代码里出现业务概念（app、便签、文件、剪贴板）。
- 为了安全，远程会话明显变慢。
- 升级之后，用户要到每一台设备跟前重新设置一遍；或者升级到一半，远处无人值守的那台机器连不上了。
- 自己设计加密算法或者握手。

## 1. 现状

核对过代码（`rust/relay/src/`、`rust/net/src/quic.rs`、`rust/service/src/peer.rs`、`rust/service/src/relay_link.rs`、`rust/hub/src/link.rs`）。

| 方面 | 现在 | 问题 |
|---|---|---|
| 中继 | relay 把 B 的一条流和 A 的一条流接起来。每份数据在 relay 上先解密、再加密 | relay 看得到全部内容（画面、键盘输入、文件） |
| relay 的身份 | 证书自签，设备不校验（代码里叫 `AcceptAny`） | 网络中间的人可以冒充 relay，拿到 relay key 和设备密码 |
| 设备的身份 | 设备没有自己的密钥。A 认 B，靠的是 relay 发的令牌 | 拿到 relay 的人可以给自己发令牌，冒充任何 B |
| 密码 | B 把明文密码发给 relay，relay 核对。局域网退路上 B 把明文密码发给 A | relay 能看到每台设备的密码；局域网里冒充 A 的人也能拿到 |
| 准入 | 一个共享的 relay key，每个请求都带。启动时从命令行传入 | 一处泄露，全部设备都要换；命令行参数在进程列表里看得到 |
| 存储 | `relay.json`，存 `secret` 的哈希、密码的哈希（单次 SHA-256）、设备名 | 文件泄露后可以离线穷举密码。密码是 8 位字母数字，约 46 位，穷举得动 |
| 会话 | 一个远程会话就是一条流，从头到尾 | 不是问题。它决定了 §4 的选择 |

## 2. 威胁模型

### 2.1 要防的人

| 代号 | 是谁 |
|---|---|
| T1 | 设备和 relay 之间网络上的人（能看、能改、能冒充任何一方的地址） |
| T2 | 互联网上任何能连到 relay 端口的人 |
| T3 | 完全拿到 relay 那台机器的人（能读磁盘和内存，能换掉 relay 程序） |
| T4 | 和设备在同一个局域网里的人 |
| T5 | 拿到了 key 的人 |

### 2.2 做完以后各自能做什么

| | 看到内容 | 冒充已有的设备 | 作为新设备加进来 | 让服务不可用 |
|---|---|---|---|---|
| T1 | 不能 | 不能 | 不能 | 能（任何在路上的人都能丢包） |
| T2 | 不能 | 不能 | 不能 | 被限速和上限挡住（§8.2） |
| T3 | 不能 | 不能 | 不能：relay 手里没有 key，只有它的一个单向的校验值（§5.2） | 能 |
| T4 | 不能 | 不能 | 不能 | 能（局域网内） |
| T5 | — | 不能 | **能。有 key 就是自己人，可以访问每一台还在接受新设备的设备** | — |

"劫持数据"（U63）对应前三列。T1 到 T4 都是"不能"。

**T5 这一行是"有了 key 就互相信任"（U77）的直接后果，要用户清楚：key 现在等于所有设备的总钥匙。** 以前拿到 relay key 的人只能占用 relay；现在拿到 key 的人能远程操作你的设备。挡住它的办法有两个开关（§6.4）和换 key（§6.5）。

这张表说的是 §11 的各步全部做完以后。升级中途的情况见 §11。

### 2.3 relay 仍然知道的

内容之外的这些，relay 作为牵线的一方必然知道，做完以后也一样：

- 每台设备的 ID、公钥指纹、公网地址、局域网地址。
- 谁在什么时候连了谁，走没走中继，中继了多少字节、多久。

relay 不再知道的：设备密码、设备名、任何令牌、任何内容。

用户的原话是"relay 不能看到任何内容"。我把"内容"理解为设备之间传的数据，不包括上面这些。要你确认（§14 第 1 条）。

## 3. 做法的比较

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | **relay 照旧接流，两台设备在接好的流里面再做一次 TLS 1.3。** 和浏览器经过代理访问 HTTPS 网站是同一个模式：代理只负责接通，加密在两头之间 | 改动最小；relay 的数据路径一行不用改，性能和现在实测的一样；这个模式是互联网上用得最久的；加密层不挑传输，以后加 TCP 入口也能用；连旧 relay 都能先用起来（§11） | relay 上仍然有一次解密和一次加密（和现在一样，不增加）；经中继的每条流多一次握手 |
| 乙 | 两台设备之间永远是一条端到端的 QUIC 连接；relay 只转发数据包，不接流 | relay 最轻；连接可以在直连和中继之间无缝切换 | service 和 hub 的连接层要重写；QUIC 套 QUIC 有包长和拥塞控制叠加的问题，要专门调；要自己设计转发包的格式和鉴权 |
| 丙 | 改用 iroh（一个 Rust 库，2026 年 6 月发布 1.0，承诺线上协议稳定）。它按公钥拨号，自带端到端加密、打洞和不看内容的 relay，relay 程序开源可自建 | 自己写的代码最少；打洞比 rapp 现在的做法强，走中继的机会更少 | 连接层全部换掉；多一个大依赖，1.0 才发布五个月；它的中继走 HTTP(S)（据我所知是在 TCP 上，这一点没有核对到原文）；9 位 ID 加密码这一套还得自己另做一个目录服务；relay 不再是自己的 |
| 丁 | 设备之间先用 WireGuard、Tailscale 一类工具组网 | 很成熟 | 每台设备多装一样东西，平板上尤其麻烦；之前已经排除（U64 的讨论） |

**选甲（我定的，方向是用户在 U65 认可的）。** 理由：

- 一个远程会话本来就是一条流（§1 最后一行）。在这条流里套一层 TLS，会话期间没有额外的往返，只多一层对称加密。
- G4 要求不比现在慢。甲不动 relay 的数据路径，所以现在的实测数字可以直接当基线；乙和丙都要重新证明。
- G6 要求最成熟。甲用到的只有 TLS 1.3，加上哈希、单向推导、消息认证码这几样最基本的东西（§5.2、§6.3），库都是 rapp 已经在用的。
- 甲不挡路：以后想换成乙那样更轻的转发，端到端这一层（设备密钥、用 key 互信、记住的指纹）原样可用。

丙是一个认真的备选，不是凑数的。如果你更看重"少维护自己的网络代码"，而不是"relay 是自己的、能做成 SaaS"，应该选丙。要你确认（§14 第 2 条）。

## 4. 结构

### 4.1 relay 只做三件事

| 功能 | 做什么 | 和现在比 |
|---|---|---|
| 登记 | 设备连上来，证明自己是谁，报上自己的地址。relay 记住"这个 ID 现在在线，连接是这一条" | 证明身份的方式变了（§5） |
| 牵线 | B 说要找某个 ID。relay 告诉 B 对方的地址，同时通知 A"有人要来"，A 借此打洞 | 不再核对密码，不再发令牌 |
| 接流 | 直连不通时，B 请 relay 接一条流到 A。relay 在 A 的长连接上开一条流，把两条流双向原样对接 | 数据路径不变。流里的内容 relay 解不开 |

relay 不知道流里是远程会话、文件还是别的数据服务。以后的数据服务（PD14）就是设备之间的又一种流，relay 不用为它改任何东西。

### 4.2 四层

| 层 | 在谁和谁之间 | 是什么 | 标识 |
|---|---|---|---|
| L1 传输 | 设备 ↔ relay；设备 ↔ 设备（直连时） | QUIC，自带 TLS 1.3。双方都出示证书 | 和现在一样的端口：relay `21116/udp`，设备 `21118/udp` |
| L2 relay 协议 | 设备 ↔ relay | 每条流上一行 JSON 请求、一行 JSON 回复（和现在一样的形式）：入网、登记、牵线、接流 | ALPN `rapp-relay/2` |
| L3 端到端 | 设备 ↔ 设备 | TLS 1.3，双方互相验证设备密钥。直连时就是 L1 的那次握手；经中继时是在接好的流里面再握一次 | 直连 ALPN `rapp/2`；流内 ALPN `rapp-e2e/1` |
| L4 设备请求 | 设备 ↔ 设备 | 现有的请求：`list_apps`、`ping`、`open`；新增 `pair`（互相证明有 key，§6.3）、`set_key`（把新 key 发给认识的设备，§6.5） | 不变 |

直连时只有一层加密。经中继时有两层：设备到 relay 的一段（L1），和设备到设备的全程（L3）。relay 只能解开外面那一层，里面是 L3 的密文。

### 4.3 一次经中继的连接

```
B                          relay                         A
│── QUIC 握手，互相出示证书 ──▶│◀── QUIC 长连接，已登记 ──────│
│── {"op":"connect","id"} ──▶│── {"op":"incoming",...} ───▶│   A 向 B 的地址打洞
│◀─ {"ok","lan","public"} ───│◀─ {"ok"} ──────────────────│
│   （局域网、直连都不通）                                    │
│── {"op":"relay","id"} ────▶│── {"op":"relayed",...} ────▶│
│◀════════ relay 把两条流对接，此后只搬字节 ═════════════════▶│
│◀──────────── TLS 1.3 握手（L3），互相验证设备密钥 ──────────▶│
│◀──────────── {"op":"open",...} 等请求，全程密文 ───────────▶│
```

## 5. 身份和准入

### 5.1 设备密钥

- 每台设备第一次启动时生成一对密钥和一张自签证书，长期使用。算法用 ECDSA P-256（我定的：它是 TLS 里支持最广的，将来单片机上的客户端也能用）。
- 存在数据目录的 `local/device.key`、`local/device.crt`，权限 0600。`local/` 不进 git（数据目录规格 D4）。
- 同一台机器上的 service（被控的一侧）和 hub（操作的一侧）共用这一对密钥。
- **指纹** = 证书里公钥部分（SubjectPublicKeyInfo）的 SHA-256。界面上显示成分组的字母数字。
- 验证只看指纹，不看证书的有效期、签发者、名字。所以不依赖设备的时钟准不准。
- 9 位 ID 保留，仍然是给人看、给人输入的地址。ID 只用来找到设备；信不信对方，只看密钥。

### 5.2 接入点和 key（照 RustDesk 的做法）

用户已定（U74）。RustDesk 的做法是：设备上填服务器的地址和一个 key，就接入了；之后设备之间用 ID 互相访问。rapp 照这个做。

- **设备上只填两样：接入点和 key。** 接入点是 relay 的地址（`主机:端口`）。字段名和现在 `service.json` 里的一样，还是 `relay` 和 `key`，界面不用变。
- **key 是 relay 第一次启动时自己生成的一串字符**，约 50 个，只有小写字母和数字，方便整串选中复制。在 relay 上用 `rapp-relay key` 查看。它不出现在任何日志里。
- **接入以后，设备之间用 ID 互相访问。有了 key 就互相信任，不再要密码**（U77）。设备密码整个取消。

key 里面其实是两段拼在一起的，用户不用知道，当成一个 key 用就行：

| 段 | 是什么 | 用来做什么 |
|---|---|---|
| 前一半 | relay 公钥指纹的前 16 字节 | 设备确认连上的是真的 relay。对不上就拒绝连接 |
| 后一半 | 16 字节的随机数，下面叫"根" | 设备从它算出两样东西，见下 |

从"根"用标准的单向推导（HKDF）算出两个互不相通的值：

| 值 | 谁知道 | 用来做什么 |
|---|---|---|
| 入网口令 | 设备和 relay | 设备向 relay 证明自己是自己人（§5.3）。relay 只存它的哈希 |
| 信任口令 | 只有设备 | 设备之间互相证明"我也有 key"（§6.3）。**relay 永远拿不到，也算不出来** |

这是 G2 还能成立的关键：relay 被拿到以后，那个人手里只有入网口令的哈希，推不回"根"，也就算不出信任口令，所以没法让任何设备信任他。

为了做到 relay 手里真的没有 key（我定的）：

- key 不是 relay 的服务进程生成的，而是管理命令 `rapp-relay key` 第一次运行时生成的。它把 key **显示一次**，只把入网口令的哈希写进数据卷，然后就忘了。
- 以后再运行 `rapp-relay key`，它会说 key 已经显示过。要再看 key，到任何一台已接入的设备的设置里看（设备存着它，默认遮住，点一下显示）。
- 剩下的风险：生成 key 的那一刻，relay 那台机器如果已经被人拿到，他能看到 key。

和 RustDesk 的区别：RustDesk 的 key 就是服务器的公钥，连设备还要另外的密码。rapp 的 key 多带了"根"，一个 key 同时管三件事：认 relay、进 relay、设备互信。

**没有 relay 的时候**（只在局域网里用 `id@ip`）：在第一台设备的设置里点"生成 key"，把它填到其他设备上。这种 key 没有前一半。以后架了 relay，换成 relay 的 key。（我定的）

将来的 SaaS：relay 用真实域名的证书，设备按域名校验；key 改由账号签发，只含入网凭据那一段。这是 §9 的事，第一版不做。

### 5.3 准入：没有密钥的连不上，没有入网的用不了

对应 G3。两道门：

1. **必须出示设备证书。** 不出示的，握手就被拒绝，连一条请求都发不了。
2. **必须入过网。** 设备第一次连 relay 时提交从 key 算出的入网口令（`enroll`）。relay 核对后记下这台设备的指纹。以后这台设备靠密钥就能进，不再提交口令。没入网的指纹只能调用 `enroll`，并且被限速。

和现在的 relay key 比：

| | 现在的 relay key | 新的 key |
|---|---|---|
| 谁定的 | 用户自己起一个，传给 relay | relay 自己生成 |
| 什么时候用 | 每个请求都带 | 核对 relay 的身份：每次连接。入网：每台设备只用一次 |
| 能不能确认 relay 是真的 | 不能 | 能 |
| 泄露以后 | 所有设备都要换，但别人只能占用 relay | 后果更重：别人能访问设备。处理见 §6.5 |
| 踢掉一台设备 | 做不到 | 在 relay 上吊销它的指纹 |
| 怎么给 relay 程序 | 命令行参数 | 不用给。relay 自己生成，存在数据卷里 |

还有一个开关：**关闭入网**。所有设备都接入以后，可以在 relay 上关掉入网（§8.7 的 `enroll`）。之后即使有人拿到 key，也加不进新设备。要加设备时再临时打开。（我定的）

### 5.4 ID 归谁

- 一个 ID 第一次登记时，就绑定到登记它的那把设备密钥。以后只有这把密钥能登记这个 ID。现在的 `secret` 字段不再需要。
- 重装系统丢了密钥，就拿一个新 ID，或者由管理员在 relay 上解除旧绑定。

### 5.5 管理

relay 所在的机器上，用同一个程序的子命令管理（通过一个只有本机能访问的套接字和运行中的 relay 说话）：

```
rapp-relay devices                 列出已入网的设备：ID、指纹、入网时间、最近在线
rapp-relay revoke <ID 或指纹>       吊销；它的连接立刻断开，以后握手被拒
rapp-relay unbind <ID>             解除 ID 和密钥的绑定
rapp-relay key                     第一次运行时生成 key 并显示一次（§5.2）
rapp-relay rotate-key              换 key：生成新的"根"，显示一次新的 key（§6.5）
rapp-relay audit [--since 7d] [--id …] [--event …]   查审计日志（§8.4）
rapp-relay check                   自检，给 Docker 的健康检查用
```

## 6. 设备之间：有 key 就互信

用户已定（U77）："有了 key 就互相信任、不再要密码"。

### 6.1 两种状态

对每一台对方设备，本机要么**认识**（存着对方的指纹），要么**不认识**。

- 每台设备都有一份认识的设备的列表：`local/paired.json`，每项是 `{指纹, 对方自报的名字, 认识的时间}`。
- B 的主机列表（`local/hosts.json`）里，每台主机多一个字段：对方的指纹。

### 6.2 认识的设备怎么连

L3 握手时双方出示证书，各自核对对方的指纹是不是存着的那个。对上了就通过。这一步不用 key，也不用 relay 发的任何东西。

B 发现 A 的指纹变了（比如 A 重装过）：只要 A 还能证明自己有 key（§6.3），就自动重新认识，并在界面上留一条提示"这台主机换了密钥"。证明不了就拒绝连接。

### 6.3 第一次怎么认识：用 key 自动完成

用户看到的：在 B 上输入 A 的 ID，就连上了。没有密码，没有确认框。

背后：L3 握手完成以后（这时双方还不认识对方的指纹），两边各发一个证明，证明"我有同一个 key"：

- 证明 = 用信任口令（§5.2）对"这次握手导出的一个值、双方的指纹、自己是哪一方"算一个消息认证码（HMAC-SHA-256）。
- **绑在这一次握手上**：中间人要插进来，就得和两头各握一次手，两边的导出值和指纹都不一样，他又没有信任口令，算不出对的证明。把一头的证明原样转给另一头也没用，因为对不上另一头的握手。
- 信任口令是 16 字节的随机数推出来的，猜不动，所以这里不需要专门的口令认证协议。握手导出值加消息认证码是把应用层的认证绑到 TLS 上的标准做法。
- 两边都验过以后，各自把对方的指纹记进认识的列表。以后走 §6.2。

没有 relay、用 `id@ip` 直接加主机时也是同一套。现在"密码认证只接受来自私有网段的连接"这条限制不再需要。

### 6.4 两个开关

key 是唯一的门，所以要有办法在不需要的时候把门关上。两个开关，默认都开（开着就是"有 key 就能进"）：

| 开关 | 在哪 | 关上以后 |
|---|---|---|
| 入网 | relay（§8.7 的 `enroll`） | 新设备即使有 key 也进不了 relay |
| 接受新设备 | 每台设备的设置 | 这台设备只认已经认识的指纹；不认识的即使有 key 也不理 |

建议写进说明：设备都接入、互相连过一次以后，把 relay 的入网关上，把无人值守的机器的"接受新设备"关上。这样即使 key 泄露，别人也进不来。要加新设备时临时打开。

设备自己的端口也可能暴露在公网上（打洞、端口映射）。所以设备的端点同样开 QUIC 地址验证；不认识的连接只能发证明，10 秒没动静就断；证明连续失败按来源限速（和现在 relay 上的数字一样：5 次以后第 n 次等 `min(2^(n-5), 300)` 秒）。

### 6.5 取消了密码以后

| | 现在 | 做完以后 |
|---|---|---|
| 连一台设备要什么 | 它的 ID 和密码 | 它的 ID（前提是两台都有同一个 key） |
| 设备密码 | 每台一个，界面上显示 | 没有了。界面上去掉 |
| 踢掉某一台设备 | 做不到，只能改密码踢掉全部 | 在 relay 上吊销它（`rapp-relay revoke`）。其余设备下次连 relay 时拿到吊销名单，把它从认识的列表里去掉，以后也不再认它 |
| 怀疑 key 泄露 | 改 relay key 和每台的密码 | 换 key（见下） |

**吊销名单为什么可以信 relay**：设备在"信任谁"上不听 relay 的，但"不再信任谁"可以听。relay 最多骗设备少信几台，那只是让服务不可用，而它本来就能做到。

**换 key**：

1. 在 relay 上运行 `rapp-relay rotate-key`，得到新的 key（显示一次）。
2. 在手边的一台设备上填新 key。
3. 这台设备把新 key 发给它认识的其他设备（走已有的端到端连接），它们再往下传。不在线的设备上线后从认识的设备那里拿到。

换 key 不影响已经认识的设备之间的连接（它们靠指纹）。影响的是以后：拿旧 key 的人进不了 relay，也没法让换过 key 的设备认他。

**丢了一台设备**：先吊销它，再换 key。顺序不能反，否则它也会收到新 key。

## 7. relay 协议（`rapp-relay/2`）

形式和现在一样：每个请求开一条流，一行 JSON 请求，一行 JSON 回复。身份来自这条连接握手时出示的证书，所以请求里不再带 key。

| 请求 | 谁发 | 内容 | 回复 |
|---|---|---|---|
| `enroll` | 没入网的设备 | `{"op":"enroll","join":"…"}` | `{"ok":true,"relay":{"version","features":[…]}}` |
| `register` | A | `{"op":"register","id":"123456789"\|null,"lan":["192.168.1.5:21118"]}` | `{"ok":true,"id":"…"}`；错误 `id taken`、`not enrolled` |
| `connect` | B | `{"op":"connect","id":"…"}` | `{"ok":true,"lan":[…],"public":"1.2.3.4:21118"}`；错误 `unknown id`、`offline`、`locked, retry in 12s`、`not enrolled` |
| `relay` | B | `{"op":"relay","id":"…"}` | 成功时不回 JSON，直接对接；失败回 `unknown id`、`offline` |

relay 发给 A 的：

| 消息 | 内容 | 说明 |
|---|---|---|
| `incoming` | `{"op":"incoming","peer":"<B 的公网地址>","fp":"<B 的指纹>"}` | A 回 `{"ok":true}` 并向 `peer` 打洞。`fp` 只供日志用，A 不拿它做判断 |
| `relayed` | `{"op":"relayed","peer":"…","fp":"…"}` | 这一行之后，这条流就是 B 发来的字节。A 在上面当 TLS 服务端 |

relay 发给任何设备的：

| 消息 | 内容 | 说明 |
|---|---|---|
| `revoked` | `{"op":"revoked","fps":["…"]}` | 设备连上时发一次，名单有变化时再发。设备据此取消认识（§6.5） |
| `going_away` | `{"op":"going_away","after_ms":3000}` | relay 要重启。设备等一会儿再重连，重连间隔带随机量 |
| `redirect`（作为 `register`、`connect`、`relay` 的回复） | `{"ok":false,"error":"redirect","relay":"host:port"}` | 第一版的 relay 不会发。设备要实现"照着去连那个地址，同样核对身份，最多跳一次"。这是给多节点留的口子（§9） |

和现在比，去掉的：每个请求里的 `key` 字段、`secret`、`pw_salt`、`pw_hash`、`name`、`password`、`token`。relay 上没有令牌了，所以"令牌 24 小时有效""改密码后旧令牌作废"这些问题一并消失。

`connect` 的限速：按发起方的指纹和来源地址、按目标 ID 分别计数，防止有人拿 relay 当跳板去敲 A 的门。

## 8. 可靠性（生产级）

### 8.1 进程和状态

- 一个进程，一个 UDP 端口。没有外部依赖（不要数据库、不要别的服务）。以一个 Docker 镜像发布（§8.5）。
- **持久的状态**都在一个数据卷里：relay 自己的密钥、入网口令、入网设备表（指纹、ID、所属租户、入网时间、是否吊销）、可选的配置文件、审计日志。清单见 §8.7。写入时先写临时文件、落盘、再改名；权限 0600。
- **内存里的状态**：谁在线、限速计数。重启就清空，设备重连后自动恢复。
- 存储藏在一个接口后面（读设备、写设备、按 ID 找）。第一版的实现是文件，SaaS 时换成数据库，上面的代码不动。
- **`relay.key` 丢了的后果**：所有设备上的 key 都对不上，要逐台重新填。所以说明里写明要备份数据卷。

### 8.2 上限和限速

全部可配，下面是默认值（我定的；实测后可以调）：

| 项 | 默认 | 防什么 |
|---|---|---|
| QUIC 地址验证 | 一直开 | 伪造来源地址，拿 relay 放大流量打别人 |
| 没出示证书 | 握手拒绝 | T2 |
| 没入网的连接 | 只能 `enroll`；10 秒没动静就断；每个来源地址每分钟 10 次 | 猜入网口令 |
| 入网口令猜错 | 和 §6.4 同样的退避 | 同上 |
| 每个来源地址的连接数 | 16 | 占满连接 |
| 总连接数 | 4096 | 占满内存 |
| 每条连接的并发流 | 128（现在是 1024） | 占满内存 |
| 每台设备同时被中继的流 | 32 | 同上 |
| 一行请求的长度 | 8 KiB（现在是 64 KiB） | 同上 |
| 入网设备数 | 1024 | 入网口令泄露后被灌满 |
| 中继的带宽 | 不限（可以按每条流、按总量设上限） | SaaS 时按租户限 |

### 8.3 重启和升级

- 收到停止信号：不再接新连接，给所有设备发 `going_away`，然后退出。
- 设备的重连：1 秒起，翻倍到 60 秒，每次加随机量（现在没有随机量；设备多了会同时涌回来）。
- 单节点时，正在中继的会话会断。hub 已有断线重连（多客户端规格），会话自己接上。目标：relay 重启后 5 秒内设备重新在线。
- relay 重启不影响局域网和直连的会话：它们不经过 relay。

### 8.4 日志、审计和指标

用户已定（U75）：留日志做审计用。所以日志分成两种，用处不同，放的地方也不同。

| | 运行日志 | 审计日志 |
|---|---|---|
| 给谁看 | 排查问题的人 | 事后要查"谁在什么时候做了什么"的人 |
| 记什么 | 出错、状态变化、每 5 分钟一行统计 | 每一次和准入、身份、连接有关的动作，成功和失败都记 |
| 写到哪里 | 标准错误，由 Docker 收集 | 数据卷里的文件：`/data/audit/2026-11-13.jsonl`，一天一个 |
| 换容器以后 | 没了（Docker 的日志跟着容器走） | 还在 |
| 保留多久 | compose 示例里设 5 个文件、每个 10 MB | 默认 180 天，总量不超过 256 MB，先删最旧的（可配，§8.7） |
| 设备怎么标识 | 指纹的前 8 位 | 完整的指纹 |

**审计日志的格式**：一行一条 JSON，只追加，文件权限 0600。每条都有时间（UTC，精确到毫秒）、事件名、租户、结果；和设备有关的带完整指纹、ID、来源地址。

**审计日志记的事件：**

| 事件 | 什么时候 | 带什么 |
|---|---|---|
| `relay_start`、`relay_stop` | 启动、停止 | 版本、生效的配置（不含机密）、停止的原因 |
| `enroll` | 一次入网尝试 | 指纹、来源地址、结果（`ok`、`bad key`、`closed`、`limit`） |
| `register` | 设备登记 | 指纹、ID、来源地址、结果（`new`、`ok`、`replaced`、`id taken`、`legacy claim`） |
| `connect` | B 请求牵线 | 发起方的指纹和地址、目标 ID、结果 |
| `relayed` | 一条中继流结束 | 发起方指纹、目标 ID、持续多久、两个方向各多少字节 |
| `lockout`、`limit` | 被限速、撞到上限 | 是哪一项、针对谁 |
| `revoke`、`unbind`、`rotate_key`、`enroll_open`、`enroll_close` | 管理动作 | 执行的是哪条命令、对象是谁 |
| `audit_prune` | 删掉了过期的审计文件 | 删了哪几天的 |

规则（我定的）：

- **永远不记**：key、入网口令、任何私钥、流里的任何内容。
- **在线探测不逐条记。** 设备每 30 秒探测一次对方在不在，经中继时每次都是一条很短的流。它们按"发起方和目标"每小时合并成一行（探测了几次）。真正的会话每条都记。区分的办法沿用现在的：5 秒以内、8 KiB 以内的算探测。
- **准入和管理类的事件立刻落盘**；其余的最多攒 1 秒。
- **审计写不进去时（比如磁盘满）**：默认继续服务，同时在运行日志里报错。可以配成"写不进就拒绝新的入网和牵线"（§8.7 的 `audit.required`），给看重审计胜过可用的部署用。
- **审计日志同时也写一份到标准错误**，带一个标记。这样用 Docker 的日志驱动就能把它实时送到另一台机器。要防"拿到 relay 的人改日志"，只有这一个办法：日志在他拿到之前已经送走了。本机的文件防不住他，所以不做哈希链之类的东西。
- 查的时候用 `rapp-relay audit`，或者直接读文件。

**审计日志能回答的问题**：这台设备是什么时候、从哪个地址入网的；某个 ID 被谁连过、什么时候、连了多久、传了多少；有没有人在试 key、试了多少次；谁在什么时候吊销了哪台设备。**不能回答的**：连上以后做了什么。那在被控端自己的访问记录里。

**设备这一侧**：被控端已有访问记录（可观测性规格：认证失败、每个请求、会话的开始和结束）。本文新增的动作也记进去：认识了一台新设备（成功、失败及原因，对方的指纹、自报的名字、来源地址、走的哪条路）、因为吊销名单取消了认识、"接受新设备"的开关、对方的密钥变了、relay 的身份对不上、key 被换了（只记发生了，不记 key）。保留多久沿用可观测性规格。

**运行日志**：沿用可观测性规格的结构化事件，事件名不变。每 5 分钟一行统计：在线设备数、正在中继的流数、这段时间中继的字节数、握手失败数、被限速的次数。

**指标接口**：可选，默认关。开了以后只在本机地址上提供 Prometheus 格式的数字。不对公网开，所以"只暴露一个端口"仍然成立。

**健康检查**：`rapp-relay check` 对自己做一次真实的握手，成功退出 0。

### 8.5 发布和部署：只发一个 Docker 镜像

用户已定（U72）："relay 发布为 docker 部署，只发一个最专业的轻量的 linux 分发的 docker 包，尺寸越小越好"。

**发布物只有一个：Docker 镜像。** 不再单独发二进制，不再发 systemd 单元和 `upgrade-relay.sh`，macOS 打包脚本里交叉编译 relay 的那一段去掉。

| 项 | 定法 |
|---|---|
| 基础镜像 | Alpine Linux（我定的：它是最通用的轻量发行版，基础层约 8 MB，压缩后约 4 MB）。版本固定到具体的小版本和摘要，不用 `latest` |
| 镜像里有什么 | Alpine 的基础层，加 `rapp-relay` 一个二进制。不装任何别的包 |
| 架构 | 同一个镜像标签下带 x86_64 和 arm64 两种，Docker 自动取对的那个。对用户来说是"一个包" |
| 怎么构建 | 多阶段构建：第一阶段在 Rust 的 Alpine 镜像里编译，第二阶段只把二进制拷进干净的 Alpine。编译用的工具不进最终镜像 |
| 二进制怎么压小 | 去掉符号；全程序优化；单编译单元；出错直接中止而不展开调用栈；tokio 只开用到的功能。**不用"按体积优化"的编译档位**：relay 的数据路径要快（G4），体积让位于速度 |
| 大小目标 | 镜像压缩后 10 MB 以内。这是估计，第一次构建出来后把实际数字写进发布说明 |
| 运行身份 | 非 root 的固定用户；根文件系统只读；去掉全部特权；禁止提权 |
| 数据 | 只挂一个卷 `/data`，里面有什么见 §8.7 |
| key | relay 第一次启动时自己生成，存在数据卷里。启动容器不需要传任何机密。`--key` 参数去掉 |
| 网络 | 主机网络模式。relay 靠"看到的对端地址"做限速和打洞，别的网络模式可能把地址改写掉。要实测确认（§14 第 5 条） |
| 健康检查 | 镜像自带：定期跑 `rapp-relay check` |
| 日志 | 运行日志写到标准错误，由 Docker 收集，compose 示例里设好大小上限和轮转。审计日志写在数据卷里（§8.4） |
| 管理 | `docker exec rapp-relay rapp-relay devices` 这样调用 §5.5 的命令 |
| 升级 | `docker compose pull && docker compose up -d`。relay 收到停止信号时按 §8.3 通知设备 |
| 镜像标签 | 每个版本一个固定标签（如 `0.6.0`），另有 `0.6` 这样跟随小版本的标签。compose 示例里写固定标签 |
| 发布到哪里 | GitHub 的镜像仓库（`ghcr.io/wizlijun/rapp-relay`）。我按代码仓库的位置填的，可以改 |

随镜像提供的只有一份 `docker-compose.yml` 示例和几行说明（开放 `21116/udp`；备份 `/data`）。

**基础镜像还能再小**：不带任何发行版（Docker 里叫 `scratch`），镜像里就只有那一个二进制，再小 4 MB 左右，也没有任何别的程序可以被利用。代价是容器里没有 shell，进不去排查；`rapp-relay` 自己的管理命令和健康检查不受影响。你说的是"轻量的 Linux 分发"，所以我按 Alpine 写；想要最小的，告诉我，改一行。

**由此带来的两个变化：**

- **relay 只能跑在 Linux 主机上。** Mac 上的 Docker 跑在虚拟机里，容器看不到真实的来源地址，relay 的限速和打洞都会失效。之前"也提供 macOS 的最精简实现"（安全要求草稿的 R4）不再做。开发和测试时仍然可以直接运行编译出来的程序，那不是发布物。
- **现有的 VPS 是用 systemd 直接跑二进制的。** 升级到本文的版本时要换成 Docker：停掉旧服务，把旧的 `relay.json` 放进数据卷（§11 第二步要导入它），再启动容器。这一步写成一份迁移说明。

### 8.6 要量的数

G4 是硬要求，所以这几条是验收条件，不是愿望。基线是改动前同一台机器、同一条线路上的数字（`scripts/benchmark-linux-session.py`、`scripts/test-linux-session-latency.py`、README 的实测码率）。

| 量什么 | 要求 |
|---|---|
| 经中继的会话，画面延迟的中位数 | 比基线多不超过 1 毫秒 |
| 经中继的会话，同样画面下的码率和帧率 | 不低于基线的 95% |
| 经中继打开一个 app 的时间 | 比基线多不超过一次两台设备之间（经 relay）的往返 |
| relay 每中继 1 Mbps 占的处理器 | 不高于基线的 105% |
| relay 空闲时的内存（100 台设备在线） | 50 MB 以内 |
| 直连和局域网的会话 | 和基线没有可测的差别 |

我的估计是都能过：会话期间多出来的只是两头各一次对称加密，现在的处理器每秒能做上千兆字节，远程会话是每秒几兆比特。但这是估计，没有测过。

### 8.7 配置

原则：**什么都不配也能跑。** 启动容器、挂上数据卷、放行端口，relay 就能用；key 自己生成。下面每一项都有默认值。

**relay 的配置项。** 来源有三个，后面的盖过前面的：默认值 → 数据卷里的 `/data/config.json`（可以没有）→ 环境变量。改了要重启才生效。

| 配置项 | 环境变量 | 默认 | 意思 |
|---|---|---|---|
| `listen` | `RAPP_RELAY_LISTEN` | `0.0.0.0:21116` | 监听的地址和端口 |
| `enroll` | `RAPP_RELAY_ENROLL` | `open` | `open` 接受新设备入网；`closed` 不接受（§5.3） |
| `log` | `RAPP_RELAY_LOG` | `info` | 运行日志的级别：`info` 或 `debug` |
| `audit.keep_days` | `RAPP_RELAY_AUDIT_KEEP_DAYS` | `180` | 审计日志留多少天 |
| `audit.max_mb` | `RAPP_RELAY_AUDIT_MAX_MB` | `256` | 审计日志总共最多占多少 |
| `audit.required` | `RAPP_RELAY_AUDIT_REQUIRED` | `false` | 审计写不进去时，是否拒绝新的入网和牵线 |
| `metrics` | `RAPP_RELAY_METRICS` | 关 | 指标接口的本机地址，如 `127.0.0.1:9116` |
| `limits.*` | `RAPP_RELAY_LIMIT_*` | 见 §8.2 | §8.2 表里的每一行各一项 |
| `legacy_key` | `RAPP_RELAY_LEGACY_KEY` | 无 | 只在升级过渡期用：旧的 relay key（§11 第二步）。第三步以后去掉 |

规则（我定的）：

- 配置文件里出现不认识的项，或者值不合法：relay 拒绝启动，并说明是哪一项。写错一个字不会被悄悄忽略。
- 启动时把生效的配置记一行（运行日志和审计日志各一份），机密不在里面。
- 命令行参数只剩一个 `--data`（数据目录，默认 `/data`）和 §5.5 的子命令。

**数据卷里有什么：**

| 文件 | 是什么 | 丢了会怎样 |
|---|---|---|
| `relay.key`、`relay.crt` | relay 自己的密钥和证书 | 所有设备的 key 都对不上了，要逐台重新填 key |
| `join` | 入网口令（key 的后一半） | 重新生成一个即可，已入网的设备不受影响 |
| `devices.json` | 入网设备表：指纹、ID、租户、入网时间、是否吊销 | 设备要重新入网；ID 的归属丢失 |
| `config.json` | 配置（可以没有） | 回到默认值 |
| `audit/` | 审计日志 | 审计记录没了，不影响运行 |
| `admin.sock` | 管理命令用的本机套接字 | 重启后重建 |

全部 0600（目录 0700）。说明里写明：备份整个数据卷；最要紧的是 `relay.key` 和 `devices.json`。

**设备这一侧的配置**（都在数据目录的 `local/` 下，不进 git；数据目录规格落地之前，就在现在的配置目录里）：

| 文件 | 变化 |
|---|---|
| `service.json` | `relay`、`key` 两个字段名不变，`key` 的含义变成 §5.2 的 key；新增 `accept_new`（接受新设备，默认开）；`secret` 和 `password` 在升级第三步以后去掉 |
| `hosts.json` | 每台主机新增对方的指纹；`password` 在升级第三步以后去掉 |
| `paired.json` | 新文件：认识的设备（指纹、对方自报的名字、认识的时间） |
| `device.key`、`device.crt` | 新文件：本机的设备密钥和证书 |

界面上用户要填的只有两样：接入点和 key。设备密码的显示和输入都去掉；加主机时只填 ID。

## 9. 往 SaaS 扩（只留位置，不实现）

第一版每一处都按"将来有很多租户、很多节点"来定数据的形状，但只实现单租户、单节点。

| 方面 | 第一版 | SaaS 时 | 第一版为它留了什么 |
|---|---|---|---|
| 租户 | 只有一个，叫 `default` | 一个账号一个租户 | 每条设备记录都带租户；牵线和接流只在同一个租户里做 |
| 准入 | 一个 key | 账号登录后签发 key：有期限，可以只用一次 | 准入是一个接口，输入"凭据"，输出"哪个租户，行不行" |
| 存储 | 文件 | 数据库 | §8.1 的存储接口 |
| 多节点、多地区 | 一个节点 | 设备登记在最近的节点；有一份"哪个 ID 在哪个节点"的目录；找的人被指去对的节点 | `redirect`（§7），设备第一版就会跟着走 |
| relay 的身份 | key 里带指纹 | 域名证书 | 设备核对 relay 身份的那一步是一个接口，可以换成按域名校验 |
| 计量和配额 | 每条中继流结束时记一行字节数 | 按租户累计，超了限速或拒绝 | 计量事件带租户和设备；§8.2 的上限按租户取值 |
| 传输 | QUIC（UDP） | 加一个 TCP 443 上的入口，给封了 UDP 的网络用 | L2 是"流上的一行行 JSON"，L3 是"任何字节流上的 TLS"，都不挑传输 |
| 不是 rapp 设备的客户端 | 没有 | 见 §10 | 设备密钥用的是单片机也支持的算法 |
| 管理 | 本机命令 | 网页控制台、接口 | 管理命令走一个内部接口，不直接改文件 |
| 观测和审计 | 运行日志、审计日志、可选的指标 | 集中的监控；按租户导出审计记录 | 指标的名字从第一版起就固定；每条审计记录都带租户 |

有一条性质对 SaaS 特别有用：relay 手里没有内容、没有密码。将来由别人托管 relay，托管的人也看不到用户的数据。

## 10. 数据服务和外部小屏（不在本文范围，只说清边界）

- **数据服务**（PD14）：便签、数值这类服务跑在某台设备上。别的设备要读，就是在已有的设备连接上开一条流，请对方"接到本机的某个服务"。这是 L4 的一个新请求，由关注数据那份规格（路线图 B2）来定。relay 不参与，不用改。
- **外部小屏**（U60、U61）：它不是 rapp 设备，说不了 QUIC。要让它经 relay 读数据，将来需要两样：一个 TCP 上的入口（§9 的"传输"一行），和它自己的一把设备密钥（像别的设备一样入网、用 key 互信）。这样它也在统一认证之内，relay 也仍然看不到内容。
  - 没有核对的：小屏的固件能不能做 TLS 1.3 和这些握手。做不到的话，小屏只能在局域网里直接读那台设备，不经过 relay。
  - 这一项排在 relay 第一版之后，单独设计。

## 11. 升级：四步，每一步都不会把远处的机器锁在外面

难点：远处无人值守的机器上没法去填新 key。办法是让手边的设备把 key 发过去。

| 步 | 做什么 | 做完以后 | 用户要做的 |
|---|---|---|---|
| 〇 | 在 VPS 上准备新 relay 的数据卷，运行一次 `rapp-relay key`，拿到新 key。旧 relay 照常跑，不动 | 手里有了新 key | 一条命令；把 key 存好 |
| 一 | 设备升级到新版本。新版本生成设备密钥，同时还会旧协议。在手边的一台设备上填新 key。它每连上一台还没有 key 的新版本设备，就在端到端加密的连接里把 key 发过去（对方凭现有的密码确认它是老相识）。两台都有了 key，就按 §6.3 互相认识 | 新版本的设备之间：内容已经端到端加密，旧 relay 看不到；key 传遍了所有连得上的设备。旧 relay 牵线时仍会收到旧密码，旧密码这时还有用 | 升级各设备；在一台设备上填一次 key。界面上每台主机显示"端到端"或"旧方式" |
| 二 | 把 relay 换成新的（同时从 systemd 换成 Docker，§8.5）。它导入旧的 `relay.json`：旧 ID 第一次登记时凭旧的 `secret` 认领一次。有 key 的设备用 key 入网。还没拿到 key 的设备（升级时不在线的）凭旧的 relay key 入网一次（`legacy_key`），之后从认识它的设备那里拿到 key | relay 不再收到任何密码。G1–G3 成立 | 在 VPS 上按迁移说明切换 |
| 三 | 设备去掉旧协议和密码。relay 去掉旧 `secret` 认领和 `legacy_key` | 代码里不再有不校验证书、明文密码、令牌。界面上不再有密码 | 无。前提是所有主机都已经显示"端到端" |

规则：

- 一台主机一旦互相认识过，以后对它**永不退回旧方式**。否则中间人可以假装对面是旧版本，把连接骗回不加密的路上。
- 第一步的设备要同时会新旧两种 relay 协议，握手时自动协商。
- 经中继时，B 怎么知道对面的 A 是不是新版本：B 先按新方式开始 TLS 握手；A 看流上的第一个字节就能分清是 TLS 握手还是旧的 JSON 请求。对面不认，B 才退回旧方式，而且仅限从没认识过的主机。
- 第一步里"凭现有的密码把 key 发过去"只在对方还没有 key 时才接受，一台设备只接受一次。

**升级期间的安全，要说清楚**：现在的系统完全信任 relay（它看得到内容，也知道密码）。所以如果 relay 在升级期间已经被人拿到并且在主动动手脚，他能在第一步里截到 key。升级不能把一个已经失守的系统变安全；它保证的是升级完成以后的事。不放心的话，第三步之后换一次 key（§6.5）。

## 13. 我替你定的

读的时候顺便看一眼，不同意的告诉我。

1. 做法选甲（§3）。
2. 设备密钥用 ECDSA P-256；验证只看公钥指纹（§5.1）。
3. key 的构成：relay 指纹的前 16 字节加 16 字节的"根"，编码成约 50 个小写字母和数字；从"根"单向推出入网口令和信任口令；key 由管理命令生成、只显示一次，relay 只存入网口令的哈希（§5.2）。
4. 准入分两道门；入网每台设备只做一次；relay 上可以关闭入网（§5.3）。升级过渡期认旧的 relay key（§11）。
5. 设备互信的证明用消息认证码，绑在当次握手上；认识以后靠指纹，不再每次用 key（§6.2、§6.3）。
6. 两个开关：relay 上的入网、每台设备上的"接受新设备"，默认都开（§6.4）。
7. 踢设备靠 relay 的吊销名单，设备只在"不再信任谁"上听 relay 的；换 key 时由设备把新 key 传给认识的设备（§6.5）。
8. relay 不再保存设备名、密码、令牌（§7）。
9. 设备第一版就实现"跟着 `redirect` 走"，虽然第一版的 relay 不发（§7）。
10. §8.2 的各个默认上限。
11. 指标接口默认关、只在本机地址上（§8.4）。
12. 基础镜像用 Alpine；同一个标签下带 x86_64 和 arm64；二进制不按体积优化的档位编译；发布到 GitHub 的镜像仓库（§8.5）。
13. 升级分四步：先拿新 key，再升设备并由手边的设备把 key 传出去，再换 relay，最后去掉旧协议和密码（§11）。
14. 审计日志：存在数据卷里，默认留 180 天、256 MB；在线探测每小时合并成一行；写不进去时默认继续服务；不做哈希链，要防篡改就实时送到别的机器（§8.4）。
15. 配置：什么都不配也能跑；默认值、配置文件、环境变量三层；写错了拒绝启动（§8.7）。
16. 没有 relay 时，key 在设备上生成（§5.2）。

## 15. 留给实现计划的

- 各请求的精确字段、错误文本的全集。
- 互信证明的精确算法：单向推导用的标签、握手导出值的标签和长度、消息认证码里各字段的顺序。动手前先做一个小验证：两个进程互信成功；中间插一个转发的进程时失败；key 不同时失败。

- 管理命令用的本机套接字的路径和格式。
- 存储文件的格式和版本号。
- 测试清单（§16 是要求，不是清单）。

## 16. 测试要求

- **冒充 relay 的测试**：写一个恶意的 relay，它把两头的流各自接到自己身上再转发。要求：不认识的设备之间互信失败；认识的设备之间握手失败；它的日志和内存里搜不到 key、信任口令和任何会话内容。
- **密钥全量检查**：所有测试结束后，relay 的数据卷、relay、service、hub 的运行日志和审计日志里搜不到 key 的"根"和信任口令（沿用可观测性规格的做法）。
- **key**：填错 key 的前一半（relay 身份对不上）和后一半（入网被拒）各是什么表现；两台设备 key 不同时互相不认；`rapp-relay key` 第二次运行不再显示；关闭入网以后对的 key 也入不了网；关闭"接受新设备"以后有 key 的新设备也连不上；换 key 以后新 key 传到了认识的设备，旧 key 入不了网；吊销以后其余设备不再认它。
- **审计**：§8.4 事件表的每一行都能在审计文件里找到对应的记录；换一个容器以后审计文件还在；过期的被删并留下 `audit_prune`；磁盘写不进去时两种配置各自的表现。
- **配置**：不给任何配置能启动；三层的覆盖顺序；写错一项拒绝启动并指出是哪一项。
- **准入**：不出示证书、没入网、被吊销，三种情况各自被挡在哪一步。
- **限速和上限**：§8.2 每一行至少一个测试。
- **升级**：§11 四步各一个测试，包括"认识过的主机不退回旧方式"和"升级时不在线的设备后来能拿到 key"。
- **重启**：relay 重启后，设备在 5 秒内重新在线，中继的会话自己接上。
- **`redirect`**：用一个会发 `redirect` 的假 relay 测设备的行为。
- **请求解析的模糊测试**：relay 的那一行 JSON。
- **压力和久跑**：若干台假设备、若干条中继流，跑 24 小时，内存不涨。
- **Docker**：容器里 relay 看到的对端地址是真实的；以非 root、只读根文件系统运行时全部功能正常；健康检查能发现 relay 不响应；`docker stop` 时设备收到 `going_away`；镜像大小在目标以内；两种架构各跑一遍冒烟测试。
- **性能**：§8.6 的表。
