## 0. 结论

**能用，但只用一半。** Sunshine 和 Moonlight 的核心技术有两块：

| 哪一块 | 是什么 | 用不用 |
|---|---|---|
| 编码 | 显卡硬件编码的视频流：不重排帧、不定期发关键帧、每帧有字节上限 | **用。** 只在画面大面积变化时用（滚动、Agent 连续出字、动画） |
| 传输 | UDP 上的 RTP，丢了不重传，靠冗余包和"作废参考帧"恢复 | **先不用。** rapp 的会话是一条可靠的流，relay 规格也是按流设计的。先把"只发最新一帧"做到端到端 |

另有三点和纪要 §4 的建议不同：

1. **"路上特别卡"的主因多半不是编码，而是排队。**（推断，见 §2.2。）所以第一步是传输上的纪律，不是硬件编码。
2. **rapp 现有的瓦片编码不换掉。** 画面静止和小范围变化时，它比视频更清楚、更省。两种编码各管一段。
3. **纪要 §4 第 3 条要更正。** rapp 现在已经是按 app 采集（一块屏上只留这个 app 的窗口），不需要改成"按单个窗口采集"。单窗口采集不带子窗口和弹出窗口（资料），会丢菜单和对话框。

## 1. 目标

### 1.1 "流畅"在 rapp 里指什么

rapp 要做好的是四件事：看、滚动、点、写（反馈文档 §0.5）。不追求游戏和看视频。所以"流畅"拆成四条：

| # | 体验 | 怎么量 |
|---|---|---|
| G1 | **不越用越慢。** 网络再差，画面最多落后固定的一小段，不会攒出几秒的延迟 | 画面延迟（A 采集到 B 显示）的最大值 |
| G2 | **点和按有回应。** 点一下、按一个键，画面很快跟上 | 操作延迟（B 发出操作到 B 看到变化） |
| G3 | **滚动和连续出字是连贯的。** 不是一秒跳几下 | 大面积变化时 B 实际显示的帧率 |
| G4 | **停下来字是清楚的。** 和现在一样 | 静止后的画面和现在的档位逐像素一致 |

出差场景（反馈文档 U17）另加一条：

| G5 | **流量不暴涨。** 滚动时的码率要降下来，静止时仍然是 0 | 同一段操作的总字节数 |

### 1.2 建议的验收数字（我定的，P0 量完基线后再校准）

| 网络 | G1 画面延迟 | G2 操作延迟 | G3 大面积变化时的帧率 |
|---|---|---|---|
| 局域网 | 中位数 ≤ 50 ms | 中位数 ≤ 80 ms | ≥ 30 fps |
| 公网、直连或中继，带宽 ≥ 5 Mbps | ≤ 往返时间 + 80 ms | ≤ 往返时间 + 120 ms | ≥ 20 fps |
| 弱网（限速 1 Mbps） | ≤ 往返时间 + 250 ms，**不随时间增长** | 同左 | ≥ 8 fps |

这些数字现在没有基线可比。现有的两个脚本量的是解码进程的管道，不是端到端（脚本自己的说明）。

### 1.3 不做

- 游戏、手柄、音频、HDR、高于 60 fps。
- 照搬 Moonlight 的协议，或者让 Moonlight 能连 rapp。
- 换掉瓦片编码；改动静止时"不发数据"的行为。
- 为了流畅让用户多装东西（用户的原则：不要求装额外的插件）。

### 1.4 不能出现的结果

- 静止时的文字比现在糊。
- 没有硬件解码的 B 连不上，或者比现在差。
- 局域网里比现在慢。

### 1.5 许可证（用户已定，修订 1）

用户的话："可以接收 GPL-3.0 协议。"（"接收"按"接受"理解。）

所以 Sunshine 和 Moonlight 的代码（都是 GPL-3.0）可以直接参考、移植、拿来用，不再限于"只学做法"。

**它改变了什么**

- P2 的探查可以从读它们的实现开始：Sunshine 怎么设 VideoToolbox 的参数，Moonlight 在 Linux 上怎么做硬件解码和帧的节奏。不用自己重新摸索。
- §6 将来要做时，冗余包和收包重组可以移植现成的。
- Linux 解码库不用避开 GPL 的选项。

**它没有改变什么**

- 推荐的做法仍是丙（§7）。甲被排除的理由是整块屏、没有窗口表和编辑器、要另装软件，和许可证无关。
- 能整段搬的不多。Sunshine 是 C++，经由 FFmpeg 调用编码器；rapp 的 A 端是 Swift，直接调系统接口，B 端是 Swift 和 Rust。多数情况是照着移植。

**代价（我的理解，不是法律意见）**

- 含有它们代码的程序，发布给别人时要按 GPL-3.0 发布，并提供对应的源码。
- 仓库现在没有 LICENSE 文件，各包也没有写许可证（2026-11-14 查过）。第一段 GPL 代码进来之前，要先把 rapp 自己的许可证定下来（§10 第 6 条）。
- rapp-relay 是单独的程序，不含这些代码，不会被连带。它用什么许可证是另一个决定。

## 2. 现状

### 2.1 一帧画面现在怎么走（代码）

```
A：ScreenCaptureKit 采集（一块屏上只留这个 app，最高 30 fps，BGRA）
   → 量化成档位的色深 → 和上一帧比，只留变了的 64×64 瓦片 → zlib（字典一直延续）
   → rapp-host 写本机 TCP → rapp-service 接到 QUIC 流 →（中继时）relay 把两条流对接
B：rapp-hub 把 QUIC 流接回本机 TCP → 解码（macOS 在界面进程里；Linux 是单独的 rapp-session 进程）
   → 画面交给 Flutter
```

已经做对的（和 Moonlight 的做法一致）：

- 画面不变不发数据。
- A 端在上一帧发完之前，新画面互相替换，只编码最新的一帧（`Server.swift` 的 `submit`）。
- B 端只保留最新一帧待显示（Linux 的输出线程）。
- 不采集光标，B 用自己的光标。
- 打字在 B 本地完成（底部编辑器）。

### 2.2 问题在哪

| # | 问题 | 依据 |
|---|---|---|
| Q1 | **"发完"不等于"对方收到"。** A 端认为一帧发完，是指交给了本机的 TCP。之后还要过 service、relay、hub 三段对接，每段各有 64 KiB 的缓冲，另加各自的套接字和 QUIC 窗口。A 看不到后面堵没堵，会继续按帧率编码 | 代码：`Server.swift` 用 `.contentProcessed`；`quic.rs` 的 `splice` 用 64 KiB 缓冲 |
| Q2 | **每一帧都依赖前一帧，编码之后不能丢。** zlib 字典跨帧延续，瓦片也是和上一帧比出来的。堵在路上的旧帧必须全部送到 | 代码：`TileCodec.swift`、README |
| Q3 | **大面积变化时瓦片编码很贵。** 滚动一下，几乎每块瓦片都变了，接近每帧发一张整图 | README 实测：Safari 一页整帧 44–96 KB（2x）；高彩 15 fps 播视频约 14.7 MB/s |
| Q4 | **量不出延迟在哪一段。** 协议里没有帧序号、时间戳和确认，B 不回报收到了什么 | 代码：`Protocol.swift` 消息 1–26 |
| Q5 | **Linux 端画面走管道，4K 到不了 30 fps。** | `tasks/todo.md`：1080p 约 63 fps，4K 约 23.5 fps |

**Q1 加 Q2，就是"路上特别卡"最可能的原因（推断，没有实测）。** 算一下：一段 64 KiB 的缓冲是 52 万比特。带宽 1 Mbps 时，填满一段就是半秒的旧画面；200 kbps 时是 2.6 秒。三段都满，再加上 Q2 不能丢，B 看到的就是几秒前的画面，而且越滚越落后。

Q3 让它更容易发生：按 README 的整帧大小估，15 fps 滚动一页网页，灰度 16 级约 5 Mbps，高彩约 12 Mbps。手机热点很容易低于这个数。（这是按"每帧接近整帧"估的上限，没有实测滚动。）

**局域网里感觉可以接受，也对得上**：带宽够，缓冲不会满。

## 3. Sunshine 和 Moonlight 的核心技术，逐条看

纪要 §3 已经核实了两者是什么。这里只看它们为什么快，以及每一条在 rapp 里怎么办。

| # | 技术 | 它怎么做（资料） | 在 rapp 里 |
|---|---|---|---|
| T1 | 硬件视频编码 | 用显卡的编码器；macOS 上是 VideoToolbox | **采用**，作为"运动层"（§5） |
| T2 | 低延迟的编码设置 | 各家编码器都选最快的一档：VideoToolbox 默认开实时模式，NVENC 默认最快的预设，软件编码默认 zerolatency | **采用。** VideoToolbox 另有专门的低延迟模式：不重排帧，进一帧出一帧（§5.2） |
| T3 | 不定期发关键帧 | 关键帧只在客户端要求时才发；编码器接口上有"请求关键帧"和"作废一段参考帧"两个动作 | **采用前一半。** 可靠的流上不丢帧，所以只在开始和尺寸变化时发关键帧 |
| T4 | 每帧有字节预算 | 按码率和帧率算每帧的预算，不让单帧突然变大 | **采用**，瓦片和视频都守同一个预算（§4.3） |
| T5 | 码率 | 客户端定一个固定的码率，主机照做（主机可以设上限） | **做得更进一步。** rapp 要在路上用，码率得自己跟着网络变（§4.4） |
| T6 | UDP + 冗余包 | 视频走 RTP；每帧额外发一定比例的 Reed-Solomon 冗余包（默认 20%），丢了的包能算回来，不重传 | **先不采用**（§6） |
| T7 | 作废参考帧 | 丢帧后，客户端告诉主机哪些帧坏了，主机改用更早的好帧做参考，不用发整张关键帧 | **先不采用**；它是 T6 的配套。VideoToolbox 有对应的能力（长期参考帧），留给 §6 |
| T8 | 硬件解码 | Moonlight 在 Windows、macOS、Linux 上都用硬件解码 | **采用**（§5.5） |
| T9 | 延迟统计 | Moonlight 的统计面板分段显示：主机处理、网络、解码、排队、渲染 | **采用，而且最先做**（§4.1） |
| T10 | 4:4:4 色度 | 只在服务端是 Sunshine 而且两头的显卡都支持时可用；Intel、AMD 的硬件解码支持不齐 | **不采用。** 静止时由瓦片层给出逐像素准确的画面（§5.4），不需要它 |
| T11 | 静止时降帧率 | 画面不动时把实际帧率降到一半左右 | **不需要。** rapp 静止时是 0 |

一句话：**T1–T4、T8、T9 是"编码链路"，拿过来；T6、T7 是"丢包不重传"，rapp 现在的连接方式用不上，先放着。**

## 4. 第一部分：传输上的纪律（不换编码）

这一部分只改 A 端的发送节奏和协议，瓦片编码不动。它对付 Q1、Q2、Q4。

### 4.1 先能量（协议 v7）

新增三条消息，老消息都不改：

| 消息 | 方向 | 内容 | 用途 |
|---|---|---|---|
| 帧头扩展 | A → B | 帧序号；A 端采集到发出花的毫秒数 | B 能算主机处理时间 |
| 帧确认 | B → A | 帧序号；B 端收到到解码完的毫秒数；是否显示了 | A 知道对方真的收到了；A 算往返时间和实际送达速率 |
| 操作标记 | B → A，再由 A 带在下一帧上 | 一个序号 | B 量操作延迟：从发出操作到看到带这个标记的帧 |

两头的时钟不用对齐：往返时间由 A 用自己的钟算（收到确认的时刻 − 发出的时刻 − B 报告的处理时间）。

B 端在流量标签的菜单里加一行统计（默认收起），分五段：主机处理、网络、解码、排队、显示，另加当前是瓦片还是视频。

v6 的客户端不发确认：A 对它保持现在的行为。

### 4.2 对方收到了，才编码下一帧

A 端把"上一帧发完"的判断，从"交给了本机 TCP"换成"**B 确认收到了**"。规则：

- 在途的帧不超过 1 帧（局域网上可以放到 2 帧，换更高的帧率；由送达速率决定）。
- 等确认的时候，新画面照现在的办法互相替换。确认一到，编码的是**此刻最新**的画面。
- 不为确认另设超时。弱网下一帧可能要走好几秒；断没断线仍由连接现有的保活来判断。
- 用户选的帧率（1、5、15、30）变成上限：网络跟得上就按它走，跟不上就自动低于它。

效果：路上的缓冲永远填不满，Q1 消失；因为不再有"编好了还没送到"的旧帧，Q2 也不再造成积压。网络慢的时候，表现从"越来越落后"变成"帧率降低，但每一帧都是新的"。

### 4.3 每帧有字节预算

预算 = 送达速率 × 帧间隔。超出预算的帧不整帧发出去，按下面的办法切开：

- 瓦片帧本来就是"一组瓦片"。一帧超预算时，只发预算内的那些瓦片，其余留给下一帧。先发光标和焦点附近的。
- 开始和切换档位时的整帧同样切开发，画面从上到下（或从焦点向外）补齐，不再是一大块卡住后面所有的帧。

线上格式不用变：现有的增量帧本来就允许只带一部分瓦片。

### 4.4 跟着网络调

送达速率和往返时间有了，A 端自己调，顺序是**先牺牲运动时的流畅，后牺牲清晰**：

1. 降大面积变化时的帧率（30 → 15 → 5）。
2. 降运动层的采集密度（§5.3）。
3. 提高运动层的压缩程度。
4. 静止后的补清晰，分更多帧慢慢补。

网络恢复后按相反的顺序升回去。**静止层的档位和密度不自动改**，那是用户自己选的。

### 4.5 这一部分做完能得到什么

G1 达成（延迟有上限）。G2 在弱网下明显改善。G3、G5 没有改善：滚动仍然是整屏瓦片，只是变成了"帧率低但不落后"。

## 5. 第二部分：运动层（硬件视频编码）

这一部分对付 Q3，达成 G3、G5。它就是 `tasks/todo.md` "未来规划"里"硬件编码（参考 Sunshine）"和"按区域选编码（参考 Xpra）"两项，合成一个做法。

### 5.1 两层，各管一段

| | 静止层（现有的瓦片编码） | 运动层（新增的视频编码） |
|---|---|---|
| 什么时候用 | 画面不动；小范围变化（打字、光标、转圈的小图标） | 大面积连续变化（滚动、Agent 连续出字把整屏往上推、动画、视频） |
| 特点 | 逐像素准确；不变不发；小变化只有几百字节 | 靠运动补偿，整屏平移只要很少的数据；有损 |
| 谁来算 | CPU | A 的硬件编码器、B 的硬件解码器 |

为什么对 rapp 特别合适：rapp 最常远程的是 Agent 的界面。Agent 出字的时候，整个对话区在连续上滚，这正是瓦片编码最贵、视频编码最便宜的画面。

### 5.2 A 端：VideoToolbox 的低延迟模式

按 Apple 的说明（资料，WWDC21）：

- 建编码会话时打开低延迟码率控制。这个模式不重排帧，进一帧出一帧；码率控制对网络变化反应更快；总是用硬件编码器。
- 苹果公布的是 H.264。**第一版用 H.264**：B 端哪里都能解。
- 可以设"每帧最大量化值"。到了上限而码率不够时，编码器的做法是丢帧而不是把画面压得更糊。Apple 举的例子正是屏幕内容里的文字。这和 §4.4 "先降帧率、后降清晰"是一致的。
- 码率由 §4.4 的送达速率给出，随时可改。

采集出来的画面（BGRA）可以直接交给编码器，不用自己转格式。

HEVC：同样码率下更清楚。Apple 芯片上有 HEVC 的实时硬件编码器（资料，Chromium 的代码注释）；但也有人在自己的机器上试低延迟 HEVC 失败（资料，FFmpeg 邮件列表）。所以放到后面，先在目标机器上探测再用。

### 5.3 什么时候切换（我定的起步值，要实测调整）

- **进入运动层**：连续 2 帧，变化的面积超过画面的 25%；或者按瓦片编码估出来的字节数超过 §4.3 的预算。
- **回到静止层**：200 ms 没有新的变化。
- 只变一帧的大变化（切换窗口、翻页）不进运动层，照旧用瓦片。
- 用户选的帧率是 1 或 5 时不进运动层。选低帧率的人要的是最省流，照现在的办法走。
- 运动层不跟档位走：选了双色档，滚动时看到的仍是彩色的视频，停下来回到双色。第一版接受这个观感差别。

变化面积从哪来：ScreenCaptureKit 每帧附带"哪些区域变了"（资料）。同一个信息还能让静止层跳过没变的瓦片，省 CPU。按 app 采集时它给不给、准不准，要先探查（§8 P2 第 1 步）。给不了就用上一帧的瓦片数。

第一版**整块画面一起切换**，不做"这一块用视频、那一块用瓦片"。后者更省，但两种编码的边界和同步都复杂，等第一版量出来不够再说。

运动层的采集密度可以比静止层低。滚动中的文字本来就看不清细节，降一档密度，编码、解码、Linux 端的管道（Q5）都轻很多。默认和静止层相同，由 §4.4 在带宽不够时自动降。

### 5.4 停下来以后补清晰

回到静止层时，B 上显示的是视频解出来的有损画面。A 端把瓦片编码器的"上一帧"当作未知，用 §4.3 的办法分几帧把准确的画面补上，先补焦点附近。

- 局域网：一两帧补完，肉眼看到的是"停下来的一瞬间变锐"。
- 弱网：几百毫秒到一两秒补完。补的过程中又动起来，就放弃补、回到运动层。

G4 由此保证：静止后的画面和现在逐像素一致。所以不需要 4:4:4（T10）。

### 5.5 B 端：解码

| B | 解码 | 画面怎么到界面 |
|---|---|---|
| macOS（Swift，`RappSession`） | VideoToolbox 硬件解码，直接解到现在用的那种画面缓冲 | 不变 |
| Omarchy / Linux（Rust，`rapp-session`） | 硬件解码（Intel 核显走 VA-API），没有就退到软件解码 | 不变：解出的画面写进同一块画布，照现在的管道交给 Flutter |
| 将来的 iPad | 和 macOS 同一套接口 | — |

B 上两层画到同一块画布：视频帧整块覆盖，瓦片帧在上面打补丁。窗口表、弹出窗口、裁剪都不用改，因为它们只认画布。

独立窗口的两个客户端（Mac 的 `rapp-client`、Linux 的 GTK 客户端）和嵌入舞台用的是同一套解码代码（`RappSession`、`rapp-client-core`），跟着一起得到运动层，不另做。

**协商**：B 在 hello 里报自己能解什么、最大多大。A 只在 B 能解时启用运动层。B 不能解（或者是 v6）就只有静止层，加上 §4 的纪律，仍然比现在好。

Linux 用哪个解码库，留给实现计划先做一次探查：用户的主控台是装了 Omarchy 的 x86 平板，就在那台机器上试。

### 5.6 尺寸

H.264 硬件编码有最大尺寸，常见是 4096 像素宽。画布是"这块屏上 app 窗口的范围"，在 5K 屏上可能超过。超过时运动层降密度到放得下为止，静止层不受影响。具体上限在目标机器上探测，不写死。

窗口改大小时画布尺寸在变，视频编码器要重建。改大小的过程中留在静止层，松手后再允许进运动层。

## 6. 第三部分：丢包不重传（暂不做，说明为什么）

Moonlight 快的另一半原因是 T6、T7：UDP、冗余包、作废参考帧。rapp 现在不做，理由：

1. **连接方式不同。** rapp 的会话是 QUIC 上的一条流；relay 规格选的做法是"relay 对接两条流，设备在流里做端到端 TLS"，已经确认。丢包不重传要求数据报一路到底，中继时做不到，要等 relay 规格里留着的"乙"方向（relay 只转发数据包）。
2. **内容不同。** 游戏每秒 60 到 120 帧，重传一个包就错过好几帧。rapp 大部分时间静止，运动时 15 到 30 帧，一次重传多等一个往返时间，§4 做完以后不会积压。
3. **没有数据。** P0 能量出"丢包造成的卡顿"占多少。占得多，再做。

如果将来要做，路线是：只在直连和局域网的路径上，用 QUIC 的数据报发运动层的帧；用 VideoToolbox 的长期参考帧做恢复（B 确认收到的帧可以被指定为参考，丢帧后 A 从一张 B 确认过的帧接着编，不用发关键帧。资料，WWDC21）；§4.1 的帧确认正好是它需要的回报通道。静止层和控制消息仍然走可靠的流。

## 7. 考虑过的做法

| | 做法 | 好处 | 为什么不选 |
|---|---|---|---|
| 甲 | 直接用 Sunshine + Moonlight 代替 rapp 的串流 | 现成 | 串的是整块屏，没有窗口表、菜单镜像、底部编辑器；要用户另装两个软件；上游在 Apple 芯片上的 H.264 有人报告每帧都是关键帧（第三方分支 Lumen 的说法，未验证）；文字在低码率下是 4:2:0。**只适合当对照**（§8 P0） |
| 乙 | rapp 全部改成视频流，去掉瓦片编码 | 只有一种编码，结构简单 | 丢掉"静止不发数据"和"逐像素准确的文字"，这两条是 rapp 相对 UU 的差别（反馈文档 F1）；没有硬件解码的 B 用不了 |
| 丙 | **两层：瓦片管静止，视频管运动；先做传输纪律** | 各用所长；可以分步做，每步单独见效；B 不能解码时自动退回 | 两种编码要切换，多一个状态机。**推荐** |
| 丁 | 只改进瓦片编码：加滚动检测（发"这一块往上挪了多少"）、块缓存 | 不依赖解码器，CPU 就能做 | 只对整像素的竖直滚动有效；采集密度不是整数倍时对不上；Agent 出字、动画、视频帮不上。传输纪律那部分和丙相同，所以丙的第一步做完再看也不迟 |

用户的话是"看看能否使用其中的核心技术"，思浩的建议是"扒一下 Sunshine 的编码方案"。丙用的正是那套编码方案，放在 rapp 需要的地方。

## 8. 分几步做

每一步做完都能单独验收，单独出实现计划。

| 步 | 做什么 | 改哪里 | 做完能看到什么 |
|---|---|---|---|
| **P0 测量** | §4.1 的三条消息和统计行；一组固定的测试场景；量基线 | 协议 v7；`rapp-host`；两个客户端 | 第一次有端到端的延迟数字；知道"路上卡"到底卡在哪一段 |
| **P1 传输纪律** | §4.2、§4.3 | `rapp-host` 的发送节奏；瓦片编码器加"按预算切开" | 弱网下不再越来越落后（G1）。**这一步就该解决"路上特别卡"** |
| **P2 运动层** | 1. 探查：采集给的变化区域、低延迟编码在目标 Mac 上的表现、平板上的硬件解码；2. A 端编码和切换；3. macOS 端解码；4. Linux 端解码；5. 补清晰 | `rapp-host`；`RappSession`；`rapp-session`；hello 里的协商 | 滚动和 Agent 出字连贯（G3），流量降下来（G5） |
| **P3 自适应** | §4.4 的阶梯；app 配置里加一项"运动层：自动 / 关"；统计行整理 | `rapp-host`；app 配置 | 带宽变化时自己升降，不用手动换档 |
| P4（看数据再定） | §6 的数据报路径；HEVC；60 fps | — | — |

**P0 的测试场景**（每个场景在三种网络下各跑一遍：局域网；经中继；限速 1 Mbps 加 2% 丢包）：

1. 在 Claude 桌面版里，用底部编辑器发一段话，看回显。
2. 滚动一段长对话 10 秒。
3. 让 Agent 连续输出 30 秒。
4. 在两个窗口之间切换 5 次。

**和 Sunshine + Moonlight 的对照**（纪要 §4 第 1 条）：放在 P0，可选。在同一台 Mac 上装 Sunshine，在 B 上装 Moonlight，跑场景 2、3，记码率和 Moonlight 统计面板里的延迟。它给 P2 一个参考：运动层做完，同样场景下不应明显差于它。要在你的机器上装两个软件，所以由你决定做不做（§10 第 2 条）。

**顺序的理由**：P1 改动最小，而且按 §2.2 的推断，它对"路上卡"最对症。如果 P0 量出来主因不是排队，就调整：先做 P2。

## 9. 我替你定的

1. 推荐做法丙（§7）。
2. 第一版运动层用 H.264，整块画面一起切换，不做分区域。
3. §5.3 的切换门槛（25%、2 帧、200 ms）和 §1.2 的验收数字，都是起步值。
4. 网络变差时，先降运动时的帧率，后降清晰；静止层的档位和密度不自动改（§4.4）。
5. 界面上不加新的档位。运动层默认自动；只在 app 配置里留一个开关。理由：设计语言要求简化，用户不该为"现在该用哪种编码"操心。
6. 不能硬件解码的 B 自动只用静止层，不提示。
7. 不在舞台上的会话（已降到 1 fps）不开运动层，硬件编码器只给正在看的那个会话。
8. 丢包不重传（§6）不排期。
9. 用户选的帧率变成上限（§4.2）；选 1 或 5 fps 时不开运动层；运动层不跟档位的色深（§5.3）。
10. 文档放在 `docs/superpowers/specs/`，没有提交 git（仓库里有你没提交的改动）。

## 10. 要你确认的

1. **"路上特别卡"具体是什么样？** 是整体慢几秒、越用越慢；还是一滚动就卡；还是打字回显慢？当时用的是什么网络？这决定 P1 和 P2 谁先做。P0 也能量出来，但你的描述更快。
2. **要不要做 Sunshine + Moonlight 的对照？** 要在一台 Mac 和平板上各装一个软件，只用来测。
3. **做法丙可以吗？** 尤其是"滚动时画面略软，停下来变锐"这个观感。如果你更想要滚动时也始终锐利，要走的是更高码率或者做法丁。
4. **§1.2 的数字。** 特别是弱网那一行：1 Mbps 下 8 fps、延迟不增长，够不够你出差时用？
5. **先做哪个 B 端的解码。** 我的建议：先在 macOS 端跑通（和 A 端同一套接口，最快看到效果），紧接着做 Omarchy 端（你的主控台）。
6. **GPL-3.0 接受到哪一层？**（修订 1）两种读法：一是 rapp 的设备端程序整体以 GPL-3.0 开源发布；二是只是不排斥，真要用到再说。我按第二种写的：现在不动许可证，第一次要搬进 GPL 代码时停下来问你。如果是第一种，可以现在就加 LICENSE。

## 11. 留给实现计划的

- v7 三条消息的字段和编号；v6 客户端的兼容路径。

## 12. 测试要求

- **单元测试**：帧预算和切开；切换状态机（进入、退出、单帧大变化不进入、改大小时不进入）；送达速率估计；v6 兼容。
- **夹具测试**：一个能限速、加延迟、加丢包的假链路。断言：限速 1 Mbps 跑 60 秒，画面延迟的最大值不随时间增长。这一条现在的版本应该是失败的，P1 之后通过。
- **画质**：补清晰完成后的画面和纯瓦片编码的画面逐像素相同。按 `tasks/lessons.md` 的教训，改动画质相关的算法时把新旧输出渲染成图片亲眼对比。
- **实机**：§8 的四个场景，三种网络，P0、P1、P2 各量一遍，数字记进 README 的"实测"一节。
- **不退步**：局域网下静止画面的码率仍是 0；relay 规格 §9.4 的性能要求照旧。
