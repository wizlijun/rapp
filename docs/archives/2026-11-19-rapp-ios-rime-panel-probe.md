# iOS 探查：输入板内嵌 Rime，实体键盘打字，候选在文字下一行

日期：2026-11-19。状态：探查规格，待执行。这是一次性试验，代码不进 main；只回答「行不行、要花多少」，不交付功能。

标了【我定的】的是我做的决定，用户没有逐条确认过，可以否掉。标了【没核对】的是凭记忆写的，动手前先核对。

## 1. 为什么

用户的话：

- 2026-11-14：「后续会改造输入法，让打字体验在文字的下一行，这样眼睛可以固定不动。减少输入法框飘来飘去的问题。」
- 2026-11-19：「我们的输入板这一块自己去实现一个输入法。一个轻量的输入法，不知道要消耗多少的代价。」「请写成一个探索 spec，我试一下。」

背景（2026-11-18、19 查到的）：

- iOS 上第三方输入法是键盘扩展，接了实体键盘后按键不经过它。iPad 配机械键盘时，用户自己的 Rime 方案用不上，只能用系统拼音。
- 做过同样事情的先例：「清歌写字板」把五笔引擎放进 app 里，用蓝牙键盘打字。
- librime 是 BSD-3 许可的引擎库；iOS 上有人打包好了（LibrimeKit：SwiftPM 二进制，带 boost、leveldb、marisa、opencc、yaml-cpp）；也有从源码编 iOS 版的脚本（Cantoboard/librime-ios-build）。
- rapp 已经有两块现成的：Flutter 画候选的 `gui/lib/embed/linux_candidates.dart`（`LinuxCandidateSnapshot`、`LinuxCandidatesSurface`），和 iOS 上接实体键盘按键的 `RappViewController.pressesBegan` → `pressHandler`。缺的是引擎，以及把「按键 → 引擎 → 候选」接起来。

和另一份探查的关系：《把系统拼音的候选条钉在文字下一行》（`2026-11-18-rapp-ios-candidate-pin-probe.md`，分支 `probe/ios-candidate-pin`）走的是「继续用系统输入法」的路；这一份走的是「自己带引擎」的路。两份互不依赖，结果放在一起定方向（§8）。

## 2. 要回答的问题

每一条要有结论；能截图的带截图，能量的带数字。设备：iPad 和 iPhone Duo 各一遍，接实体键盘。记下机型和系统版本。

| 编号 | 问题 |
|---|---|
| R1 | **按键归谁（最大的未知数）**：编辑区有焦点时，rapp 在 `pressesBegan` 里把按键吞掉（不交给 `super`），系统输入法还会不会收到这一下——会不会照样组字、弹出它自己的候选条。系统输入源是「简体拼音」和「英文」时各试一遍。 |
| R2 | **引擎能不能进 app**：librime 能不能链进 iOS 工程（真机 arm64 和模拟器），初始化、部署方案、开会话。用的是现成的包还是自己编的，哪个版本。 |
| R3 | **打字这一圈通不通**：按键 → 引擎 → 组字显示在编辑区（带下划线）→ 候选 → 选字上屏。字母、数字选字、空格、退格、Esc、回车、翻页、Shift 切中英、中文标点，逐个过。 |
| R4 | **候选在文字下一行**：候选固定出现在编辑区文字的下一行，打字时不跟着光标横向移动。用现有的候选画法（或它的精简拷贝）能不能直接用。 |
| R5 | **手感**：每次按键引擎用了多少毫秒；按住退格、按住方向键有没有连发（`pressesBegan` 不带自动重复【没核对】，可能要自己做）；连续快打有没有丢键、乱序。 |
| R6 | **代价**：安装包大了多少；引擎加载后内存多了多少，打一阵之后多少；首次部署（编词库）在设备上要多久；冷启动慢了多少。小词库和大词库各量一遍。 |
| R7 | **和系统的东西能不能共存**：拔掉实体键盘只用软键盘时，行为和现在一样（走系统输入法）；内置引擎开着时听写还能不能用；一个「内置 / 系统」开关能不能随时切回系统输入法（打日文等其他语言时要用）。 |
| R8 | **用户自己的方案（可选）**：把一份现成的 Rime 用户目录放进 app，能不能不改就用。 |

## 3. 做法的选择

引擎：

| 做法 | 取舍 |
|---|---|
| **嵌入 librime（已选）**【我定的】 | 引擎现成，选字、翻页、中英切换、标点都在引擎里，外壳只转发按键和画结果；用户现有的 Rime 方案和词库能直接用；代价是多一组 C++ 依赖和词库体积 |
| 嵌入 libime（小企鹅自带拼音的引擎） | 整句效果好；但只有拼音和码表，没有 Rime 的方案生态，iOS 上没找到现成的打包 |
| 自己写拼音引擎 | 体积最小；原型很快，但整句、调频、模糊音、双拼、中英混输这些要磨很久 |

接在哪里：

| 做法 | 取舍 |
|---|---|
| A 直接接进现有输入板（`FlutterEditor`、`ComposerPanel`） | 离产品最近；但探查失败时白改，还会弄脏 main |
| **B 单独的探查页（已选）**【我定的】 | 不碰现有输入板；能放开关和测量面板；结论出来后再按正式设计接进去 |

引擎由谁调【我定的】：探查里由原生一侧（Swift）调 librime，按键不绕 Dart；候选和组字通过通道发给 Dart，形状照 `LinuxCandidateSnapshot`（行的序号、标签、文字，当前高亮，有无上一页下一页），这样现有的画法可以拿来用。以后跨平台时引擎放在哪一层（Dart FFI、Rust、各平台原生），不在这次定。

## 4. 探查程序

分支 `probe/ios-rime-panel`，从 main 拉，不合并。入口【我定的】：构建时带 `--dart-define=RAPP_PROBE=rime`，启动后直接进探查页；不带这个参数时行为和 main 完全一样（`scripts/build-ios.sh` 不传 `--dart-define`，探查构建要直接调 flutter 或给脚本加一个只在探查分支上的参数）。探查页的入口可以借 `probe/ios-candidate-pin` 上已有的写法，但两条分支互不依赖。

**按键怎么走**

- 探查页的编辑区有焦点、并且开关在「内置」时：`RappViewController` 的 `pressHandler` 先把这一下交给探查的处理器，处理器把 `UIKey`（键位和修饰键）换成 Rime 的键码和修饰位，交给引擎，然后把这一下吞掉。
- 引擎没有在组字、并且这一下引擎不要（比如方向键、⌘ 组合键）：不吞，照常交给 Flutter。
- Shift 这类修饰键的抬起也要发给引擎（Rime 靠 Shift 抬起切中英）【没核对：键码表和修饰位的定义以 librime 的 `rime_api.h` 和现有前端的做法为准】。
- 开关在「系统」、或者没有实体键盘时：处理器什么都不做，一切和现在一样。

**探查页长什么样**

- 一个仿写作面板的框：宽 720（屏幕窄时取屏宽减 16），字号 15、行高 22，一行起步、往上长，底边不动。组字显示在光标处，带细下划线。
- 候选固定在框内文字的下一行，从文字左缘开始，最多四行（和 macOS 的 Sumi 候选一致）。
- 一行状态：引擎是否就绪、当前方案、中 / 英、上一次按键引擎用时（毫秒）。
- 开关和按钮：「内置 / 系统」；方案切换（小词库 / 大词库）；「重新部署」。
- 一块测量面板，用户截图就能带回来：首次部署用时、引擎加载前后的内存、最近 50 次按键的引擎用时（中位数和最大值）。

**词库**【我定的】

- 小：朙月拼音（librime 的默认数据：prelude、essay、luna-pinyin）。
- 大：雾凇拼音（rime-ice，GPL-3.0）。
- 探查构建只在自己的设备上装，不分发；词库怎么随产品走（打进包里，还是让用户自己下载），不在这次定，只把每一份数据的许可证记下来。
- R8（可选）：探查构建打开「文件」app 可见的文稿目录，把一份 Rime 用户目录放进去，在探查页里选它。

## 5. 参考线【我定的，只用来判断「够不够好」，不是验收标准】

- 每次按键引擎用时：中位数 10 毫秒以内。
- 大词库下引擎带来的内存：100 MB 以内。
- 首次部署期间有进度，并且这段时间仍能用系统输入法打字。
- 安装包增量只记录，不设线。

## 6. 不做的、不能出现的

- 不改 `FlutterEditor`、`ComposerPanel`、`NativeEditor`、`SessionPlugin` 的现有行为；不改协议；不改 A 侧。
- 不做自己的软键盘；不做用户词库同步；不做设置界面；不做 Android、桌面。
- 只用公开 API。
- 不带 `RAPP_PROBE` 构建出来的 app 和 main 没有任何差别（包括不链接 librime）。
- 模拟器可以先跑通 R2–R4，但 R1、R5、R6、R7 的结论以真机为准：没在真机上看过的，写「待用户实机」，不写结论。

## 7. 交付

- 测量文档 `docs/superpowers/measurements/2026-11-19-rapp-ios-rime-panel.md`：R1–R8 一张表（结论、证据、机型和系统版本）；一张数字表（安装包、内存、首次部署、按键用时，小词库和大词库各一列）；链接进来的每个库和每份数据的名字、版本、许可证。

## 8. 探查完之后怎么定

| 结果 | 下一步 |
|---|---|
| R1 不成立（按键吞不掉，系统输入法照样组字） | 记下试过的办法：系统输入源切到英文时是否成立；编辑区不和系统建立文字输入连接时是否成立。都不成立，这条路在 iOS 上放下 |
| R1–R4 成立，R5、R6 在参考线以内 | 写正式设计：引擎放在哪一层（要能跨平台）、词库怎么分发、用户词库放哪和怎么同步、开关和回退、接进现有输入板。先在 iOS 上做成产品 |
| 成立，但代价超出参考线 | 看是词库的问题还是引擎的问题：换小词库、预编译词库、或改用 libime 再量一次 |
| 另一份探查（钉住系统候选条）也成立，用户用着顺手 | 两条路摆在一起由用户选；系统输入法够用的话，内嵌引擎可以不做 |

## 9. 留给执行的人

- librime 用现成的包还是自己编；编译选项；要不要带 lua、octagram 这些插件（探查里默认不带）。
- 键码表的写法；通道上消息的名字和格式。
- 探查页的排版；测量面板的样子。
- 内存怎么量（建议用进程的 `phys_footprint`）。

## 10. 我定的，一览

1. 引擎用 librime，不自己写（§3）。
2. 单独的探查页，不改现有输入板（§3）。
3. 探查里由原生一侧调引擎，候选的形状照 `LinuxCandidateSnapshot`（§3）。
4. 入口用 `--dart-define=RAPP_PROBE=rime`（§4）。
5. 词库取朙月拼音和雾凇拼音各一份；可选支持用户自己的 Rime 目录（§4）。
6. 参考线：按键 10 毫秒、内存 100 MB（§5）。
7. 只管实体键盘；软键盘和其他语言继续走系统输入法（§2 R7、§6）。
