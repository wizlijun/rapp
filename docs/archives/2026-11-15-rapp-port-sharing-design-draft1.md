## 1. 一句话和边界

**一台设备把本机的某个端口注册成"分享"，其他持 key 的设备就能用 `名字.rapp:端口` 访问它。** 路上走的是 rapp 已有的设备连接：同一个 key、设备之间 TLS 1.3 互相验证、局域网优先、不通时经 relay。公网上不出现任何服务端口。

本文的用词：

| 词 | 意思 |
|---|---|
| 分享方 | 注册了端口、让别人访问的设备 |
| 访问方 | 去访问别人端口的设备 |
| 普通设备 | 填了主 key 的设备。能分享，也能访问 |
| 服务器设备 | 填了服务器 key 的设备。只能分享，只能被访问 |
| 入口 | 访问方机器上，让 `名字.rapp:端口` 生效的那一部分 |

各类设备的角色（S7、S8、S11）：

| 设备 | 分享端口 | 访问别人 | 用哪把 key |
|---|---|---|---|
| Mac、Windows、Linux 桌面、PC 平板 | 能 | 能，系统里任何程序 | 主 key |
| 无界面 Linux | 能 | 不做 | 服务器 key |
| iPad、Android 平板、手机 | 不能 | 能，只在 rapp 内置浏览器里 | 主 key |

不做（第一版）：

- 公网入口：没装 rapp 的一方（手机浏览器、云端的 AI 产品、外部 webhook）访问不到（S3）。
- https（§15 第 7 步）。
- UDP。只转发 TCP。
- 把端口转发到分享方本机以外的地址（比如它局域网里的 NAS、路由器）。只接到分享方自己的 `127.0.0.1`。
- 访问方自己起别名、自己指定本机端口（`ssh -L` 那种）。
- 无界面 Linux 上的入口、终端和画面。
- iPad、Android 上系统层的 `.rapp` 域名（要靠 VPN 类型的系统扩展，用户没选，U133）。
- 打洞。照 2c §6，放到以后。所以不在同一个局域网的两台设备，流量都经 relay。

不能出现的结果（做成了也算失败）：

- 公网上多出任何一个服务端口；relay 上出现 HTTP 入口。
- relay 看到设备名、端口号或者任何内容。
- 用户需要知道、输入或维护任何 IP；出现虚拟网卡、路由、要用户理解的地址段（S10）。
- 没注册的端口被访问到。
- 一台服务器被攻破以后，对方能借它的 key 进入别的设备。
- 每加一个服务，要在访问方再配一次。
- 转发大流量时，远程会话明显变卡。

## 2. 用户看到的

**在提供服务的机器上**（一次）：

```
$ rapp name gpu1                 起一个短名；和别的设备重名时当场拒绝
$ rapp share 8000 11434 22       分享三个端口，立刻生效
$ rapp shares
端口     备注      状态
8000              有服务在听
11434             有服务在听
22                有服务在听
```

桌面设备上，同样的事在"本机"面板里做：短名一个输入框，分享的端口一张小表。

**在访问的机器上**：

```
浏览器     http://gpu1.rapp:8000/
命令行     curl http://gpu1.rapp:11434/api/tags
MCP        http://gpu1.rapp:8000/mcp
SSH        ssh gpu1.rapp             scp、rsync、git 一样
任何 TCP    rapp pipe gpu1 5432       把标准输入输出接到那个端口
```

三种名字都作数（S12）：

```
123456789.rapp             9 位 ID，永远可用
gpu1.rapp                  短名
bruces-macbook-pro.rapp    机器名的小写，自动有
```

**设备面板多出一栏**，点一下复制地址；无界面的机器上是 `rapp hosts`：

```
设备            域名                       分享的端口
gpu1            gpu1.rapp                  8000  11434  22
mini            mini.rapp                  8888
书房的 Mac      bruces-macbook-pro.rapp    （没有分享）
ubuntu          重名，请起一个短名          3000         ← 只能用 ID 访问
```

**第一次在一台桌面机上用域名**：点"启用 `.rapp` 域名"，系统要一次管理员授权（§9）。不授权也能用 `ssh` 和 `rapp pipe`。

**装一台无界面的服务器**（§11）：装一个程序，填接入点、服务器 key、短名，然后 `rapp share`。服务器 key 在任何一台普通设备的设置里能看到。

## 3. 做法的选择

要解决的核心问题：让"另一台设备上的端口"在访问方看起来就是一个普通的地址，同时不开公网端口、不让 relay 看到内容。

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | **在已有的设备连接上加一种请求"接到你本机的某个端口"；访问方本机有一个入口，把 `名字.rapp:端口` 接到这种请求上** | 信任、加密、选路、relay 全部沿用，relay 几乎不改；没有虚拟网卡和路由；一个 key 管到底 | 桌面上启用域名要一次管理员授权；很多本机服务只认 `localhost`，要做 HTTP 适配（§10） |
| 乙 | 虚拟网卡加虚拟 IP（Tailscale、WireGuard 的模式） | 任何协议都通，包括 UDP | 就是用户嫌麻烦的那种：多一层网络要维护；平板上占 VPN 位置；和 S10 相悖 |
| 丙 | 在 relay 的公网 IP 上开入口（frp 的模式） | 没装 rapp 的也能访问 | relay 会看到内容，没认证的人能敲门，和 relay 规格的 R1、R3 相悖；每个服务仍要配端口 |
| 丁 | 只做本机代理，浏览器和各个程序各自配代理 | 不要管理员授权 | 做不到"任何程序直接用"；SSH、curl、MCP 客户端都要单独配 |
| 戊 | frp 的点对点模式，或 SSH 反向隧道 | 现成 | 另一套认证、另一个守护进程；每个服务仍要配端口 |

**选甲**（用户已定：U130 定了不做公网入口，U132 定了域名形式，U134 定了注册端口和不要虚拟网）。丁在平板的内置浏览器内部被用到，那里不需要用户配置（§12）。

入口这一层还有一个选择，是这次设计里最需要用户过目的：

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| A | **每台设备在访问方本机对应一个回环地址**（127 开头，只在本机有效） | 几台 host 用同一个端口也不冲突；任何 TCP 协议都行 | 多一张内部的"设备 → 回环地址"表（用户看不到）；macOS 上开机时要加地址 |
| B | 所有 `.rapp` 名字都指向 `127.0.0.1` | 更小，没有地址表 | 本机自己占着 11434 时，`gpu1.rapp:11434` 没地方接；非 HTTP 协议下两台设备分享同一个端口时分不清 |

**选 A**（我定的，待用户确认，§17）。理由是 S8：几台 host 分享计算能力，很可能跑同一种服务、用同一个端口。回环地址不是虚拟网：没有网卡，没有路由，别的机器看不到，用户从不输入。

## 4. 安全

### 4.1 安全靠什么

1. **公网上没有服务端口。** 每台设备只向外连 relay。NAT 后面的机器不开任何入站端口。对外开着的仍然只有 relay 的那一个 UDP 端口。
2. **只有持 key 的设备能连。** 沿用 relay 规格 §6、§7：入网、设备密钥、端到端 TLS 1.3。relay 被攻破也看不到内容、冒充不了设备。
3. **只交出注册过的端口。** 默认什么都不交出，SSH 也要注册一次（我定的；用户没有反对）。
4. **服务器只能被访问**（§8，S13）。
5. **入口只在本机回环地址上监听。** 同一个局域网里的其他机器用不了。
6. **留记录**（§14.2）。

### 4.2 威胁表（接在 relay 规格 §4 后面）

| 代号 | 是谁 | 能做什么 |
|---|---|---|
| T5 | 拿到主 key 的人 | 和以前一样：是自己人。现在还能访问所有设备分享的端口 |
| T6 | 拿到服务器 key 的人（比如攻破了一台服务器） | 能作为一台新的服务器设备入网、分享端口、占用还没人用的名字。**不能**访问任何设备分享的端口，不能远程操作任何设备，不能抢已经有主的名字和 ID |
| T7 | 访问方机器上的其他本机用户 | 能连入口，也就能访问别的设备分享的端口。入口只该开在自己一个人用的机器上；这也是无界面 Linux 不带入口的原因之一 |
| T8 | 访问方浏览器里的恶意网页 | 被 §10.3 的检查挡住；挡不住的部分和这些服务在自己机器上面对的一样 |

T6 那一行是服务器 key 要达到的效果。它比主 key 多带一把公钥，原因在 §8.2。

### 4.3 两条已知的缺口（不是这次带来的）

- 主 key 仍然是总钥匙（relay 规格 §4.2 的 T5）。
- 被吊销的设备在同一个局域网里仍然被认识它的设备接受（2c §6）。

## 5. 结构

只有三样东西：

| | 在哪 | 是什么 |
|---|---|---|
| 分享表 | 分享方的 `rapp-service` | 这台设备交出哪些本机端口（§6） |
| 名字 | relay 登记，访问方查询 | 短名、机器名各对应哪台设备（§7） |
| 入口 | 访问方的 `rapp-service`（桌面）；app 内（平板、手机） | 把 `名字.rapp:端口` 上的连接接到对方的端口（§9、§12） |

入口放在 `rapp-service` 里，不放在 `rapp-hub` 里（我定的）：服务一直在跑，界面关着的时候 host 之间也要通。现在向外拨号的代码在 hub（`rust/hub/src/link.rs` 的 `Dialer`），要挪成 service 和 hub 共用。

### 5.1 设备之间新增的请求

走 relay 规格的 L4（设备请求），一条流一个请求，一行 JSON。

| 请求 | 内容 | 回复 |
|---|---|---|
| `list_shares` | `{"op":"list_shares"}` | `{"ok":true,"shares":[{"port":8000,"note":"…"}],"short":"gpu1","machine":"ubuntu-gpu"}` |
| `forward` | `{"op":"forward","port":8000}` | `{"ok":true}`，此后这条流就是那个端口上的字节；错误 `not shared`、`refused`（端口上没有服务在听）、`limit` |

规则：

- 这两个请求**只在按 key 互信的连接上受理**（`rapp/2` 直连，或经 relay 的端到端流）。旧的密码认证连接上一律回 `not supported`。
- 分享方连本机的 `127.0.0.1:端口`；连不上再试 `[::1]:端口`。
- 半关闭要保留（一头写完、另一头还在写），否则 SSH、HTTP 的某些用法会断。
- 每台来访设备同时转发的连接有上限（默认 256，我定的），超了回 `limit`。

### 5.2 经 relay 时不能每条连接各握一次手

relay 规格里，经中继的每一条流都要在里面再做一次 TLS 握手。远程会话一个会话一条流，这没问题。网页不一样：打开一个页面就是几十条 TCP 连接。

要求（我定的）：**一对设备之间经 relay 只建一条长开的加密通道，转发的连接在它里面复用。** 通道建好以后，每新开一条转发连接，额外的耗时不超过两台设备经 relay 的一个往返。用什么复用、要不要先量一量"每条各握一次手"到底多慢，留给实现计划。

局域网直连时不需要：一条 QUIC 连接上本来就能开很多条流。

### 5.3 不拖慢远程会话

转发的流和远程会话的流走同一条设备连接。要求：同一对设备之间有大流量转发时，远程会话的输入和画面延迟不明显变差。做法（流的优先级，或限制转发占的份额）和验收的数字留给实现计划，用流畅串流规格 §4.1 的工具量。

## 6. 分享端口（S9）

- **注册**：`rapp share <端口>…`，或"本机"面板里的表。可以带一句备注。`rapp unshare <端口>` 取消。立刻生效，不用重启。
- **注册时那个端口上不必有服务在听。** 服务后启动也行。
- **存在哪**：设备数据目录 `local/shares.json`（0600，不进 git）。每项：端口、备注、是否原样转发（§10.4）。
- **取消分享**：已经接着的连接立刻断开。
- 上限：一台设备最多分享 64 个端口（我定的）。

`rapp` 这个命令名是我定的。现在 `rapp` 是界面程序的名字，`rapp-service` 不接受参数（`rust/service/src/main.rs`），所以要有一个和服务说话的命令行。是给界面程序加子命令，还是另做一个小程序、另起名字，留给实现计划；无界面的机器上没有界面程序，那里必须有它。

## 7. 名字（S6、S12）

### 7.1 三种名字，一个名字空间

| 名字 | 从哪来 | 规则 |
|---|---|---|
| ID | 现有的 9 位数字 | 永远可用，relay 已经保证不重复 |
| 短名 | 用户在设备自己身上起 | 小写字母、数字、连字符；字母开头；2 到 32 个字符（长度我定的） |
| 机器名 | 系统主机名（现有的 `rapp_net::config::hostname()`） | 转小写；其他字符换成连字符；首尾的连字符去掉；结果是纯数字或者空的，就没有机器名 |

- 地址是 `<名字>.rapp:<端口>`。`<名字>` 前面还可以有别的层（`a.b.gpu1.rapp`），都算 gpu1：有些网页服务靠子域名区分站点（我定的）。
- 现有的"设备名"（显示用，可以是中文、可以很长）不变。
- 名字在设备自己身上设一次，所有访问方看到的都一样。所以写着 `gpu1.rapp` 的配置可以原样拷到另一台机器上用。没选"访问方各自起别名"，理由是那样每台都要配，而且同一台设备在不同机器上名字不一样。

### 7.2 全局不冲突，由 relay 把关（S12）

只有 relay 知道所有设备，包括当时不在线的。设备之间互相问，问不到离线的那台。

- 设备向 relay 登记自己的名字。relay 把名字绑到这台设备的密钥上，和现在绑 ID 是同一个做法。别的设备再登记同一个名字，被拒绝。
- **relay 存的是名字的指纹，不是名字。** 指纹 = 用 key 推出的一个密值对名字算的消息认证码。relay 没有 key，算不出、也猜不出原名。relay 规格 §4.3 的"relay 不知道设备名"仍然成立。
- 短名和机器名在同一个名字空间里：你的短名不能和别人的机器名一样，反过来也是。
- **提交短名时当场检查**：被占了就拒绝，不存下来，提示"已被占用"。
- **机器名是自动的，没法当场拒绝**：两台都叫 `ubuntu`，先登记的生效；后一台的机器名不作数，界面和 `rapp hosts` 里提示它起一个短名，在那之前用 ID。
- **改短名**：旧名字立刻释放。界面提醒：用旧名字写的配置会失效。
- 设备被吊销或者 `unbind`：它的名字一起释放。

### 7.3 访问方怎么查

1. 名字是 9 位数字：就是 ID。
2. 否则算出指纹，问 relay 是哪个 ID（§13 的 `resolve`）。结果在本机缓存。
3. 和那台设备连一次，按现有的办法互信，取它的 `list_shares`。

所以一台新设备填好接入点和 key 以后，直接写 `http://gpu1.rapp:8000` 就能用，不需要先和 gpu1 连过。

**名字钉在设备密钥上**（我定的）：访问方第一次用一个名字时，记下它对应的设备指纹。以后 relay 说这个名字换了一台设备，访问方不自动跟过去，而是拒绝并提示"gpu1 换了设备"，用户确认一次才接受。和 SSH 的 `known_hosts` 是一个道理：防的是"relay 被攻破，加上有人拿到了服务器 key"时冒充一台已有的服务器。

### 7.4 没有 relay 时

只在局域网里用 `ID@地址` 直连、没有 relay 的时候，没有全局的裁判。退回到每台访问方各自先到先得：先认识的那台占着名字，后来的重名设备只能用 ID。

## 8. 服务器 key（S13）

### 8.1 用户看到的

- 任何一台普通设备的设置里，key 那一栏下面多一行"服务器用的 key"，点一下显示、复制。命令行是 `rapp server-key`。它由主 key 推出来，不用另外保管。
- 装服务器时填它。之后这台设备：能入网、能登记名字、能分享端口、能被普通设备访问。**它发起的任何访问，所有设备都不接受；它也访问不了别的服务器。**
- 从服务器 key 推不回主 key。
- 换 key（2c）时，服务器 key 跟着变，每台服务器上要重新填一次。

### 8.2 构成

主 key 的"根"（relay 规格 §6.2）用现有的单向推导再推出三样：

| 值 | 谁知道 | 用来做什么 |
|---|---|---|
| 服务器根 | 普通设备、服务器设备 | 像主 key 的"根"一样，再推出服务器的入网口令、服务器的信任口令、名字指纹用的密值 |
| 来访签名的私钥 | 只有普通设备 | 普通设备访问服务器时，对这一次握手签名 |
| 来访签名的公钥 | 都知道 | 服务器用它验证"来的是持主 key 的设备" |

服务器 key = relay 指纹的前 16 字节 + 服务器根 + 来访签名的公钥。

为什么要多一把公钥：如果服务器和访问方只共用一个口令（现在普通设备之间就是这样），那么拿到服务器 key 的人也有这个口令，就能冒充访问方去敲别的服务器。用签名以后，服务器只能验证、不能伪造。**代价是服务器 key 比主 key 长：大约 110 个字符，主 key 是 56 个。**只在装服务器时粘贴一次。

如果能接受"一台服务器被攻破后，对方能访问别的服务器分享的端口（仍然进不了任何桌面设备）"，可以不要这把公钥，服务器 key 就和主 key 一样长，实现也更简单。我选了带公钥的做法，因为它才做到 §1 说的"进不了别的设备"。见 §17。

### 8.3 谁接受谁

| 发起方 → 接受方 | 发起方出示什么 | 结果 |
|---|---|---|
| 普通 → 普通 | 现有的互信证明（主 key 的信任口令） | 和现在一样 |
| 普通 → 服务器 | 来访签名，绑在这一次握手上 | 接受。服务器用服务器的信任口令回一个证明，访问方把它记成"服务器" |
| 服务器 → 普通 | 它没有主 key 的信任口令 | 拒绝。已经记成"服务器"的设备，它发来的请求也一律拒绝 |
| 服务器 → 服务器 | 它没有签名私钥 | 拒绝 |

- `paired.json` 的每一项多一个角色：普通或服务器。
- 签名和证明都绑在当次握手上，做法照 relay 规格 §7.2。签名算法用 Ed25519（我定的：现有的库能从一个种子直接得到密钥对）。不自己设计算法。
- relay 那一侧也拦一道（§13）：服务器设备发的 `connect`、`relay`、`resolve` 被拒绝。这只是多一层；真正的门在设备上，因为 relay 本身不被信任。

## 9. 入口：桌面（Mac、Linux 桌面、Windows、PC 平板）

### 9.1 三件事

1. **回答 `.rapp` 的域名查询。** `rapp-service` 里有一个只回答 `.rapp` 的小解析器，只在本机回环地址上听。查到的名字回它对应的回环地址；不认识的回"没有这个名字"；IPv6 的查询立刻回"没有"，不让程序干等。
2. **每台设备一个回环地址。** 从一段固定的回环地址里分配（比如 `127.77.0.x`，具体哪一段留给实现计划），存在 `local/` 下，分配以后不变。同一个名字今天和明天指向同一个地址。
3. **在那个地址上、对方分享的每个端口上监听。** 有连接进来，就向对方发 `forward`，两头对接。

对方分享的端口从 `list_shares` 得到，缓存在本机；对方的分享有变化时要跟上（怎么得知变化留给实现计划）。对方不在线时：监听照旧，连接进来后立刻断开。

第一次查一个从没用过的名字时，解析器要等监听准备好了再回答（问 relay、连上对方、取到分享的端口），否则程序拿到地址马上去连会扑空。最多等几秒，超时就照常回答；具体多久留给实现计划。

### 9.2 系统层怎么生效：一次管理员授权

`.rapp` 不是系统认识的域名，没有不要管理员权限的做法。授权只做一次，做的事情是"告诉系统 `.rapp` 结尾的名字去问本机的 rapp"。之后设备增减都不再需要管理员权限，也不用反复改 `hosts` 文件。

| 系统 | 打算怎么做 | 验证过吗 |
|---|---|---|
| macOS | `/etc/resolver/rapp` 指向本机的解析器；一个系统启动项在开机时给回环口加上那一段地址 | 机制是系统自带的；没有在这个项目里试过 |
| Linux 桌面 | 回环地址不用加（整个 127 段本来就在本机）。域名交给本机解析器的办法要先验证：systemd-resolved 的配置，或者一个只改 `hosts` 里 rapp 那一段的小助手 | 未验证 |
| Windows | 系统自带的"某个后缀交给某个解析器"的规则；回环地址不用加 | 未验证 |

没授权时：`ssh` 和 `rapp pipe` 照常可用（§9.4）；界面上"启用 `.rapp` 域名"的按钮一直在。

### 9.3 会碰到的冲突

| 情况 | 表现 |
|---|---|
| 本机有服务监听了"所有地址"的同一个端口（Linux 上尤其会） | 那个端口在入口上接不了。`rapp hosts` 和设备面板在那个端口旁边标"本机端口被占用"。用 `rapp pipe` |
| 1024 以下的端口（80、443、22） | Linux 上普通程序默认不能监听；macOS 上未验证。打算在授权那一次里一并解决；解决不了的，标"需要权限"。SSH 不受影响 |
| 设备太多，回环地址用完 | macOS 上开机时加的地址数是固定的（默认 64，我定的）。超了的设备只能用 `rapp pipe` |

### 9.4 SSH 和 `rapp pipe`

`rapp pipe <名字> <端口>`：把标准输入输出接到那台设备的那个端口。名字带不带 `.rapp` 都认。它只和本机的 `rapp-service` 说话，不需要域名解析、不需要监听、不需要管理员权限。

SSH 用它，在 `~/.ssh/config` 里加一次，对所有设备生效：

```
Host *.rapp
    ProxyCommand rapp pipe %h %p
```

"启用 `.rapp` 域名"时顺手问一句要不要加这两行；也可以自己加。scp、rsync、git 都走这一条。SSH 自己的登录验证（密钥、`known_hosts`）不变，rapp 不碰。

## 10. HTTP 适配

### 10.1 为什么需要

这是域名形式带来的代价，之前在对话里没有讲到。

很多跑在本机的服务会检查请求里的 `Host`，只认 `localhost` 和 `127.0.0.1`，别的一律拒绝。这是它们防"恶意网页借浏览器访问本机服务"的办法。据我所知，Ollama、Jupyter、Vite 这类开发服务器、新版的 MCP 服务器框架都有这种检查（没有逐个实测，§16）。浏览器访问 `http://gpu1.rapp:8000` 时，请求里写的是 `Host: gpu1.rapp:8000`，会被这些服务拒绝。

不处理的话，用户得去改每一个服务的配置，那就不是"注册一个端口就能用"了。

### 10.2 做法

分享方的 `rapp-service` 在把连接接到本机端口之前，看一眼开头的字节：

- **是 HTTP/1.x 的请求**：把请求里的 `Host` 换成 `localhost:端口`；`Origin`、`Referer` 里如果是这台设备自己的 `.rapp` 名字，也换成 `localhost:端口`。响应里 `Location`、`Access-Control-Allow-Origin` 出现的 `localhost:端口`，换回访问方用的那个名字。同一条连接上后面的每个请求同样处理。WebSocket 和流式响应（MCP 用的那种）原样通过。
- **不是**（SSH、数据库、TLS、HTTP/2）：原样转发，一个字节不动。

放在分享方做（我定的）：它知道本机服务认什么；平板的内置浏览器过来也用得上；"要不要适配"这个开关跟着分享的端口走。

改写的范围就是上面列的这几个头。正文里写死的地址不改。精确的清单、各种边角（分块传输、`Expect`、请求走私的防护）留给实现计划，并且要拿几个真的服务来验（§19）。

### 10.3 顺带的两条检查

因为适配等于替服务关掉了它自己的那道检查，要补上同样的防护：

1. **`Host` 不是这台设备的 `.rapp` 名字（或 ID）的请求，拒绝。** 防的是恶意网站把自己的域名解析到入口的回环地址上。
2. **公网网页发起的请求，拒绝。** 判断办法：浏览器会标明请求是不是跨站发起的，以及发起的页面是谁。发起页面不是 `.rapp`、不是 `localhost`，而且不是用户自己在地址栏打开或点链接过来的，就拒绝。`mini.rapp` 上的网页调 `gpu1.rapp` 上的接口，放行；之后服务自己的跨域设置照常生效。

第 2 条的精确规则留给实现计划。某个端口确实要让公网网页调用时，注册时加一个选项放开（我定的）。

### 10.4 关掉适配

`rapp share 8000 --raw`：这个端口原样转发，不看内容。给"服务自己已经配好了认 `.rapp` 域名"或者"适配把它弄坏了"的情况用。

## 11. 无界面 Linux（S4、S11）

**这推翻了终端会话规格 §1 的"不做 Linux 无界面的安装包"。** 当时的理由是服务器上已经有 sshd，不想再装一个能给出 shell 的守护进程；并且留了一个例外：服务器在 NAT 后面、谁也 SSH 不到。用户说他的无桌面机器多数在 NAT 后面（U131），正是那个例外。

发布物：`rapp-service` 一个程序、命令行、一个 systemd 单元。`rapp-service` 现在就不依赖任何图形库（`rust/service/Cargo.toml`）。

- **只做分享**：没有入口，不碰系统的域名解析，不需要回环地址，用普通用户身份运行。
- **不给终端、不给画面**：`list_apps` 回空；终端会话默认关（它本来就有开关，`local/term.json`）。它自己不给出 shell；`ssh gpu1.rapp` 的登录仍然由服务器的 sshd 把关。
- **不用界面完成设置**：填接入点、服务器 key、短名，各一条命令或者一条命令带三个参数。key 不出现在命令行参数里（会留在 shell 历史和进程列表里），从标准输入或文件读（我定的）。
- **状态和排错**：`rapp status`（连没连上 relay、ID、名字、角色）、`rapp shares`、`rapp hosts`。
- **升级**：第一版手动换程序。现有的自动更新只管 `.app`。
- 架构：x86_64 和 arm64。

以后真有服务器要访问别人，入口的代码和 Linux 桌面是同一份，那时它需要主 key。

终端会话规格里"服务器上不装东西、由一台代管设备 SSH 过去"的那条路不变。经它转发端口（用 SSH 自带的转发）排在 §15 第 7 步。

## 12. 平板和手机（S7）

- 只当访问方。不分享端口（iPad、Android 上本来也没有 `rapp-service`，反馈文档 U18）。
- **rapp 内置一个浏览器**：地址栏里写 `http://gpu1.rapp:8000/`。页面的请求不出 app：交给 app 里的同一份底座代码，查名字、连设备、发 `forward`。没有 VPN，没有系统设置要改。
- Safari 和其他 app 用不了 `.rapp`。平板上的终端需求由 rapp 已有的终端会话承担。
- 它跟着平板主控台一起做。现在 `gui/` 下只有 macos、linux、windows 三个目标；平板上要先把 hub 从子进程改成库（反馈文档 U16 小节已经记了这一条）。
- 内置浏览器怎么把请求交给 app（两个系统各自的网页控件支不支持、Flutter 这边用什么）未验证，留到做平板的时候。

设备面板里点一个分享的端口：桌面上用系统浏览器打开；平板上用内置浏览器打开。

## 13. relay 的改动

relay 规格说 relay 只做登记、牵线、接流。这次加的两处都属于"登记"，relay 仍然不知道任何业务，也不知道任何名字。**之前在对话里说过"relay 一行都不改"，不成立，更正在这里。**

**一、名字指纹**

| 请求 | 内容 | 回复 |
|---|---|---|
| `register` 多一个字段 | `"names":["<指纹>", …]`（最多 2 个：短名、机器名） | 回复里多 `"names":{"<指纹>":"ok" 或 "taken"}` |
| `claim`（新） | `{"op":"claim","name":"<指纹>","release":"<旧指纹>"}` | `{"ok":true}`；错误 `name taken`。占新的和放旧的是一步完成的 |
| `resolve`（新） | `{"op":"resolve","name":"<指纹>"}` | `{"ok":true,"id":"123456789"}`；错误 `unknown name` |

- 登记簿的设备记录多一项：这台设备占着的指纹。
- `resolve` 和 `connect` 一样限速，防止有人拿它来试名字。
- 审计多一种事件 `name`（占用、释放、被拒，只记指纹）。
- 请求的名字和字段是我的提议，最后以实现计划为准。

**二、设备的角色**

- `rapp-relay key` 生成 key 时，除了主 key 的入网口令的哈希，再存一份服务器入网口令的哈希。入网时对上哪一个，这台设备就是哪种角色，记在登记簿里。
- 服务器角色的设备：可以 `register`、`claim`，可以被 `connect`、`relay`；它自己发的 `connect`、`relay`、`resolve` 回 `host only`。
- `rapp-relay rotate-key` 同时换掉两份哈希；2c 里"所有设备要重新输入 key"对服务器设备同样成立，它们要输入新的服务器 key。
- `rapp-relay devices` 多一栏角色；审计的 `enroll` 多记角色。
- **已经在跑的 relay** 没有第二份哈希。怎么补上，留给实现计划。我的提议：由任意一台已入网的普通设备提交一次，relay 只接受第一次；不用换 key。

relay 规格 §4.3 的"relay 知道什么"多两行：每台设备占着几个名字的指纹；每台设备是哪种角色。

## 14. 配置和记录

### 14.1 设备这一侧新增的文件

都在设备数据目录的 `local/` 下，0600，不进 git。

| 文件 | 内容 |
|---|---|
| `service.json` 多一项 | `short`（短名）。key 的种类由 key 自己的写法区分，不另存 |
| `shares.json` | 分享的端口：端口、备注、是否原样转发、是否放开公网网页 |
| `names.json` | 访问方：名字 → 设备指纹（钉住的）、设备 → 回环地址、对方分享的端口的缓存 |
| `paired.json` 每项多一个角色 | 普通、服务器 |

### 14.2 记录

- **分享方的访问记录**（可观测性规格）多一种事件"转发"：谁（指纹、自报的名字）访问了哪个端口、走的哪条路、多少字节、多久。网页会开很多连接，所以按"来访设备 + 端口"合并，每 10 分钟一行，带连接数；一个来访设备第一次访问某个端口立刻记一行（我定的）。被拒绝的（没分享、角色不对、§10.3 的两条检查）每次都记，同一原因有限速。
- **relay 的审计**：`relayed` 照旧（一条长开的通道一行）；新增 `name`；`enroll` 带角色。
- **永远不记**：两种 key、任何口令和私钥、流里的内容、请求的网址。

### 14.3 界面

- **本机面板**：短名（输入框，提交时检查重名）；分享的端口（表，加、删、备注）；"服务器用的 key"（遮住，点一下显示）；"启用 `.rapp` 域名"的状态和按钮。
- **设备面板**：§2 里那一栏。设备的角色是服务器时标出来；它没有 app 列表。
- 视觉上的细节照设计语言，留给界面那一步的计划。

## 15. 分期

每一步单独写实现计划，做完能单独用。

| 步 | 做什么 | 做完以后 |
|---|---|---|
| 1 底座 | 分享表和 `rapp share`；`list_shares`、`forward`；`rapp pipe` 和 SSH 的两行配置；访问记录；经 relay 的复用通道（§5.2）；向外拨号的代码挪成共用 | 两台普通设备之间：用 ID 能 `ssh`，`rapp pipe` 能接任何分享了的端口；没分享的端口被拒 |
| 2 名字 | 短名、机器名；relay 的名字指纹；`resolve`；访问方钉住名字 | `ssh gpu1.rapp`；重名当场被拒 |
| 3 服务器 | 服务器 key（设备和 relay 两边）；无界面 Linux 的安装包和命令行 | NAT 后面的一台服务器装好、分享端口，从桌面 `ssh gpu1.rapp`；从那台服务器发起的访问全部被拒 |
| 4 桌面入口 | 解析器、回环地址、监听、一次授权。先 macOS 和 Linux 桌面，Windows 随后 | 浏览器、curl、MCP 客户端直接用 `http://gpu1.rapp:8000` |
| 5 HTTP 适配 | §10 | Ollama、Jupyter、一个 Vite 开发服务器、一个 MCP 服务器，不改它们的配置就能用 |
| 6 平板和手机 | 内置浏览器。跟着平板主控台 | 平板上打开 `http://gpu1.rapp:8000` |
| 7 以后 | https（每台访问方一张只对 `.rapp` 有效的本地证书）；经 SSH 代管的主机转发；服务器上的入口 | — |

顺序的理由：用户最痛的是 NAT 后面的服务器上的 http、mcp、ssh。第 1 到 3 步做完，SSH 这一条已经完整可用；第 4、5 步补上浏览器和 MCP。relay 的两处改动分别在第 2、3 步，可以攒成一次 relay 发布，由实现计划安排。

**不做 https 的后果**（用户知道，U132 之后的讨论）：浏览器只把 `localhost` 当作安全来源，`http://gpu1.rapp:8000` 不算。路上的数据仍然是全程加密的；受影响的是要求安全来源的网页功能（剪贴板、麦克风、后台缓存），比如 code-server 这类网页版编辑器。

## 19. 测试要求

- **分享**：没分享的端口回 `not shared`；取消分享后已有连接断开；端口上没有服务时回 `refused`；半关闭保留；并发上限。
- **只在互信的连接上**：旧的密码认证连接上发 `forward` 被拒。
- **名字**：三种名字都能解析到同一台设备；短名重名当场被拒；机器名重名时后一台不作数并有提示；改名后旧名字释放；relay 的数据卷和日志里搜不到任何名字的原文；名字换了设备时访问方拒绝并提示。
- **服务器 key**：用服务器 key 入网的设备，角色是服务器；它向普通设备、向另一台服务器发起的连接都被拒；普通设备能访问它；只拿到服务器 key 的进程冒充访问方失败；中间插一个转发的进程时签名验证失败；从服务器 key 的所有字节里推不出主 key 的任何口令（按构造检查）。
- **relay**：服务器角色发 `connect`、`relay`、`resolve` 被拒；`resolve` 的限速；审计里有 `name` 和带角色的 `enroll`。
- **入口**：两台设备分享同一个端口，各自的域名各通各的；本机占着同一个端口时的表现和提示；对方不在线时连接立刻断开；没授权时 `rapp pipe` 和 SSH 可用；卸载后系统的解析设置还原。
- **HTTP 适配**：拿真的 Ollama、Jupyter、一个 Vite 开发服务器、一个 MCP 服务器（含流式响应）、一个 WebSocket 服务各跑一遍，不改它们的配置；`Host` 不对的请求被拒；公网网页发起的请求被拒，`.rapp` 之间的放行；`--raw` 时一个字节不动；请求走私的常见写法被拒。
- **性能**：经 relay 打开一个有 50 个请求的页面的时间；复用通道建好后新开一条连接的额外耗时（§5.2）；一条大流量转发进行时，远程会话的延迟（§5.3）。
- **机密全量检查**：所有测试结束后，各处的日志和 relay 的数据卷里搜不到两种 key、任何口令和私钥。
- **无界面**：在一台没有图形环境的 Linux 上从安装到 `ssh 名字.rapp` 走通；非 root 运行；重启后自己恢复。
