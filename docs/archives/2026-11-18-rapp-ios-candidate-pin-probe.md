# iOS 探查：把系统拼音的候选条钉在文字下一行

日期：2026-11-18。状态：探查规格，待执行。这是一次性试验，代码不进 main；只回答「能不能、怎么做」，不交付功能。

标了【我定的】的是我做的决定，用户没有逐条确认过，可以否掉。标了【没核对】的是凭记忆写的，动手前先对照源码。

## 1. 为什么

用户的话：

- 2026-11-14：「后续会改造输入法，让打字体验在文字的下一行，这样眼睛可以固定不动。减少输入法框飘来飘去的问题。」
- 2026-11-18（试过仓输入法、fcitx5-ios 之后）：「只能适应 apple 自带中文输入了。」「他是否允许调整浮动候选框为固定候选框」「写一段 spec，我让其他 agent 试一下。」

背景（2026-11-18 查到的）：

- iOS 上第三方输入法是键盘扩展，接了实体键盘后按键不经过它，候选是系统输入法出的。所以 iPad 配机械键盘只能用系统自带的中文输入法。
- 没有查到 iPadOS 提供「候选栏固定 / 跟随光标」的设置。
- 但有两个别人的 bug 说明候选条的位置是 app 报给系统的：
  - super_editor #3008（https://github.com/Flutter-Bounty-Hunters/super_editor/issues/3008 ）：iPad 接实体键盘时，原生 app 有两处候选——光标旁的浮动候选条，和屏幕底部居中的输入辅助条；那个 Flutter 编辑器里只剩底部那条。
  - pairlet #399（https://github.com/heypandax/pairlet/issues/399 ）：同一台 iPad、同一个系统拼音，别的 app 里候选条跟着输入框，那个 app 里固定在屏幕左上角。

推断（没验证，这次探查就是验证它）：rapp 的编辑框向系统报一个固定的位置，候选条就停在那里。

## 2. 要回答的问题

每一条要有结论和截图。设备：iPad 和 iPhone Duo 各一遍，接实体键盘，系统「简体拼音」。记下机型和系统版本。

| 编号 | 问题 |
|---|---|
| Q1 | **现状**：现在的 rapp（main）写作面板里打拼音，有没有浮动候选条，出现在哪里；有没有底部居中那一条。iPad 和 Duo 是否一样（iPhone 上可能根本没有浮动候选条）。 |
| Q2 | **锚点**：系统显示浮动候选条前，向文本控件问了哪些位置（`firstRect(for:)`、`caretRect(for:)`、`selectionRects(for:)`，各自传进来的范围是什么）；改哪一个的返回值，候选条跟着动。 |
| Q3 | **能不能钉住**：让候选条的左上角落在钉点 P（见 §4）。继续打拼音、翻页、选字、光标移到前面几行、文字写到多行时，它是否一直停在 P。 |
| Q4 | **下面要留多少地方**：候选条多高（pt）；展开成多行候选时多高、往哪边展开；P 下面空间不够时它会不会翻到文字上面或盖住文字。写作面板要为它留几行。 |
| Q5 | **副作用**：钉住之后，光标画在哪里、选区把手、编辑菜单、听写的提示、英文的行内预测，是否还在正确的位置。拔掉实体键盘只用软键盘时，行为应该和没改一样。 |
| Q6 | **退路**：不报位置（或报到屏幕外）时，浮动候选条是否消失、只剩底部居中那一条；那一条里能不能照常用数字键和空格选字。 |
| Q7 | **Flutter 里能不能做**：不用原生控件，只通过 Flutter 的文字输入通道报同样的矩形，结果和原生是否一样。 |
| Q8 | **别的输入法**：日文罗马字、简体双拼各试一句，钉住的位置是否还成立。 |

## 3. 做法的选择

| 做法 | 取舍 |
|---|---|
| A 直接改 `FlutterEditor` | 离产品最近；但 Flutter 的 `EditableText` 每帧自己往系统报光标和组字的位置，要改就得分叉它，还会弄脏 main；探查失败时白改 |
| **B 单独的探查页：先原生控件，再 Flutter 输入通道（已选）**【我定的】 | 原生控件给出系统的真实行为（Q2–Q6），也是 iPad 规格 §8.4 里 P2 原生编辑框要走的路；Flutter 那一步只回答「P1 的 Flutter 编辑框能不能先做」（Q7）；都不碰现有输入板 |
| C 不探查，直接在 app 里内嵌 Rime | 候选位置完全自己画；但工作量大得多，而且用户已经决定先适应系统输入法 |

## 4. 探查程序

分支 `probe/ios-candidate-pin`，不合并（和 `probe/ipad-p0` 一样）。用现有的 iOS 构建方式装到设备上。入口【我定的】：构建时带 `--dart-define=RAPP_PROBE=candidate`，启动后直接进探查页，不进主界面；不带这个参数时行为和 main 完全一样。

**探查页长什么样**

- 一个仿写作面板的框：宽 720（屏幕窄时取屏宽减 16），字号 15、行高 22，一行起步、往上长，底边不动。默认放在屏幕中部，下面留足空间。
- 钉点 P =（框内文字左缘，最后一行底边往下 4）。页面上用一条细的彩色线把 P 和「报给系统的矩形」画出来，截图里能直接比对报的位置和候选条实际出现的位置。
- 一个「贴底」开关：把框挪到屏幕底部，框下面只留 0 / 48 / 96 pt（Q4）。
- 模式切换，当前模式显示在页面上：
  - M0 原样：报真实的位置（对照组）。
  - M1 钉住：不管光标在哪，都报一个固定矩形，目标是候选条落在 P。报什么矩形能让它正好落在 P（报最后一行的行框，还是报 P 本身），由探查定。
  - M2 横向固定：x 固定在文字左缘，y 跟着光标所在的行。
  - M3 不报：返回空矩形或屏幕外的矩形（Q6）。
- 页面下半部一块日志区，显示最近 20 次系统的位置查询：方法名、范围、返回的矩形。用户在真机上截图就能带回来，不需要连 Xcode。

**第一步：原生控件（Q2–Q6、Q8）**

`gui/ios/Runner` 里加一个 `UITextView` 子类，分别用两个开关控制是否改写 `firstRect(for:)` 和 `caretRect(for:)`，这样能分清候选条认的是哪一个，以及只改 `firstRect(for:)` 够不够（改 `caretRect(for:)` 会连带把画出来的光标挪走，这是 Q5 要看的）。只用公开 API；不碰 `UIKeyboardImpl` 之类的私有接口【我定的，上架要求】。

**第二步：Flutter 输入通道（Q7）。第一步的 M1 成功了才做。**

探查页里另放一个自己实现 `TextInputClient` 的最小输入框（自己接 `TextInput.attach`，自己画文字和组字下划线），按同样的 M0–M3 调 `TextInputConnection` 的 `setCaretRect`、`setComposingRect`、`setEditableSizeAndTransform`【没核对：方法名和它们在 iOS 引擎 `FlutterTextInputPlugin.mm` 里对应到 `firstRectForRange:` / `caretRectForPosition:` 的关系，按 Flutter 3.44.1 的框架和引擎源码核对】。不要去改 `EditableText`，也不要拦平台通道。

## 5. 不做的、不能出现的

- 不改 `FlutterEditor`、`ComposerPanel`、`NativeEditor` 和任何现有输入板代码；不改协议；不改 A 侧。
- 不做候选的自绘、不接 Rime、不做词库导入。
- 不带 `RAPP_PROBE` 构建出来的 app 和 main 没有任何差别。
- 模拟器（I/O › Keyboard › Connect Hardware Keyboard）可以先看个大概，但结论以真机为准：没在真机上看过的那一条，写「待用户实机」，不写结论。

## 7. 探查完之后怎么定

| 结果 | 下一步 |
|---|---|
| 原生能钉住（Q3 成立，Q5 没有不能接受的副作用） | 写进 iPad 规格 §8.4 的 P2 原生编辑框：候选钉在文字下一行，写作面板按 Q4 的数字留出位置 |
| Flutter 通道也能钉住（Q7 成立） | 评估要不要在 P1 的 `FlutterEditor` 上先做，不等 P2 |
| 钉不住，但 M3 能只留底部那一条（Q6 成立） | 退一步：只用底部固定的那一条，眼睛的落点也是固定的 |
| 都不行 | 保持系统默认行为；「内嵌 Rime、候选自己画」作为以后的选项重新评估 |

## 9. 我定的，一览

1. 单独的探查页，不改现有输入板（§3）。
2. 入口用 `--dart-define=RAPP_PROBE=candidate`（§4）。
3. 原生一步用 `UITextView` 子类，不自己从头实现 `UITextInput`（§4）。
4. 只用公开 API（§4）。
5. Flutter 那一步放在原生成功之后（§4）。
6. 钉点 P 取「文字左缘、最后一行底边往下 4」（§4）。
