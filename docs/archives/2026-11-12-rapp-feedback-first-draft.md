## 需求反馈：质疑与替代方案（2026-11-12）

> 本节记录 rapp 收到的外部质疑，以及被拿来对比的替代方案。
> 目的不是反驳，而是用这些反馈校准需求：哪些是 rapp 不该做的，哪些是 rapp 必须证明的。
> 标注「原话」的是反馈者或需求方的表述，标注「分析」的是整理时的判断，尚未经过验证。

### 1. 核心问题重申

**原话（需求方）：** 我现在的问题就是注意力瓶颈问题，跟 harness 无关。

rapp 要解决的是需求方自己使用 Claude 时的注意力瓶颈，不是 agent 怎么执行、怎么编排的问题。
后面三条反馈都要放在这个前提下看。

### 2. 反馈记录

#### 反馈 A：「不如去用 UU，看不懂 rapp 的价值」

- **原话：** 不如去用 UU，看不懂我们这个 rapp 的价值。
- **指的是：** 网易 UU 远程，免费的远程控制软件。
- **成立的部分（分析）：** UU 远程已经很成熟。免费版开放 4K/144Hz、不限时长和设备数，Mac 被控也已支持。
  如果把 rapp 描述成「远程控制 Mac」，自己造一个确实不划算。
- **没打中的部分（分析）：** UU 的方向和 rapp 相反。
  - UU 传的是整个桌面（小窗模式也是整块远端屏幕的悬浮窗）；rapp 要的是单个 app 窗口，B 端缩放时 A 端窗口跟随。
  - UU 走高画质高码率路线；rapp 要的是 4/8/16 bit 的极限省带宽、文字清晰。
  - UU 逐键发送、用远端输入法；rapp 要在 B 端本地组字后一次发送。
  - UU 闭源、需要网易账号；rapp 是个人自用、自主可控。
- **对需求的影响：** rapp 的定位描述不能是「远程控制」。价值必须落在上面四点差异上，并且要能演示出来。

#### 反馈 B：「Raft / Slock 这种大部分时候就差不多了」

- **原话：** raft 或者说 slock 这种其实大部分时候就差不多了。
- **指的是：** Raft（原名 Slock，Botiverse 出品），人和 AI agent 在频道、线程、任务里协作的聊天式工作区。
  agent 通过守护进程跑在用户自己的机器上，支持多台机器。
- **含义（分析）：** 想用 A 上的东西，多数时候不需要看到 A 的画面，给跑在 A 上的 agent 发消息派任务就够了。
  这条质疑的不是 rapp 的实现，而是「远程操作 GUI」这个需求本身。
- **成立的部分（分析）：** 写代码、跑命令、改文件、查日志这类任务，agent 加聊天确实够用，带宽只有文字。
- **没打中的部分（分析）：** 它解决的是 harness 层。瓶颈在人的注意力时，更多 agent 意味着更多需要过目的输出。
  聊天流串行、信息密度低，不适合注意力受限的人做判断。
- **对需求的影响：** rapp 不和 agent 协作平台竞争「派任务」。rapp 的位置是那些必须由人亲眼看、亲手操作的界面。

#### 反馈 C：旁边团队的「完全聊天控制」方案

- **原话（需求方）：** 旁边团队做出了完全聊天控制的，只能用 API 和无头模式。根本解决不了我用 Claude 的问题。
- **形态：** 全部通过聊天控制，只走 API 和无头模式，没有 GUI。
- **为什么不解决问题（分析）：** 无头模式丢掉的正是 GUI 里为人的注意力设计的部分：
  会话列表、可视化的变更、可以直接点的确认。diff、产物、多个会话的状态被压成一条文字流。
- **对需求的影响：** rapp 的目标 app 明确包含 Claude 本身。需求是把那个为人设计的界面原样带到人所在的地方，而不是替换它。

### 3. 替代方案对照

| 方案 | 形态 | 解决的问题 | 和 rapp 需求对不上的地方 | 开源 |
|---|---|---|---|---|
| 网易 UU 远程 | 整桌面远程控制 | 远程办公、游戏串流 | 整桌面、高码率、远端输入法、需账号 | 否（闭源） |
| RustDesk | 整桌面远程控制，可自建中继 | 自主可控的远程桌面 | 整桌面，不针对弱网文字场景，无本地组字 | 是（AGPL-3.0） |
| Sunshine + Moonlight | 低延迟串流 | 游戏串流 | 整桌面、高码率，目标是画质和帧率 | 是（GPL-3.0） |
| Raft（原 Slock） | 人与 agent 的聊天式协作区 | 多 agent 的协作与派发 | 解决 harness，不解决人的注意力；没有 GUI 现场 | 源码可见（FSL），据报道计划开源 |
| 旁边团队的全聊天控制 | 聊天 + API + 无头模式 | 用聊天驱动 agent | 没有 GUI；文字流串行、密度低 | 未知 |
| **rapp** | 单个 app 窗口的远程使用 | 人低成本回到同一个现场做判断 | — | 自用 |

### 4. 由反馈得出的定位表述（分析，待确认）

> 别的方案解决的是 agent 怎么干活，rapp 解决的是人怎么低成本地回到现场做判断。
> rapp 不是 UU 的替代，也不是 Raft 的替代，而是把为人设计的那个界面原样搬到人所在的地方。

现有三个设计点和这个定位的对应关系：

- **单窗口：** 不被整个桌面分散注意力。
- **低带宽（4/8/16 bit）：** 任何网络下都能随手看一眼。
- **本地组字、一次发送：** 回应时不被延迟打断。

### 5. 待验证与待确认

1. **「注意力瓶颈」的具体类型（待需求方确认）。** 是人不在 A 旁边时够不着现场，还是同时开的会话太多、切换不过来？
   前者 rapp 能解决；后者 rapp 帮不上，需要另外的方案。这决定 spec 往哪边收。
2. **降色深是否真的省带宽（待实测）。** H.264/HEVC 在低码率下可能比简单的调色板量化更省。
   rapp 的优势预计只出现在文字和 UI 为主的画面上，并且要靠区域差分加无损压缩实现。
3. **对比实验（建议作为原型的验收方式）。** 同一个 app，把带宽限到约 200 kbps，分别用 UU 最低画质和 rapp 原型，
   比较文字可读性和打字体验。UU 也够用则接受反馈 A；rapp 明显胜出则该演示就是价值说明。
4. **价值范围的边界。** rapp 的三个差异点是需求方自己的痛点，不是大众需求。
   个人自用工具不需要说服所有人，但需要在文档里写明它不打算覆盖的场景（纯终端任务、可委托给 agent 的任务）。
