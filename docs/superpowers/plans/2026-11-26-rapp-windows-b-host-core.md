# rApp Windows — Phase B (Host Core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `rust/host-core`, the OS-independent half of a rApp host worker, and prove on the Mac that it behaves like the Swift host, so that phase D only has to supply Windows system calls.

**Architecture:** `host-core` is a Rust library that owns everything a host worker does except talking to the operating system: the picture protocol, quantising, tile coding, compression, pacing, the session loop, the window/focus/clipboard/transfer/lock rules, the state-rule engine and the worker command line. The operating system is reached only through a small set of traits (`platform.rs`). Correctness comes from three things: fixtures generated by Swift tests from `Sources/RappCore/` and compared in Rust; a line-by-line mapping table for the behaviour that lives only in `Sources/rapp-host/`; and whole-session tests where `host-core` on a fake platform is driven by the real Rust controller code. Everything runs in the Mac gate. Nothing under `Sources/` changes.

**Tech Stack:** Rust (std threads and channels, no async runtime); Swift tests (XCTest, `Tests/RappCoreTests/`) as fixture generators; zlib through the backend chosen by probe C1; `serde`/`serde_json`; `unicode-segmentation`; `zeroize`.

**Spec:** `docs/superpowers/specs/2026-11-26-rapp-windows-design.md` — §5.3 (the three boundaries), §6.1–6.9 (what the host does), §14.1–14.2 (how it is checked), §17.2 row B (scope and done line). Read those sections before starting. Probe results: `docs/superpowers/specs/2026-11-26-rapp-windows-probe-results.md`, section C1.

## Global Constraints

- **Precondition:** probe C1 has a recorded verdict (plan P, Task 2). Tasks 1–2 and 4 do not depend on it and may start before; Task 3 and everything that compresses may not. (The code draft of 2026-11-26 was written before C1 ran and assumes stock zlib through `libz-sys`; C1 confirms or overturns that — see the draft notes.)
- **`Sources/` is never modified** (spec U10). Generators are new files under `Tests/RappCoreTests/HostCoreFixtures/`. If a Swift symbol is not visible to tests, the generator works around it (see Task 2); it does not change the symbol's access level.
- **`rust/host-linux/` is never modified** (spec U9). Its `gate.rs`, `pause.rs`, `pacing.rs`, `wire.rs` may be copied as a starting point; the copy is then made to pass the Swift fixtures. Where the two disagree, Swift wins.
- `host-core` contains no `cfg(windows)`, no `cfg(target_os …)`, no `cfg(unix)`, no `windows`/`windows-sys`/`libc` dependency, no `tokio`. From the outside world it uses only `std` networking, files, threads and time. Task 1 adds a test that enforces this.
- `host-core` uses `rapp_client_core::protocol::VERSION` as the protocol version. It defines no second version constant.
- Work happens on the **Mac**, on a branch in a worktree, merged into the Mac's local `main` per `CLAUDE.md`. `host-core` is shared code: every merge goes through the full Mac gate and is released like any other macOS change, so **macOS, Linux and iOS behaviour must not change** — in particular no existing crate's dependencies or features change (see Task 3 on `flate2`).
- Every task ends with the Mac gate's Rust and Swift parts green: `swift test`, `cargo test --manifest-path rust/Cargo.toml --workspace --no-fail-fast`, `cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets -- -D warnings`. The gate must not get noticeably slower: the whole of `host-core`'s tests plus the session tests stay under 60 s on the Mac.
- Fixed strings are copied from Swift character for character: error texts sent on the wire, session end reasons, paste errors, worker event field names (spec §6.1). Chinese strings stay Chinese.
- Never log or print the unlock password, the token, or typed text. The password is held in a `zeroize::Zeroizing` buffer and never reaches stdout, stderr or a log line.
- Names: a Rust function or field is the Swift name in `snake_case`; a type keeps its Swift name. Exceptions are listed in the task that makes them (`Windows.swift` → `wintable.rs`, to keep it apart from the operating system).
- On the Mac: `grep` is ugrep, use `/usr/bin/grep`; there is no `timeout` command; never read `docs/archives/`; commit by path, never `git add -A`, never `cargo fmt --all`.

## Review Focus

Inputs and conditions the spec implies but does not spell out, most likely first. Each is pinned to a task.

1. **A peer sends garbage**: truncated message, a length of 4 GiB, an unknown type, a known type with a short payload, a host-to-client type sent by a client. Expected: the session ends with the Swift error text, the worker stays up for the next session, no panic, no allocation larger than `maxMessageLength`. → Task 2 (parser), Task 13 (session).
2. **The controller vanishes mid-session** (socket closed during a frame, during a file transfer, while the unlock password is being typed). Expected: held keys and buttons are released, stay-awake ends, the `.rapp-part` file stays for resume, the unlock lock file is freed, and the next `hello` is served. → Tasks 13, 16, 17.
3. **The picture source goes away**: capture returns an error, returns nothing for a long time, the region becomes empty, the app exits, every window closes. Expected: a capture error ends the session with `capture stopped: …`, a gone app with `<name> quit`, closing every window ends nothing; never a hang or a busy loop. → Task 14.
4. **Hostile or awkward file names from the controller**: `..\x`, `a/b`, `CON`, `nul.txt`, `x.` , `x `, 300 characters, an empty name, two files with the same name. Expected: the file lands inside the transfer directory under a legal, unique name; nothing is written outside it. → Task 10.
5. **A controller that stops acknowledging frames or asks for 0 fps.** Expected: memory stays bounded (only the latest frame is kept, the in-flight cap holds), no frame is sent while paused, and frames resume with a diff against the last frame the controller got (`Server.swift:1203`; a full frame only when the mode changed while paused). → Tasks 6, 14.

## Fixture rules (apply to every task)

- **Who writes:** a Swift test class in `Tests/RappCoreTests/HostCoreFixtures/`, calling only code in `Sources/RappCore/`. **Who reads:** a Rust test in `rust/host-core/tests/`. A fixture, its generator, the Rust code it checks and the Rust test land in the same commit.
- **Write or compare:** every generator ends in `HostFixture.check(name, bytes)`. With `RAPP_WRITE_FIXTURES=1` it writes `rust/host-core/tests/fixtures/<name>`; without, it rebuilds the bytes in memory and fails if they differ from the file. So a change in `Sources/RappCore/` turns `swift test` red until fixtures are regenerated, and regenerated fixtures turn `cargo test` red until `host-core` follows. Generators must be deterministic: own seeded generator (as `ScrollScenes` does), no system random, no clock, no dictionary iteration order.
- **Two formats.** *Binary* (`.bin`): a sequence of records `u8 tag, u32 LE length, payload`; the meaning of each tag is documented in the generator's header comment and repeated in the Rust test's header. *Cases* (`.json`): a JSON array of `{"name": …, "in": …, "out": …}`, written with sorted keys and pretty-printed so diffs are readable. Traces (pacing, tracker, state engine) are cases whose `in` is a list of calls with their `now` and whose `out` is the list of results.
- **Comparison is typed and exact.** The Rust test deserialises `in` and `out` into Rust types (`serde`), calls the Rust function, and compares with `==`. It never compares JSON text and never compares `serde_json::Value` for computed results. No float tolerance. Swift `Float` fields are `f32` in Rust, `CGFloat`/`Double`/`TimeInterval` are `f64`; a generator writes a `Float` as `Double(value)` so the round trip is exact. JSON fixtures never contain NaN or infinity; the binary reject fixtures may carry NaN bit patterns, as bytes.
- **Coverage floor:** a generator contains at least every scenario of the existing Swift unit tests for that module (`Tests/RappCoreTests/<Module>Tests.swift`), re-expressed as input → Swift-computed output, plus the extras listed in the task. Reuse the existing helpers (`ScrollScenes`, `RuleCanvas`, `RuleFixtures`).
- **If byte identity turns out impossible for one output**, stop and write down why in `PORTING.md` under “Not byte-exact” (`rust/host-core/PORTING.md`; Task 18 completes the file, the first task that needs it creates it with that one heading), then use the fallback the spec allows (§14.2): Swift's decoder decodes `host-core`'s output to identical pixels. Only the deflate layer and what depends on compressed sizes may need this, and only if C1 says so (Task 3).

## Porting traps (apply to every task)

- Swift `String.count`, `prefix(n)` count **grapheme clusters**. Use `unicode-segmentation` (`graphemes(true)`). `utf16.count` is `encode_utf16().count()`. Every string-length fixture includes a combining mark, a flag emoji and a ZWJ emoji.
- `x.rounded()` is round-half-away-from-zero: `f64::round`. `Int(x)` truncates and traps when out of range; in Rust write the range check Swift relies on, do not lean on `as` saturation silently.
- Swift traps on integer overflow, `&+`/`&*` wrap. Port `&+` as `wrapping_add`; port plain `+` on untrusted input as `checked_add` and return the same error Swift would reach, or prove the bound.
- Swift dictionaries and sets have no order; wherever Swift sorts before iterating, sort the same way; use `BTreeMap` where order reaches an output.
- JSON lines for the service are compared as parsed objects (key order is not part of the contract) but the number kind is: an integer stays an integer.
- `"\(double)"` prints `1.0`, Rust prints `1`. Where a number is interpolated into a string that leaves the process, the fixture covers it.
- No call to the platform's maths library in fixture-covered code (none exists in `Sources/RappCore/` today). If one appears, use the `libm` crate so Mac and Windows agree.

### Task 3: Deflate

**Files:**
- Create: `rust/host-core/src/deflate.rs`, `rust/host-core/tests/deflate.rs`, `Tests/RappCoreTests/HostCoreFixtures/DeflateFixtures.swift`
- Modify: `rust/host-core/Cargo.toml`; `rust/Cargo.lock` changes by itself on the first cargo run (`libz-sys` is already in the lock file through other crates; never edit the lock by hand, never touch its version lines)
- Fixture: `deflate.bin`

Swift side for reference (`Sources/RappCore/Deflate.swift`): system zlib, `deflateInit_` at level 6 (so window bits 15, memory level 8, default strategy, zlib wrapper), `deflate(…, Z_SYNC_FLUSH)` per call, one stream per connection, `compress(_:ifAtMost:)` compresses on a `deflateCopy` of the stream and keeps the copy only if the output fits, `reset()` on a full frame.

**Decision — the backend is linked directly, not through `flate2`.** `flate2` cannot copy a stream, and turning on a `flate2` zlib feature here would switch the whole workspace's `flate2` (the controller's decoder in `rapp-client-core`, `host-linux`) to that backend through Cargo's feature unification — a behaviour and build change on macOS, Linux and iOS this plan is not allowed to make. So `host-core` depends on the C-style zlib interface of C1's winner: `libz-sys` (features `static`, no default features) for stock zlib, `libz-rs-sys` for zlib-rs, `libz-ng-sys` for zlib-ng. `deflate.rs` is the only file with `unsafe`; it holds the `z_stream` in a `Box` (zlib keeps a pointer back to it) and calls `deflateInit_`, `deflate`, `deflateCopy`, `deflateReset`, `deflateEnd`. After adding the dependency, `cargo tree -p rapp-client-core -e features` must show `flate2` with the same features as before; write both outputs in the commit message.

If C1 found **no** identical backend: use the closest one it names, and Step 1's Rust test compares the *inflated* bytes instead, inflating through the same binding (`inflateInit_`, `inflate`) in a test helper — `flate2` stays out of this crate's `Cargo.toml` altogether (Task 1's boundary test). Record it in `PORTING.md` “Not byte-exact”, and note that Task 5's slice boundaries depend on compressed sizes (see there).
