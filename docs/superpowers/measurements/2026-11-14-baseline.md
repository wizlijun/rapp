# Baseline on the current version (v6), before step 1

Taken on commit 082a7d7 (feat/smooth-step1, before any step-1 change; measure-video.py is added by the commit that adds this file), 2026-11-14.
Machine: MacBook Pro, Apple M5, lid closed, external 4K display, UI looks like 1920x1080 at **30 Hz** (so the test clip draws about 30 fps, not 60; capture is 30 fps). A and B run on the same Mac over loopback (A's service, rapp-weaknet, B's hub + rapp-session). One rig at a time, test page window visible and frontmost.
Commands (each writes one table below): `scripts/measure-video.py --profile lan --mode color16 --density original --fps 30 --minutes 5`; `scripts/measure-weak.py --profile lan|s0|n1..n4 --path direct|relay --minutes 5|10`, seed 1.

Caveat for the video table and every latency row (cause localised to the capture layer, see section 1; machine state suspected, not proven): in this session ScreenCaptureKit reports ~30 complete frames per second for the test clip's window, but almost none differ in pixels (a few per second, then nothing for seconds), although the clip app calls draw() ~30 times per second. B receives exactly what A's host sends, and A's host sends only frames that differ, so the scripts are not the cause. Read the sample counts (n) next to each median.

Latency method note: the video table (section 1, re-run in fix round 1) and the 1-minute check of measure-weak.py use first arrivals of each frame. The latency rows of sections 2-8 were taken before that fix and count every arrival (resends of the same frame included), which inflates their median and p95; they have not been re-run.

37 frames were received in 5 minutes and 9022 were drawn by the clip. The earlier 5-minute run (before the script fixes: edges not counted, all arrivals counted) gave 95 distinct frames, gap p99 and stall 40647 ms, latency 67 / 92 ms (n=108); the amount of content reaching B varies from run to run on this machine, which is part of the anomaly. The 1-minute smoke run also gave only 35-49 frames in 24-60 s, so the smoke expectation "about 30 distinct frames per second" was not met today.

Which rows fail §4.2 S1 (a 60 fps target; v6 caps at 30 fps anyway): distinct frames per second, gap p99, longest stall and screen latency median all FAIL (latency p95 98 ms also exceeds 80 ms). Two rows pass only trivially, because almost nothing was sent: bitrate (0.0 / 0.1 Mbps vs <= 20) and crash (0 vs 0). They say nothing about the encoder or the transport under load. The encode row is not measured until step 2. The numbers are kept as measured.

Why (evidence, layer by layer, 20 s probes with the clip running):
- B side (script): rapp-session's `traffic` events equal the frames B decodes (e.g. 9, 1, 0, 0, 3, 1, 0... frames per second, bytes 12286, 585, 0, 0, 2275...), 0 frames with an unreadable mark. So 0.0 Mbps is true: almost nothing was sent.
- A host (`rapp-host serve` run directly, same app, 30 fps, color16): its own `[stats]` line reads `65.1 kbps 3 fps` in the first second, then `0.0 kbps 0 fps` for every following second. The host sends nothing.
- Capture (a standalone ScreenCaptureKit probe with the host's filter, sourceRect, 30 fps, 1288x752): 29-30 `complete` frames per second with a valid screenRect, but only 6-8 of them differ in pixels in the first second and almost none after (e.g. "frames whose pixels differ: 0:8 1:1"). The host's encoder correctly skips identical frames (spec: skipped frames cost nothing).
- Clip app: its marks file shows 30 draw() calls per second, and a Timer instead of the display link gives the same result, so it is not the display link.
- With a screencapture loop running in parallel the changes arrive in more bursts, but still not continuously.
Conclusion: the cause is localised to the capture layer (ScreenCaptureKit delivers frames whose pixels hardly change although the clip draws 30 times per second); the scripts, rapp-session and the host's encoder behave correctly. Why the capture layer sees so few changes is not established. Machine state is suspected (lid closed, external 4K display at 30 Hz, RustDesk running), but no test has isolated any of these. Task 4 saw ~29 fps in earlier sessions on the same machine; re-take this table when the display is in that state.
