# Recovery after an outage: keep-alive and stall detection (Task 16)

Goal: after the network is back, B is usable again in <= 5 s. Numbers are the "network back to usable" row of
`scripts/measure-weak.py` (PageDown probe every 0.5 s after the outage ends, recovery = send time of the credited probe
minus the time the network came back). Same Mac, loopback, one rig at a time, seed 1, 10 min per run. Each run has 3
outages in its reading phase (3 min), so n=3 per run; with so few samples the medians are rough.

Runs: `s0` = profile s0 as is (10 s outage every 60 s from t=30); `o15` = s0 with `--outage 60:15:30` (15 s outage every 60 s from t=30);
each on `--path direct` and `--path relay`. Release binaries rebuilt before each step.

## What happened

- M0: three of four runs pass <= 5 s; s0 relay has one 6.46 s. (The baseline file shows 8.61 s and 7.52 s on the same code, so run-to-run spread is several seconds.)
- M1 (Step 2) does not get every recovery under 5 s: o15 direct 7.53 s, o15 relay 5.92 s, s0 relay 5.88 s. Medians are
  better only for s0 direct; they are worse for the other three. One seed and n=3 cannot separate that from noise, but there is no sign
  that a 1 s keep-alive fixes the backoff problem.
- M3 (Step 3) is much worse: 2.67 to 36 s. The stall detector closes the connection after 4 s of silence, which is
  inside every outage (10 s and 15 s), so the session ends during the outage; the script's reconnect (same policy as the GUI) then fails
  against the dead link and backs off 1, 2, 4, 8, 15 s, so the first attempt after the network is back can be up to 15 s late.
  Before M3 the same session simply survived the outage inside QUIC (30 s idle timeout). It also cost 10-11 auto-reconnects per run
  (M0/M1: 0-4) and in one run 20 duplicated characters (`o15 direct`: missing 0, extra 20).
  The M3 unit test passed (hub emits `closed` with reason `connection stalled` within 6 s of the link going down; the GUI maps it to 网络断了), so the
  mechanism works as specified; what hurts is closing the session during an outage shorter than the reconnect backoff.
- relay path: ran locally (rapp-relay on 127.0.0.1, weaknet between B's hub and the relay). The proxy sits on B's side only,
  so the A to relay leg is never cut; these numbers say nothing about a cut on that leg.

## Final state

Neither M1 nor M3 is kept in code: the target (<= 5 s on every recovery) was not reached by either, and M3 made it clearly worse.
The code is back to keep-alive 10 s and no stall detection. Only `scripts/measure-weak.py` changed (new `--outage EVERY:FOR:OFFSET`, a
per-outage list in the recovery row, stale "no v7 stats yet" note fixed). The M1 + M3 diff is kept out of the repo as
`.superpowers/sdd/2026-11-14-rapp-smooth-streaming-step1/task-16-m1m3.patch`.

Open: recovery <= 5 s is not met (M0 worst 6.46 s in this session, 8.61 s in the baseline). Untried: fix the cause
(quinn's PTO backoff after a long silence) instead of detecting it, for example a lower PTO backoff cap in the transport, or a reconnect
that does not wait out backoff while the outage is still on; both change transport behaviour and need their own measurement.
