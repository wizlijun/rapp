## Q1 Duo 两块屏、两个方向的尺寸

**外屏两个方向都是手机形态（短边 466）；内屏 669×951，两个方向都是 Pad 形态（短边 669）。F3 在模拟器上成立，600 不用改。**

| 屏 | 方向 | 逻辑尺寸 | 短边 | 像素比 | 安全区 [左,上,右,下] | F1 形态 | 来源 |
|---|---|---|---|---|---|---|---|
| 外屏 | 竖 | 466×678 | 466 | 3 | [0,0,84,34] | 手机 | 量的 |
| 外屏 | 横 | 678×466 | 466 | 3 | [0,0,84,34]（见下） | 手机 | 量的 |
| 内屏 | 竖 | 669×951 | 669 | 3 | 没量到 | Pad | 屏幕像素 2007×2853 ÷ 3 |
| 内屏 | 横 | 951×669 | 669 | 3 | 没量到 | Pad | 开内屏时进来过一帧 951×669（Q3） |

- 两块屏的像素尺寸来自 `simctl io` 列出的显示口：外屏 “LCD” 1398×2034，内屏 “LCD-1” 2007×2853。
- 外屏竖持时，状态栏在**右边**，是一条 84 pt 的竖条，不在上面。截图 `probe-data/phone-v1a-1/duo-outer.png` 看得到。所以手机形态的顶栏不能假设安全区在上面，四边都要照 `MediaQuery.padding` 留。
- 外屏横过来以后，安全区还是报 [0,0,84,34]，没有跟着转。这像是模拟器的毛病，要真机确认。
- 转屏：从发命令到新尺寸到达是 215 ms（竖→横）和 184 ms（横→竖），一步到位，中间没有别的尺寸。命令是 `any`（放开方向）时，先到一帧横、378 ms 后又回到竖，因为模拟器的“设备方向”是竖。
- Flutter 只看得到一块屏：`platformDispatcher.displays` 一直只有 `display0 466x678@3`，内屏亮着时也一样。`displayFeatures` 一直是 0 个，没有折痕。

| 和 600 的距离 | 值 |
|---|---|
| 外屏短边 | 466，比 600 小 134 |
| 内屏短边 | 669，比 600 大 69 |
| 能用的常量范围 | 467–669 之间都能让 F3 成立；600 在里面 |

## Q2 开合时窗口大小的变化序列

**模拟器开合不了，没量。待用户实机。**

- 没有 Simulator.app，系统的“合上、展开”没法从命令行发。
- 试过用 `simctl io <id> screenConfig` 把内屏、外屏的电源轮流开关，模拟开合：
  - 第一次让 app 退到后台；
  - 之后几次 SpringBoard 反复崩溃重启，只能 `simctl shutdown` 再 `boot` 救回来。
  所以这条路不能拿来做十次。
- 唯一一次有用的数据（第一轮日志）：打开内屏电源时，app 进了后台，这时到了一帧 951×669（Pad），**232 ms 后**又变回 466×678（手机）。如果这在真机上也会发生，就是一个过渡帧：形态在它上面会跳一次。

| 第一轮，打开内屏电源 | 时间（相对 app 启动） | 内容 |
|---|---|---|
| 生命周期 | +27548 → +27556 ms | `inactive` → `hidden` → `paused` |
| 尺寸 | +28661 ms | 951×669，短边 669，Pad；**这时 app 在后台** |
| 尺寸 | +28893 ms（隔 232 ms） | 466×678，手机 |
| 生命周期 | +89366 → +89625 ms | 重新打开 app 以后才回到 `resumed` |

iPad 拖窗口时的序列可以参考（Q5）：每 16–33 ms 来一帧，连续变；越过 600 的那一刻上边的安全区跟着跳（0 ↔ 32）。

## Q3 开合时的生命周期、进程和组件树

**模拟器上：进程没重启（同一个 pid），组件树只挂了一次（`tree mount n=1`，没有第二次）；但 app 进了后台（`paused`），而且在后台时收到了尺寸变化。真机上合上、展开是不是一直 `resumed`，待用户实机。**

| 项 | 模拟器（第一轮） |
|---|---|
| 进程 | 同一个 pid（14815），没重启 |
| 组件树 | `tree mount n=1`，从头到尾只有一次 |
| 生命周期 | `resumed` → `inactive` → `hidden` → `paused`，一直停在后台，直到重新打开 |
| 后台时收到尺寸 | 收到，两帧（见 Q2） |

这告诉 V1b 一件事，不管真机怎样都该做：app 不在 `resumed` 时来的尺寸不当真。原因有两条：
- 系统在后台给 app 拍快照，会临时把窗口设成另一块屏的大小；
- 那时切形态，回到前台就会先看到错的外壳。

## Q5 iPad 窗口的各档尺寸

**窗口宽 375–594 是手机形态，607 以上是 Pad 形态。最窄的窗口是 375 宽，竖持、横持都能拖进手机形态，也能拖回来。验收第 2 条对得上。**

在 iPad Pro 11-inch（M5）模拟器上，用 UI 测试打开“设置 › 多任务与手势 › 窗口化 App”。然后拖 rapp 窗口的右下角，看系统给出的窗口和 app 自己记下的尺寸。

| 方向 | 拖到的窗口宽 | 高 | F1 形态 |
|---|---|---|---|
| 竖（屏 834×1210） | 834（全屏） | 1210 | Pad |
| 竖 | 777、615 | 1183 | Pad |
| 竖 | 594、575、535、456 | 1183 | 手机 |
| 竖 | 375（最窄，往 320 拖也停在 375） | 1183 | 手机 |
| 横（屏 1210×834） | 1210（全屏） | 834 | Pad |
| 横 | 799、783、607 | 834 | Pad |
| 横 | 588、456、420、399、375 | 834 | 手机 |

- 拖的时候每 16–33 ms 一帧，一路连续变（例如 612 → 594 → 576 → 557），没有跳。
- 越过 600 的那一帧前后，系统把上边的安全区从 0 改成 32，往回拖时从 32 改回 0。比如竖持：612 宽时上边是 0；594 宽先报 0，8 ms 后同一个宽度又报一次，上边变成 32。32 大概是窗口自己的控制按钮（红绿灯）挪进了内容区。这说明 iPadOS 自己也在 600 左右换窄窗的排法，F1 的 600 和系统对得上。
- 窗口被拖矮以后，下边的安全区从 20 变成 10。
- iPad mini（A17 Pro）全屏是 744×1133，像素比 2，Pad。模拟器上转屏请求被忽略，横屏照算是 1133×744，也是 Pad。
- **没测 Split View 和 Slide Over。** iPadOS 27 上，“窗口化 App”关着时 Split View 只能靠手势拉出来，UI 测试做不到。窗口化模式的最窄窗口（375）和以前 Slide Over 的宽度差不多，验收第 2 条的“最窄分屏”可以用它代替。

## 给 V1b 的常量

| 项 | 建议 | 依据 |
|---|---|---|
| 手机形态的判断 | **不改**：短边 < `foldedShortSide`（600） | 外屏 466、内屏 669，iPad 系统自己也在 600 左右换排法（Q1、Q5） |
| 防抖 | **保持计划里的 250 ms**，等真机序列出来再调 | 转屏 184–215 ms 一步到位；拖窗口每 16–33 ms 一帧，250 ms 等的是手停下来；模拟器上那个过渡帧隔了 232 ms |
| 不在前台时 | **不是 `resumed` 就不切**：记下最新尺寸，回到 `resumed` 再判一次（照样走防抖） | Q3：后台时收到过另一块屏的尺寸 |
| widget 测试加的尺寸 | 外屏 466×678、678×466（手机）；内屏 669×951、951×669（Pad） | Q1；安全区用外屏的 [0,0,84,34] 再测一遍，顶栏不能被右边盖住 |
| iPad 窄窗 | 加 375×1183、594×1183（手机），615×1183（Pad） | Q5 |

V1b 计划里的 `FormSwitch` 还没有“不在前台不切”这一条（`docs/superpowers/plans/2026-11-27-rapp-phone-v1b-shell.md` Task 4）。执行时在 Task 4 加上，并加一个测试 `size while paused does not flip`：先 `paused`，再来 951×669，形态不变；回到 `resumed`，尺寸是 466×678，形态还是手机。Task 12 照真机的数字改防抖。

## 对规格的影响

- F3 在模拟器的数字上成立，600 不用改。真机数字回来以后再确认一次。
- 规格没说 app 在后台时来的尺寸怎么办。建议在 §4.1 补一句：“不在前台时不切形态，回前台再按当时的窗口判”。这是给实施者的，不改用户看到的行为。

## 给下一期的话

- 别想在模拟器上测开合：`screenConfig power` 会把 SpringBoard 弄崩。要用真机。
- Duo 模拟器的显示口 UUID 每次开机都变，用 `--display=primary`（外屏）和 `--display=primary-1`（内屏）。开机后 app 在外屏上。
- `bool.fromEnvironment` 只认 `true`，`--dart-define=X=1` 读出来是 false，要用 `String.fromEnvironment`。
- `scripts/build-ios.sh` 不传 `--dart-define`，探查包要自己 `flutter build ipa --export-method development --dart-define=…`。
- iPad 模拟器能用 XCUITest 打开窗口化 App 再拖窗口角（`probe-data/phone-v1a-1/ipadui/`）。xcodegen 生成工程，一个空的宿主 app 加一个 UI 测试 target。

## 真机操作单（给用户，十分钟以内）

真机包已经编好：探查分支的 `gui/build/ios/ipa/rApp.ipa`，带记录器。装上后会**盖掉** Duo 上现在的 rApp，接入设置还在。测完让发版 session 下次装包时装回正式版。

1. 用能传数据的 USB 线把 Duo 直接插到 Mac 上（别经过 hub），解锁。
2. 在 Mac 上运行：
   ```
   /Users/bruce/git/rapp/.worktrees/phone-v1a-1/probe-data/phone-v1a-1/duo-real.sh install
   ```
   app 在 Duo 上打开，底部有一块黑底绿字的列表，右上有黄色的 “probe”。
3. 展开着，等顶栏连上你的设备，开一个会话（终端或画面都行）。竖持停 5 秒，横过来停 5 秒，再竖回来。
4. 合上，在外屏上打开 rApp（如果它没自己出来）。竖持停 5 秒，横过来停 5 秒，再竖回来。
5. 合上、展开，来回十次。每一步停 4 秒左右，大约一分半。中途 app 不在前台了也别管，接着做。
6. 最后停在展开的状态，截一张屏（列表那块要在画面里）。合上再截一张。
7. 在 Mac 上运行：
   ```
   /Users/bruce/git/rapp/.worktrees/phone-v1a-1/probe-data/phone-v1a-1/duo-real.sh fetch
   ```
   日志存到 `probe-data/phone-v1a-1/logs/duo-real.log`。告诉我“做完了”，再把两张截图发我。

日志里只有窗口尺寸、生命周期和连接档位，没有你输入的文字。
