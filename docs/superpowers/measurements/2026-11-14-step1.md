## 6. Diagnosis of the two flip failures (systematic debugging, fix round 1)

Method: no change to any repo file. A throw-away wrapper (outside the repo, `scratchpad/diag.py`) runs `scripts/measure-weak.py` unchanged and additionally logs, with the script's clock, each PageDown send, each frame arrival and each rapp-session `traffic` event (bytes in the last second). Two 3-minute runs, `--profile s0 --path direct` and `--profile n3 --path direct`, seed 1; raw: `.superpowers/sdd/2026-11-14-rapp-smooth-streaming-step1/task18-diag/` (`s0.json`, `n3.json`, `*.md`, `*.log`). The 3-minute runs have only 4 flips each (s0 median 2.87 s, n3 median 12.66 s), so they are evidence for the mechanism, not new acceptance numbers. The byte figures come from 1-second buckets and are approximate.

What the evidence shows:
- A flip carries one full page of the test page. **The stream mode during these flips was not recorded** (host logs were in deleted temp dirs; `measure-weak.py` ignores the `{"event":"weak"}` event), so it is open whether step 1's weak tier (duogray, density <= 1) was already active; the "color16 1x" assumption is unverified. Repeatedly the same per-flip amounts appear in the traffic buckets: about 36 KB (36,460 / 35,792 B), sometimes 47-54 KB (two frames, or a re-sent frame).
- **s0 (200 kbps = 25 KB/s, 150 ms each way, 5% loss).** 36 KB needs at least 36/25 = 1.5 s of pure link time, plus one round trip (0.3 s) for the PageDown to reach A and the first bytes to come back: a floor of about 1.8 s before any loss. Measured: 2.44 s (10 min direct), 2.64 s (relay), and in the diagnostic run the first frame arrived at +1.5 to +3.1 s after the key (several flips with 2 frames, last frame up to +5.4 s). So the 2 s target is within about 0.5 s of the physical floor for a 36 KB full frame; whether a smaller frame is the way to close it depends on what the weak tier did, which was not recorded. Two possibilities. (a) The tier never fired on s0: by the spec numbers the first slice of 8 KB takes about 0.6 s (< the 1 s probe) and a 36 KB flip queues about 1.5 s (< the 3 s rule), so the link never looked weak; then the stream was color16 and the tier calibration (probe and 3 s thresholds) is the likely cause of the miss. (b) The tier fired and the 36 KB figure is already duogray: then duogray flips are about 36 KB, not the 8-17 KB the spec estimates, and that estimate is wrong. Either way this is not shown to be a defect of the slicing code. **The next run must log the weak/mode event** (the `{"event":"weak"}` line and the host's `stream ->` log) next to each flip. The baseline's 7 s was the same bytes over a link that was not being used well; step 1 got to 1.5x the floor.
- **n3 (2 Mbps, 75 ms each way, 30% random loss).** The link time for 36 KB is only about 0.15 s, yet flips take 6.00 s (10 min), 5.00 s (30 min) and 12.66 s (3 min diagnostic; individual flips +3.5, +7.7, +4.2 s). The delay is loss recovery, not bandwidth. Task 17 measured the same effect on a plain bulk stream: on n3 cubic reaches 15.5 kbit/s of the 2 Mbit/s link and BBR 1600 kbit/s (`2026-11-14-cc.md`); cubic treats every random loss as congestion and its window stays collapsed, so a 36 KB frame needs seconds. Task 17 kept cubic because BBR failed its fixed rule on s0 and n2 (0.89x / 0.70x throughput, ping p95 3.96x / 2.25x). This is the best evidence, not proven by a controller swap in this task (that would be a transport change, and Task 17 already ran it); the sample is small and the flip times vary by 2x between runs.
- Verdict: neither is a small, clearly-rooted defect in this branch's code. N3's cause is a known, already measured trade-off in the congestion controller (cubic vs BBR); s0's is the frame size against a 25 KB/s link. **Open items for the controller:** (a) N3: choose a loss-tolerant controller only for lossy links, or accept cubic's N3 result; (b) s0: first find out whether the weak tier fired during flips (see above), then recalibrate the tier or the frame-size estimate, or accept 2.4-2.6 s.
