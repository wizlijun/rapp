  极高的样本，它就会被拉向那个极端值，从而失去"典型值"的意义。中位数只看排序后中间位置的值，在 robust statistics 里它的

  50%，也就是说将近一半的数据被污染之前，它都不会被拉到任意离谱的位置，所以收入、房价、接口延迟、用户停留时长这类常见的
  heavy-tailed 或 skewed distribution 数据，用 median
  更能反映大多数人的真实情况。但也要注意，中位数不具备可加性，没法像平均数那样乘以样本量还原出总量，在样本很小、数据对称

  quickselect 这类线性时间的选择算法。所以实际工作中比较好的做法是同时报告 mean 和
  median：两者接近，说明分布大致对称；两者差得远，就说明可能有 outlier
  或者分布严重偏斜，这时应该以中位数为主要的集中趋势指标，再配合 IQR 等稳健的离散度指标一起描述数据。

## 重排的规则，和各自在哪里出错

入口：`List<ReadBlock> reflow(List<String> rows, {List<bool>? wrapped, required int cols, int? screenFrom, JoinTrace? trace})`。输入是协议给的 SGR 行（滚回在前、屏幕在后），输出是一串块：`prose`（段落）、`heading`、`raw`（原样，带最宽格数）、`tool`（工具调用一行）、`meta`（耗时之类），每块带说话人 `me` / `it` / `unknown`。顺序：解析 → 剪掉屏幕底部的输入框 → 去重 → 分类和接行。

| # | 规则 | 出错的地方 |
|---|---|---|
| 1 | **剪底部**：只在屏幕部分（`screenFrom` 以后）找最后 6 行里的输入提示（`❯`、`›`、`>`）和它上下的横线，连同下面的状态行一起剪掉 | 每家写法不同，CLI 一改版就可能失效；输入框高过 6 行时（用户在打很长的话）CC 的状态行会留下来 |
| 2 | **去重**：连续 6 行以上（至少 4 行非空）和前面一模一样的一段，只留第一次。CC classic 在弹框出现、消失时会把对话的一段再打一遍到滚回里 | 真的重复 6 行以上的输出（比如两次一样的命令结果）会被吞掉；CC 弹框的残片（“Edit file / stats.py”）不完全一样，去不掉，会留一小块 |
| 3 | **去框**：`╭─╮ │ │ ╰─╯` 面板拆成里面的文字，左边的 `│ ` 竖线也去掉，去掉以后按里面的宽度重算 | 面板里再套面板、面板两边不齐时会退成原样 |
| 4 | **丢转圈**：`✻ Pondering…`、`⣯  Generating...`、`… esc to interrupt` 这类一个词加省略号的行丢掉；`✻ Crunched for 27s` 这种耗时行留作 `meta` | 规则按三家现在的字符写；新的转圈字符会被当正文留下（S2 说拿不准的保留，错在安全的一边） |
| 5 | **认原样**：表格（框线字符、`━━  ━━` 隔开的横线、两列以上对齐的空隙）、代码（缩进 + 关键字 / 括号 / 赋值 / 注释的样子）、diff（`diff --git`、`@@`、`+`/`-` 开头而后面像代码）、块字符画都放进 `raw`，不接行，保留缩进 | 汉字和英文混着的一句话恰好以 `xxx(...)：` 结尾时会被当成代码（合成测试里 80 列时 1 处）；Codex 工具结果折到 `│ ` 那一行时整段退成原样；agy 带长命令的工具行（`● Ran (python3 -c "…")`，117 格）是原样；agy 开头的字画横幅是原样 |
| 6 | **认说话人**：第 0 列的回合记号——CC `❯ `=我、`⏺ `=它；Codex `› `=我、`• `=它；agy 粗体 `> `=我，后面没记号的正文=它。记号去掉，直到下一个记号前都算同一个人 | agy 的回答没有自己的记号，它的工具行是 `● Explored`；用户输入里如果第 0 列就以 `• ` 开头会认错（没见到） |
| 7 | **认标题和列表**：粗体且短于 0.6×宽的一行，或 `## ` 开头，是标题；`- * • 1.` 开头（可带光标 `❯ `）是新的一项，每项一块 | 粗体判断跳过了回合记号；Codex 的 `• ` 既是回合记号又是列表点，靠缩进分 |
| 8 | **接硬折行**（下一节）：先看协议的 `wrapped`，再猜 | 见 Q3 |

## Q2 哪些能重排，哪些原样，哪些坏

- **能重排、读得顺**：说明段落（包括中英混排、被折成十来行的长句）、标题、列表、我的提问、工具调用一行、耗时行。
- **原样 + 横滑，能看**：代码（宽 55–60 格，手机横滑一点）、diff、命令输出。
- **原样 + 横滑，难读**：Codex / agy 的 Markdown 表格（115–118 格，一屏只看到两列）。
- **坏的**：
  - 备用屏下滚回为 0，只能读最后一屏，往上滚到顶就没了（CC、Codex 默认）。备用屏的样本里还有固定在上面的横幅和半刷新的帧。
  - CC classic 弹框残片留一小块。
  - 剪底部的规则每家各写一份，CLI 改版就要跟。

## Q3 硬折行和真换行分不分得清

**协议有标记，但用不上。** `screen` / `history` 每行带 `wrapped`（仿真器的 WRAPLINE：字写到最后一格自动折到下一行）。17 份样本、共 1,504 行，`wrapped` 全是 0：三家都自己算好宽度、自己发换行，终端从没自动折过。所以只能猜。

**猜法**：A 行被折过，当且仅当“A 的宽度 + 间隔 + B 行第一个词的宽度 > 折行宽度”——也就是说，如果 B 的第一个词放得进 A 的行尾，CLI 就不会把它折下来，A 是真换行。

- 间隔：A 尾和 B 头都是全角字时为 0，否则为 1。
- 词：按空格切；B 头是汉字时只取第一个字（Codex 在汉字间折）。
- 折行宽度：样本里最宽的正文行，若它 ≥ 0.85×列数；否则用列数（宁可多留换行）。
- 接上时，两边都是全角字不加空格，否则加一个空格。

**错误率**：

| 测法 | 结果 |
|---|---|
| 真实样本 9 份，全部接 / 不接的判断 144 个（接 90，留 54） | 对着 CC、Codex 自己的对话记录核了 81 个：**0 错**。另有 22 个是界面自己生成的行（CC 的表格键值、提问框、改文件框、Codex 退出提示），记录里没有，逐个看都是该留的换行。agy 21 个逐个看，全对 |
| 合成测试：从样本会话的记录里取 CC / Codex 真实回答（15 条，74 行），加规格正文 102 行，按 Ink（只在空格折）和 Codex（汉字间也折）的方式在 120 列、80 列折开，再重排，数原样还原的行 | 段落之间有空行时（三家都这样画）：**4 种组合全部 176/176 还原**，其中被折开的 38 行（120 列）/ 63 行（80 列）全对 |
| 同上，但把段落间的空行全部去掉（最坏情况） | 120 列 168–170/176（95–97%），80 列 158/176（90%）。错的是一句短话恰好放得下下一句的第一个词，被接成一段 |

注意：规则是照这批样本调出来的，真实样本上的 0 错有过拟合的成分；合成测试的文字不全是调规则时见过的，更可信一些。调规则时出过一次错（面板去框后宽度没重算，`Python：` 和 `python3 -m venv` 被接起来），已修。

## Q4 重排要多久

`gui/benchmark/reflow_probe.dart bench`：取 4 份样本拼成 1000 行滚回 + 1 屏 40 行（约 11.6 万字符，排成 203 块），按 120 列排；每轮先热身 20 次，再取 200 次（整段）/ 1000 次（只排屏幕）的中位数。

| 测法 | 整段（1000 + 40 行） | 只排屏幕（40 行） |
|---|---|---|
| `dart run`（JIT），load 21，3 次 | 7.35 / 7.60 / 8.24 ms | 0.367 / 0.368 / 0.370 ms |
| 同上，load 68–141 时 | 14.5–16.4 ms | 0.37–0.85 ms |
| AOT（`dart compile exe`），load 4，3 次 | 7.23 / 7.18 / 7.19 ms | 0.359 / 0.355 / 0.361 ms |

- **手机上估计**：Flutter 的 Release 是 AOT，实测和 JIT 热身后差不多；近两代 iPhone 单核和 M 系列差距在 1–2 倍。估整段 10–20 ms，只排屏幕 1 ms 以内。
- **跟不跟得上流式输出**：跟得上。输出时只有屏幕在变，每次屏幕更新重排 40 行不到 1 ms，按 16 ms 一帧算绰绰有余。整段重排只在打开阅读视图、往上滚拿到新的滚回时做一次；滚回只增不改，也可以只排新来的那段再接上（探查里没写增量）。

## Q5 分不分得清“我”和“它”

**分得清**：三家每一回合都在第 0 列打记号（CC `❯`/`⏺`，Codex `›`/`•`，agy 粗体 `>`），按记号就能标出哪段是我说的、哪段是它说的；所有样本里没有认错的。

## 没验过的

- 真机（iPhone / Duo）上的耗时和读起来的感觉。
- 120 列以外的终端宽度（只在合成测试里试了 80 列）；很窄的终端（比如 Duo 上开的）。
- 长会话：滚回几千行、`MAX_HISTORY` 多片拼接以外的情况。
- 流式输出过程中的半刷新帧（同步更新没结束时取到的屏）；只测了最后的静止画面和几个中途切点。
- Linux、Windows 被控端。
- 其他 CLI 版本、主题、设置（比如 CC 的 `/tui` 别的选项、Codex 的颜色主题、关掉 Markdown 渲染）。
- agy 没对着它自己的对话记录核（它的记录在自己的数据库里，没去读），只逐个看过。
- 规则在同一批样本上调、在同一批样本上测，有过拟合。
- 用户在阅读视图里切“看原样”再切回来的衔接。

## 对规格的影响

规格没改。下面是和规格对不上、或者规格要补的地方：

1. **S1“可以往上滚”的前提不成立**：CC 和 Codex 默认跑在备用屏，协议的 `history` 是空的，阅读视图只拿得到最后一屏 40 行。要往上滚，得让 rapp 起这两家时带上 `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` / `--no-alt-screen`（这会改用户在电脑上看到的样子：CC classic 模式弹框时会把对话重打一遍，整屏不再固定），或者第一版接受“只读当前一屏”。这要用户定。agy 不受影响。
2. **S8 的理由要改**：规格说“从屏幕上分不清哪句是我说的、哪句是它说的”。实测分得清（Q5）。S8 不做左右两边的对话仍可以保留，但理由不对；也可以考虑在一条文字里给“我说的”换个底色。这要用户定。
3. **S2“拿不准的保留”**：和现在的做法一致。表格、代码、diff 不重排，按原样横滑。宽表格（115–118 格）在手机上难读，规格没说怎么办；可接受横滑，或以后把表格拆成“一行一张卡”。
4. **I5“不加协议”**：成立。`wrapped` 标记已经在协议里，只是三家用不上；猜折行不需要新字段。
5. **S2 的“看原样”**：备用屏下“看原样”和阅读视图看到的是同一屏，切换主要用来看表格和颜色。

  - Codex 的 `└ ` 工具结果会被表格规则误认，工具规则要放在表格规则前面。
  - 面板、竖线去掉以后一定要重算行宽，否则会把真换行接上。

- 每加一家 CLI，就要加它的回合记号、底部输入框和转圈的写法；最好每家一张小表，不要散在正则里。
- 增量：滚回只增不改，可以只重排新来的部分，再和上一块接（上一块最后一行可能要和新来的第一行接）。
