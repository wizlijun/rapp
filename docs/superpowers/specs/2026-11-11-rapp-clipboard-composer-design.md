# rapp 剪贴板与编辑器 · 协议 v5

日期：2026-11-11
范围：macOS 的 host、client（`Sources/`）和 hub（`rust/hub`）。relay、service 不改。Windows、Omarchy 上的 host/client 以后再升级（§2.6）。
前置：多窗口 spec（`2026-11-11-rapp-multiwindow-design.md`，协议 v4）。本文只写和 v4 不同的地方。
参照：Claude Code CLI 输入框的粘贴体验（长文字、图片变成 `[Pasted text #1 +N lines]`、`[Image #1]` 这样的块）。

---

## 0. 目标

### 0.1 你说的

- 支持远程鼠标交互，尤其优化"选中文本复制"：B 上拖鼠标选中，点输入框后面的「复制」按钮，文本就到 B。
- A 上右键的复制、复制图像、复制文件等，全部都要传到 B。
- A→B 的大块内容：有 relay 时可经 relay 中转；直连时 A 提供 API 给 B 下载，允许断点续传。方案选"单独下载流"（§1.2），relay 只原样转发，不存内容。
- B 窗口菜单上有剪贴板历史列表，每个窗口连接单独一份。
- A 上复制的东西全部进历史；文字自动写进 B 的系统剪贴板。
- 反向粘贴：B 往 A 贴大量文字、二进制内存对象、图片，在输入框里粘贴，体验参考 Claude Code CLI。点发送时一项一项贴到 A（比如先贴对象，再贴其它），最后人工在 A 上提交。
- 输入框也能加文件上传。输入框成了很重要的交互。

### 0.2 本文的假设（请核对）

- 「复制」按钮就是给 A 发 ⌘C；A 的剪贴板一变，内容经 `clip` 回到 B。
- 历史和断点续传都只在一次会话里有效：会话断了，历史清空，没传完的从头来。
- A 上复制文件夹这一版不支持，历史里记一条"文件夹（不支持）"。
- B→A 发送时，A 的剪贴板临时被占用，全部贴完再恢复成原来的内容。
- 发送后不自动按回车。编辑器空着时回车照旧直接发给 A，所以"再按一次回车"就是在 A 上提交。

### 0.3 用语

| 词 | 意思 |
|---|---|
| 会话流 | 现有的那条连接，跑 hello、frame、windows… |
| 旁路连接 | B 另开的连接，只用来传一件东西（下载一项或上传一项），传完就关 |
| clip | A 上复制了一次，A 记成一条，有编号 |
| 条目 | B 编辑器里按发送拆出来的一段：一段文字或一个块 |
| 块 | 编辑器里代表大文字、图片、数据、文件的一个整体，如 `[贴入文字 #1 +243 行]` |

## 1. 整体结构

### 1.1 两个方向

```
A→B  A 上复制 ─► rapp-host 记成 clip ─► 会话流 clip ─► B 历史（文字自动进 B 剪贴板）
                                         B 点历史里的图片/文件 ─► 旁路连接 fetch ─► B 的 ~/Downloads/rapp/
B→A  B 编辑器 ─► 发送拆成条目 ─► 大条目走旁路连接 put ─► A
                                  会话流 paste(条目) ─► A 写剪贴板、按 ⌘V ─► 会话流 pasted
```

### 1.2 旁路连接

- B 连会话用的那个地址（`rapp://host:port`），再连一次，第一条消息是 `fetch` 或 `put`（§2.1），不是 `hello`。
- 走 hub 时，那个地址是 hub 在本机开的监听口。hub 在会话期间一直接受新连接，每个新连接走一次现有的 `open`，再原样转发（§5）。service 的 `open` 本来就是把流原样接到 worker 的端口，所以 service 不用改。走 relay 时，这条流和会话流一样被原样转发，relay 也不用改。
- 直连 rapp-host（不经 hub，比如 `rapp-host serve --bind 0.0.0.0`）时一样能用。
- rapp-host 同时最多 4 条旁路连接，第 5 条回 `error("busy")`。旁路连接不占会话的位置，所以不会触发会话的 "busy"。
- 旁路连接只能取本会话的 clip、只能往本会话的条目里写，拿不到 A 上的任意文件。token 用会话那个。

### 1.3 断点续传

- 下载：B 先写 `<名字>.rapp-part`。断了就用这个文件现有的字节数作 offset 重新 `fetch`。
- 上传：A 收到的部分留着（文件是 `.rapp-part`，文字、数据在内存）。B 重新 `put` 时，A 回 `transferStart(have)`，B 从 `have` 处接着发。
- 自动重试：旁路连接断了，B 等 1、2、4 秒各重试一次，还不行就停下来报错，用户可以手动再来。
- 只在同一个会话里有效（§0.2）。

## 2. 协议 v5

线上格式不变。`hello` 的版本号从 4 改成 5。下面是新增的消息；v4 的消息都不变。

### 2.1 新消息

| 类型 | 名字 | 方向 | 负载 |
|---|---|---|---|
| 19 | clip | A→B（会话流） | 编号 u32，种类 u8，见 §2.2 |
| 20 | paste | B→A（会话流） | 序号 u32，来源 u8（0 = 文字就在消息里，1 = 已上传的条目），文字：字符串；条目：条目号 u32 |
| 21 | pasted | A→B（会话流） | 序号 u32，错误：字符串（空 = 成功） |
| 22 | fetch | B→A（旁路，第一条） | version u8 = 5，token，clip 编号 u32，文件序号 u16，offset u64 |
| 23 | put | B→A（旁路，第一条） | version u8 = 5，token，条目号 u32，种类 u8，类型名（UTI），文件名，总字节数 u64 |
| 24 | transferStart | A→B（旁路） | fetch：总字节数 u64；put：have u64（A 已有的字节数） |
| 25 | chunk | 双向（旁路） | 数据，每块最多 256 KB |

- 下载：B 发 `fetch` → A 回 `transferStart(总字节数)` → A 从 offset 起一块块发 `chunk` → 发够了 A 关连接。
- 上传：B 发 `put` → A 回 `transferStart(have)` → B 从 have 起发 `chunk` → 收够总字节数，A 回一个空的 `chunk` 表示收齐，再关连接。
- 出错一律回 `error(原因)` 再关连接，比如 `unknown clip`、`file changed`、`busy`、`disk full`。
- `paste` 里的文字最多 60000 字节 UTF-8（字符串是 u16 长度），更长的必须先 `put`。

### 2.2 clip 的种类

| 种类 | 值 | 后面跟着 |
|---|---|---|
| 文字 | 0 | 截断了 u8（0/1），文字：u32 长度 + UTF-8（最多 1 MB） |
| 图片 | 1 | 宽 u16，高 u16，字节数 u64（PNG） |
| 文件 | 2 | 个数 u16（最多 100），每个：文件名（字符串），字节数 u64 |
| 数据 | 3 | 类型名（UTI），字节数 u64 |
| 不支持 | 4 | 说明（字符串），比如"文件夹（不支持）" |

`put` 的种类用同一套值：0 文字、1 图片、2 文件、3 数据。

### 2.3 A 怎么判断 clip 的种类（纯函数）

A 剪贴板上的类型，按这个顺序取第一个符合的：

1. 有文件 URL：都是普通文件 → 文件；里面有文件夹 → 不支持。
2. 有 `public.png` 或 `public.tiff` → 图片（TIFF 转成 PNG）。
3. 有 `public.utf8-plain-text` → 文字（富文本只取纯文字）。
4. 有别的类型、数据不到 64 MB → 数据（取第一个类型）。
5. 都不是 → 不记。

### 2.4 握手

- 会话流和 v4 一样：hello → ready → …。版本不是 5 的 hello 回 `protocol version mismatch` 后断开。
- 旁路连接的第一条必须是 `fetch` 或 `put`，版本、token 不对就回 `error` 后断开。

### 2.5 对坏输入的处理

- `fetch` 的 clip 编号不在历史里（已被挤掉），或文件序号越界：`error("unknown clip")`。
- 要下载的文件在 A 上的大小或修改时间和复制时不一样：`error("file changed")`。
- `paste` 引用的条目还没收齐：回 `pasted(序号, "not uploaded")`。
- 文件名：只取最后一段，去掉 `/`、`:`、开头的 `.`，空了就叫 `file`。重名时加 ` (2)`、` (3)`…

### 2.6 旧端与其它平台

- v4 的 Windows、Omarchy 端要升级到 v5 才能连。不支持剪贴板的 host 也合法：不发 `clip`，`paste` 一律回 `pasted(序号, "not supported")`，旁路连接回 `error("not supported")`。

## 3. host（macOS）

### 3.1 监视剪贴板（A→B）

- 会话期间每 0.3 秒读一次 `NSPasteboard.general.changeCount`。
- 变了，并且这时前台 app 是本会话的 app，才记一条 clip（每个窗口连接只有它自己那个 app 复制的东西）。前台是别的 app 时不记，只更新 changeCount。
- host 自己写剪贴板（§3.3 的粘贴和恢复）造成的变化不记。
- 每个会话最多留 50 条，旧的挤掉。clip 编号从 1 起。
- 数据：
  - 文字放在 clip 消息里。
  - 图片的 PNG、数据放在内存里。
  - 文件只记路径、大小和修改时间，下载时再读。

### 3.2 旁路连接（A 端）

- 在会话的监听口上接受，第一条消息决定是 `fetch` 还是 `put`。
- fetch：从内存或文件的 offset 处读，一块块发出去。
- put：
  - 文字、图片、数据收在内存里，上限 256 MB。
  - 文件写到 A 的 `~/Downloads/rapp/<名字>.rapp-part`，收齐后改名去掉 `.rapp-part`。这个目录不自动清理，因为粘贴到 app 里的文件常常只是引用这个路径。
  - 收到的条目留到会话结束。

### 3.3 粘贴（B→A）

收到 `paste(序号, …)`：

1. 这次发送的第一条：把 A 剪贴板现有的全部内容存起来（所有项、所有类型），总共超过 64 MB 就不存，日志写一行。
2. 按条目种类写 A 的剪贴板：
   - 文字 → 纯文字；
   - 图片 → PNG；
   - 数据 → 它的 UTI；
   - 文件 → 文件 URL。
3. 目标 app 不在前台就先激活，然后查焦点窗口属于目标 app：不属于就回 `pasted(序号, "target not frontmost")`，不按键。
4. 发 ⌘V（keyCode 9，Command），等 150 毫秒，回 `pasted(序号, "")`。
5. 恢复：最后一条贴完 2 秒内没有新的 `paste`，就把第 1 步存的内容写回去。会话结束时也恢复。

条目一条一条来（B 等到 `pasted` 才发下一条），A 不排队。

### 3.4 「复制」按钮

B 发的是普通的 key 消息（⌘C 按下、抬起），A 照 v4 处理。之后剪贴板的变化走 §3.1。

## 4. client（macOS）

### 4.1 编辑器（取代单行输入框）

```
┌──────────────────────────────────────────────────────────────┐
│ 上传 2/3 · app.log 45%                                 取消   │  ← 有传输时才出现
├──────────────────────────────────────────────────────────────┤
│ 帮我看下这个报错 [贴入文字 #1 +243 行] 还有截图 [图片 #1]       │
│ 和日志 [文件 app.log 2.3 MB]                                  │
├──────────────────────────────────────────────────────────────┤
│                                     📎 附件   复制   发送 ⏎   │
└──────────────────────────────────────────────────────────────┘
```

- 多行 `NSTextView`，随内容变高，最多 8 行，再多就滚动。字体、占位文字照现在的输入框。
- 块是一个不可拆的附件（`NSTextAttachment`），画成圆角小标签：
  - `[贴入文字 #n +N 行]`；
  - `[图片 #n 宽×高]`；
  - `[数据 #n 类型 大小]`；
  - `[文件 名字 大小]`。
  
  编号在一个窗口里递增。块可以整块删掉，光标可以停在块的前后。
- ⌘V 粘贴，看 B 剪贴板上有什么（纯函数，§6）：
  - 文件 URL → 每个文件一个文件块（文件夹不收，提示一行）。
  - 图片（PNG、TIFF）→ 图片块。
  - 文字：不到 800 字且不到 10 行 → 直接插成文字；否则 → 贴入文字块。
  - 别的类型 → 数据块。
- 📎 附件：打开选文件面板，可多选，选了就插成文件块。把文件拖进编辑器也一样。
- 按键：
  - 回车：发送。
  - ⇧回车：换行。
  - 输入法正在组字时，回车照输入法的意思处理，不发送。
  - 编辑器空着时：回车、退格、Tab、Esc、方向键直接发给 A（照现在的输入框）。

### 4.2 发送

1. 按顺序拆成条目：连续的文字（去掉首尾空白，空的不要）是一个条目，每个块是一个条目。
2. 不到 60000 字节的文字条目放在 `paste` 里直接发。其余条目先 `put`，一次传一个，传输条显示 `上传 i/n · 名字 百分比`。
3. 按顺序一个个发 `paste`，等到对应的 `pasted` 再发下一个。
4. 全部成功：清空编辑器。不按回车。
5. 中途失败：停下来，已经贴过的条目从编辑器里去掉，剩下的保留，传输条显示错误原因（比如"A 上的目标窗口不在最前"）。再点发送就从剩下的开始；已经上传的部分续传。
6. 「取消」：停止当前的上传或下载，已经收到的部分留着，下次续传。
7. 发送进行中，发送按钮变灰；编辑器可以继续编辑，但只影响下一次发送。

### 4.3 「复制」按钮

发 ⌘C（keyCode 8，Command）的按下和抬起。A 上剪贴板变了以后，clip 回来，文字自动写进 B 的剪贴板（§4.4）。按钮上短暂显示"已复制"，2 秒内没收到 clip 就显示"A 上没有复制到东西"。

### 4.4 收到 clip

- 记进这个窗口连接的历史，最多 20 条（A 留 50 条，B 只显示最近 20 条）。
- 文字：自动写进 B 的系统剪贴板。图片、文件、数据只进历史。

### 4.5 「A 的剪贴板」历史菜单

- 放在应用菜单和流量标签的右键菜单里，是一个子菜单，最新的在最上面：
  - `文字 · 帮我看下这个报…`（前 30 个字）；
  - `图片 1280×720 · 340 KB`；
  - `文件 app.log · 2.3 MB`（多个时写 `3 个文件 · 12 MB`）；
  - `数据 com.adobe.pdf · 80 KB`；
  - `文件夹（不支持）`（灰的）。
- 点一项：
  - 文字直接写进 B 的剪贴板。
  - 图片、数据下载到内存，下载完写进 B 的剪贴板。
  - 文件下载到 B 的 `~/Downloads/rapp/`（`.rapp-part` 续传，重名加序号），下载完把这些文件写进 B 的剪贴板，日志写路径。
  - 传输条显示 `下载 名字 百分比`。B 每个窗口一次只传一件，其余排队。
- 按住 ⌥ 点：把这一项插进编辑器（文字按 §4.1 的规则插，其它变成块）。图片、文件要先下载。

### 4.6 JSON 输出

不加新事件。

## 5. hub（Rust）

- `session.rs`：rapp-client 连上来以后，本机监听口不关。之后每来一个连接，就对同一台主机、同一个 app 走一次 `request(Op::Open{app})`，拿到的流和这个连接原样转发；会话结束时一起关。
- 旁路连接失败不影响会话。
- 每条旁路连接在 service 那边都是一次 `open`：会让 worker 多计一个会话（传完就减回去），也会在 A 的连接管理窗口（`--cm`）里短暂出现一行。这一版接受，不另做区分。
- 不改 relay、service、协议 op。

## 6. 纯函数（RappCore，单元测试）

- v5 新消息的编码、解码（每种 clip 都要）；坏长度、坏种类报错。
- `clipKind(types:)`：§2.3 的顺序。
- `pasteDecision(types:text:)`：§4.1 的 ⌘V 规则（800 字、10 行的边界）。
- `composerItems(...)`：§4.2 第 1 步的拆分（文字和块交错、首尾空白、空段）。
- `safeFileName(_:)`、`uniqueName(_:existing:)`：§2.5。
- `resumeOffset(partSize:total:)`：part 文件比总长还大就从 0 来。
- `historyTitle(_:)`：§4.5 的显示文字。
- `ClipStore`：最多 50 条、挤掉旧的、按编号取、自己写的 changeCount 不记。
- `PasteSession`：存剪贴板、2 秒后恢复的时机（时间作参数传进去）。

- `./scripts/check.sh` 末行 `EXIT=0`；`cargo test`、`cargo clippy` 没有警告。
- hub 测试（用假的 rapp-host）：会话期间第二个连接被转发到新的 `open`；会话结束后监听口关掉。
- host 测试（本机回环，不碰真剪贴板）：
  - fetch 中途断开，用 offset 续传，得到的字节一致；
  - put 中途断开，`have` 正确，续传后字节一致；
  - 第 5 条旁路连接回 busy；
  - 未知 clip 回 error。
- 实机验收：
  - 我自己开 TextEdit，开之前确认它没在运行，新建空白文档，按 PID 定位，用完不保存就关；
  - 本机同时是 A 和 B，所以测试前先存好本机剪贴板，测完恢复；
  - 要看到的：
    - B 编辑器里贴一大段文字（变成块）加一张图，发送后 TextEdit 里依次出现；
    - 在 B 上拖选 TextEdit 里的文字，点「复制」，B 的剪贴板里是那段文字；
    - 历史菜单里有这些条目；
    - 一个文件下载到一半时断开连接，再点一次就从断点续传（看日志里的 offset）。

## 8. 不做的（这一轮）

- relay 上存内容、A 离线后还能下载。
- 文件夹（复制和上传都不做）。
- 跨会话的历史和续传。
- B 的剪贴板一变就自动同步到 A（B→A 只走编辑器）。
- Windows、Omarchy 端的剪贴板。
- GUI（Flutter）里的历史或传输界面。
