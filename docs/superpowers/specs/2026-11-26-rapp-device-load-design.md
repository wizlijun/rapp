# 设备资源与余力（设计）

日期：2026-11-26。状态：用户已确认（2026-11-26），并定下 U4：先搭整体框架，各系统的细节以后慢慢调。

## 1. 为什么做

rapp 把好几台设备连在一起，每台上都跑着终端、claude / codex 这类 agent、远程桌面。现在总览里只能看出一台设备在不在线，看不出它**还扛得住多少**。等发现时，往往已经磁盘写满、内存耗尽，或者过热降频，跑了很久的任务就断了。

用户要的是一个整体能力，分三层：

1. **看得到**：每台设备的 CPU、GPU 负载，温度，工作目录所在磁盘的余量，内存余量。
2. **评估余力**：把这些合成「这台还能扛多少」，好比较各台设备。
3. **边界前预警与调度**：快到边界前就提醒，并给出能马上执行的处理办法。终端里的 agent 也要能读到这些信息，自己挑设备、自己收手。

## 3. 目标、非目标、反目标

**目标**
- 所有跑 rapp 服务的设备（macOS、Linux、Omarchy）都采集 §5 的各项资源。
- 总览设备列显示余力和最紧的一项；点开有明细和 1 小时折线（§7）。
- 警告分「注意」「危险」两级（§6），进「需要你」和提示队列，带建议动作（§8）。
- `rapp load` 命令给人看、给 agent 用（§9）。

**非目标（这次不做）**
- 自动处理（U1 的 B）：自动暂停、迁移、清理、杀进程。
- 在界面里改阈值。阈值是 §6 的一张固定表，代码里只有一处。
- 长期历史、写盘、导出。
- iPad、iPhone 自己那一列：iOS 上没有 rapp 服务，所以「本机」列在 iOS 上不显示余力行。它看其他设备照常能看。
- Windows：目前没有 Windows 版服务。
- 网络带宽、进程数、文件句柄。以后需要再加，§5 的结构要能容纳新项。

**反目标（做成这样就算失败，哪怕功能上能用）**
- **采样本身给机器添负担。** 预算是平均不超过单核 0.5%、常驻内存不超过 5 MB。超了就是失败。
- **需要 `sudo`、额外安装软件或驱动。** 读不到的项直接不显示，不去找绕路的办法。
- **替用户删文件、杀进程。** 建议动作只能是 rapp 自己的东西，比如清理它自己的升级缓存、打开某个终端、在别的设备新建终端。
- **刷屏。** 一个问题只占一行，越线反复抖动时不会来回弹；可以「暂时不提醒」。
- **让旧版本连不上。** 不提升图形协议版本。旧设备不支持就当作没有这项能力，不报错。

## 4. 方案

- **A. 服务端采样，持续推送（选中）。** 每台设备的 rapp 服务自己采样，保留 1 小时，在本机算出趋势和警告级别。
  - 界面经 hub 订阅一条 `watch_load` 流，用法和现在的 `watch_terms` 一样。
  - `rapp load` 经本机服务，向各台设备发一次性请求 `load`，用法和现在的 `rapp hosts` 一样。
  - 规则只在服务里写一份，界面和 CLI 看到的结论一致；没开界面时 CLI 照样有趋势数据。
- **B. 塞进 `list_apps` 回复，由界面定时去问。** 改动最小，但只有界面开着、问到的那一刻才有数据，趋势只能在界面里拼，CLI 拿不到。和 U1 的 C 冲突，不选。
- **C. 借用外部监控工具**（node_exporter、Prometheus 之类）。每台都要另装东西，违反反目标，不选。

## 5. 采集什么

服务每 **5 秒**采样一次，保留最近 **1 小时（720 个点）**。每一项都可能读不到（平台不支持、没有这块硬件）。读不到的项不出现在回复里，界面显示「—」，也不参与余力计算。

| 项 | 取什么 | macOS | Linux / Omarchy |
|---|---|---|---|
| CPU | 总占用 %（两次采样之间的平均）、核数、1 分钟平均负载 | `host_processor_info` / `sysctl` | `/proc/stat`、`/proc/loadavg` |
| GPU | 占用 %（多块卡取最高的那块） | IOKit 注册表里 `IOAccelerator` 的 `PerformanceStatistics`（不需要 sudo） | amdgpu 读 `/sys/class/drm/card*/device/gpu_busy_percent`；有 `nvidia-smi` 时读它的输出（最多 1 秒，超时这次就不要了）；Intel 核显读不到，不显示 |
| 内存 | 总量、可用量、swap 已用；系统给出的压力级别（如果有） | `vm_statistics64` 算可用量，`kern.memorystatus_vm_pressure_level` 读压力级别 | `/proc/meminfo` 的 `MemAvailable`；有 `/proc/pressure/memory` 时也读 |
| 热度 | 四级：正常 / 偏热 / 严重 / 危急；Linux 另带摄氏度 | 系统的热压力等级（`ProcessInfo.thermalState` 或同等的公开接口）。**拿不到摄氏度**：Apple 芯片读温度需要 sudo 或私有接口，这一条按反目标不做 | 所有 `thermal_zone*` 和 `hwmon` 温度取最高。有 trip 点就按 trip 点分级：到 `passive` 算严重，到 `critical` 算危急；没有 trip 点按 80 / 90 / 95 ℃ 分成偏热、严重、危急 |
| 磁盘 | 每块「工作盘」的总量、可用量、可用 inode | `statvfs` | `statvfs`（inode 用尽在 ext4 上是真实的边界） |
| 电源 | 有电池时：电量 %、是否接着电源 | IOKit `IOPSCopyPowerSourcesInfo` | `/sys/class/power_supply/*` |

**工作盘**：下面这些路径所在的盘，同一块盘（同一个 `st_dev`）只算一次，每块盘记下它覆盖了哪些路径：
- 本机每个 rapp 文本终端前台程序的当前目录（rapp-term 已经读到了，见 `rust/term/src/pty/fg.rs`，只是还没交给服务）；
- rapp 数据目录（`State.home`）；
- 升级缓存目录；
- 用户主目录。

`statvfs` 在网络盘上可能卡住，所以每块盘单独读，2 秒超时。超时的盘这次显示「读不到」，不会拖住其他项。

**进程排行**：只在有人问的时候才取（明细被展开、或 CLI 带了 `--top`），不在常规采样里。取 CPU、内存各前 5 名；如果某个进程属于某个 rapp 文本终端，就标出是哪个终端。

## 6. 警告规则

级别只有三种：正常、**注意**（橙）、**危险**（红）。

| 项 | 注意 | 危险 |
|---|---|---|
| 磁盘可用 | 剩 < 10% **且** < 20 GB | 剩 < 5% **且** < 5 GB；或不论盘多大，剩 < 1 GB |
| 磁盘趋势 | 按最近 10 分钟的写入速度，预计 ≤ 60 分钟写满 | 预计 ≤ 15 分钟写满 |
| inode | 剩 < 10% | 剩 < 5% |
| 内存 | 可用 < 10%；或 macOS 压力级别为 warn | 可用 < 5%；或 macOS 压力级别为 critical |
| 内存趋势 | 最近 10 分钟可用量一直在降，预计 ≤ 30 分钟降到 5% | — |
| 热度 | 偏热持续 ≥ 5 分钟 | 严重或危急（这时系统已在降频） |
| CPU | 占用 ≥ 90% 持续 5 分钟 | — |
| GPU | 占用 ≥ 90% 持续 5 分钟 | — |
| 电池 | 没接电源且 ≤ 20% | 没接电源且 ≤ 10% |

- **趋势预测**：用最近 10 分钟的采样做线性拟合。只有在持续增长时才算：斜率为正，并且 10 分钟内至少用掉 1 GB 或 1%。避免下载一个大文件就算出「5 小时后满」。
- **防抖**：升级立刻生效；降级要连续 1 分钟都回到线内才算。
- **磁盘阈值为什么用「且」**：开发机的盘常年只剩 10% 左右。用「或」的话，2 TB 的盘剩 200 GB 也会一直亮橙，「需要你」里永远挂着一行，违反「不刷屏」。用「且」：大盘按绝对量（20 GB）判断，小盘按比例（10%）判断。突然被快速写满的情况交给趋势那一行去抓。
- **磁盘**：每块盘分开判断。警告里写明是哪块盘、覆盖了哪些路径。
- 这张表在服务代码里只有一份，CLI 和界面都只显示服务算出的结论，各自不重算。

## 7. 余力与界面

**余力（0–100）** 是一个木桶分：每项先换算成 0–1 的「剩余份额」，再取最小值乘 100。

| 项 | 怎么换算 |
|---|---|
| CPU | 1 − 最近 1 分钟平均占用 |
| GPU | 1 − 最近 1 分钟平均占用 |
| 内存 | 可用 ÷ 总量 |
| 磁盘 | 所有工作盘里最紧那块的「可用 ÷ 20%」，封顶 1。也就是剩 20% 以上就算满分 |
| 热度 | 正常 1、偏热 0.6、严重 0.3、危急 0 |
| 电池 | 接着电源算 1；否则电量 ÷ 50%，封顶 1 |

取到最小值的那一项就是「最紧的一项」。余力用来比较设备、排推荐。**颜色不看余力，看 §6 的警告级别。** 这样 CPU 一时跑满只会让余力变低，不会变红。

**设备列**（`gui/lib/ui/overview.dart` 的 `_Column`）：在状态行下面加一行。

```
┌ MacBook-M4-Pro ─────────┐
│  ⌘ ● 在线 · 局域网       │
│  余力 ▓▓▓▓▓▓░░░░  磁盘 剩 6% │   ← 最紧的一项；注意=橙，危险=红，正常=次要文字色
│  …终端、应用…            │
└─────────────────────────┘
```

- 正常时右侧文字也写最紧的那一项，如「CPU 42%」，只是用次要颜色。
- 设备离线、版本太旧不支持、或者还没收到第一份数据时，这一行不显示。不显示陈旧的数字。
- 「本机」列：macOS 和 Linux 上经本机服务的 IPC 取数据（`ServiceMonitor` 那条连接）；iOS 上不显示（见非目标）。

**明细**：点这一行展开（在列内展开，或弹出浮层，由构建者决定），每项一行，后面带 1 小时折线。

```
CPU   42%  （8 核，负载 3.1）          ╱╲__╱‾
GPU   18%                              __╱‾╲_
内存  剩 9.1 / 36 GB · swap 1.2 GB     ‾‾‾╲__
热度  正常                             ──────
磁盘  /  剩 38 GB (6%) · 约 40 分钟后写满  ← 橙
        覆盖：~/git/rapp（终端 2 个）、数据目录、主目录
      /Volumes/Data  剩 1.2 TB (61%)
        覆盖：/Volumes/Data/models（终端 1 个）
电池  78% · 接着电源
占用最多的进程（展开时才取）：
  cargo  CPU 380%  ← 终端「rapp · 2」
  …
```

- 折线用当前主题的次要颜色。超过阈值的线段用警告色。
- 进程属于某个 rapp 终端时，点它就跳到那个终端。

## 8. 警告与建议动作（U1 的 A）

**需要你**：新增一类 `NeedKind.resource`。每台设备的每个越线项占一行，例如：
- 「MacBook-M4-Pro 磁盘约 40 分钟后写满（/，剩 6%，含 ~/git/rapp）」
- 「omarchy-box 过热，系统正在降频」

一项从正常变成注意或危险、或者从注意升到危险时，也往提示队列（`hint`）记一条。

**建议动作**：只做 rapp 自己能安全执行的事，按项给：

| 项 | 动作 |
|---|---|
| 磁盘 | 「看在这块盘上的终端」：列出当前目录在这块盘上的 rapp 终端，点了跳过去。（不做「清理升级缓存」：升级装好、运行稳定后服务已经会自动删掉缓存（`update.rs` 的 `remove_when_healthy`），剩下的多半是待装版本，删了反而影响升级。） |
| 内存 / CPU / GPU / 热度 | ①「看占用最多的进程」：展开明细里的进程排行。②「到 <余力最高的设备> 上新建终端」：和现有「新建」走同一条路（`open_term`，不带 `from`），在那台设备的默认目录（主目录）打开。等「新建用上次的终端目录」（term-restore 规格）做完，这里会自动用上，本功能不依赖它。 |
| 电池 | 没有动作，只提醒。 |
| 所有项 | 「1 小时内不再提醒」：只针对这台设备的这一项。已经在「注意」时又升到「危险」，照样提醒。这个设置**记在各自的界面里**（GUI 偏好，按「设备 id + 项」记，重启后仍有效），不回写到被观察的设备，所以协议仍然只读。每台界面各自设置，iPhone 上点了不影响 Mac 上的提醒。 |

不提供「结束进程」「删除文件」这类动作（反目标）。要结束 rapp 终端，用现有的「结束终端」。

## 9. 给 agent 用的命令（U1 的 C）

```
rapp load [设备…] [--top] [--json]   各设备的余力、各项数值、警告；不写设备名就列出全部，含本机
rapp load pick [--json]              推荐一台设备，并说明原因
```

- `rapp load`：每台设备一行，列出：设备、余力、CPU、GPU、内存剩余、热度、最紧的盘，以及警告（中文，例如「磁盘约 40 分钟后写满」）。不在线的设备写「不在线」；版本太旧的写「版本太旧，不支持」。
- `rapp load pick`：在线、有终端能力、并且没有「危险」的设备里，选余力最高的。余力相同时选 CPU 更空的那台。本机也参加比较。`--json` 输出 `{id, name, headroom, tightest, reason}`。
- **退出码**：`0` 正常；`3` 本机服务连不上（和现有命令一致）；`4` 用于 `pick`，表示没有一台合适。
- `--json` 的字段名稳定，写进本规格的附录（构建时补上），agent 可以放心按字段解析。
- 让 agent 知道有这个命令：写进 `rapp` 的用法说明和 README 的「给 agent 的说明」一节。不往 agent 的对话里自动注入任何东西。

## 10. 协议

都是服务之间的 JSON 请求，**不改图形协议版本**。

- `load`：一次性请求。回复 `{ok, at, headroom, tightest, items: {...}, disks: [...], warnings: [...]}`。带 `"history": true` 时附上 1 小时的采样；带 `"top": true` 时附上进程排行。
- `watch_load`：流式请求。先回一份带历史的完整快照，之后每 5 秒推一行当前值和警告。hub 对每台在线设备开一条，开流、断线重试、旧设备的「不支持」处理，都和 `rust/hub/src/terms.rs` 的 `watch_terms` 一样。hub 把每行转成发给界面的 `load` 事件。
- 旧设备不认识这两个请求，会回错误。hub 把这台记为「不支持」，10 分钟后再问一次，和 `Watch::Unsupported` 的做法一样。
- 权限：能 `list_apps` 的连接就能 `load`。安全只靠中继这一道门，这里不另设门槛。
- 本机 IPC 也提供 `load` 和 `watch_load`，供本机列和 CLI 用。
- testkit 里比对整个 JSON 的那些断言要同步更新（`rust/testkit/tests/`）。

## 11. 测试要点

- 采样器能换成假的：规则测试直接喂合成的序列，覆盖 §6 每一行，包括防抖、趋势的最低门槛、读不到的项。
- 余力计算：最小值的取法、读不到的项不参与、最紧项的选取。
- 不同平台的采集只测「能解析系统给的格式」：喂固定样本，比如一段 `/proc/meminfo`、一个 thermal_zone 目录树。
- 预算：测试里跑 1 小时的模拟采样，内存占用不增长；真机检查时看服务的 CPU 占用。
- 界面：余力行三种颜色；离线、不支持、无数据时隐藏；明细展开；需要你行和动作；「1 小时内不再提醒」。
- CLI：表格输出、`--json` 字段、`pick` 的选择和退出码 4。

## 12. 留给构建者的

- 具体用哪个 crate 还是自己写系统调用（`sysinfo` 之类可以用，但它不读 GPU，Apple 芯片上的读法也要核对）。
- 明细是在列内展开还是弹出浮层；折线的具体画法。
- `nvidia-smi` 的调用方式和缓存。
- 计划怎么分阶段。按 U4，第一份计划先打通整条链路，每个系统的采集器先做「第一版」：
  - macOS：CPU、内存（含压力级别）、热压力、磁盘；
  - Linux：CPU、内存、磁盘、`thermal_zone` 最高温度（先按 80/90/95 ℃ 分级）。
  - GPU、电池、hwmon / trip 点、`nvidia-smi`、进程排行，在第一份计划里只留好位置（数据结构和界面能显示，采集器暂时返回「读不到」），之后各开小计划补。

## 13. 我替用户做的决定（请确认）

1. Mac 显示热压力四级，不显示摄氏度（拿不到）；Linux 两样都显示。
2. 增加了**电池**和 **inode**：都属于「包括但不限于」，而且都是真实的边界。
3. 阈值用 §6 的固定表，界面里不能改。
4. 余力用木桶分（取最小值）；颜色只看警告级别，不看余力。
5. 采样间隔 5 秒；进程排行只在有人问时才取。
6. 「工作路径」取：终端当前目录、数据目录、升级缓存、主目录。
7. 离线设备不显示旧数据。
8. 「1 小时内不再提醒」只针对单台设备的单一项，再升级照样提醒；记在各自的界面里，各台界面互不影响。
9. 磁盘阈值用「且」：剩 <10% 且 <20 GB 算注意，剩 <5% 且 <5 GB 算危险，剩 <1 GB 一律危险。
10. 不做「清理升级缓存」这个动作（服务已经会自动清理）。
11. 「到别的设备新建终端」先在那台设备的主目录打开，不等 term-restore。
