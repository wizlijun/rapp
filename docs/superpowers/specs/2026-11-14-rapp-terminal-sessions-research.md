# rapp 终端会话：调研与方案选项

日期：2026-11-14。状态：**讨论中，方案未定**。本文只记录调研结果和可选方案，不改任何已定决策；用户选定方案后另写设计规格。
标「原话」的是用户的话；标「我的分析」「我的建议」的是整理时的判断；标「未实测」的只查了文档或源码，没有跑过。

相关文档：主界面规格（`2026-11-12-rapp-main-window-design.md`）、需求反馈（`2026-11-12-rapp-requirements-feedback.md`）、流畅串流设计（`2026-11-14-rapp-smooth-streaming-design.md`）、设计语言（`2026-11-12-rapp-design-language.md`）。

## 1. 用户提出的要求（2026-11-14，原话）

> 对于没有桌面的远程服务器，跑 tmux 这种终端让任务一直在后台工作，这种工具也应该被 rapp 管理起来。我巡检。
> 持续后台监控的常见 terminal 的体验可能变得很重要了。
> windows 和 mac 下的 tty，协议，就用 lixungeng 的方法（https://github.com/swigger/hurryvc）来做。但 linux 的 tmux 这类工具，应该怎么做最好，还需要去研究。
> 这样所有管理 agent 工作的容器都会在我们的掌控下，我们可以随时在上面看到工作状态，和即时打断介入。
> 反倒是 agent 内部子任务自己跑的，我们介入不了，那么就介入他们的主 cli 或 app 就可以做到了吧。

归纳成三件事（我的归纳）：

1. **范围扩大**：rapp 管的不只是 GUI app 的窗口，还有跑 Agent 的终端会话，包括没有桌面的 Linux 服务器。
2. **两个动作**：巡检（随时看到工作状态）和介入（即时打断、回一句）。
3. **已定和待定**：Windows、macOS 用 hurryvc 的方法（已定）；Linux 上 tmux 这类工具怎么接（待研究，本文回答）。

## 3. hurryvc 是怎么做的（读了源码，版本 b54749d）

仓库很小：Rust 约 3900 行，C++ 约 400 行，Vue 前端一个。结构是三个角色。

| 角色 | 做什么 |
|---|---|
| 生产端 `hurryvc run -- <命令>` | 开一个伪终端，把命令跑在里面。Unix 上用 `portable-pty`；Windows 上用**随程序带的新版 ConPTY**（`conptylib` 加 `OpenConsole.exe`），不用系统自带的 |
| 服务端 `hurryvc server` | WebSocket 中转：收生产端的画面，发给网页；收网页的输入，发给生产端 |
| 消费端 | 网页，显示画面，发文字和几个控制键 |

**关键做法：传的不是字节流，而是“屏幕状态”。**

- 生产端把伪终端的输出喂给一个内嵌的终端仿真器（`alacritty_terminal`），得到一张字符网格。
- 第一次发整屏快照（`TermSnapshot`）：行数、列数、光标位置，每一行是若干段“文字 + 前景色 + 背景色 + 粗体等”。
- 之后每次只发变了的行（`TermDelta`）。
- 滚出屏幕的内容另走一条“历史”通道，纯文字，最多 1000 行。
- 输入：一段文字，或一个预定义的键（回车、Tab、退格、Esc、方向键、Ctrl-C、Ctrl-D）。
- 本地优先：生产端同时把输出原样写到自己所在的终端，本地键盘照常能用。远程只是第二个观众。
- 只有有人在看时才发画面（`StartData` / `StopData`）。

**对 rapp 来说要改的地方（我的分析）**

| hurryvc 现状 | rapp 需要 |
|---|---|
| 内容以明文 JSON 经过服务端，服务端能看到全部 | 已定：relay 不能看到任何内容。终端数据要走 rapp 自己的设备间加密隧道，不要 hurryvc 的服务端 |
| 每来一块输出就算一次快照并发送，没有限速 | 弱网下要合并、限速，只发最新状态（和流畅串流设计里“延迟不随时间增长”同一个要求） |
| 输入只有文字和 10 来个键 | 要能发任意按键，以及把底部编辑器里的整段文字作为“粘贴”发过去 |
| 历史只有纯文字 1000 行 | 够巡检用；归档和回放要另外设计 |
| 被跑的命令是 `hurryvc run` 的子进程，`hurryvc run` 退出它也结束 | 桌面机上可以接受（人就在旁边）。无人值守的机器上，持有伪终端的进程必须独立于 rapp 的服务，否则升级或重启 rapp 会杀掉正在干活的 Agent |
| 远程改尺寸会直接改伪终端的尺寸 | 本地终端的尺寸不会跟着变，本地显示可能错位（我从代码推断，未实测） |

**许可证**：仓库里没有 LICENSE 文件。rapp 整体以 GPL-3.0 发布，**不能直接搬它的代码**，除非作者给出许可。它用到的两个库可以直接用：`alacritty_terminal`（Apache-2.0）、`portable-pty`（MIT，来自 WezTerm）——这两个许可证是我记得的，用之前要核对。“用它的方法”没有问题；要不要请作者加一个许可证，由用户定。

## 4. tmux 自己提供了什么

tmux 有一个**控制模式**（`tmux -C` / `-CC`），是给程序用的文字协议，iTerm2 的 tmux 集成用的就是它。

| 能力 | 怎么做 | 来源 |
|---|---|---|
| 接到已有的 tmux 上 | `tmux -C attach -t <会话>`，标准输入发 tmux 命令，标准输出收回复和通知 | tmux wiki |
| 知道哪个面板有新输出 | `%output %<面板> <内容>` 通知（内容里的控制字符用八进制转义） | tmux wiki |
| 知道会话、窗口、面板的增减改名 | `%window-add`、`%window-close`、`%session-changed`、`%layout-change` 等通知 | tmux wiki |
| 不影响别人的窗口尺寸 | 控制模式的客户端不调用 `refresh-client -C` 时，不影响其他客户端的尺寸 | tmux wiki |
| 流量控制 | `pause-after` 标志：客户端落后太多时 tmux 暂停该面板的输出，客户端之后用 `capture-pane` 补齐。不设这个标志，落后 300 秒会被断开 | tmux wiki、手册 |
| 订阅某个值的变化 | `refresh-client -B`（tmux 3.2 起） | tmux wiki |
| 读一个面板当前的整屏 | `capture-pane -e -p -t %N`（带颜色转义）；光标位置、是否在备用屏幕等用格式变量查 | tmux 手册（未实测） |
| 发按键 | `send-keys -l`（原样文字）、`send-keys -H`（十六进制） | tmux wiki |
| 发一段粘贴 | `set-buffer` 加 `paste-buffer -p`（程序开了括号粘贴模式时带上粘贴标记） | tmux 手册（未实测） |

要点：**tmux 自己就是一个终端仿真器，而且一直在后台持有着每个面板的屏幕状态。** 所以在 Linux 上不需要像 hurryvc 那样再开一个伪终端、再跑一个仿真器，直接问 tmux 要屏幕就行。

## 5. 别人怎么做（2026-11-14 检索）

| 谁 | 做法 | 对我们的意义 |
|---|---|---|
| cmux 的“远程 tmux 镜像” | 经 SSH 跑 `tmux -CC attach`，自己实现控制模式客户端；`%output` 流进本地的终端面；输入用 `send-keys`；粘贴用 `paste-buffer -p`；要求 tmux 3.2 以上 | 证明“控制模式接已有 tmux”这条路走得通。它列出的限制：SSH 断了要重连重填；多行粘贴在它那里退化成逐键发送 |
| pmux-agent | 用 `pipe-pane` 取输出给网页里的 xterm.js | 它的文档写明一个坑：`pipe-pane` 只能拿到开始之后的输出，之前设置的模式（备用屏幕、隐藏光标）会丢，要另外补状态。这是“传字节流”方案的通病 |
| Herdr | 给终端会话加“阻塞、工作中、完成、空闲”四种状态；Claude Code、Codex 靠**读屏幕底部内容加规则**判断 | 证明不装 hook 也能判断状态。它自己也说这是信号，不是保证 |
| Agent of Empires、amux 等 | 每个 Agent 一个 tmux 会话，加一个终端或网页面板 | tmux 已经是这类工具事实上的容器。它们各管各的；rapp 的位置在它们下面一层：任何终端会话都收 |
| Zellij | 自带网页服务，浏览器或另一个终端可以远程接入会话 | 用 Zellij 的人可以以后单独适配；不能要求用户为了 rapp 换成 Zellij |
| Claude Code 的 issue | 有人请求官方提供“会话状态”的接口，理由是现在从外面没有可靠办法判断空闲、工作、等输入 | 屏幕规则是眼下唯一不装 hook 的办法，要按“会变”来设计（规则放配置里，可更新） |

## 6. 方案选项

**A. 屏幕状态同步，两种容器后端（我的建议）**

对主控台只有一种“终端会话”，传的是字符网格的快照和行增量（hurryvc 的传法）。被控端按平台用两种后端取得网格：

- **tmux 后端**（Linux、macOS，有 tmux 的地方）：控制模式接到已有的 tmux，网格直接向 tmux 要。已经在跑的会话不用重启、不用改启动方式。
- **自带后端**（Windows 必用；macOS、Linux 没有 tmux 时用）：`rapp run -- <命令>`，hurryvc 的方法（伪终端加内嵌仿真器）。

**B. 字节流终端**

主控台里嵌一个完整的终端仿真器，被控端把原始字节流（SSH，或控制模式的 `%output`）原样传过来。

- 好处：保真度最高（鼠标、任意按键、任何全屏程序），是终端软件的标准做法。
- 问题：每个字节都要按顺序送到，弱网下延迟会越积越多；断线重连后要补状态（§5 pmux-agent 的坑）；三个平台的主控台都要一个靠得住的仿真器；被控端拿不到“屏幕上现在是什么字”，状态判断和文字快照要另外做一遍。

**C. 继续走像素**

在被控端开一个终端软件的窗口，用现有的 rapp 串流。

- 好处：不用新协议，今天在有桌面的 Mac 上就能用。
- 问题：没有桌面的服务器做不了，而这正是这次要求的起点；传文字用像素最浪费；拿不到文字。

**D. 换用自带远程能力的工具（Zellij 网页端、ttyd 等）**

- 问题：要用户换工具或另开网页服务，不经过 relay，和“一个接入点一把钥匙”不一致。只作为参照。

**为什么建议 A（我的分析）**

1. 和 rapp 串流的取向一致：只送最新状态，画面不变不发数据，延迟不累积。地铁、高铁上“至少能打字和阅读”，文字网格比像素容易得多。
2. 被控端手里有文字，巡检的状态判断、“等你”信号、文字快照都从同一份数据来。
3. Windows、macOS 的做法用户已定为 hurryvc，它传的就是屏幕状态；Linux 用同一种传法，主控台只需要一种显示。
4. Linux 上不重复造 tmux：会话的存活交给 tmux，rapp 的服务重启、升级都不影响正在跑的 Agent；rapp 坏了，SSH 加 `tmux attach` 仍然能用。

A 的代价：保真度不如 B（鼠标操作、少数全屏程序的细节）；tmux 后端依赖 tmux 3.2 以上。

## 7. 方案 A 的结构（草图，选定后再细化）

```
主控台（Flutter）                                    被控设备（含无桌面的 Linux）
┌─────────────────────┐    rapp 隧道（设备间加密，可经 relay）   ┌──────────────────────────────┐
│ 终端舞台：原生画字符网格 │ ◄── 快照 / 行增量 / 历史 ───────── │ 终端服务（rapp 的被控端里）      │
│ 底部编辑器、按键排、打断 │ ─── 文字块 / 按键 / 打断 ────────► │  ├ tmux 后端：控制模式连接 ──────┼─► 已有的 tmux
│ 状态灯、需要你、全景     │ ◄── 会话列表 / 状态 ────────────── │  └ 自带后端：rapp run（伪终端）──┼─► claude / codex / shell
└─────────────────────┘                                    └──────────────────────────────┘
```

### 7.1 tmux 后端

- **发现**：列出本机用户的 tmux 会话、窗口、面板；用控制模式的通知跟踪增减。
- **取画面**：`%output` 只当作“这个面板脏了”的信号，合并限速后用 `capture-pane -e` 取整屏、查光标，和上一次比，发变了的行。没人看的会话降到很低的频率（只为状态判断）。
  备选做法是把 `%output` 的字节喂给自己的仿真器（cmux 的做法）。先用前一种，因为随时可以重取、不会和 tmux 的状态走岔；两种都在探查里试一下（§9）。
- **输入**：单个按键用 `send-keys`；底部编辑器里的一整段用粘贴方式发（`paste-buffer -p`）；打断是发 Esc 或 Ctrl-C。
- **尺寸**：默认不改。rapp 接上去看，不影响别处（比如 SSH）接着的那个终端的尺寸，主控台按原尺寸缩放显示。要按主控台的屏幕重排，是一个明确的动作。
- **新开会话**：机器上有 tmux 时，从 rapp 新开的终端会话就开成 tmux 会话（我的建议）。

### 7.2 自带后端（Windows、macOS，以及没有 tmux 的 Linux）

- hurryvc 的方法：伪终端（Windows 上带新版 ConPTY）加 `alacritty_terminal`，输出同一种快照和增量。
- 相对 hurryvc 要改的四点见 §3 的表：走 rapp 隧道、合并限速、任意按键和粘贴、持有伪终端的进程独立于 rapp 的服务。
- 用法是 `rapp run -- claude`。本地照常显示和操作，远程是第二个观众。

### 7.3 主控台一侧

- 终端舞台不解码视频，直接用等宽字体画网格。文字始终是清楚的。
- 输入沿用主界面规格 §3.5 的输入区：本机输入法写完整段发送；“按键”一排在终端里是主要操作（Esc、Tab、方向键、回车、Ctrl-C）。
- 流量：一屏文字的快照是几 KB 的量级，增量更小（我的估计，未实测）。

### 7.4 巡检：状态从哪来

三层信号，从便宜到贵，都不需要 hook：

| 层 | 信号 | 用来判断 |
|---|---|---|
| 容器事实 | 进程还在不在、退出码、当前在跑的命令、最后一次输出的时间、响铃 | 活动、空闲、已退出 |
| 安静时长 | 输出停了多久 | 可能在等人 |
| 按 app 的屏幕规则 | 屏幕底部几行匹配某个 CLI 的“等确认”“等输入”样子。规则放在已定的“每个 app 的默认配置”里 | 等你 |

第三层是信号，不是保证（§5 Herdr、Claude Code issue）。各家 CLI 的界面会变，规则要能单独更新。
按设计语言 §0 的三条检查：这些状态平时只改灯；能自己进入“需要你”的只有“等你”和“已退出且退出码非 0”（后一条是我的建议，待定）。

### 7.5 对主界面对象模型的影响

- 新增一种会话：**终端会话**，键是（设备, 容器, 会话名），一台设备可以有很多个。tmux 的窗口对应现有的“窗口标签”。
- 设备可以是“只有终端”的（无桌面的服务器）：设备面板里没有 app 列表，只有终端会话列表和“新开”。
- 全景模式里终端会话的缩略图可以是最后几行文字，几乎不花流量。主界面规格 §8 第 4 条因为流量而不做的实时缩略图，对终端会话可以做。

## 8. “介入主 CLI 或 app 就够了吗”

用户的判断：Agent 内部自己跑的子任务介入不了，介入它们的主 CLI 或 app 就可以。

基本成立（我的分析）：子 Agent 是主 CLI 进程里派出去的，状态由主 CLI 的界面显示，打断主 CLI 也就停了它们。三处例外要知道：

1. **被放到后台的进程**。Agent 用后台方式起的长任务（构建、训练、服务），打断主 CLI 之后可能还在跑。办法：终端服务可以列出每个会话下面的进程树，只读，让人看得到“这个容器里还有什么在跑”。要不要做，待定。
2. **Agent 自己开的 tmux 面板**。有些 CLI 的多 Agent 模式会把队友开在新的 tmux 面板里。用 tmux 后端的话，这些面板会自动出现在 rapp 里，反而是好事。
3. **跑在厂商云端的任务**。不在自己的机器上，没有终端可接。只能经厂商的 app 去看，也就是 rapp 原有的 GUI 那条路。

## 9. 没有验证的，建议先探查

动手之前花一两天探查，代码不保留：

1. `capture-pane -e` 取 Claude Code、Codex 的界面：中日文宽字符、真彩色、光标位置对不对；每秒取 10–20 次的开销。
2. 整段粘贴（含换行）进 Claude Code、Codex 的输入框，是不是当成一段，而不是逐行提交。cmux 的文档说它那边多行会退化成逐键。
3. rapp 以控制模式接着的同时，另一个终端用普通方式接同一个会话，两边尺寸和显示是否互不影响。
4. 屏幕规则对 Claude Code、Codex 当前版本的命中率：故意造出“等确认”“等输入”“工作中”各十次，看判对几次。
5. 用户常用的发行版上 tmux 的版本是否在 3.2 以上。

## 10.1 补充：Linux 上其他同类工具，要不要都接（2026-11-14）

用户的问题（原话）：“linux 下常用的 tmux 类似的工具还有哪些，我们是否需要都介入。”

**我的建议：不需要都接。** 判断一个工具值不值得接，看两条：能不能从外面读到它当前的屏幕；能不能从外面送输入，而且不把正在用的那个客户端挤掉。

| 类别 | 工具 | 从外面能做什么 | 建议 |
|---|---|---|---|
| 完整的复用器 | tmux | 控制模式：通知、取屏、送键都有 | 第一档，做 |
| 叠在 tmux 上的 | byobu（tmux 模式）、Agent of Empires、amux 等 Agent 管理器 | 底下就是 tmux | 自动覆盖，不用另做 |
| 完整的复用器 | Zellij | 命令行动作可以导出屏幕、写入字符（按我的记忆，未实测）；另有自带的网页服务 | 第二档 |
| 完整的复用器 | GNU screen | `hardcopy` 导出屏幕、`stuff` 送输入（按手册，未实测）。没有变化通知，只能定时去取；导出的是纯文字，没有颜色 | 第二档，只有老机器才需要 |
| Agent 专用的复用器 | Herdr | 本机的 socket 接口，可以读面板、等状态；它自己已经做了状态判断 | 第二档 |
| 只保活、不管屏幕 | dtach、abduco | 只转发原始字节，不存屏幕，重新接上时之前的画面没有了 | 不接 |
| 只保活 | shpool | 一个会话同一时间只允许一个客户端，rapp 接上去会和用户自己的终端冲突 | 不接 |
| 只保活 | zmx | 自己存了终端状态，但没查到给外部程序读屏的接口（未核实） | 不接，有需要再看 |
| 不是终端容器 | nohup、systemd、docker 后台运行 | 没有终端可接 | 不接 |
| 不是容器，是传输 | mosh、Eternal Terminal | 管的是网络这一段，会话存活还是靠上面那些 | 不相关 |

三档的处理：

- **第一档（做）**：tmux 后端，加 rapp 自带的后端（`rapp run`）。
- **第二档（留接口，有人用再做）**：Zellij、GNU screen、Herdr。它们都有给外部用的接口，各写一个后端即可。
- **第三档（不做）**：只保活的工具和后台运行的进程。使用说明里写一句：想让 rapp 看得到，就把命令放在 tmux 里或用 `rapp run` 启动。

**对设计的要求**：被控端的后端做成一个固定的小接口——列出会话、取网格、订阅变化、送输入，另有可选的新开、结束、改尺寸。传输协议和主控台只认这个接口。以后加一种工具是加一个后端，不动别处。“要不要都接”的答案因此是：接的是一个接口，不是 N 个工具。

待用户回答：自己的服务器上除了 tmux 还在用哪一个。在用的提到第一档。
