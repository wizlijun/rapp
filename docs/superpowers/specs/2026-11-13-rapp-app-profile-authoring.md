# rapp：app 配置编写规范（给 AI 和人照着写）

日期：2026-11-13。状态：**已采用**（用户 2026-11-13：「可以写一套配置规范的规格文档，后续有什么应用要做适配，可以让 ai 根据文档来生成配置。」）

依据：《app 配置设计》（`2026-11-13-rapp-app-profiles-design.md`，下称「设计」）。两份不一致时以设计为准，并回来改这份。

## 0. 怎么用

把这份文档和要适配的 app 名字交给 AI，说：「按 rapp app 配置编写规范，给 〈app〉 生成一条配置。」AI 照 §1–§6 一步步做，最后交出：

1. 一条 JSON（§5 的格式），
2. 一张自查表（§6，每项写 ✓ 或原因），
3. 一句话说明为什么这么配。

内置配置加到 `gui/assets/app_profiles.json` 的 `apps` 末尾，并在设计 §9 的表里补一行；用户自己的配置写进 B 配置目录的 `apps.json`（也可以在 GUI 的配置页里填，效果一样）。

## 1. 先判断值不值得适配

只适配**最有可能远程用**的 app（用户 2026-11-13 定的过滤）。判断一个问题：

> **人不在 A 前时，要用的东西是不是只在 A 上？**

| 是 → 收 | 否 → 不收 |
|---|---|
| A 上跑着的任务：终端、写代码、本地运行的 AI 任务 | 云端同步、在 B 上直接打开就能用：笔记同步类、团队聊天、邮件、日历、纯网页的 AI 对话 |
| A 上的文件：本地文档、本地工程 | 很少远程用的：视频会议 |
| 只能在一台电脑登录的账号：微信、企业微信 | |
| A 上浏览器里的登录状态、A 所在的内网 | |

不收时，回答「不收」和理由即可，不生成 JSON。拿不准时收进设计 §9 的「候补」，不进第一批。

## 2. 找 app 标识（`ids`）

一份配置可以同时写三种系统的标识（设计 D3），比较时不分大小写。

| 系统 | 标识是什么 | 怎么查（只读） |
|---|---|---|
| macOS | bundle id | `defaults read "/Applications/<名>.app/Contents/Info" CFBundleIdentifier` |
| Windows | exe 文件名，带 `.exe` | 任务管理器 →「详细信息」里的进程名 |
| Omarchy | 窗口 class | `hyprctl clients` 输出里的 `class:` |

规则：
- 在装了这个 app 的机器上查到的，算**已核对**；只凭公开资料填的，算**待核对**（§5 的 `tested` 不影响这一点，核对情况写进设计 §9 的「✓」一栏）。
- 一个 app 有新旧两个标识（改过名、国际版 / 国内版）时，都写上，常见的在前。
- 同一个 app 家族共用一份配置（例：Word、Excel、PowerPoint 写在一条里）。
- **不要猜**：查不到又没有可靠资料，就写「待核对」并停下来问人，不编一个标识。

## 3. 选画面（`stream`）

取值只能是下面这些（和 GUI 串流菜单一一对应）：

- `mode`：`duogray`（双色·灰度）、`duocolor`（双色·彩色）、`color16`（高彩）
- `density`：`adaptive`（自适应）、`original`（原画）
- `fps`：`1`、`5`、`15`、`30`

按 app 画面里**主要是什么**来选，对上第一行就停：

| 画面主要是 | mode | density | fps | 例子 |
|---|---|---|---|---|
| 单色文字，要马上看到打字回显 | `duogray` | `adaptive` | 15 | 终端 |
| 文字，靠颜色分块或代码高亮；或者文字一个字一个字地出来 | `duocolor` | `adaptive` | 15 | 写代码、AI 对话、带颜色的终端（Warp） |
| 文字，画面变得慢 | `duocolor` | `adaptive` | 5 | 文档、聊天 |
| 图片、网页、混合内容 | `color16` | `adaptive` | 15 | 浏览器 |
| 要看清每个像素 | `color16` | `original` | 15 | 设计、看图 |
| 持续在动的画面 | `color16` | `adaptive` | 30 | 播放视频 |

规则：
- `fps: 1` 不用作任何 app 的默认（那是串流菜单里「最省」的临时档）。
- 拿不准时往省流量的一边选（灰度 < 彩色 < 高彩，5 < 15 < 30），用户试过再改。

## 4. 其余字段

| 字段 | 内置配置 | 用户自己的配置 |
|---|---|---|
| `afterSend` | 一律 `"none"` | 用户明确说「发完要回车」才写 `"return"` |
| `composer` | 一律 `true` | 用户明确说「这个 app 不要输入区」才写 `false` |
| `windows` | 一律空（设计 D8：隐藏规则猜错了会让人找不到窗口） | 只按用户点名的窗口写，见下 |
| `tested` | 一律 `false`（界面上显示「未实测」） | 不写 |

写窗口规则（只给用户自己的配置）：
- 每条：`kind`（可选，`normal`、`dialog`、`floating`、`sheet`、`popover`、`menu`、`tooltip` 之一）、`title`（可选，通配：`*` 配任意多个字，其余原样比，不分大小写）、`child`（可选，不写就是 `true`，主窗口不受影响）、`action`（`hide` 或 `noComposer`）。
- 按顺序比，第一条对上的生效：具体的写在前，宽的写在后。
- 标题会随内容变（网页、文件名），只保留不变的那部分，其余换成 `*`。例：`下载 — 3 项` 写成 `下载*`。
- `kind` 和 `title` 都不写会配上所有子窗口，除非用户就是这个意思，否则别这么写。
- 要藏 `dialog` 或 `sheet` 时，先提醒用户：「它可能在等你回应，藏了以后 A 上的 app 看起来会卡住；标签栏的『已隐藏 N 个』可以找回来。」
- 标题通配只写能认出这类窗口的最短片段，不写文件名、网页标题这类私事。

## 5. 格式

一条配置：

```json
{
  "name": "Ghostty",
  "ids": ["com.mitchellh.ghostty"],
  "stream": {"mode": "duogray", "density": "adaptive", "fps": 15},
  "afterSend": "none",
  "composer": true,
  "windows": [],
  "tested": false
}
```

- `name`：给人看的名字，1–40 字，用 app 自己的叫法（中文系统里显示中文名的用中文名）。
- `ids`：至少一个，见 §2。
- 字段顺序照上面写，便于对照；没写的字段按设计 §2 的「没写时」处理。
- 文件里**不能有**密码、token、剪贴板内容、窗口里的文字。

用户配置的例子（用户说：「Chrome 的下载窗口别显示，设置对话框里不要输入区」）：

```json
{
  "name": "Chrome",
  "ids": ["com.google.Chrome", "chrome.exe", "google-chrome"],
  "windows": [
    {"kind": "floating", "title": "下载*", "action": "hide"},
    {"kind": "dialog", "title": "设置*", "action": "noComposer"}
  ]
}
```

这里只写了 `windows`：画面等字段沿用内置配置（设计 D4，按字段合并，用户的优先）。

## 6. 交出前自查

- [ ] 过了 §1 的判断（内置配置必须过；用户配置是用户点名的，可以跳过）
- [ ] `ids` 至少一个，每个都已核对或标了「待核对」；没有编出来的
- [ ] `ids` 和 `app_profiles.json`、`apps.json` 里已有的配置不重复（重复时改已有的那份，不新加）
- [ ] `stream` 三个值都在 §3 的取值里；`fps` 不是 1
- [ ] 内置配置：`afterSend` 是 `none`、`composer` 是 `true`、`windows` 是空、`tested` 是 `false`
- [ ] 窗口规则（如有）：具体的在前；动态部分换成了 `*`；藏 `dialog`/`sheet` 已提醒
- [ ] JSON 能解析（`python3 -m json.tool` 过一遍整个文件）
- [ ] 内置配置：设计 §9 的表里补了一行（组、名字、标识、画面、为什么这么配）
- [ ] 没有密码、token、私人内容

## 7. 以后改这份规范

设计里加了新字段（如第二版的标题栏、按键、「在等你」，设计 §7）时，同步改 §4、§5、§6；新的取值加进 §3 的表里，并写一行例子。
