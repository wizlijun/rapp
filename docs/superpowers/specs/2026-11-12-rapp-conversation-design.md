# rapp 沟通机制设计规格（讨论中）

日期：2026-11-12。状态：**讨论中**。逐段和用户确认，每段标了"已确认"或"待确认"。全部确认后再整理成正式规格，然后才写实现计划。本文不改代码。

上位文档：`2026-11-12-rapp-main-window-design.md`（下称"主界面规格"）、`2026-11-12-rapp-design-language.md`（下称"设计语言"）。
来由和原话：`2026-11-12-rapp-requirements-feedback.md`（下称"反馈文档"）的 U25–U28。

## 0. 设计简报（已确认）

**出发点（用户原话的意思）**

把每个"设备上的 app"当作一个干活的员工。别人用 Slack 式的群聊和 Agent 沟通，Grok Bot 也把 Agent 做成长期同事。要在现有 dashboard 上加一层和员工沟通的机制。

**目标体验（U33，用户原话的意思）**

我在一台电脑上工作了一段时间，固定用几个工具，和它们磨合好了，沟通顺畅、出活也顺。现在我要出差。我希望它们自己干活，需要我的时候，我确认一下就行。

这段话是整份设计的验收场景：出差时拿出平板，看得到谁需要我，看一眼就明白是什么事，确认或回一句，然后它们接着干。

**要达到的效果**

| # | 效果 | 出处 |
|---|---|---|
| G1 | 在一个地方回复所有员工，不用进它们的窗口 | U26 |
| G2 | 有一条总的时间线：谁什么时候说了什么，我回了什么 | U26 |
| G3 | 一句话发给多个员工 | U26 |
| G4 | 员工之间能看到彼此的上下文 | U26 |
| G5 | 有一个助理替用户记住每个员工在做什么，帮着找到人、起草、汇报。这是最痛的一条 | U26 |

**四条不变的规则**

| # | 规则 | 出处 |
|---|---|---|
| K1 | 员工都是官方 app，用的是用户自己的订阅 | U27 |
| K2 | 不侵入 app：不 hook、不植入代码，只用官方发布的 app。看，只靠像人眼一样看画面；说，只靠打字和语音输入。文字只从画面里识别，不去读 app 内部 | U27、U30 |
| K3 | 每一次发给员工的话都由用户触发。助理可以起草，不能自己发 | 反馈文档 §0.6 的界线；U28 选定的方案 |
| K4 | 不依赖聊天式的多 Agent 服务 | U27 |
| K5 | 不要求用户安装任何额外的插件、skills、hooks，就能把事都做了 | U29，用户要求记住的准则 |
| K6 | 全部上下文都有带时间线的记录。用处有三个：将来给 Agent 提供充足的上下文、做安全审计、回看找问题 | U30 |

K5 我的理解（待用户纠正）：rapp 自己的安装包不算"额外"。它说的是两件事：不往员工的 app 里装任何东西；也不要求用户为了用沟通机制和助理再另装别的。所以助理必须是装好 rapp 就能用的，不能靠给某个 Agent 装 skill 或接插件来实现。

**选定的方向（U28，用户说"暂时使用"）**

以"画面即消息"为底，上面加一个只起草和汇报的助理；真文字只给已经有配置的常用 app 加，而且按 K2，文字只从画面里来。

## 0.1 先后顺序（U34，用户已定）

用户的话：先实现可靠的基础交互能力和极度流畅的性能，再做上下文的记录（不仅供误操作时回看，也供 Agent 当上下文），最后再利用本机闲暇的算力（无头 harness）做智能助理。每一层都应该以 AI 时代的工作为目标。

| 阶段 | 做什么 | 对应本文哪一段 |
|---|---|---|
| 一 | 可靠的基础交互，极度流畅的性能 | 不在本文。是主界面规格和各子项目（S2–S6）正在做的事 |
| 二 | 上下文记录 | §2 消息层；§3 沟通界面里靠记录才能做的部分（收件箱、时间线、转发） |
| 三 | 智能助理，用本机闲暇的算力跑无头的 harness | §4 |

§3 里的群发、给员工起名字不依赖记录，放在阶段一还是阶段二，待定（§9 第 5 条）。

**这个顺序给设计加的三条约束（我的分析）**

1. **记录不能拖慢交互。** 阶段一的目标是极度流畅，阶段二加上去以后不能让它变差。被控端的记录要低优先级运行；有人连着操作时，实时画面优先。
2. **记录的格式从第一天起就要让 Agent 读得懂。** 用普通文件：时间线是一行一条的文本，识别出的文字是文本，快照是图片，按员工、按日期分目录。这样阶段三的助理只要是一个能读目录的无头 harness 就够了，不需要插件、不需要专门的接口（K5）。
3. **助理不是实时的。** "闲暇的算力"意味着它在机器空下来的时候成批地干：读新增的记录，写出每个员工的一句话近况、要用户确认的事项清单、起草的回复。结果也写成文件，界面读文件显示。发送仍然由用户按（K3）。

**阶段一要给后面留的口子（我的分析，供排期时参考）**

- 被控端的采集进程能在没人连的时候继续跑（现在闲置 60 秒就关）。
- 输入区发送的那条路上，能记下"发了什么、发给谁"。
- 采集那一头能说出"这一帧哪些块变了"，供判断有没有动静。

## 1. 整体分四层（已确认；消息层的位置按 U31 改到被控端）

| 层 | 做什么 | 新的还是已有的 |
|---|---|---|
| 画面流 | 像素进来，系统级输入出去 | 已有，不改 |
| 消息层 | 从画面里得到"消息"并完整记录，每个员工一条线 | 新增。记录在被控端做，操作端需要时通过网络取回（U31）。仍然只看画面，不碰 app |
| 沟通界面 | dashboard 上的收件箱、时间线、群发、转发 | 新增 |
| 助理 | 读消息层里的花名册和时间线，回答"谁在做什么"，起草，汇报 | 新增 |

每一层只依赖它下面那一层。没有助理时，消息层和沟通界面能单独用；助理关掉不影响照常和员工说话。

## 2. 消息层（按 U31–U33 定稿；用户没有逐条确认，有不对的随时改）

### 2.1 一条消息是什么

| 种类 | 内容 | 怎么来的 |
|---|---|---|
| 我发的 | 原文，加上附带的块（图片、文件）。打字和语音输入最后都是输入区里的文字，记的是同一样东西 | 输入区发送时记下来 |
| 我做的 | 在画面上的点击、滚动，和直接发给对方的按键 | 发出去时记一行：什么时刻、对哪个窗口、做了什么 |
| 对方的 | 一张整窗快照，加上从快照里识别出的文字 | 窗口"有动静，然后安静下来"时拍一张 |

存的是整窗快照，不是只剪变化的那一块。聊天类 app 一有新内容就整体上滚，变化的区域差不多就是整个窗口；整窗快照也正是用户切过去会看到的样子。

### 2.2 什么时候拍

- **有动静**：窗口里有成片的变化。只在一小块地方反复变的（光标闪、转圈）不算。
- **安静下来**：连续 3 秒没有动静。秒数可以按 app 配。
- **长回复**：动静持续时，每隔 10 秒留一张中间快照，免得前半段滚走了看不到。
- 不管这次动静是不是由用户的话引起的，都拍。员工自己干完活、自己弹出确认，同样会进时间线。

### 2.3 状态用"未读"，不用"等你"

rapp 分不清"说完了在等你"和"只是停了一下"。所以不去猜，只标"未读"：

- 拍到新快照，这个员工标为未读。
- 用户看过这张快照，或者回复了，未读自动清除。

这顺带解决了设计语言 §0 第 3 条的差距：不再需要「已处理」按钮，也不必等 S8 的信号。主界面规格里"Agent 等你"的灯改成由"未读"点亮。

### 2.4 记录在被控端做（U31）

用户的决定：在 host（被控端）里记录，需要时通过网络取回。

这样做带来三个变化：

- **没人连着的时候也在记。** 被控端对"员工"保持采集，不依赖操作端是否在线。K6 的"全部上下文"由此成立。
- **识别更准。** 被控端手里是原始画面，不是省流之后的。文字识别放在被控端做，不受档位影响，之前担心的"省流档位下识别不准"就没有了。
- **记录是唯一的一份。** 用户从台式机、平板哪个操作端连过来，看到的是同一条时间线。用户发的话、做的操作本来就要经过被控端，在那里记一次就够。

**哪些 app 要一直记**：按 U33，员工就是用户在这台电脑上固定用的那几个工具。所以：

- 名单是明确的一份，每台被控端各有自己的。可以在那台电脑自己的 rapp 界面里定，也可以从操作端定。
- 名单里的 app 只要开着就记，不管用户是坐在这台电脑前直接用，还是从别处连过来用。出差前在本机磨合的那段过程也因此留在记录里，助理将来读得到。
- 用户坐在被控端前直接打的字，rapp 不记，也不该记（那等于键盘记录）。这段时间的记录只有画面；用户说过的话会出现在画面里，由文字识别带出来。
- 名单外的 app 不记。

现在"常用"存在操作端的 `workspace.json` 里（S5），要改成被控端也有一份。

**被控端要改的地方**：现在每个 app 的采集进程是有人打开才拉起，闲置 60 秒就关掉（平台规格 §3）。要改成名单里的 app 一直有一个在记的进程。

### 2.5 完整记录（K6）

分三档，越往下越占地方，都存在被控端：

| 档 | 记什么 | 多大 | 留多久（我的默认，待定） |
|---|---|---|---|
| 时间线 | 每件事一行：我发的话、我做的操作、拍了快照、未读和已读、连上和断开 | 很小，纯文字 | 一直留 |
| 快照和识别出的文字 | §2.1 的内容 | 文字为主的窗口一张几 KB 到几十 KB（README 的实测） | 一直留，设总量上限 |
| 完整画面流 | 按现有的编码、带时间存下来的画面流，只含变化的部分，能逐帧回放 | 画面不动时不占地方；有动静时和流量一样大。没有专门量过，要实测 | 滚动保留最近若干天，天数可配 |

三个用处各自用到哪一档：

- 给 Agent 上下文：时间线加识别出的文字，必要时带快照。
- 安全审计：时间线（什么时候发了什么、做了什么）加当时的快照。
- 回看找问题：完整画面流。

### 2.6 取回

- 操作端一连上，先取时间线和识别出的文字（很小），用来显示未读和时间线。
- 快照在要看的时候取，取过的在操作端留一份缓存。
- 完整画面流只在回放时取。
- 走现有的连接和认证，新增几种请求：列出记录、取某一段。协议细节写计划时定。
- 已读的标记记在被控端，这样换一个操作端也不会重复提醒。

### 2.7 做不到的和要小心的

- **分不清"说完了"和"卡住了"。** 这是只看画面的固有限制。
- **被控端关机、睡眠、锁屏的时候不记。** 这时员工也不在干活，所以不算漏。前提见 README"A 没人照看时"。
- **一直采集有代价。** 被控端要长期占着屏幕录制，耗多少 CPU 没量过。另外，据我所知 macOS 对持续录屏的 app 会隔一段时间重新要求用户确认（没有核对）。没人照看的机器上弹这个确认就会停录，这一点要实机验证。
- **这份记录很敏感，而且现在放在每一台被控端上。** 屏幕上出现过的一切、发出去的每一句话都在里面，包括不小心露出来的密码和密钥。要做到：文件权限收紧、能暂停、能指定某些 app 不记、能删掉某一段。做到哪一步，待定（§9 第 2 条）。
- **经 relay 取回时，relay 看得到内容。** 平台规格 D8 接受过"拿到 VPS 的人能看到中继流量"。记录比实时画面更集中，这一条的分量也变重了。见 `2026-11-12-rapp-relay-security-requirements.md` 第 10 条。
- **先只做 macOS 的被控端。** Windows 和 Omarchy 的被控端还在协议 v3，记录功能要等它们追上来。

### 2.8 怎么测

"有动静、安静下来、该不该拍"是一段纯计算：输入是一串"什么时刻、哪些块变了"，输出是"在什么时刻拍"。用编好的序列做单元测试，再拿录下来的真实画面流回放验证。
存和取用临时目录做往返测试：写进去的时间线、快照、画面流，取回来逐字节一致。

### 2.9 借鉴屏幕记录类产品的经验（U32）

用户的话（U32）：这是吸收了那类"监控屏幕来获得上下文"的创业项目的经验；海量数据交给 AI，会有更多可能。

2026-11-12 查了两个有代表性的：Screenpipe（本机全天记录屏幕，给 Agent 当记忆）和微软的 Recall（因隐私问题被迫重做）。来源见本节末尾。

**可以直接借的做法**

| 它们怎么做 | rapp 怎么用 |
|---|---|
| Screenpipe 不按固定间隔拍，而是有事才拍：切换 app、点击、滚动、打字停顿、复制，另加约 5 秒的空闲兜底 | 和 §2.2"有动静才拍"是一个思路。可以把"用户刚发了话""用户刚点了一下"也算作触发，不只看画面变化 |
| Screenpipe 存的是截图加文字，不存连续视频；相同的画面跳过 | 和 §2.5 前两档一致。rapp 多出的第三档（完整画面流）是因为画面流本来就只含变化，存下来几乎不额外花钱 |
| Screenpipe 给出的参考数字：约每月 5–10 GB，内存约 600 MB，CPU 约 5–10%（它记的是整个屏幕加麦克风） | rapp 只记员工的窗口，应该更小，但要实测。这组数字可以当上限来对照 |
| Screenpipe 通过本机接口让 Agent 查询：按关键词搜、按时间取、取某一帧的上下文 | 助理那一层读记录时，接口可以照这个形状设计：搜、按时间取、取某一刻的画面 |
| Recall 第一版每 5 秒截一次屏存在本机，被批评成恶意软件的现成目标，预览版被撤回 | 记录是个靶子。保护要在第一版就有，不能后补 |
| Recall 重做后加的东西：默认关闭、由用户明确开启；托盘图标显示正在记录、随时可暂停；可以排除指定的 app；可以删除某一段时间、某个 app 的内容或全部；可以设保留多久、占多少磁盘；加密存放；自动拦下密码、证件号、信用卡号 | 这就是 §2.7"记录很敏感"那一条该做的清单。我的建议见 §9 第 2 条 |

**rapp 和它们不一样的地方**

- 它们记的是用户自己的整块屏幕，什么都在里面。rapp 记的是被控端上"员工"的窗口，范围窄得多，也更像一份工作日志。
- Screenpipe 取文字时优先读系统的辅助功能接口，文字识别只是兜底。按 K2，rapp 只从画面里识别。这样取到的文字会粗一些、没有结构，换来的是对任何 app 都一样、完全不碰 app。这是按用户的规则做的取舍，记在这里。

**"海量数据"对默认值的影响**

既然数据多是好事，保留的默认值往多里定：时间线和识别出的文字一直留；快照的总量上限定得宽一些；完整画面流留的天数可配。同时，哪些 app 要一直记，默认范围也可以放宽，见 §9 第 4 条。

来源：<https://docs.screenpipe.com/architecture>、<https://www.securityweek.com/microsofts-controversial-recall-returns-with-proof-of-presence-encryption-data-isolation-opt-in-model/>（2024-09-27）。都是转述，没有逐条核对。

## 3. 沟通界面（待确认；属于阶段二）

原则：不新开一套界面，把四件事接到主界面已有的位置上。舞台仍然整块留给远程窗口（主界面规格 D12）。

### 3.1 收件箱（G1）

- 位置：顶栏已有的"需要你"。现在点开最多列 3 件、每件只有一个"查看"。
- 改成：列出所有未读的员工，最新的在上。每一条有：状态灯、员工的名字、所属项目、最新快照的缩略图、识别出的最后几行文字、时间。
- 每一条下面直接带一个输入框。在这里回一句就发给那个员工，不用切过去。点缩略图才切到它的窗口。
- 回复了或看过了，这一条自动从收件箱消失（§2.3）。

### 3.2 时间线（G2）

- 单个员工的时间线：输入区旁边加一个「记录」按钮，点开是盖在舞台上的浮层。我发的话是文字，对方的是快照卡片，按时间排。点一张快照放大看；长按或右键可以从那一刻开始回放。
- 总时间线：放在全景模式里，作为第四层"动态"，所有员工的事按时间混排，可以按项目、按员工筛。

### 3.3 群发（G3）

- 输入区上方加一行"发给谁"。默认是当前这个员工；可以再加别的员工，或者直接选一个项目。
- 点发送后，rapp 按顺序把同一段话贴给每个收件人。每个收件人各记一条。哪个没贴成，在提示里说明，其余的照发。
- 这仍然是用户按一次发送触发的（K3）。

### 3.4 转发（G4）

- 每张快照卡片上有「转给…」。选一个员工后，这张快照作为图片块进入输入区，用户可以再补一句话，然后发送。
- 输入区本来就支持把图片贴给对方（协议 v5）。接收的员工是通过看图得到上下文的。

### 3.5 员工的名字和一句话近况（G5 的一半）

- 每个员工可以起一个名字（比如"写前端的"）。不起名字时显示"app 名 @ 设备名"。
- 会话列表和收件箱里，名字下面显示一句话近况：最近一张快照里识别出的最后一行。有助理时，由助理写成一句人话（§4）。

### 3.6 和现有交互规则的关系

- 浮层只盖不挤（主界面规格 §5 第 1 条）：收件箱、时间线都是浮层，不改变舞台大小。
