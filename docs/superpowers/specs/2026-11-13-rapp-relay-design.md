## 1. 一句话和边界

**relay 是一个只认设备密钥、只搬密文的接线服务。** 它帮两台设备找到对方、接通对方；接通以后经过它的每一个字节，它都解不开。

不做（第一版）：

- 多节点、多地区；账号、计费、网页管理界面。§14 留了位置。
- TCP 入口；给不是 rapp 设备的客户端（比如外部小屏）用的入口。§15 说明了边界。
- Docker 镜像以外的发布形式；在 macOS、Windows 主机上跑 relay。
- 对 relay 隐藏"谁在什么时候连了谁"。relay 是牵线的，这些它必然知道（§4.3）。

不能出现的结果（做成了也算失败）：

- relay 的代码里出现业务概念（app、便签、文件、剪贴板）。
- 为了安全，远程会话明显变慢。
- 换到新 relay 的过程中，远处无人值守的机器连不上了，或者要人到每台机器跟前去设置。
- 自己设计加密算法或者握手。
- 新 relay 里留着旧协议的代码。

## 2. 用户看到的

**架 relay**（一次）：

1. 在一台 Linux 主机上启动容器，放行一个 UDP 端口。不用填任何配置。
2. 运行 `docker exec rapp-relay rapp-relay key`，得到一串 key。它只显示这一次。

**接入一台设备**：在 rapp 的设置里填两样，接入点（relay 的地址）和 key。

**访问另一台设备**：输入它的 ID。两台设备填的是同一个 key，就直接连上。没有密码，没有确认框。

**平时**：什么都不用管。想知道谁连过谁，查审计日志（§11）。

**出事的时候**：

| 情况 | 做什么 |
|---|---|
| 要踢掉一台设备 | 在 relay 上吊销它 |
| 丢了一台设备 | 先吊销它，再换 key |
| 怀疑 key 泄露 | 换 key：在 relay 上生成新的，在手边一台设备上填一次，它会传给其他设备 |
| 设备都接入了，想锁死 | 关掉 relay 的"入网"，关掉无人值守机器的"接受新设备" |

## 3. 做法的选择

要解决的核心问题：两台设备经过 relay 通信，怎样让 relay 解不开。

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | **relay 把两台设备各自的一条流接起来；设备在接好的流里面做一次 TLS 1.3，互相验证。** 和浏览器经过代理访问 HTTPS 网站是同一个模式：代理只负责接通，加密在两头之间 | 每一层都是现成的、用得最久的东西；relay 对每一段各自做重传和拥塞控制，性能可以预期；加密层不挑下面的传输，以后加 TCP 入口也能用；relay 里没有任何业务 | relay 上每份数据有一次解密、一次加密（外面那层）；经中继的每条流多一次握手 |
| 乙 | 两台设备之间永远是一条端到端的 QUIC 连接；relay 只转发数据包 | relay 最轻；连接可以在直连和中继之间无缝切换 | QUIC 套 QUIC，包长和拥塞控制叠加，要专门调；转发包的格式和鉴权要自己设计，和 R6 相悖 |
| 丙 | 改用 iroh（一个 Rust 库，2026 年 6 月发布 1.0，承诺线上协议稳定）。它按公钥拨号，自带端到端加密、打洞和不看内容的 relay，relay 程序开源可自建 | 自己写的代码最少；打洞比 rapp 现在的做法强 | 多一个大依赖，1.0 才发布五个月；它的中继走 HTTP(S)（据我所知是在 TCP 上，没有核对到原文）；relay 不再是自己的，R8 无从谈起；"一个 key 就互信"仍然要自己做 |
| 丁 | 设备之间先用 WireGuard、Tailscale 一类工具组网 | 很成熟 | 每台设备多装一样东西，平板上尤其麻烦 |

**选甲**（我定的；方向是用户在 U65、U73 认可的）。

既然是重构，"改动小"不再是理由。甲仍然是我的选择，理由是另外三条：

- **R6**：甲用到的只有 QUIC 的流和 TLS 1.3，加上哈希、单向推导、消息认证码这几样最基本的东西。库都是 rapp 已经在用的。
- **R4**：一个远程会话就是一条从头到尾的流（现有设计如此）。在流里套一层 TLS，会话期间只多一层对称加密，没有额外的往返。乙要重新证明它不比现在慢。
- **R8**：甲的加密层和传输无关，relay 以后换传输、加节点，设备之间的信任关系不受影响。

乙作为以后的升级方向保留：真到了 relay 的处理器成为瓶颈的规模，可以把"接流"换成"转发包"，§6、§7 的身份和互信原样可用。

## 4. 威胁模型

### 4.1 要防的人

| 代号 | 是谁 |
|---|---|
| T1 | 设备和 relay 之间网络上的人（能看、能改、能冒充任何一方的地址） |
| T2 | 互联网上任何能连到 relay 端口的人 |
| T3 | 完全拿到 relay 那台机器的人（能读磁盘和内存，能换掉 relay 程序） |
| T4 | 和设备在同一个局域网里的人 |
| T5 | 拿到了 key 的人 |

### 4.2 各自能做什么

| | 看到内容 | 冒充已有的设备 | 作为新设备加进来 | 让服务不可用 |
|---|---|---|---|---|
| T1 | 不能 | 不能 | 不能 | 能（在路上的人总能丢包） |
| T2 | 不能 | 不能 | 不能 | 被限速和上限挡住（§9.2） |
| T3 | 不能 | 不能 | 不能：relay 手里没有 key（§6.2） | 能 |
| T4 | 不能 | 不能 | 不能 | 能（局域网内） |
| T5 | — | 不能 | **能。有 key 就是自己人** | — |

R1、R2 对应前三列的 T1–T4：都是"不能"。

**T5 那一行是 R11 的直接后果：key 等于所有设备的总钥匙。** 拿到 key 的人可以远程操作每一台还在接受新设备的设备。key 存在每台设备上，所以任何一台设备被人拿到，key 就泄露了。应对的办法是两个开关（§7.3）、吊销和换 key（§7.4）。

### 4.3 relay 知道什么

| relay 知道 | relay 不知道 |
|---|---|
| 每台设备的 ID、公钥指纹、公网地址、局域网地址 | key |
| 谁在什么时候找过谁、走没走中继、中继了多久、多少字节 | 设备之间传的任何内容 |
| | 设备名、设备上有什么 app、设备之间谁认识谁 |

"不能看到任何内容"（R1）在本文里的意思是右边那一列。左边那些是牵线必须知道的。

## 5. 结构

### 5.1 relay 只做三件事

| 功能 | 做什么 |
|---|---|
| 登记 | 设备连上来，用设备密钥证明自己是谁，报上自己的 ID 和地址。relay 记住"这个 ID 现在在线，连接是这一条" |
| 牵线 | B 说要找某个 ID。relay 把 A 的地址告诉 B，同时通知 A"有人要来"，A 借此打洞 |
| 接流 | 直连不通时，B 请 relay 接一条流到 A。relay 在 A 的连接上开一条流，把两条流双向原样对接，之后只搬字节 |

relay 不知道流里是什么。远程会话、文件、以后的数据服务（PD14）都只是"设备之间的一条流"，relay 不用为它们改任何东西（R5）。

### 5.2 四层

| 层 | 在谁和谁之间 | 是什么 | 标识 |
|---|---|---|---|
| L1 传输 | 设备 ↔ relay；设备 ↔ 设备（直连时） | QUIC，自带 TLS 1.3。双方都出示证书 | relay 默认 `22026/udp`；设备 `22028/udp` |
| L2 relay 协议 | 设备 ↔ relay | 每个请求一条流：一行 JSON 请求，一行 JSON 回复（§8） | ALPN `rapp-relay/2` |
| L3 端到端 | 设备 ↔ 设备 | TLS 1.3，双方互相验证设备密钥。直连时就是 L1 的那次握手；经中继时是在接好的流里面再握一次 | 直连 ALPN `rapp/2`；流内 ALPN `rapp-e2e/1` |
| L4 设备请求 | 设备 ↔ 设备 | 互信证明、传 key，以及 rapp 的业务请求（列 app、打开 app……）。本文只定前两个（§7） | — |

直连时只有一层加密。经中继时有两层：设备到 relay 的一段（L1），和设备到设备的全程（L3）。relay 只能解开外面那一层，里面是 L3 的密文。

### 5.3 一次经中继的连接

```
B                          relay                         A
│── QUIC 握手，互相出示证书 ──▶│◀── QUIC 长连接，已登记 ──────│
│── {"op":"connect","id"} ──▶│── {"op":"incoming",...} ───▶│   A 向 B 的地址打洞
│◀─ {"ok","lan","public"} ───│◀─ {"ok"} ──────────────────│
│   （局域网、直连都不通）                                    │
│── {"op":"relay","id"} ────▶│── {"op":"relayed",...} ────▶│
│◀════════ relay 把两条流对接，此后只搬字节 ═════════════════▶│
│◀──────────── TLS 1.3 握手（L3），互相验证设备密钥 ──────────▶│
│◀──────────── 设备之间的请求，全程密文 ─────────────────────▶│
```

选路的顺序不变：局域网 → 直连（打洞）→ 中继。

### 5.4 relay 内部的划分

每一块是一个接口，后面可以换实现。第一版每块只有一个最简单的实现；§14 说明 SaaS 时换哪一块。

| 模块 | 管什么 | 第一版的实现 |
|---|---|---|
| 传输 | 监听、握手、开流 | QUIC |
| 准入 | 这条连接是哪台设备、哪个租户、让不让进 | 设备证书加入网（§6.4） |
| 登记簿 | 入网的设备：指纹、ID、租户、是否吊销 | 一个文件 |
| 在线表 | 哪个 ID 现在在哪条连接上 | 内存 |
| 牵线 | `connect`、`incoming` | — |
| 接流 | 对接两条流、计量 | — |
| 限额 | 限速、上限、配额 | 内存里的计数 |
| 审计 | 记下每一个安全相关的动作 | 数据卷里的文件 |
| 管理 | 本机的管理命令 | 本机套接字 |
| 配置 | 读配置、校验 | 默认值、文件、环境变量 |

## 6. key、身份和准入

### 6.1 接入点和 key（R10）

设备上只填两样：

- **接入点**：relay 的地址，`主机:端口`。
- **key**：一串字符，以 `rapp` 开头，共 56 个，只有小写字母和数字，方便整串选中复制。不带 `rapp` 的旧写法也认。

key 管三件事：确认连上的是真的 relay；向 relay 证明自己是自己人；设备之间互相信任。

RustDesk 的 key 是服务器的公钥，连设备还要另外的密码。rapp 的 key 多带了一段随机数，所以一个 key 就够，不再要密码（R11）。

### 6.2 key 的构成，以及 relay 为什么没有 key

key 是两段拼在一起的。用户不用知道，当成一个 key 用。

| 段 | 是什么 | 用来做什么 |
|---|---|---|
| 前一半 | relay 公钥指纹的前 16 字节 | 设备确认连上的是真的 relay。对不上就拒绝连接 |
| 后一半 | 16 字节的随机数，叫"根" | 推出下面两个值 |

从"根"用标准的单向推导（HKDF-SHA-256）算出两个互不相通的值：

| 值 | 谁知道 | 用来做什么 |
|---|---|---|
| 入网口令 | 设备和 relay | 设备向 relay 证明自己是自己人（§6.4）。relay 只存它的哈希 |
| 信任口令 | 只有设备 | 设备之间互相证明"我也有 key"（§7.2）。relay 永远拿不到，也算不出来 |

这是 R2 和 R11 能同时成立的关键。relay 被拿到以后，那个人手里只有入网口令的哈希，推不回"根"，算不出信任口令，所以没法让任何设备信任他。

为了让 relay 手里真的没有 key（我定的）：

- key 由管理命令 `rapp-relay key` 生成，不由服务进程生成。它把 key **显示一次**，只把入网口令的哈希写进数据卷。
- 以后再运行这条命令，它会说 key 已经显示过。要再看 key，到任何一台已接入的设备的设置里看：设备存着它，默认遮住，点一下显示。
- 剩下的风险：生成 key 的那一刻，relay 那台机器如果已经被人拿到，他能看到 key。

**没有 relay 的时候**（只在局域网里用 `ID@地址` 直连）：在第一台设备的设置里点"生成 key"，填到其他设备上。这种 key 没有前一半。以后架了 relay，换成 relay 的 key。（我定的）

### 6.3 设备密钥和 ID

- 每台设备第一次启动时生成一对密钥和一张自签证书，长期使用。算法用 ECDSA P-256（我定的：它是 TLS 里支持最广的，将来单片机上的客户端也能用）。
- 存在设备数据目录的 `local/` 下，权限 0600，不进 git。同一台机器上被控的一侧和操作的一侧共用这一对。
- **指纹** = 证书里公钥部分的 SHA-256。验证只看指纹，不看证书的有效期、签发者、名字，所以不依赖设备的时钟。
- **ID** 仍然是 9 位数字，是给人看、给人输入的地址。ID 只用来找到设备；信不信对方，只看密钥。
- 一个 ID 第一次登记时，绑定到登记它的那把设备密钥。以后只有这把密钥能登记这个 ID。重装系统丢了密钥，就换一个新 ID，或者由管理员在 relay 上解除旧绑定。

### 6.4 准入（R3）

两道门：

1. **必须出示设备证书。** 不出示的，握手就被拒绝，一条请求都发不了。
2. **必须入过网。** 设备第一次连 relay 时提交入网口令。relay 核对后记下这台设备的指纹。以后这台设备靠密钥就能进。没入网的指纹只能做"入网"这一件事，并且被限速。

relay 上有一个开关可以**关闭入网**（§10 的 `enroll`）。关上以后，新设备即使有 key 也进不来。

### 6.5 管理命令

在 relay 的容器里运行，通过一个只有本机能访问的套接字和服务进程说话：

```
rapp-relay key                     第一次运行时生成 key 并显示一次
rapp-relay rotate-key              换 key：生成新的"根"，显示一次新的 key
rapp-relay devices                 列出入网的设备：ID、指纹、入网时间、最近在线
rapp-relay revoke <ID 或指纹>       吊销；它的连接立刻断开，以后握手被拒
rapp-relay unbind <ID>             解除 ID 和密钥的绑定
rapp-relay enroll open|closed      打开或关闭入网
rapp-relay audit [--since 7d] [--id …] [--event …]    查审计日志
rapp-relay check                   自检，给健康检查用
```

## 7. 设备之间：有 key 就互信（R11）

### 7.1 认识

对每一台对方设备，本机要么**认识**（存着对方的指纹），要么**不认识**。每台设备有一份认识的设备的列表，每项是指纹、对方自报的名字、认识的时间。

认识的设备之间：L3 握手时双方出示证书，各自核对对方的指纹。对上了就通过。这一步不用 key，也不用 relay 发的任何东西。

### 7.2 第一次怎么认识

L3 握手完成以后（这时双方还不认识对方的指纹），两边各发一个证明，证明"我有同一个 key"：

- 证明 = 用信任口令对"这次握手导出的一个值、双方的指纹、自己是哪一方"算一个消息认证码（HMAC-SHA-256）。
- **绑在这一次握手上**：中间人要插进来，就得和两头各握一次手，两边的导出值和指纹都不一样；他没有信任口令，算不出对的证明；把一头的证明原样转给另一头也对不上另一头的握手。
- 信任口令是随机数推出来的，猜不动。握手导出值加消息认证码，是把应用层的认证绑到 TLS 上的标准做法。
- 两边都验过以后，各自把对方的指纹记下来。以后走 §7.1。

对方的指纹变了（比如重装过）：只要它还能给出对的证明，就自动重新认识，界面上留一条提示。给不出就拒绝。

没有 relay、用 `ID@地址` 直连时也是同一套。

### 7.3 两个开关

key 是唯一的门，所以要能在不需要的时候把门关上。默认都开（开着就是"有 key 就能进"）：

| 开关 | 在哪 | 关上以后 |
|---|---|---|
| 入网 | relay | 新设备即使有 key 也进不了 relay |
| 接受新设备 | 每台设备的设置 | 这台设备只认已经认识的指纹 |

设备都接入、互相连过一次以后，把两个都关上，key 泄露了别人也进不来。加新设备时临时打开。要不要默认关上，见 §20。

设备自己的端口也可能暴露在公网上（打洞、端口映射）。所以设备的端点同样开 QUIC 地址验证；不认识的连接只能发证明，10 秒没动静就断；证明连续失败按来源限速。

### 7.4 吊销、换 key、丢设备

**吊销**：在 relay 上吊销一台设备。relay 断开它，并把吊销名单发给其余设备；它们把它从认识的列表里去掉，以后也不再认它。

设备在"信任谁"上不听 relay 的，但"不再信任谁"可以听：relay 最多骗设备少信几台，那只是让服务不可用，而它本来就能做到。

**换 key**：

1. 在 relay 上运行 `rapp-relay rotate-key`，得到新的 key（显示一次）。旧 key 立刻不能入网。
2. 在手边的一台设备上填新 key。
3. 这台设备把新 key 发给它认识的其他设备（走端到端连接），它们再往下传。不在线的设备上线后从认识的设备那里拿到。

换 key 不影响已经认识的设备之间的连接（它们靠指纹）。

**丢了一台设备**：先吊销，再换 key。顺序不能反，否则它也会收到新 key。

## 8. relay 协议（`rapp-relay/2`）

每个请求开一条流：一行 JSON 请求，一行 JSON 回复。身份来自这条连接握手时出示的证书，请求里不带任何凭据（入网除外）。

设备发给 relay：

| 请求 | 谁发 | 内容 | 回复 |
|---|---|---|---|
| `enroll` | 没入网的设备 | `{"op":"enroll","join":"…"}` | `{"ok":true,"relay":{"version","features":[…]}}`；错误 `bad key`、`closed`、`limit` |
| `register` | 被控的一侧 | `{"op":"register","id":"123456789","lan":["192.168.1.5:22028"]}` | `{"ok":true,"id":"…"}`；错误 `id taken`、`not enrolled` |
| `connect` | 操作的一侧 | `{"op":"connect","id":"…"}` | `{"ok":true,"lan":[…],"public":"1.2.3.4:22028"}`；错误 `unknown id`、`offline`、`locked, retry in 12s`、`not enrolled` |
| `relay` | 操作的一侧 | `{"op":"relay","id":"…"}` | 成功时不回 JSON，直接对接；失败回 `unknown id`、`offline` |

relay 发给设备：

| 消息 | 内容 | 说明 |
|---|---|---|
| `incoming` | `{"op":"incoming","peer":"<对方的公网地址>","fp":"<对方的指纹>"}` | 设备回 `{"ok":true}` 并向 `peer` 打洞。`fp` 只供日志用，设备不拿它做判断 |
| `relayed` | `{"op":"relayed","peer":"…","fp":"…"}` | 这一行之后，这条流就是对方发来的字节。设备在上面当 TLS 服务端 |
| `revoked` | `{"op":"revoked","fps":["…"]}` | 设备连上时发一次，名单有变化时再发（§7.4） |
| `going_away` | `{"op":"going_away","after_ms":3000}` | relay 要重启。设备等一会儿再重连，间隔带随机量 |

任何请求都可能得到这个回复：

| 回复 | 说明 |
|---|---|
| `{"ok":false,"error":"redirect","relay":"主机:端口"}` | 第一版的 relay 不会发。设备要实现"照着去连那个地址，同样核对身份，最多跳一次"。这是给多节点留的口子（§14） |

协议里没有密码，没有令牌，没有设备名。

`connect` 的限速：按发起方的指纹和来源地址、按目标 ID 分别计数，防止有人拿 relay 当跳板去敲别的设备的门。

## 9. 可靠性（R7）

### 9.1 进程和状态

- 一个进程，一个 UDP 端口，没有外部依赖（不要数据库、不要别的服务）。
- **持久的状态**都在一个数据卷里（清单见 §10）。写入时先写临时文件、落盘、再改名。
- **内存里的状态**：谁在线、限速计数。重启就清空，设备重连后自动恢复。
- 时间只用于日志的时间戳；任何判断都不依赖时钟准不准。

### 9.2 上限和限速

全部可配（§10）。下面是默认值（我定的；实测后可以调）：

| 项 | 默认 | 防什么 |
|---|---|---|
| QUIC 地址验证 | 一直开 | 伪造来源地址，拿 relay 放大流量打别人 |
| 没出示证书 | 握手拒绝 | T2 |
| 没入网的连接 | 只能入网；10 秒没动静就断；每个来源地址每分钟 10 次 | 试 key |
| 入网失败、`connect` 失败 | 连续 5 次以后，第 n 次失败要等 `min(2^(n-5), 300)` 秒 | 同上；拿 relay 当跳板 |
| 每个来源地址的连接数 | 16 | 占满连接 |
| 总连接数 | 4096 | 占满内存 |
| 每条连接的并发流 | 128 | 占满内存 |
| 每台设备同时被中继的流 | 32 | 同上 |
| 一行请求的长度 | 8 KiB | 同上 |
| 入网设备数 | 1024 | key 泄露后被灌满 |
| 中继的带宽 | 不限（可以按每条流、按总量设上限） | SaaS 时按租户限 |

### 9.3 重启和升级

- 收到停止信号：不再接新连接，给所有设备发 `going_away`，然后退出。
- 设备的重连：1 秒起，翻倍到 60 秒，每次加随机量，避免设备多了同时涌回来。
- 单节点时，正在中继的会话会断，设备自己重连接上。目标：relay 重启后 5 秒内设备重新在线。
- relay 重启不影响局域网和直连的会话：它们不经过 relay。

### 9.4 性能要求（R4）

这几条是验收条件。基线是现在的 relay 在同一台机器、同一条线路上的数字（`scripts/benchmark-linux-session.py`、`scripts/test-linux-session-latency.py`、README 的实测码率）。

| 量什么 | 要求 |
|---|---|
| 经中继的会话，画面延迟的中位数 | 比基线多不超过 1 毫秒 |
| 经中继的会话，同样画面下的码率和帧率 | 不低于基线的 95% |
| 经中继打开一个 app 的时间 | 比基线多不超过一次两台设备之间（经 relay）的往返 |
| relay 每中继 1 Mbps 占的处理器 | 不高于基线的 105% |
| relay 空闲时的内存（100 台设备在线） | 50 MB 以内 |
| 直连和局域网的会话 | 和基线没有可测的差别 |

我的估计是都能过：会话期间多出来的只是两头各一次对称加密，现在的处理器每秒能做上千兆字节，而远程会话是每秒几兆比特。这是估计，没有测过。

## 10. 配置（R13）

原则：**什么都不配也能跑。** 启动容器、挂上数据卷、放行端口，relay 就能用。

### 10.1 relay 的配置项

来源有三个，后面的盖过前面的：默认值 → 数据卷里的 `config.json`（可以没有）→ 环境变量。改了要重启才生效。

| 配置项 | 环境变量 | 默认 | 意思 |
|---|---|---|---|
| `listen` | `RAPP_RELAY_LISTEN` | `0.0.0.0:22026` | 监听的地址和端口 |
| `enroll` | `RAPP_RELAY_ENROLL` | `open` | `open` 接受新设备入网；`closed` 不接受 |
| `log` | `RAPP_RELAY_LOG` | `info` | 运行日志的级别：`info` 或 `debug` |
| `audit.keep_days` | `RAPP_RELAY_AUDIT_KEEP_DAYS` | `180` | 审计日志留多少天 |
| `audit.max_mb` | `RAPP_RELAY_AUDIT_MAX_MB` | `256` | 审计日志总共最多占多少 |
| `audit.required` | `RAPP_RELAY_AUDIT_REQUIRED` | `false` | 审计写不进去时，是否拒绝新的入网和牵线 |
| `metrics` | `RAPP_RELAY_METRICS` | 关 | 指标接口的本机地址，如 `127.0.0.1:9116` |
| `limits.*` | `RAPP_RELAY_LIMIT_*` | 见 §9.2 | §9.2 表里的每一行各一项 |

规则（我定的）：

- 配置里出现不认识的项，或者值不合法：relay 拒绝启动，并说明是哪一项。写错一个字不会被悄悄忽略。
- 启动时把生效的配置记一行，运行日志和审计日志各一份。
- 没有任何机密需要通过配置传给 relay。
- 命令行参数只有 `--data`（数据目录，默认 `/data`）和 §6.5 的子命令。

### 10.2 数据卷里有什么

| 文件 | 是什么 | 丢了会怎样 |
|---|---|---|
| `relay.key`、`relay.crt` | relay 自己的密钥和证书 | 所有设备上的 key 都对不上了，要换 key |
| `join` | 入网口令的哈希 | 没法入网新设备，换 key 即可；已入网的不受影响 |
| `devices.json` | 登记簿：指纹、ID、租户、入网时间、是否吊销 | 设备要重新入网；ID 的归属丢失 |
| `config.json` | 配置（可以没有） | 回到默认值 |
| `audit/` | 审计日志 | 审计记录没了，不影响运行 |
| `admin.sock` | 管理命令用的套接字 | 重启后重建 |

文件 0600，目录 0700。说明里写明：备份整个数据卷；最要紧的是 `relay.key` 和 `devices.json`。

### 10.3 设备这一侧的配置

都在设备数据目录的 `local/` 下，不进 git（数据目录规格 D4）。

| 文件 | 内容 |
|---|---|
| `service.json` | `relay`（接入点）、`key`、`id`、`name`、`accept_new`（接受新设备，默认开） |
| `hosts.json` | 主机列表。每台主机：ID、名字、局域网地址、对方的指纹 |
| `paired.json` | 认识的设备：指纹、对方自报的名字、认识的时间 |
| `device.key`、`device.crt` | 本机的设备密钥和证书 |

没有 `secret`，没有 `password`。界面上用户要填的只有接入点和 key；加主机时只填 ID。

## 11. 日志和审计（R12、R13）

日志分两种，用处不同，放的地方也不同。

| | 运行日志 | 审计日志 |
|---|---|---|
| 给谁看 | 排查问题的人 | 事后要查"谁在什么时候做了什么"的人 |
| 记什么 | 出错、状态变化、每 5 分钟一行统计 | 每一次和准入、身份、连接有关的动作，成功和失败都记 |
| 写到哪里 | 标准错误，由 Docker 收集 | 数据卷里的文件：`audit/2026-11-13.jsonl`，一天一个 |
| 换容器以后 | 没了（Docker 的日志跟着容器走） | 还在 |
| 保留多久 | compose 示例里设 5 个文件、每个 10 MB | 默认 180 天，总量不超过 256 MB，先删最旧的 |
| 设备怎么标识 | 指纹的前 8 位 | 完整的指纹 |

### 11.1 审计日志

格式：一行一条 JSON，只追加，权限 0600。每条都有时间（UTC，精确到毫秒）、事件名、租户、结果；和设备有关的带完整指纹、ID、来源地址。

| 事件 | 什么时候 | 带什么 |
|---|---|---|
| `relay_start`、`relay_stop` | 启动、停止 | 版本、生效的配置、停止的原因 |
| `enroll` | 一次入网尝试 | 指纹、来源地址、结果（`ok`、`bad key`、`closed`、`limit`） |
| `register` | 设备登记 | 指纹、ID、来源地址、结果（`new`、`ok`、`replaced`、`id taken`） |
| `connect` | 请求牵线 | 发起方的指纹和地址、目标 ID、结果 |
| `relayed` | 一条中继流结束 | 发起方指纹、目标 ID、持续多久、两个方向各多少字节 |
| `lockout`、`limit` | 被限速、撞到上限 | 是哪一项、针对谁 |
| `key`、`rotate_key`、`revoke`、`unbind`、`enroll_open`、`enroll_close` | 管理动作 | 执行的是哪条命令、对象是谁 |
| `audit_prune` | 删掉了过期的审计文件 | 删了哪几天的 |

规则（我定的）：

- **永远不记**：key、入网口令、任何私钥、流里的任何内容。
- **在线探测不逐条记。** 设备定时探测对方在不在，经中继时每次都是一条很短的流。它们按"发起方和目标"每小时合并成一行。真正的会话每条都记。5 秒以内、8 KiB 以内的算探测。
- **准入和管理类的事件立刻落盘**；其余的最多攒 1 秒。
- **审计写不进去时（比如磁盘满）**：默认继续服务，同时在运行日志里报错。`audit.required` 设成 `true` 时，改为拒绝新的入网和牵线。
- **审计日志同时写一份到标准错误**，带一个标记。用 Docker 的日志驱动就能把它实时送到另一台机器。要防"拿到 relay 的人改日志"（T3），只有这一个办法：日志在他拿到之前已经送走了。本机的文件防不住他，所以不做哈希链之类的东西。

审计日志能回答的：某台设备什么时候、从哪个地址入网；某个 ID 被谁连过、什么时候、多久、多少字节；有没有人在试 key；谁在什么时候吊销了哪台设备、换了 key。

不能回答的：连上以后做了什么。那在被控端自己的访问记录里。

### 11.2 设备这一侧的记录

被控端的访问记录（可观测性规格）里新增这些事件：认识了一台新设备（成功、失败及原因，对方的指纹、自报的名字、来源地址、走的哪条路）；因为吊销名单取消了认识；"接受新设备"被打开或关上；对方的密钥变了；relay 的身份对不上；key 被换了（只记发生了，不记 key）。

### 11.3 运行日志、指标、健康检查

- 运行日志：结构化的一行一条，格式沿用可观测性规格。每 5 分钟一行统计：在线设备数、正在中继的流数、中继的字节数、握手失败数、被限速的次数。
- 指标接口：可选，默认关。开了以后只在本机地址上提供 Prometheus 格式的数字，不对公网开。
- 健康检查：`rapp-relay check` 对自己做一次真实的握手，成功退出 0。

## 12. 发布和部署（R9）

**发布物只有一个：Docker 镜像。**

| 项 | 定法 |
|---|---|
| 基础镜像 | Alpine Linux（用户在 U73 确认）。版本固定到具体的小版本和摘要 |
| 镜像里有什么 | Alpine 的基础层，加 `rapp-relay` 一个程序。不装任何别的包 |
| 架构 | 同一个镜像标签下带 x86_64 和 arm64 两种，Docker 自动取对的那个 |
| 怎么构建 | 多阶段：第一阶段编译，第二阶段只把程序拷进干净的 Alpine |
| 程序怎么压小 | 去掉符号；全程序优化；单编译单元；出错直接中止；只开用到的库功能。不用"按体积优化"的编译档位：数据路径要快（R4），体积让位于速度 |
| 大小目标 | 镜像压缩后 10 MB 以内。这是估计，第一次构建出来后把实际数字写进发布说明 |
| 运行身份 | 非 root 的固定用户；根文件系统只读；去掉全部特权；禁止提权 |
| 数据 | 只挂一个卷 `/data`（§10.2） |
| 网络 | 主机网络模式。relay 靠"看到的对端地址"做限速和打洞，别的网络模式可能把地址改写掉。**要先实测** |
| 健康检查 | 镜像自带，定期跑 `rapp-relay check` |
| 升级 | `docker compose pull && docker compose up -d` |
| 镜像标签 | 每个版本一个固定标签，另有跟随小版本的标签。compose 示例里写固定标签 |
| 发布到哪里 | GitHub 的镜像仓库（`ghcr.io/wizlijun/rapp-relay`）。我按代码仓库的位置填的，可以改 |

随镜像提供一份 `docker-compose.yml` 示例和几行说明（放行端口；备份 `/data`；怎么把审计日志送到别的机器）。

relay 只能跑在 Linux 主机上：Mac 和 Windows 上的 Docker 跑在虚拟机里，容器看不到真实的来源地址。开发和测试时可以直接运行编译出来的程序，那不是发布物。

## 13. 重构怎么落地（R14）

### 13.1 代码

- **relay 是新写的**：一个新的 crate，按 §5.4 划分模块。它不含旧协议的任何代码，不读旧的 `relay.json`。写完以后，现有的 `rust/relay` 整个删掉。
- **设备这一侧的连接层也是新写的**：设备密钥、连 relay、端到端握手、互信、选路，放在一个独立的模块里，接口是"给我一条到某个 ID 的、已经验证过对方的流"。上面的业务代码（列 app、打开 app、传文件）改成只调这个接口。
- 现有的连接代码（`rapp-net` 里的 QUIC 部分、service 的 `relay_link` 和 `peer` 的认证部分、hub 的 `link`）在迁移期间原样留着，只用来连旧 relay 和旧版本的设备；迁移结束后整块删掉。新旧两套不互相调用。

### 13.2 迁移：新旧两个 relay 并行一段时间

> **2026-11-14 更新**：用户决定不做迁移，旧 relay 直接删掉，新 relay 改名为 `rapp-relay`（见 `2026-11-14-drop-relay1-design.md`）。下面这一节作废，留作记录。

因为新 relay 不认旧协议，迁移靠的是两个 relay 同时跑，设备的过渡版本两边都会连。

| 步 | 做什么 | 做完以后 | 用户要做的 |
|---|---|---|---|
| 〇 | 在 VPS 上启动新 relay 的容器，用另一个端口（两个 relay 默认都是 22026，不能共用）。运行 `rapp-relay key` 拿到 key。旧 relay 不动 | 两个 relay 同时在跑 | 启动容器；放行新端口；存好 key |
| 一 | 设备升级到过渡版本：里面有新旧两套连接层。在手边的一台设备上填新的接入点和 key。它每经旧的路连上一台过渡版本的设备，就在端到端加密的连接里把接入点和 key 发过去（对方凭现有的密码确认它是老相识）。拿到 key 的设备接入新 relay，之后互相按 §7 认识 | key 传遍了所有连得上的设备。已经互相认识的设备之间只走新的路 | 升级各设备；在一台设备上填一次。界面上每台主机显示"新"或"旧" |
| 二 | 所有主机都显示"新"以后，停掉旧 relay | 只剩新 relay。R1–R3 成立 | 停掉旧服务，关掉旧端口 |
| 三 | 设备升级到去掉旧连接层的版本。密码从界面和配置里消失 | 代码里不再有不校验证书、明文密码、令牌 | 升级各设备 |

规则：

- 两台设备一旦按新方式互相认识过，以后**永不退回旧的路**。否则中间人可以假装对面是旧版本，把连接骗回不加密的路上。
- 第一步里"凭现有的密码收下 key"只在这台设备还没有 key 时才接受，只接受一次。
- 升级时不在线的设备：上线后仍然连着旧 relay，手边的设备下次连上它时把 key 发过去。所以旧 relay 要等所有主机都显示"新"才能停。

**迁移期间的安全，要说清楚**：现在的系统完全信任旧 relay（它看得到内容，也知道密码）。如果旧 relay 在迁移期间已经被人拿到并且在主动动手脚，他能在第一步里截到 key。迁移不能把一个已经失守的系统变安全；它保证的是迁移完成以后的事。不放心的话，第三步之后换一次 key。

## 14. 往 SaaS 扩（R8；只留位置，不实现）

第一版每一处都按"将来有很多租户、很多节点"来定数据的形状，但只实现单租户、单节点。

| 方面 | 第一版 | SaaS 时 | 第一版为它留了什么 |
|---|---|---|---|
| 租户 | 只有一个，叫 `default` | 一个账号一个租户 | 每条设备记录、每条审计记录都带租户；牵线和接流只在同一个租户里做 |
| 准入 | 一个 key | 账号签发 key，有期限，可以只用一次 | 准入模块是一个接口：输入凭据，输出"哪个租户，行不行" |
| relay 的身份 | key 里带指纹 | 真实域名的证书，设备按域名校验 | 设备核对 relay 身份的那一步是一个接口 |
| 存储 | 文件 | 数据库 | 登记簿是一个接口 |
| 多节点、多地区 | 一个节点 | 设备登记在最近的节点；有一份"哪个 ID 在哪个节点"的目录 | 在线表是一个接口；`redirect` 回复，设备第一版就会跟着走 |
| 计量和配额 | 每条中继流记字节数 | 按租户累计，超了限速或拒绝 | 限额模块按租户取值；审计里有每条流的字节数 |
| 传输 | QUIC（UDP） | 加一个 TCP 443 上的入口，给封了 UDP 的网络用 | L2 是"流上的一行行 JSON"，L3 是"任何字节流上的 TLS"，都不挑传输 |
| 管理 | 本机命令 | 网页控制台、接口 | 管理模块是一个接口，命令不直接改文件 |
| 观测和审计 | 运行日志、审计日志、可选的指标 | 集中的监控；按租户导出审计记录 | 指标和审计事件的名字从第一版起固定 |

有一条性质对 SaaS 特别有用：relay 手里没有内容、没有 key。将来由别人托管 relay，托管的人既看不到用户的数据，也进不了用户的设备。

## 15. 边界：数据服务和外部小屏

- **数据服务**（PD14）：便签、数值这类服务跑在某台设备上。别的设备要读，就是在已有的设备连接上开一条流，请对方"接到本机的某个服务"。这由关注数据那份规格（路线图 B2）来定。relay 不参与，不用改。
- **外部小屏**（U60、U61）：它不是 rapp 设备，说不了 QUIC。要让它经 relay 读数据，将来需要一个 TCP 上的入口（§14 的"传输"一行），以及它自己的一把设备密钥和 key，像别的设备一样入网、互信。
  - 没有核对的：小屏的固件能不能做 TLS 1.3 和这些握手。做不到的话，小屏只能在局域网里直接读那台设备。
  - 这一项排在 relay 第一版之后，单独设计。

读的时候顺便看一眼，不同意的告诉我。

1. 做法选甲（§3）。

## 20. 要你确认的

1. **key 等于所有设备的总钥匙**（§4.2 的 T5）。这是"有了 key 就互相信任"的后果。你清楚这一点就行。
2. **key 只在生成时显示一次**（§6.2）。这是为了让 relay 手里没有 key。之后要看，到已接入的设备的设置里看。
3. **两个开关要不要默认关上**（§7.3）。默认开：加设备最省事，但 key 泄露就等于失守。默认关：每次加设备要先打开，但平时锁死。我写的是默认开。
4. **迁移时新旧两个 relay 并行**（§13.2），VPS 上要多放行一个端口，直到旧的停掉。这是"新 relay 不含旧代码"的代价。
5. **§12 的主机网络模式要先实测。** 我还没有测。

## 21. 留给实现计划的

- 各请求的精确字段、错误文本的全集。
- 互信证明的精确算法：单向推导用的标签、握手导出值的标签和长度、消息认证码里各字段的顺序。动手前先做一个小验证：两个进程互信成功；中间插一个转发的进程时失败；key 不同时失败。
- 设备收到别人传来的 key 时怎么判断它是不是更新的。我的提议：拿它的入网口令去问 relay 认不认。
- 经中继的小请求（比如定时的在线探测）每次都握一次手是否太重。可以用 TLS 的会话恢复，也可以直接用 `connect` 的回复判断在线。量了再定。
- 管理套接字的格式；登记簿文件的格式和版本号。
- 新 relay 在迁移期间用哪个端口。
- 三项先做的验证：互信证明；主机网络模式下 relay 看到的来源地址；性能基线。

## 22. 测试要求

- **冒充 relay**：写一个恶意的 relay，它把两头的流各自接到自己身上再转发。要求：不认识的设备之间互信失败；认识的设备之间握手失败；它的日志和内存里搜不到 key、信任口令和任何会话内容。
- **机密全量检查**：所有测试结束后，relay 的数据卷、各处的运行日志和审计日志里搜不到 key 的"根"和信任口令。
- **key**：填错前一半（relay 身份对不上）和后一半（入网被拒）各是什么表现；两台设备 key 不同时互相不认；`rapp-relay key` 第二次运行不再显示；关闭入网以后对的 key 也入不了网；关闭"接受新设备"以后有 key 的新设备也连不上。
- **吊销和换 key**：吊销以后其余设备不再认它；换 key 以后新 key 传到了认识的设备，旧 key 入不了网；先换 key 后吊销时，被吊销的设备拿不到再下一个 key。
- **准入**：不出示证书、没入网、被吊销，各自被挡在哪一步。
- **限速和上限**：§9.2 每一行至少一个测试。
- **审计**：§11.1 事件表的每一行都能在审计文件里找到；换一个容器以后审计文件还在；过期的被删并留下 `audit_prune`；写不进去时两种配置各自的表现。
- **配置**：不给任何配置能启动；三层的覆盖顺序；写错一项拒绝启动并指出是哪一项。
- **重启**：relay 重启后，设备在 5 秒内重新在线，中继的会话自己接上。
- **`redirect`**：用一个会发 `redirect` 的假 relay 测设备的行为。
- **迁移**：§13.2 每一步一个测试，包括"认识过的设备不退回旧的路"和"升级时不在线的设备后来能拿到 key"。
- **请求解析的模糊测试**；**压力和久跑**（若干台假设备、若干条中继流，24 小时，内存不涨）。
- **Docker**：容器里 relay 看到的对端地址是真实的；非 root、只读根文件系统下全部功能正常；健康检查能发现 relay 不响应；`docker stop` 时设备收到 `going_away`；镜像大小在目标以内；两种架构各跑一遍冒烟测试。
- **性能**：§9.4 的表。
