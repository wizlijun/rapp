# rapp 规格拆分和阶段（内置插件、数据服务、relay）

日期：2026-11-13。状态：**我的提议，待用户确认拆法和顺序**。本文不改代码。

用户的要求（反馈文档 U70）："生成对应的产品决策文件，并把确定性的大块能力抽象合并为不同 spec 分阶段去实现。"

- 决定本身在 `2026-11-13-rapp-product-decisions.md`（下称"决策文件"），编号 PD1–PD15。
- 本文只做两件事：把这些决定归并成几份规格；给这几份规格排先后。
- 本文不是规格。每份规格轮到它的时候再单独写、单独请用户确认，然后才写实现计划。下面每份只写到"范围、已定的、动笔前要先定的、依赖"。

## 1. 怎么归并的

七个插件不是七份规格。按"底下是不是同一块能力"归并，得到七份：

| 规格 | 一句话 | 合并了什么 | 来自 |
|---|---|---|---|
| A1 数据目录 | 所有数据放在 `~/rapp`，文字用 git 管 | 配置集中、git 同步 | PD13 |
| A2 relay 通道 | relay 只让认证过的两方连上，搬运它解不开的数据 | relay 看不到内容、统一认证、与业务无关；数据服务和小屏经 relay 接入 | PD15、PD14 的中转部分 |
| B1 全局搜索 | 一个入口搜到 rapp 的核心对象并启动；别的知识库通过接口接进来 | 搜索插件 | PD9 |
| B2 关注数据 | 便签、提醒、数值是同一类数据，由一个数据服务提供，在几个地方显示 | 便签、提醒、资源监控三个插件，加数据服务的本机和自建服务器两种部署 | PD7、PD8、PD12、PD14、PD5 |
| C1 书写 | 备忘存在 vault 里；编辑器是可换的插件；沉浸式书写是特色 | 备忘插件、Sumi、语音输入 | PD6 |
| C2 专注 | 写作和 AI 对话时自动进入的界面状态：不打扰，只显示当前项目的东西 | 专注插件；工作台设想里"切换项目就切换工具"的那部分 | PD10、PD1 |
| D1 记录 | 画面转成的文字同步；截图留本机、定期删除 | 快照插件 | PD11 |

为什么便签、提醒、资源监控并成一份（B2）：

- 它们的数据现在就在同一份里。用户的 xiaobucubic 显示服务用一个接口同时给出订阅用量、流量和便签消息。
- 用户说了它们之间的关系："需要你"是提醒的子集（U66）；提醒可以做在便签里（U54）；资源的状态在便签里用颜色表示（U69）。分成三份规格，这些关系就要在三处各写一遍。
- 它们共用同一个问题：数据服务跑在哪里（PD14）。

为什么 relay 单独一份（A2），不并进 B2：用户说 relay 要与业务无关（U64）。它不该知道便签的存在。

## 2. 阶段

顺序是按依赖排的。和用户之前定的大顺序（U34：先基础交互和性能，再记录，最后助理）对得上：A、B、C 属于"基础"，D 是"记录"，E 是"助理"。

| 阶段 | 规格 | 为什么排在这里 |
|---|---|---|
| A 地基 | A1 数据目录、A2 relay 通道 | 后面的同步都靠 A1；跨网络的数据服务、小屏都靠 A2。A2 同时补上现有远程会话"relay 看得到内容"的问题 |
| B 自己就能做的 | B1 全局搜索、B2 关注数据 | 不依赖别的应用。B1 只用到 rapp 已有的对象。B2 先做本机的数据服务，就不用等 A2 |
| C 接已有工具 | C1 书写、C2 专注 | C1 要等 note.md 那边把 Sumi 独立出来。C2 要用到 B2 的提醒（专注时攒着）和 C1 的书写（进入时自动专注） |
| D 记录 | D1 记录 | 就是沟通机制设计的阶段二，本来就排在基础之后 |
| E 助理 | 不单独成规格 | 就是沟通机制设计的阶段三。前面各份规格里留给助理的位置见 §4 |

同一个阶段里的两份互不依赖，可以分开做。

A1 已经有用户确认过的规格和实现计划（都是另一个会话写的），还没有开始实现。其余六份都还没有规格。

## 3. 每份规格

### A1 数据目录

- 规格已有：`2026-11-13-rapp-data-dir-design.md`，状态"已确认"。实现计划也已有：`docs/superpowers/plans/2026-11-13-rapp-data-dir.md`（2026-11-13 核对时一步都还没有勾，代码里的路径还是旧的）。两份都是另一个会话写的，这一份不用再做设计。
- 这一轮新增、要补进那份规格的：用户说每个终端都要装 git（PD13）。那份规格现在写的是"没装 git 就不做版本记录，只提示"。两者怎么统一，待用户定。
- 动笔前要先定的：平板上没有系统自带的 git 怎么办。
- 依赖：无。

### A2 relay 通道

**规格已按用户后来的要求整篇重写：`2026-11-13-rapp-relay-design.md`（U71–U79），用户已确认。下一步是写实现计划。** 和下面这段写规格之前的范围相比，变了的有：设备密码取消，一个 key 管接入和互信；只发 Docker 镜像；relay 和设备的连接层都新写；迁移用新旧两个 relay 并行。 下面是写规格之前列的范围，留作对照；"动笔前要先定的"三条在那份规格里的去向：第 1 条见它的 §6（用密码配对，用户不多一步），第 2 条见 §11（三步升级），第 3 条见 §10（小屏排在第一版之后，固件能力仍未核对）。

范围：

- 经 relay 的连接，加密在两头的设备之间建立，relay 只转发解不开的数据。
- 设备互相认得对方，不靠 relay 担保。relay 被攻破后，拿到它的人看不到内容，也冒充不了设备。
- relay 提供的是通用的通道。远程会话走它，数据服务也走它；relay 不为某种数据做专门功能。
- 外部小屏这类不是 rapp 设备的客户端，怎么经过统一认证接进来。

已定的：PD15 全部；PD14 里"relay 可以做中转""小屏接入 relay 的地址"。

方向认可的：首选设备之间直接用 TLS 1.3 互相验证，配对时记住对方证书的指纹（U65）。

动笔前要先定的：

1. 设备第一次怎么互相认识。
2. 已经配好的设备怎么过渡。
3. 小屏怎么注册；它的固件能不能自己解密。如果不能，小屏经 relay 这条路就得另想办法，或者小屏只在局域网里用。

要实测的：两头多加一层加密以后，远程会话的延迟和流畅度有没有变化。用户的前提是"不消耗额外资源、更流畅"。

依赖：无。

动到的已有文档：平台规格的 D8；relay 安全要求草稿（那份草稿可以并进这份规格）。

不包含：便签、提醒这些数据本身（在 B2）。

### B1 全局搜索

范围：

- 一个全局的搜索入口。
- rapp 自己搜：资源、应用（搜到就能启动）、全局剪贴板、全局文件。
- 一个接口，让别的知识库工具把它们的搜索结果交给 rapp 显示。第一个接进来的是 note.md 的 vault 搜索。

已定的：PD9 全部。

动笔前要先定的：

1. "资源"包括哪些。我的理解是设备、会话、app 窗口、项目。
2. 搜索入口放在界面哪里。
3. 接口的形式。note.md 现成有命令行和给 Agent 调用的工具接口两种。

依赖：无。vault 那部分结果只在配了 vault 的机器上有（U49），所以搜索必须在没有 vault 时照常工作。

不包含：vault 的索引和搜索本身（note.md 的事）。

### B2 关注数据（便签、提醒、数值）

范围：

- **一份数据规范**，描述三种东西：
  - 便签：少数最重要的大块记事。
  - 提醒：一个集合；"需要你"是其中一个特殊的优先级类别。
  - 数值：用户要关注的数（硬件、AI 订阅用量、流量……），每个数值属于某台主机或者全局。
- **一个数据服务**，按这份规范提供数据。可以跑在本机，也可以跑在用户自己的服务器上、rapp 配置它的地址。
- **几处显示**：
  - rapp 里的便签客户端：一个便签，里面切换多条。
  - 全局提醒区域：另开的一个地方。
  - 资源预览：每台主机上一份，全景里一份全局的。
  - 外部小屏：读同一个服务。
- 新的资源预览由 Agent 按规范生成。

已定的：PD7、PD8、PD12 全部；PD14 里本机和自建服务器两种部署；PD5（尽量减少提醒）。

动笔前要先定的：

1. 便签服务是搬进 rapp，还是 rapp 管着它启动和连接。
2. 便签和资源预览是一个东西的两个页面，还是两个插件共用一份数据。
3. 数值谁采集；Agent 生成的是采集、显示，还是两者。
4. 便签里的颜色守不守设计语言第 1 条。
5. 现有的"需要你"（会话上的标记）怎么并进提醒的数据里。

依赖：本机部署不依赖别的。服务在别处、要经 relay 时依赖 A2。任务状态在 NEXT 里管，rapp 只显示；没有 NEXT 时便签照常能用（PD3）。

动到的已有文档：主界面规格里"需要你"的数据来源；设计语言（如果便签要有自己的颜色规则）。

不包含：任务的状态管理（NEXT 的事，主界面规格的非目标"rapp 不做任务模型"不变）；助理对提醒的过滤（阶段 E）。

### C1 书写

范围：

- 备忘的文件存在 note.md 的 vault 里。
- vault 只在用户选的少数机器上；别的设备通过 rapp 的共享机制读写。
- 编辑器是一个可以换的插件。
- Sumi 独立成原生体验的书写模块，作为默认的全局备忘编辑器。沉浸式书写是 rapp 的特色能力。
- 语音输入：用户说的是"将来"，这份规格只留位置。

已定的：PD6 全部。

动笔前要先定的：

1. "系统提供的资源共享机制"具体是哪一种。
2. Sumi 独立出来由谁做、放在哪里。它现在是 note.md 的一个插件，带一个原生编辑器的桥接模块。
3. Sumi 是否也用在主界面的输入区。

依赖：note.md 那边把 Sumi 独立出来；A1（如果备忘的草稿要先落在 `~/rapp`）。

### C2 专注

范围：

- 专注是一种界面状态，不是一个页面。
- 进入写作、进入 AI 对话时自动进入。
- 专注时：不主动提醒；界面沉浸；只显示和当前项目相关的东西。
- 专注时攒下的提醒去提醒区域。

已定的：PD10 全部。

动笔前要先定的：

1. 界面要不要从以设备为先改成以项目为先（PD1）。"只显示当前项目的东西"至少要求每样东西都知道自己属于哪个项目。这是决策文件里牵动最大的一个待定项，建议在写这份规格之前单独定。
2. 专注时"需要你"还打不打断。
3. 怎么退出；能不能手动开关。

依赖：B2（提醒区域）；C1（书写）；现有的项目功能（S5）。

### D1 记录

范围：

- 画面转成文字；文字用 git 同步（放进 `~/rapp`）。
- 截图留在产生它的那台机器上，不同步，可以设置定期删除。

已定的：PD11 全部。

动笔前要先定的：

1. 同步的文字里可能带有屏幕上出现过的密码、密钥，同步前要不要过滤。数据目录规格对剪贴板有过同样的顾虑，做法是只存用户钉住的。
2. 现场快照要不要。要的话它是文字，直接进 `~/rapp`。
3. 截图默认多久删一次。

依赖：A1。

和已有文档的关系：这份不另写新规格，而是并进沟通机制设计（`2026-11-12-rapp-conversation-design.md`）的阶段二，改它的 §2.5、§2.6。那份文档还在"讨论中"。
