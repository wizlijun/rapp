## 1. 用户的问题（2026-11-25，原话）

> 另外，作为 claude app、chatgpt 等客户端应用。提问执行时，会有一些正在工作中的状态。是否有办法使用不侵入的方式取到。以确认能拿到当前客户端的等待状态。

> 例如当期会话中 chat 后面的 stop 按钮。 左边任务中的圆点标记等。

归纳（我的归纳）：对 GUI 客户端，想知道三种状态：在干活、做完了、在等人确认或回答。约束是不侵入。用户点了两个具体的标志：**当前会话输入区的停止按钮**，和**左边任务列表里每一行的圆点**。前一个只管正开着的那个会话；后一个一眼管所有任务，包括没打开的，对巡检更有用。

## 2. 和已有决定的关系

- **K2**（沟通机制设计 §0）：不 hook、不植入代码，只用官方发布的 app；看，只靠像人眼一样看画面；文字只从画面里识别。
- **§2.3**：rapp 分不清“说完了在等你”和“只是停了一下”，所以不猜，只标“未读”（有动静，然后安静 3 秒）。
- **§2.9**：提到 Screenpipe 优先读系统的辅助功能接口，rapp 按 K2 只从画面识别。
- **现状**：macOS 被控端已经在用辅助功能接口做别的事（`Sources/rapp-host/` 里的 `FocusReader`、`MenuBarReader`、`InputInjector`、`WindowResizer` 等），辅助功能权限本来就要了。Linux 被控端有 `rust/host-linux/src/accessibility.rs`。

GUI 客户端没有终端里 OSC 7501 那样“程序自己报状态”的通道。能用的是下面三类。

## 3. 三类办法

### A. 只看画面（完全守 K2）

两家客户端在生成时，发送按钮都会变成停止按钮，做完变回去。这是画面上最稳定的状态标志。

- 做法：app 配置里给这个 app 写“状态区”规则：窗口里哪一块、什么样子算什么状态。被控端手里是原始画面，在本机比对，不走网络。两块：
  - **输入区的按钮**（相对输入区定位）：是停止按钮就是当前会话在干活。
  - **侧栏每一行的标记**（相对侧栏定位）：按行取出“标题文字 + 标记的样子”，得到一张“任务 → 状态”的表。一个窗口里有很多任务，这张表才对得上“员工”的粒度。
- 等人确认：靠文字识别，在规则里写关键词（“允许”“Allow”这类按钮上的字）。这就是 app 配置第二版留着的“在等你的迹象”。**更正（2026-11-25）**：被控端现在没有文字识别（沟通机制设计里只有规划），R6 加上：用 Apple Vision 在本机识别，不上网，识别出的文字不写日志。
- 好处：不碰 app，和现在的原则一字不差。
- 代价：客户端改版，规则要跟着改；主题、缩放、语言都会影响。
- 看得到看不到（读了代码，2026-11-25 的 main）：rapp 的 app 会话先在当前屏幕上找这个 app 的窗口（`Sources/rapp-host/WindowCapture.swift:68`，只找屏幕上的），再按“这块屏幕、只含这个 app”截（`:146`），开会话时先把 app 切到前台（`:60`）。
  - **被别的窗口挡住不影响**：截的时候只含这个 app 的窗口。
  - **最小化了看不到**；**在别的桌面空间上**，开会话时找不到窗口（`:93` 报 `has no window on screen`）。会话开着时窗口被拖到别的空间会怎样，**未实测**。
- 管得到哪些：rapp 只截**开着会话的**窗口。“侧栏圆点一眼管所有任务”的前提是这个 app 开着 rapp 会话、侧栏没收起；没开会话的 app 什么都看不到。会话被暂停（v15，主控台没在看）时仍按每秒 1 帧截（`Sources/rapp-host/Server.swift:1178`），所以没在看的会话照样能认状态。
- 比现在好在哪：现在的“安静 3 秒”分不清“还在想”和“做完了”。有了停止按钮这个标志，“在干活”期间不再误判未读，做完的那一刻能立刻知道。

### B. 系统层面的信号（不碰 app 的内容）

| 信号 | 说明 | 可靠吗 |
|---|---|---|
| 系统通知 | ChatGPT 桌面端的设置里可以选回合结束的提醒什么时候显示，权限和提问的通知各有单独的开关。Claude 桌面端有“回复完成”的通知开关 | Claude 这边 2026 年有多份“开了也不弹”的问题报告；有一份说权限请求的通知是稳的、完成的不稳。macOS 没有公开接口读别的 app 的通知，只能看通知横幅的画面或读通知中心的界面 |
| 完成提示音 | 有报告说 Claude 桌面端每次回复完都会响一声，而且关不掉（issue 标题写的是 desktop app）。ChatGPT.app 的资源里带着 `codex-notification.wav`、`codex-classic.wav`，多半也会响，未实测 | 要抓这个 app 的声音；用户关了声音就没有 |
| Dock 角标 | 经辅助功能接口读 Dock 每一项的 `AXStatusLabel`，**实测读得到**（§5.1）；探查时两家都没有角标。`lsappinfo` 试了，读不出（返回空），不用它 | 两家什么时候打角标没有查到 |
| 进程的网络、CPU | 生成时有持续的网络流 | 太粗，后台同步也会有流量 |

这一类只能当辅助，不能当主要依据。它们都要求用户在 app 里把通知打开，这是 app 自己的设置，不是往里装东西。

### C. 辅助功能接口读界面结构（最准，但要你放宽 K2）

操作系统给读屏软件用的接口：macOS 的 Accessibility、Windows 的 UI Automation、Linux 的 AT-SPI。能直接问“窗口里有没有一个叫‘停止’的按钮”，不用认图。

- 业界把它当作不侵入的正路：OpenAI 自己的“Work with Apps”就是靠 macOS 的辅助功能接口读别的 app。
- 两家都是 Electron 做的（本机核对，2026-11-25：Claude.app 的 `Frameworks` 里有 Electron；ChatGPT.app 的 `Resources` 里有 `app.asar`，框架改名叫 `Codex Framework.framework`）。Electron 做的 app 默认不把网页部分的界面树暴露出来，要由辅助软件设一个 `AXManualAccessibility` 属性才打开。这是 Electron 文档写明给第三方辅助软件用的办法，不是 hook，也不注入代码；但它确实让 app 内部切换了一个模式，会多花一点性能。
- 有些 app 设了属性也不暴露，只有开着系统读屏才行。
- 和 K2 的出入：K2 写的是“只靠画面”。C 读的是界面结构，不是画面。要用它，得把 K2 放宽成“可以经系统的辅助功能接口读**状态**（有没有某个按钮），不读内容”。
  - 权限：rapp 已经在用同一个接口读焦点和菜单栏，不用新要权限。
  - 但不只是“多读一样东西”：设 `AXManualAccessibility` 是**写**一个属性，app 会因此切换模式。
  - 界面树一旦打开，里面的文字也读得到。“只读状态、不读内容”是 rapp 自己守的规矩，接口本身不分这两样。

### 不考虑的

远程调试端口（要改启动参数）、读 app 的本地数据库和日志（算逆向）、注入脚本。都违反 K2 和“不逆向”。

## 4. 我的建议（已采纳，2026-11-25）

**先做 A，B 里的通知当补充，C 留作可选。**

1. A 完全在现有原则之内。被控端已有画面和“哪些小块变了”；被控端现在没有文字识别，R6 加上（Vision，本机）。规格见 `2026-11-25-rapp-app-state-rules-design.md`。
2. 状态的词汇和终端那边对齐：`working`、`done`、`blocked`，主控台的灯和“需要你”用同一套（程序状态设计 §5.6、§5.7）。GUI 这边是推断出来的，界面上要和 CLI 自己报的区分开，比如标一个“推断”。
3. C 的准确度最高。如果 A 的规则维护起来太累，再请你决定要不要放宽 K2。

## 5. 没有验证的，建议先探查

1. Claude 桌面端、ChatGPT 桌面端当前版本：生成时停止按钮的位置和样子；浅色、深色、不同缩放下稳不稳。
2. 两家在“等权限”“在提问”时画面上的固定特征，文字识别认不认得出。
3. 辅助功能接口：两家设了 `AXManualAccessibility` 以后暴露多少，界面树里有没有停止按钮。默认状态两家都测了，窗口内容都读不到（§5.1）。设这个属性属于方案 C，C 留作可选，**这一条先不做**。ChatGPT 在 2026 年 7 月换了新的桌面端，旧的改叫 ChatGPT Classic；新版就是 Codex 应用换了名字（包标识 `com.openai.codex`），也是 Electron 做的（§3C）。
4. 两家的完成通知在你的机器上到底弹不弹。
5. **用 rapp 自己的会话**看一遍：开会话后侧栏在不在画面里、圆点认不认得出；会话开着时把窗口拖到别的桌面空间，画面还有没有（§3A）。
6. Dock 角标：两家什么时候打（§3B）。读法已经验过。

还没做的（1 的浅色深色和缩放、2、4、5、6）都要动桌面。按用户的话（§6），这些不单独做，在会话开着时不断确认（规则规格 §10.1）。

### 5.1 已经测了的（2026-11-25，在用户的 Mac 上，只读）

经用户批准，对 ChatGPT 桌面端（包标识 `com.openai.codex`，版本 26.1120.50957）做了一次只读探查，没有点击、没有输入。

**用的是 Claude 的电脑操作工具，不是 rapp 的被控端。** 下表的“取窗口画面”和“辅助功能接口”都是那个工具的结果。rapp 自己截图的方式不一样（§3A），所以“在别的桌面空间上也取得到”**不能**搬到 rapp 上；界面树读到 0 个元素这一条，rapp 的 `FocusReader` 多半也一样（Electron 默认不给界面树），但没用 rapp 验过。

| 项 | 结果 |
|---|---|
| 取窗口画面 | **取得到**，而且窗口当时在另一个桌面空间上、不在眼前，也取得到 |
| 左边任务列表的标记 | **画面上看得见**：当时有 7 行带绿色圆点，1 行带另一种圆形图标，其余没有标记。各种标记是什么意思要用户确认 |
| 停止按钮 | 当时没有任务在跑，没看到。输入区右下角是一个绿色的圆形按钮 |
| 辅助功能接口 | **默认什么都读不到**：界面树里可读的元素是 0 个 |
| Claude 桌面端 | 这次没法测：它不在这套工具允许操作的应用里。换成 rapp 的被控端，或者写个小 Swift 脚本，就能测（包标识 `com.anthropic.claudefordesktop`，版本 7.37095.0） |

两个结论：

1. **ChatGPT 桌面端的画面上有方案 A 要的标志**，包括用户点的侧栏圆点。rapp 截不截得到、截到的画面里侧栏在不在，要用 rapp 的会话再看（§5 第 5 条）。
2. **方案 C（辅助功能接口）对它不是开箱即用的**。要先设 `AXManualAccessibility` 让它把界面树暴露出来，设了以后暴露多少还没测。这进一步支持先做 A。

### 5.2 第二次探查（2026-11-25，同一台 Mac，只读）

用户说“全部做完，中途不用问我”之后做的。这次用一个只读的小 Swift 程序加系统自带的 `screencapture`：只列窗口、读界面树、读 Dock、截两家窗口的图，**不设任何属性、不点击、不输入**，也没有把 app 切到前台。截图留在本机临时目录，不进仓库；下面只记界面上的标志，不记会话内容。

| 项 | ChatGPT（26.1120.50957） | Claude（7.37095.0） |
|---|---|---|
| 当时在干活吗 | 没有任务在跑 | **有一个在跑** |
| 输入区右边的按钮 | 浅绿色圆底、向上箭头（发送；输入框空着，看着是不可点的样子） | **黑色实心方块**，就是停止按钮 |
| 对话里的进行标志 | — | 回复下面一行：三个橙色点，接动词和计时（`Weighing 6m 22s`），再接在哪台机器上跑 |
| 侧栏每一行 | 行尾绿色圆点，这次 9 行有 | **这次一行标记都没有**，在跑的那一行只是选中的底色 |
| 侧栏之外 | 最左边一列图标里，“主页”图标右上角有一个绿点，像是汇总 | 顶栏有一个电脑图标带绿点，像是连着的设备，和任务状态无关（我的猜测） |
| 界面树（辅助功能接口，默认状态） | 256 个元素，几乎全是菜单栏（菜单项 218）；窗口里只有外框和 3 个按钮，**网页内容一个都没有** | 282 个元素，同样几乎全是菜单栏；窗口里也没有网页内容 |
| Dock 角标（Dock 的界面树里读 `AXStatusLabel`） | 没有 | 没有 |

几点结论：

1. **Claude 桌面端“在干活”在画面上很好认**：停止按钮是一个实心方块，旁边还有带计时的进行行。方案 A 对它的“在干活”成立。
2. **Claude 侧栏的“圆点”这次没看到。** 用户后来说了（见 §6）：Claude 的会话在工作时侧栏是灰点。这次在跑的那一行正好是选中的，可能选中时不显示，也可能灰点太淡没看出来。在画面上认出灰点之前，Claude 只能管**当前打开的那个会话**。
3. ChatGPT 最左一列“主页”图标上的绿点：按用户说的绿点的意思，是“有任务有新结果”的汇总，比数侧栏还省事。
4. §5.1 里“界面树 0 个元素”说的应该是窗口内容那部分：菜单栏其实读得到，网页内容读不到。结论不变。
5. Dock 角标的读法验过了，能用；什么时候有角标还不知道。

## 6. 待用户定

已定（2026-11-25，用户原话“按你推荐的来”）：**先做 A，B 里的通知当补充，C 留作可选**。K2 不放宽；A 的规则维护起来太累时，再请用户定要不要放宽。
