## 1. 一句话和边界

**终端会话是 rapp 里的第二种会话：传的是字符网格，不是像素；被控端有一个与具体工具无关的终端层，tmux、自带的伪终端、SSH 上去的主机都只是它的后端。**

目标：

- 在主界面里像看 app 窗口一样看终端会话：列得出、点得开、状态一眼看得到。
- 在输入区写一段发过去；一个键打断。
- 换一种终端管理应用，或者换成 SSH 上去的主机，只加一个后端，协议、主界面都不动。

不做（第一版）：

- 派任务、编排、替用户回复。rapp 没有任务模型（主界面规格 §1 的非目标不变）；每一次发给对方的话都由用户触发（沟通机制 K3）。
- 判断“在等你”。照沟通机制 §2.3，状态用“未读”，不去猜。按 app 的“在等你”规则是 app 配置的第二版。
- 鼠标转发、终端里的图片、把记录写盘。
- Zellij、GNU screen、Herdr 的后端。只留接口。
- 读 CLI 自己的文件、日志，或者装 hook。只看终端上显示的字（§16 第 1 条）。

不能出现的结果（做成了也算失败）：

- rapp 接上去看的时候，改了别人正在用的那个终端的尺寸，或者把它挤掉。
- rapp 的服务重启或升级，杀掉了正在跑的 Agent。
- 网络差时越用越慢（流畅串流 G1）。
- relay 的代码里出现“终端”这个概念（relay 规格 §1）。
- 协议或主界面里出现 tmux 专有的东西，换后端时要跟着改。

## 2. 用户看到的

**设备面板**里，每台设备在 app 列表下面多一组“终端”。没有桌面的设备只有这一组。

```
bruce-mac                                    ● 在线 · 局域网
 App     Claude · Safari · Terminal …
 终端    ● work      claude   3 个面板   刚刚有输出      [打开]
         ○ build     cargo    1 个面板   12 分钟没动静   [打开]
         ● train @gpu1  python  1 个面板   未读            [打开]     ← 经 SSH 代管的主机
         [新开终端…]
```

**舞台**里是等宽字体画出来的字符网格，文字始终是清楚的。顶栏、窗口标签、输入区、流量标签都是现有的；一个面板一个标签。

```
┌ 顶栏 ── ●claude / bruce-mac · work ─ [1 claude] [2 logs] ───── [需要你 1] [▂ 0.3 KB/s ▾] ┐
│ ● Update(src/relay.rs)                                                                    │
│   ⎿ 12 additions, 3 removals                                                              │
│ Do you want to proceed?                                                                   │
│ ❯ 1. Yes   2. No                                                                          │
│                                                        [Esc] [⌃C] [Tab] [↑] [↓] [⏎] [输入] │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

**全景**里，终端会话那一块的缩略图位置直接显示最后几行文字。

和 app 会话的差别，用户能感觉到的三处：

- 被控端不用亮着屏幕、不用解锁，也不要“屏幕录制”“辅助功能”权限。
- 不会移动被控端的鼠标，不会把窗口切到最前；被控端的输入法不相干。
- 流量小一到两个量级（我的估计，未实测）。

## 3. 做法的选择

| 做法 | 是什么 | 取舍 |
|---|---|---|
| **A. 屏幕状态同步（选这个）** | 被控端拿到字符网格，发快照和变了的行；主控台画网格 | 只送最新状态，延迟不累积；被控端手里有文字，状态、缩略图、以后的记录都从这一份来；主控台不用解码器，纯 Flutter。代价：不转发鼠标，少数全屏程序的细节不如 B |
| B. 字节流终端 | 主控台嵌一个完整的终端仿真器，原始字节原样传 | 保真度最高。但每个字节都要按序送到，弱网下越积越多；断线后要补状态；被控端拿不到“屏幕上是什么字” |
| C. 继续走像素 | 被控端开一个终端 app 的窗口，用现有串流 | 今天就能用（内置配置里已经有“终端”一项）。但没有桌面的服务器做不了，这正是 TR1 |

选 A 的理由：它和流畅串流的规则一（发送端不排队）是同一个取向；TR4 定的 hurryvc 传的就是屏幕状态；TR7 要求的“后端可换”在 A 里最自然，因为后端只需要交出一张网格。

你还没有明确说选哪个。我按 A 写了这一稿；要换，告诉我。

## 4. 结构：终端层

新增一个 crate `rust/term`（包名 `rapp-term`），既是库也是一个可执行文件。分四层，上层只依赖下层：

```
┌ 对外：worker（给 rapp-service 用的命令行和线协议，§5、§6）                  ┐
├ 核心：会话表、网格、快照和行增量、未读、限速、“只留最新”                   │  与工具无关
├ 后端：tmux │ 自带伪终端 │ （以后：Zellij、screen、Herdr）                  │  每种工具一个
└ 执行器：本机进程 │ SSH 到某台主机                                          ┘  命令在哪里跑
```

**后端接口**（示意，签名在实现计划里定）：

```rust
pub trait Backend: Send + Sync {
    fn caps(&self) -> Caps;                                   // 能不能新开、结束、改尺寸、翻历史
    async fn list(&self) -> Result<Vec<SessionInfo>>;         // 会话、面板、当前命令、最后输出时间
    async fn watch(&self, pane: &PaneId) -> Result<Watch>;    // “脏了”的通知 + 取当前网格
    async fn input(&self, pane: &PaneId, input: Input) -> Result<()>;   // 一段文字（粘贴）或按键
    async fn history(&self, pane: &PaneId, before: u64, lines: u32) -> Result<Vec<Line>>;
    async fn create(&self, name: &str, command: &[String]) -> Result<SessionInfo>;      // 可选
}
```

后端只交出四样东西：会话列表、网格、输入的入口、历史。核心拿到网格以后的事（比较、限速、发给谁、未读）后端不管。

**执行器**把“在哪里跑命令”从后端里拆出来：

```rust
pub trait Runner: Send + Sync {
    async fn spawn(&self, program: &str, args: &[String]) -> Result<Child>;   // 一个带标准输入输出的进程
}
// Local：本机起进程。Ssh { dest }：`ssh <dest> <program> <args…>`。
```

tmux 后端只通过执行器起进程，所以“本机的 tmux”和“SSH 上去的 tmux”是同一份后端代码，只换执行器（§8）。这就是 TR7 和 TR8 落在代码里的样子。

**会话的名字**【我定的】：终端会话用一个以 `term:` 开头的 app 标识，格式 `term:<后端>[@<主机>]:<会话名>`。例：`term:tmux:work`、`term:tmux@gpu1:train`、`term:pty:claude-1`。
这样现有按（设备, app）存的东西都不用改格式：`workspace.json` 的常用和项目、hub 的会话表、S3 的重连。

## 5. 接进现有组件

| 组件 | 现在 | 要加的 |
|---|---|---|
| `rapp-relay`（新旧都是） | 只搬流 | 不改。终端只是设备之间的又一条流（relay 规格 §5.1、§15） |
| `rapp-service`（`rust/service`） | 设备请求只有 `list_apps`、`ping`、`open`（`rust/net/src/msg.rs`）；每个 app 拉起一个 `rapp-host` | 新请求 `list_terms`、`watch_terms`；`open` 的 app 以 `term:` 开头时接到 `rapp-term` worker，不找 `rapp-host`。机器上没有 `rapp-host`（无桌面的 Linux）时 `list_apps` 回空表，不算错 |
| worker | `rapp-host serve --app … --json` | `rapp-term serve --bind 127.0.0.1 --port 0 --token-env RAPP_TOKEN --json`，守平台规格 §5 的通用约定（JSON 行事件、stdin 关了就退出、退出码）。一台设备一个，不是一个会话一个 |
| `rapp-hub`（`rust/hub`） | 命令 `apps`、`open`、`close`… | 新命令 `terms`（列一台设备的终端会话）；每台在线设备挂一条 `watch_terms`，把变化作为事件给 GUI。`open` 带 `embed:true` 的那条路原样复用 |
| GUI（`gui/lib/embed`） | `SessionPort` 抽象；macOS 由 runner 解码，Linux 由 `rapp-session` 解码 | 一个纯 Dart 的 `TermSessionPort`：连 hub 给的本机端口，说 §6 的线协议，发出现有的 `SessionEvent`（窗口表、流量、断开）。一个 `TermStage` 控件画网格。不需要原生代码 |
| 设备之间的连接 | 现在是 `rapp/1`；relay 规格定了新的连接层，计划还没写 | 不依赖哪一个。终端请求是 relay 规格里说的 L4 设备请求，连接层换了它不用改 |

因为主控台这一侧不需要解码器，终端会话在 macOS、Linux、Windows 的主控台上是同一份代码；以后的 iPad、Android 主控台也是。

**顺带的一件事**：Linux 和 Windows 的被控端现在都还没有（README：“Linux 被控端仍未实现”）。终端会话不需要采集窗口，所以它会是这两个系统上最先能用的被控能力。

## 6. 线协议（`open` 之后的那条流）

沿用平台规格 §2.1 的约定：JSON 行，UTF-8，一行不超过 64 KiB。消息名和字段在实现计划里定；这里定有哪几种、守什么规则。

| 方向 | 消息 | 内容 |
|---|---|---|
| A→B | 开场 | 协议版本、后端名、能力（能否新开、改尺寸、翻历史） |
| A→B | 面板表 | 这个会话的面板：编号、标题、当前命令、行列数、是否已退出。对应主界面的窗口标签 |
| A→B | 屏幕 | 某个面板的整屏或只有变了的行；每行是若干段“文字 + 前景 + 背景 + 粗体等”；光标位置；版本号。一屏太大就分几条 |
| A→B | 历史 | 应答“往上翻”，一批纯文字行 |
| A→B | 已粘贴 | 应答一段文字：成功或原因。输入区据此清空或保留草稿（和 app 会话的 `pasted` 一样） |
| B→A | 看哪个 | 当前标签是哪个面板；没有就只收面板表 |
| B→A | 确认 | 收到并画完了哪个版本 |
| B→A | 文字 | 一段文字，作为一次粘贴送进去；可带“之后补一个回车” |
| B→A | 按键 | 具名的键（Esc、Tab、方向键、回车、⌃C…）或原始字节 |
| B→A | 往上翻 | 要哪个位置之前的多少行 |
| B→A | 改尺寸 | 只在用户明确要求时发 |

**规则（对应流畅串流规则一）**：A 对每个面板只留最新的一张网格。上一条“屏幕”没被确认之前不发下一条；确认到了，发的是“B 已确认的那一版”和“现在”之间的差。网络慢时表现为刷新变慢，但每次都是最新的，不会越落越远。

**设备级的监视流**（`watch_terms`）：会话的增减、每个会话的状态（§9）、最后几行文字（给全景用，变化后至少隔 2 秒才再发）。hub 只在 GUI 开着时挂它。

## 7. 后端

### 7.1 tmux 后端（第一个做）

- **一条常驻的控制连接**（`tmux -C`，经执行器起）当命令通道：列会话、取屏、送键都从这条连接的标准输入发，不为每次操作起一个进程。这一点对 SSH 尤其要紧。
- **取画面**：控制模式的输出通知只当作“这个面板脏了”的信号，合并限速后用 `capture-pane -e` 取整屏、查光标。tmux 自己就是仿真器，屏幕以它为准，随时可以重取。
- **没人看的会话**：不逐个盯着，每 2 秒问一次列表（最后输出时间、当前命令、是否退出）。
- **输入**：按键用 `send-keys`；一段文字用缓冲区加 `paste-buffer -p`，程序开了括号粘贴时带粘贴标记。
- **尺寸**：默认不设。控制模式的客户端不设尺寸时不影响别的客户端（tmux wiki）。主控台按面板原来的行列数缩放字号显示。
- **新开**：`new-session -d`。从 rapp 新开的终端，机器上有 tmux 就开成 tmux 会话【我定的】：rapp 的服务重启不影响它，rapp 坏了也还能 SSH 加 `tmux attach`。
- **范围**：只看 rapp 服务所属用户的默认 tmux 服务。别的 socket 以后加配置项。
- 版本下限暂定 tmux 3.2，探查后定。

### 7.2 自带伪终端后端（TR4，hurryvc 的方法）

- 用在 Windows（必用），以及没有 tmux 的 macOS、Linux。
- 做法同 hurryvc：开伪终端（Windows 上随包带新版 ConPTY），输出喂给 `alacritty_terminal`，从它的网格取快照。
- 用法：`rapp-term run -- claude`【我定的】。本地终端照常显示和操作，rapp 是第二个观众。
- 和 hurryvc 不同的三处：内容走 rapp 的设备连接，不经任何明文的中转；发送受 §6 的规则限速；持有伪终端的是一个独立的小进程，rapp 的服务和 worker 重启后重新接上它，不杀它里面的程序。
- **许可证**：hurryvc 仓库没有许可证文件，rapp 是 GPL-3.0（PD16），所以不搬它的代码，按它的方法重写。它用的 `alacritty_terminal`（Apache-2.0）和 `portable-pty`（MIT）可以直接依赖（许可证用之前再核对）。请作者加许可证是另一条路，见 §16。

### 7.3 以后的后端

Zellij、GNU screen、Herdr 都有给外部程序用的接口（调研 §10.1），各写一个后端即可。只保活不存屏幕的工具（dtach、abduco、shpool）和后台运行的进程（nohup、systemd、docker）不接；使用说明里写：想让 rapp 看得到，就把命令放进 tmux，或者用 `rapp-term run` 启动。

## 8. SSH 上去的主机（TR8）

**做法**：tmux 后端配上 SSH 执行器。一台装了 rapp 的设备（下称“代管设备”）用系统自带的 `ssh` 连到远程主机，在那边跑 `tmux -C`。远程主机上**不装任何 rapp 的东西**，只要有 tmux 和 SSH。

```
主控台 ══ rapp 连接 ══▶ 代管设备（rapp-service + rapp-term）── ssh ──▶ gpu1 上的 tmux
```

- 在主界面里，这些会话列在代管设备下面，名字带 `@主机`（§2 的图）。
- **rapp 不保管 SSH 的凭据**。它只存“目标”这一个字符串（就是你平时 `ssh` 后面写的那个），连接用的密钥、跳板、端口都照代管设备上那个用户的 `~/.ssh/config`。rapp 以不交互的方式调用 `ssh`：要输密码或确认指纹的目标连不上，界面上写原因，不弹窗。
- 目标的名单存在代管设备的 `$ROOT/local/term.json`（不进 git）。可以在那台设备的界面里加，也可以从主控台加。
- 连接断了自己重连，间隔照流畅串流规则二（1 秒起翻倍，15 秒封顶）。
- 自己这台主控台也是一台设备（平台规格 D1：每台装同一个包）。所以最简单的用法是：在主控台上加 SSH 目标，本机的服务去连。平板当主控台时没有服务，要靠另一台设备代管。

**这条路对 TR1 的意义**：没有桌面的服务器不必先等 Linux 的无界面安装包。第一步在现有的 macOS 上做完 tmux 后端，加上 SSH 执行器，服务器上的 tmux 就能进主界面。在服务器上直接装 rapp 是之后的事（§13 的 T6），好处是少一跳、不依赖代管设备开着。

要小心的（都列进 §14 探查）：后台服务的环境里可能没有 ssh-agent；每台远程主机多一条常驻的 SSH 连接；延迟多一段。

## 9. 状态、未读、需要你

和已有规格对齐，不另起一套。

**会话的生命周期**照主界面规格 §4 和 S3：连接中、活动、空闲、已断开、已结束。

- “结束会话”只是不再看它，从列表里去掉；**不结束被控端的程序**。结束远端的程序第一版不提供【我定的】。
- 活动和空闲：10 秒没有新的屏幕就是空闲（S3 §2.1 的同一条规则）。

**被控端那一头的状态**（来自后端的列表，不用连着看也有）：

| 状态 | 怎么来的 |
|---|---|
| 有输出 / 多久没动静 | 最后输出的时间 |
| 当前命令 | 面板里前台的程序名（`claude`、`cargo`…） |
| 已退出 | 面板里的程序结束了 |

**未读**照沟通机制 §2.2、§2.3：有动静，然后连续 3 秒安静下来，这个会话标为未读；用户在舞台上看过，或者回复了，未读清除。

- “看到哪了”记在被控端（worker 的内存里），几个主控台看到的未读是同一份【我定的】。服务重启后丢了就按“最后输出时间晚于服务启动”来算。
- 未读点亮主界面的“等你”灯（沟通机制 §2.3 已定由未读点亮）。
- 守设计语言 §0 的三条检查：状态平时只改灯，不弹窗、不抢焦点；看过就自己退回去，不需要「已处理」按钮。

**全景**：终端会话那一块显示最后几行文字。

**和记录的关系**：沟通机制的阶段二要“在被控端记录、文字从画面里识别”。终端会话的文字是现成的，不用识别。第一版不写盘；核心在“安静下来”时已经有一份文字快照，记录那份规格（路线图 D1）定下存哪里以后直接接上。

## 10. 输入

| 入口 | 行为 |
|---|---|
| 输入区（主界面规格 §3.5） | 本机输入法写完一段，作为一次粘贴发过去，等“已粘贴”再清空。发送后补不补回车，照 app 配置的 `afterSend` |
| 按键排 | Esc、⌃C、Tab、方向键、回车。打断就是 Esc 或 ⌃C（不同 CLI 用的不一样，两个都摆着） |
| 舞台有焦点时直接打字 | 逐键发过去（和 app 会话点了画面以后一样） |
| 附件（图片、文件） | 第一版不支持，按钮灰着并说明 |

**app 配置**：终端会话按面板的当前命令去配 `ids`（比如给 `claude`、`codex` 各写一份），第一版只用到 `afterSend` 和 `composer` 两项。`stream`（档位、密度、帧率）对终端不适用。

**流量标签的菜单**在终端会话里换成：字号（适应宽度 / 原样）、刷新（实时 / 省流）；“会话”那一组不变【我定的】。

## 11. 配置、数据、日志

- 新增 `$ROOT/local/term.json`（每台设备一份，不进 git，0600）：是否允许终端会话；SSH 目标的名单。写进《配置规范总览》。
- 自带后端的持有进程的 socket 放在 `$ROOT/local/term/`。
- 日志照可观测性规格和 app 配置 D9：记“谁在什么时候打开了哪个终端会话、发了几次输入”，**不记屏幕内容和输入内容**。访问记录里终端会话和 app 会话列在一起。

## 12. 多个主控台、安全

- **多个主控台同时看同一个终端会话：允许，不接管**【我定的】。app 会话是“后来者接管”（多客户端设计 §4.1），因为窗口只有一个尺寸、鼠标只有一个；终端是文字，各看各的没有冲突。输入谁发都进去。
- **终端会话就是那台机器上的一个 shell。** 现在能连上设备的人本来就能远程用它的终端 app，所以不是新开了一类权限，但更直接。按 relay 规格“有 key 就互信”，不另加密码。每台设备有一个开关“允许终端会话”，默认开【我定的】。
- **SSH 目标把信任往外延了一层**：能连上代管设备的人，也就够得着它名单里的主机。所以名单是每台设备各自的、明确加的，不同步。

| 步 | 做什么 | 验收 |

| T0 探查 | §14 的几件事，代码不留 | 每件有结论 |

## 14. 先探查的（T0）

1. `capture-pane -e` 取 Claude Code、Codex 的界面：宽字符、真彩色、光标对不对；每秒取 10 次的开销。不行就改成把输出字节喂给自己的仿真器（和 §7.2 共用）。
2. 一条控制连接能不能既当命令通道又收所有要看的面板的通知；tmux 的版本下限。
3. 带换行的一段文字粘贴进 Claude Code、Codex，是不是一段（cmux 的文档说它那边多行会退化成逐键）。
4. rapp 以控制模式接着时，普通客户端的尺寸和显示不受影响。
5. SSH：从后台服务（LaunchAgent）里不交互地连得上吗；一条常驻连接上控制模式稳不稳；断了能不能干净地重来。

## 16. 要你确认的

1. **只看终端上显示的字，算不算守住了“不侵入 app”（沟通机制 K2）。** 我的读法：算。终端的字符网格就是屏幕上显示的东西，rapp 不读 CLI 自己的文件，不装 hook。K2 的原话是“文字只从画面里识别”，这里是直接拿到画面上的字，没有经过识别。
2. **终端的未读算不算进顶栏“需要你”的数字。** 主界面规格 §3.6 把“Agent 等你”算在内。但 Agent 每停一次都算一件，数字可能一直不为 0，和“尽量减少提醒”（PD5）有点顶。两个走法：算进去；或者只亮灯、不进数字。
3. **SSH 目标从主控台远程加，还是只能在代管设备本机加。** 远程加方便；只能本机加更稳妥（§12 第 3 条）。
4. **hurryvc**：按它的方法重写（我按这个写的），还是请作者加许可证后直接用它的代码。
5. **T4 和 T5 的先后**（§13）。
6. 这份规格确认后，反馈文档 F2 的结论（“纯终端的活不在 rapp 范围里”）改成“终端会话在范围里，派任务仍然不做”。
