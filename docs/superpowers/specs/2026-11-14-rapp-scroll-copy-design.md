# rapp 串流：滚动复制与改尺寸保留旧画面

日期：2026-11-14。状态：**第 1 稿，待用户确认**。

读法：标"代码"的是在仓库里读到的；数字都是起步值，实测后再调。

## 0. 一句话

画面整体挪动（终端出新行、网页滚动、从左/上边拉窗口）时，只发"这一块从旧画面哪里复制"，加上新露出来的部分；窗口改尺寸不再发整帧，旧画面原样搬进新画布；整帧不再先清黑。协议升到 v9，**不再兼容旧版本**。

## 1. 为什么做

用户原话："目前看着像整篇的刷新，没有局部刷新"；"窗口调整尺寸时，也会大面积刷新，看上去很卡"。用户确认场景是终端出新行和网页滚动。

现在的原因（代码）：

- 编码器（`Sources/RappCore/TileCodec.swift` `FrameEncoder.encodeSlices`）只把每个 64×64 块和上一帧**同一位置**的块比。画面往上挪 1 行，几乎每块都变了，等于整帧重发。
- 截图区域是所有窗口的外框，向 8 点取整，每秒查 10 次（`Windows.swift` `captureRegion`，`Server.swift` `tableChanged`）。拖动窗口边时像素尺寸一直在变，编码器见尺寸变了就发整帧（`full = forceFull || width != previousWidth || ...`），每秒最多约 10 个整帧。
- 解码器收到整帧时把画布清零（`FrameDecoder.decode`：`samples = [UInt8](repeating: 0, ...)`），客户端每收到一片就画一次（`EmbeddedSession.swift` `.frame`、`rapp-session.rs` `Incoming::Frame`），所以整帧是一层黑底从上往下填。

这直接关系到流畅串流规格的 G0（弱网下能阅读）和 G2（滚动流量不暴涨）。

## 2. 和流畅串流规格的关系

`2026-11-14-rapp-smooth-streaming-design.md` 的第二步（规则三）计划用 H.264 "运动层"处理好网络下的滚动，并把"只给瓦片编码加滚动检测"列为没选的替代方案（理由：帮不上 Agent 出字和动画）。本设计**不替代**规则三，而是补它够不着的地方：

- 弱网档不开运动层（规则二），滚动只能靠瓦片编码；
- 帧率低于 15、选了双色档时也是瓦片编码；
- 第二步目前没有排期（`tasks/todo.md`）。

将来做规则三时，静止层就是本设计改过的瓦片编码。规则三写的"静止层不改"届时以本设计为准。规则三的"停下来补清晰"和本设计 §5.5 的"静止后修正"目的相同，做规则三时合并。

## 3. 目标、不做、不能出现的情况

| # | 要什么 | 怎么验 |
|---|---|---|
| S1 | 终端连续出字、上下滚一行到一屏，只发新露出的行和真正变了的块 | §7 |
| S2 | 网页、文档上下滚动，固定的顶栏/侧栏不影响识别 | §7 |
| S3 | 拖窗口改尺寸（任意一边）不发整帧，没有黑屏扫过 | §7 |
| S4 | 停下来后画面和现在逐像素一致（流畅串流规格 G3） | §7 |
| S5 | 主机每帧多花的时间小，不拖慢帧率 | §7 |

**不做：** 近似复制（用户决定：先只认完全对上，见 §5.3）；左右滚动的检测（窗口区域本身左右挪的偏移照样用，见 §5.3）；块缓存（来回切页签）；视频编码；任何新的界面开关或档位。

**不能出现：**
- 画面出错：复制来源不对、错位、残留旧内容不更新。宁可多发，不能画错。
- 停下来后的画面比现在糊（双色档尤其要注意，见 §5.5）。
- 网络好时帧率下降。

## 4. 做法对比（已选）

| 做法 | 取舍 | 结论 |
|---|---|---|
| **A. 块级"从旧画面复制"** | 每块单独验证，对不上的块照常编码，画面不会错，最坏就是省得少；固定的顶栏/侧栏天然不受影响；分片照常 | **选这个** |
| B. 整块区域平移（"这个矩形挪 dy"） | 字节最少，但要找准滚动区域边界；一页里有多个可滚区域时容易判错，判错就退回整帧 | 不选 |
| 截图区域取大（向 64 点取整留余量） | 只改主机，小幅改尺寸时像素尺寸不变 | 不选：改尺寸保留旧画面以后就多余了 |
| 块缓存（RDP 位图缓存） | 管来回切换，不是这次的问题 | 以后再说 |
| H.264 视频编码 | 文字发虚，弱网也不用它 | 属于流畅串流规格第二步 |

用户的决定：选 A，加上"改尺寸保留旧画面"和"整帧不清黑"；**完全不考虑旧客户端，兼容旧版本的代码删掉**。

## 5. 设计

### 5.1 版本：只认 v9

- 协议版本升到 9。主机只接受 v9 的 hello，其他版本照现在的 `ProtocolVersionMismatch` 报错（"update both sides"）。
- 删掉为旧版本留的代码。代码里已知的有：
  - Swift：`oldestClientVersion`、`clientSendsFrameAcks` / `clientUnderstandsInputBlocked` / `clientUnderstandsInputSource` 和它们的调用判断；`PacedSender` 的 `acks` 参数和 `pumpV6`（v6 不带确认的发送）；`Server.swift` 里按 `helloVersion` 分支的地方。
  - Rust：`client-core/src/protocol.rs` 的 `[4, 5, 6, 7, 8].contains(&version)` 和可选的 `protocol` 参数；`rapp-session.rs` 的 `version >= 7` 判断。
  - `WorkerCLI.swift`、`rapp-host/main.swift`、`rapp-client/main.swift` 里和版本选择有关的选项。
  实现时以全仓搜索为准，删干净；测试里专门测旧版本行为的用例一并删掉。

### 5.2 帧格式（v9）

帧消息（type 4）仍然一条消息一片。和 v8 的区别：

1. **标志字节**：原来的 `isFull`（0/1）改成标志位：
   - `full`：这一片开始一个整帧（同现在）；
   - `start`：这一片是一帧的第一片；
   - `end`：这一片是一帧的最后一片；
   - `copies`：这一帧里有复制块（只在 `start` 片上有意义）。
   一帧只有一片时 `start` 和 `end` 都置上。
2. **带 `start` 的非整帧片多带一个"搬画布"头**：新画布尺寸就是这片的 width/height；外加像素偏移 (dx, dy)，意思是"新画布 (x, y) 处 = 旧画布 (x + dx, y + dy) 处"。尺寸没变、偏移是 (0, 0) 时就是普通差量帧。旧画布外的部分是"未覆盖"，内容不确定（解码器填 0），主机保证会发。
3. **新块类型：复制**（编号用现在没占用的值，例如 5）。块体是源左上角 (sx, sy)，源矩形和目标块同大小，必须整个落在参考画布内，否则按坏帧处理（结束会话，同现在）。
4. **参考画布** = 这一帧 `start` 片做完"搬画布"之后、解第一个块之前的画布。同一帧后面的片里的复制块也从它取，不受本帧已写的块影响。解码器只在 `copies` 置上时留这份副本。

字节布局（字段宽度、有符号、顺序）由实现者定，但 Swift 和 Rust 必须完全一致，并写进 `TileCodec.swift` 顶部的格式注释。

### 5.3 主机：要比什么、试哪些偏移

主机除了"解码器画布的模型"（现在的 `previous`，存样本），**再存一份上一帧的原始像素（BGRA）**。原因：双色档按对齐到画面原点的 16×16 小块挑深浅两色，内容挪了不是 16 的倍数时，同一段文字落进不同的小块，压出来的样本可能对不上，复制就配不上。

不变式：模型里每个像素的样本，都是原始像素副本里同一位置像素的一种正确表示（要么是它的量化结果，要么是挪过来的内容在别的对齐下的量化结果）。

每帧：

1. **搬画布**：截图区域的原点或像素尺寸变了，就把模型和原始像素副本按偏移搬进新尺寸。偏移 = 区域原点之差 × 每点像素数，取整。新露出的地方标成"未覆盖"，它们不能当"没变"，也不能当复制源。
2. **同位置判断**：一块和模型的样本相同，或者和原始像素副本相同，就不发。
3. **复制判断**：变了的块依次试候选偏移，源块完全对上（样本相同或原始像素相同）就发复制块，否则照常编码。
4. **候选偏移**：
   - 区域原点的偏移，已经在第 1 步体现为 (0, 0)；
   - 检测到的上下滚动量：给当前帧和原始像素副本的每一行算指纹，**按 64 像素宽的列条分别投票**，取得票最多的几个 dy（起步值：最多 3 个）。按列条投票，是为了固定侧栏、滚动条不挡住识别。全是同一颜色的行（空行）不参与投票。
   - 上一帧用过的 dy（连续滚动时多半相同）。
5. 算法细节（指纹函数、投票范围、提前退出）由实现者定。
6. **缩放截图**（用户决定）：弱网档、「省流 1x」等密度低于 A 本机像素时，截图是缩小过的。网页平滑滚动挪的距离常常不是整点，缩小后像素对不上，复制就配不上。第一版**只认完全对上**（样本相同或原始像素相同），不做近似匹配：终端按整行滚动不受影响，双色档也能靠样本相同配上一部分。验收时把弱网档的数字也测出来（§7），不够再考虑放宽。
7. **耗时**起步预算：1080p 的窗口每帧额外不超过 3 ms（用户的 Mac 上实测），超了再调候选数或范围。

### 5.4 主机：其他改动

- `PacedSender.offer` 和编码器的输入加上原始像素和区域。量化在会话队列之外做（现在就是），原始像素要从 `CVPixelBuffer` 拷出一份，因为缓冲会被复用。
- 整帧只在这几种时候发：会话第一帧、换档位（新编码器）、密度改变（像素和点的比例变了，内容搬过去也对不上，按整帧处理更简单）。区域尺寸或原点变了**不再**发整帧。
- 分片照旧：按块行从上往下切，32 KB 一片、首片 8 KB。分片只在 `start` 片带搬画布头。

### 5.5 静止后修正（保证 S4）

按原始像素判"没变"或"能复制"时，模型里的样本可能和这一帧的量化结果不同（双色档内容错位挪过来的块）。这种块记为"近似"。

画面停下来以后（起步值：300 ms 没有新帧），主机拿最近一帧（`Server.swift` 已经保存了 `latest`）再编一次，只比较近似块的样本，不同的重发，然后清掉近似标记。这样停下后的画面和现在逐像素一致。途中又来了新帧就照常编码，近似标记保留到下一次静止。

### 5.6 客户端

三处解码器要改成同一套格式：

- Swift `FrameDecoder`（`TileCodec.swift`）：Mac GUI（`RappSession/EmbeddedSession.swift`）和 `rapp-client` 共用；
- Rust `client-core/src/codec.rs`、`protocol.rs`：Linux 的 `rapp-session` 和 `client-gtk` 用。

显示规则：

- **整帧**：从 `start` 片到 `end` 片解完之前，**不更新显示**，继续显示上一张完整画面。去掉"黑底从上往下扫"。
  会话的第一帧没有上一张画面，照现在一片一片画；首片 8 KB 的做法保留（我的决定：没有旧画面可留时，先看到一部分比空着好）。
- **有"未覆盖"区域的差量帧**（改尺寸、新露出边）：同整帧，`end` 片解完才更新显示，避免新露出的地方先闪黑（我的决定：比在两端约定填充颜色简单；代价是慢网上拖窗口时新边出现得晚一点）。
- **其他差量帧**：照现在，每解一片就画一次（弱网下先看到上面的部分）。
- 帧确认照旧每片一个。

## 6. 约束

- 不能画错（§3 不能出现的情况）。Swift 和 Rust 两个解码器对同一串帧必须得到完全相同的画布。
- 主机的模型和解码器画布任何时候都一致。
- 截图、量化、分片、弱网档、帧确认的现有行为不变，除了 §5 写明的改动。
- GPL-3.0；不加新的第三方依赖。

## 7. 验收

| 验什么 | 怎么验 | 起步目标 |
|---|---|---|
| 正确性 | 随机生成一串帧（上下挪任意行数、改尺寸拉四条边、局部变化、固定侧栏），编码再解码，解码画布和主机模型逐字节相同 | 全部通过 |
| 两端一致 | 同一组帧数据（由 Swift 编码器生成、存成测试文件），Swift 和 Rust 解出的画布逐字节相同 | 全部通过 |
| S1 终端 | 本机像素密度下，终端里连续输出、一行一行往上推，统计每帧字节 | 双色·灰度和高彩下都比现在少 80% 以上 |
| S2 网页 | 本机像素密度下，有固定顶栏和侧栏的网页，滚轮上下滚，统计总字节 | 比现在少 60% 以上 |
| S3 改尺寸 | 拖动窗口上下左右四条边，看 service.log 和画面 | 拖动期间没有整帧；没有黑屏扫过 |
| S4 停下 | 双色·灰度下滚动后停下，等 1 秒，比较解码画布和整帧重编的结果 | 逐像素一致 |
| 弱网档 | S1、S2 在弱网档（双色·灰度 + 密度 1.0，Retina 的 A）下再测一遍 | 终端比现在少 80% 以上；网页只记录数字，不设目标 |
| S5 耗时 | 1080p 窗口持续滚动时主机每帧的编码耗时 | 比现在多不超过 3 ms |

## 8. 留给实现者的

- 帧格式的字节布局（§5.2）、复制块的编号。
- 行指纹和投票算法、候选偏移的数量和范围（§5.3）。
- "未覆盖"区域在模型里的表示方式。
- 静止后修正的触发方式（定时器还是借用现有的每秒 tick），只要满足 §5.5 的时间。
- 测试文件的格式和存放位置。
