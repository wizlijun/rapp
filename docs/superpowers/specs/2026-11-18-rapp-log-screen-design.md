# rapp 日志界面设计

日期：2026-11-18。依据：《可观测性设计》（`2026-11-11-rapp-observability-design.md`，日志格式、`service.log` / `hub.log` 的事件清单、访问记录 §6）和《主窗口设计》§3.7（本机页的访问记录只显示 5 条加「更多」）。

## 0 为什么做

用户用日志**排查问题**：连不上、被拒绝、服务出错时，想看到原因。现在只有两条路：本机页的访问记录（只是 `service.log` 里筛出来的一小部分，而且只有本机），或者「打开日志文件夹」自己翻几 MB 的 JSON 行。

问题的原因常常不在本机：从本机连 mini 被拒绝，拒绝原因写在 mini 的 `service.log` 里，本机的 `hub.log` 只有一行 `route` 警告。所以这个界面除了本机，还要能看**另一台设备**的日志。

## 1 目标、不做的、做错了算失败的

**目标**

- 打开日志界面，不用翻就能看出最近出了哪几类问题、各几次、最近一次的原因。
- 能在本机和任一台在线的其他设备之间切换，看到对方那边的日志，三份日志合成一条时间线。
- 点开一条能看到全部字段和原文，并能一键看这一刻前后发生了什么。
- 服务停着、或者起不来的时候，本机的日志照样能看（这正是要排查的时候）。
- macOS、Linux、Windows 和 iPad 用同一套界面。

**不做**

- 中继服务器（VPS）的日志：中继没有读日志的接口，用户选了不做。
- 实时推送 / 订阅：打开时读一次，之后定时补新的就够了（§4.4）。
- 改日志的写法、加新事件、改轮转规则。这次只读，不写。
- 告警、通知、导出报告。
- 给读日志另加权限（§3.3）。

**算失败的**

- 打开后满屏 info，问题埋在几千行里。默认必须只看问题。
- 本机服务一出错，日志界面也打不开或一片空白。
- 读日志让界面卡住，或者一次查询把对方的服务拖慢。
- 日志里出现密码、令牌、中继 key 等秘密（现在的日志本来就不写这些，这次也不能因为转发而引入）。

## 2 做法的选择

考虑过三种：

1. **（选中）Rust 里一个统一的读日志查询。** 读一台机器日志目录下的三份文件，在 Rust 里筛选、归类、分页。本机由 hub 直接读，别的设备通过 hub 发一条新的请求给对方的服务，由对方读它自己的日志目录。界面只负责中文摘要和排版。读取和归类的逻辑只有一份，本机和其他设备看到的完全一致。
2. **界面直接读本机文件，别的设备走协议。** 本机做得快，但同样的读取、筛选和归类要在 Dart 和 Rust 各写一份，迟早对不上。
3. **对方把日志实时推过来。** 要做订阅、断线重连和限流，复杂很多；排查时读一次再定时补，已经够用。

用户选了第 1 种。

## 3 数据：读日志查询

### 3.1 读什么

一台机器的日志目录下的三份。桌面上 service 和 hub 用的是同一个目录（`rapp_net::log::log_dir()`）；iPad 的 hub 用启动时传进来的 `$root/logs`（`gui/lib/main_ios.dart`）。查询读的是 hub 自己那个目录。hub 现在不知道自己的日志目录（`rapp_hub::Opts` 只带一个 `Log`），要在 `Opts` 里加上这个路径：

| 来源 | 文件 | 格式 |
|---|---|---|
| `service` | `service.log` + `service.log.1` | JSON 行（可观测性 §2） |
| `hub` | `hub.log` + `hub.log.1` | JSON 行 |
| `launchd` | `launchd.log` | 纯文本（进程的 stdout/stderr），只有 macOS 有 |

- 文件不存在就当空的（iPad 只有 `hub.log`；Linux、Windows 没有 `launchd.log`）。
- `launchd` 尾部另有 16 KB 的总上限（100 行各 1 KB 放不进一行回复）：从最新的一行往前数，超过 16 KB 就不再往前加，所以行数可能少于 100。
- **`launchd.log` 不并进时间线。** 它的大多数行（service 的 `eprintln!`、panic 输出）没有时间，只能靠文件修改时间去猜，而修改时间每写一行都会变，并进去会让翻页和定时补新的都乱掉。所以它单独提供：查询带 `tail_launchd:true` 时，回复里多一个 `launchd`，内容是这份文件的最后 100 行原文（字符串数组，单行超过 1 KB 截短）。界面上它是「启动输出」，见 §4.2。它不参与三张卡的计数。
- 每条结果都带上 `src`：`service` / `hub`（哪份日志）。事件本身以原始行 `raw` 传回，界面自己解析；日志里原有的 `src` 字段（以下称 `from`）因此原样保留，不和外层的 `src` 冲突。`service.log` 里有 `"src":"host"` / `"term"`（worker 的 stderr），`hub.log` 里有 `"src":"client"`（`hub/src/session.rs`）。
- 坏行跳过（和 `read_recent` 一样）。

### 3.2 归类：三张卡

归类放在 Rust 里（`rapp_net::log` 里一个纯函数），每条结果带一个 `kind`：`unreachable`（连不上）/ `refused`（被拒绝）/ `fault`（服务出错）/ 没有。

**归类看事件和字段，不只看 `lvl`。** 现在的代码里有几类该算问题的事件是记成 info 的（下表注明了）。规则以代码实际写出来的事件为准：

| kind | 哪些事件 |
|---|---|
| `refused` | `auth_fail`；`rejected`；`map_refused`；`forward_refused`；`result` 不是 `ok` 的 `request`（不含 `watch_terms`）；`result:"refused"` 的 `trust`（warn，`service/src/peer.rs`、`relay_link.rs`，就是 §0 里"mini 拒绝了我"的那种）；`relay_revoked`（info） |
| `unreachable` | `hub.log` 里 warn/error 的 `route`；`hub.log` 里 warn/error 的 `log`（例如 `<id> via <path>: …; reconnecting`，`hub/src/link.rs`）；`service.log` 里带错误的 `relay`：`state:"error"`（warn）或者 `state:"connecting"` 且带 `error` 字段（info，`service/src/state.rs`），也就是本机自己连不上中继 |
| `fault` | 其余 warn/error 的事件（`update_failed`、`worker_exit`、`permissions`、`update_check`、`result` 不是 `refused` 的 `trust`、`log` 等）；以及 `from` 为 `host`/`term`/`client` 的 `log`（子进程 stderr 转写，一律是 info）中，`msg` 含 `panic`、`fatal`、`error`（不分大小写）的那些 |

- 其余事件不归类（`kind` 为空），只在「全部」里出现。`presence` 离线不算问题：笔记本合盖、手机锁屏都会离线，算进去会让「连不上」一直有数，用户看了也没用；它在「全部」里照常可见。
- **重复行**：日志把连着一样的行合成一行，后面跟一行 `{"ev":"repeat","repeat":N}`（不写重复的是哪条）。查询要把 `repeat` 并到它前一条上：前一条事件多一个字段 `repeat: N`，`repeat` 行本身不单独返回；`counts` 里这条算 `1+N` 次。倒序读的时候，`repeat` 先读到、它的前一条后读到，跨块、跨 `.log` / `.log.1` 也要接上。界面上这一行的摘要后面加「（又重复 N 次）」。
- 规则表要随事件清单（可观测性 §4）一起维护。`kind` 是界面上卡片和「只看问题」的唯一依据。

### 3.3 谁能读

- **本机**：GUI 问自己的 hub，hub 直接读本机日志目录。桌面上 hub 是 GUI 启动的子进程 `rapp-hub`，iPad 上是进程内的 FFI，都不依赖 service，所以服务停着也能读。
- **其他设备**：hub 向对方发新请求 `logs`，对方的 **service** 读自己的日志目录作答。凡是现在能对这台设备发 `list_apps` 的连接（认证过的），都能发 `logs`，不另加权限。这符合"中继是唯一的门，其他保持简单"的取舍。
- 对方是旧版本：它会回 `unknown op`。界面在设备选择旁显示「对方版本太旧，看不到它的日志」。
- 对方不在线：照常显示 hub 的连接错误。
- 不涉及窗口流协议（`client-core` 的 `protocol::VERSION`），不用升协议版本。

### 3.4 请求和回复

同一个查询有两个入口，参数和回复一样：

- GUI → hub：`{"cmd":"logs", "id"?: <设备 id>, …参数}`。不带 `id` 是本机。
- hub → 对方 service：新的 `Op::Logs { …参数 }`（`rapp_net::msg`），在 `service/src/peer.rs` 里处理。

参数（都可省）：

| 参数 | 意思 |
|---|---|
| `before` | 一个游标（上一次回复的 `older`）：只要它之前的（翻页用） |
| `after` | 一个游标（上一次回复的 `newer`）：只要它之后的（定时补新的用） |
| `around` | 一条事件的游标（每条事件都带 `at`）：返回它前后各 60 秒内的全部（忽略 `problems`、`kind`、`src`、`q`：两份日志、所有级别都给），时间从旧到新 |
| `tail_launchd` | `true`：回复里带 `launchd.log` 的最后 100 行（§3.1） |
| `problems` | `true`：只要有 `kind` 的 |
| `kind` | 只要这一类 |
| `src` | 来源数组，比如 `["service","hub"]`；省略是全部 |
| `q` | 搜索词：原始行里包含它（不分大小写）才要 |
| `limit` | 最多几条，默认 200，上限 500 |

回复：

```json
{"ok":true,
 "events":[{"src":"service", "at":"<游标>", "kind":"refused", "repeat":2, "raw":"<日志里的原始一行>"}, …],
 "more":true, "older":"<游标>", "newer":"<游标>",
 "again":[{…一条事件…}],
 "counts":{"unreachable":12, "refused":3, "fault":1},
 "latest":{"unreachable":{…一条事件…}, "refused":{…}, "fault":{…}}}
```

- `events` 默认按时间从新到旧（`around` 除外）。两份日志按 `ts` 合并，`ts` 相同时按来源（`service` 在前）、再按在文件里的先后排，保证顺序稳定。
- **游标，不用裸的 `ts`**：`ts` 只到毫秒，一阵连发的事件常常同一个毫秒，用 `ts` 做翻页边界会漏掉或重复。每条事件带一个 `at`，回复带 `older`（这一页最旧那条之前）和 `newer`（最新那条之后）。游标对界面是不透明的字符串，由 Rust 定义内容，例如 `ts`、来源和该行在文件里的位置。日志在两次查询之间轮转过（`.log` 变成 `.log.1`），游标对不上时按 `ts` 退回，宁可多给几条重复的，界面按 `at` 去重。
- **`newer`**：首页和 `after` 回复里，`newer` 是这几份日志里**最新的一行**（一条事件，或者它后面的 `repeat` 行）的游标，**不管它合不合筛选条件**；`events` 为空时也给。这样「只看问题」或搜索一条都没对上时，定时补新的也有起点，每次只读上次以后新写的部分，而不是每 5 秒把整份日志扫一遍。`after` 回复里只在确实有比游标新的行时才给 `newer`（没有就不给，界面沿用原来的）。`before` 回复的 `newer` 照旧是这一页最新那条。`older` 只在 `events` 不为空时给。
- **`again`**：只出现在 `after` 回复里。某份日志最新的那条事件，在游标之后又写了 `repeat` 行（重复次数变多了），而且它合筛选条件，就把它（带上新的总 `repeat`）放进 `again` 再发一次；形状和 `events` 里的一样，`at` 不变。界面只用它**替换**已经列着的同一 `at` 的行，不新增（没列着的，比如比已加载的都旧，就不管）。`again` 和 `events` 一起算 `limit` 和字节上限，放不下就是 `gap`。
- `gap`：只出现在 `after` 回复里：比游标新的行太多，没给全（中间有缺口），界面要重新查首页。
- `more`：还有更早的没给（被 `limit` 或字节上限截断了）。
- `counts` / `latest`：最近 24 小时内各类的条数（含重复次数）和最近一条。只在请求不带 `before`/`after`/`around` 时给（用来画三张卡），不受 `src`、`q`、`kind` 影响。
- **字节上限**：JSON 行协议一行最多 64 KB（`rapp_net::line::MAX_LINE`）。回复必须小于它：凑满约 56 KB 就停，置 `more:true`。单条 `raw` 超过 4 KB 的，解析后把每个超过 1 KB 的字符串值截短，重新序列化作 `raw`，并加 `"truncated":true`（`raw` 仍是合法 JSON）。`latest` 里的事件也是这个形状。
- 读取要从文件尾部往前读，够数就停，不能每次把 10 MB 全读进来再筛（`read_recent` 现在是整份读入，要改或另写）。`counts` 需要扫完 24 小时，按时间往前扫到 24 小时前就停。
- 这条查询在 service / hub 里放到阻塞线程池里跑，不占住 IPC 和会话的异步循环。

## 4 界面

### 4.1 进出

- 进：本机页访问记录下的「更多」（iPad 的本机页一样）。进来时选中本机。
- 日志界面占顶栏以下的整块舞台（和「全景」同一层：`MainState` 里一个 `logs` 标记，舞台在 `Stage` / `Overview` / `LogScreen` 之间换），顶栏照常。侧栏是打开的，进入时把它收起。
- 出：标题行左边的「‹ 返回」、Esc（和退出全景同一套 Esc 顺序：先关角落、再关侧栏、再关日志界面、再关全景、再退全屏），或者在侧栏 / 顶栏点了别的会话。
- 日志界面打开时，舞台上没有会话画面：按全景的规则处理（会话都按"不在台上"的帧率走）。

### 4.2 版面

```
┌ 顶栏 ─────────────────────────────────────────────────┐
│ ‹ 返回  日志  [本机 ▾]               [搜索…]  ⟳  打开文件夹 │
├────────────────────────────────────────────────────────┤
│ ┌ 连不上  12 ──┐ ┌ 被拒绝  3 ────┐ ┌ 服务出错  1 ──┐        │
│ │ 路由失败       │ │ 密码不对        │ │ 升级下载失败     │        │
│ │ mini · 2 分前  │ │ 5.6.7.8 · 23:30 │ │ 昨天 21:03       │        │
│ └──────────────┘ └───────────────┘ └───────────────┘        │
│ [只看问题] [全部]      来源：[service] [hub]   [启动输出 ▸]    │
│ 23:47:02 hub     ⚠ 路由失败 mini · 中继 · relay 超时            │
│ 23:30:11 service ⚠ 拒绝 5.6.7.8 · 密码不对                    │
│ 23:29:40 service   会话结束 iPhone · 989 秒                    │
│ …                                                              │
│                       [加载更早的]                              │
└────────────────────────────────────────────────────────┘
```

- **设备选择**：本机加上所有其他设备（和设备页一样的状态灯和名字）。离线的设备也列出来，选了显示连不上的原因。
- **三张卡**：各显示 24 小时内的条数，以及最近一条的中文摘要和时间（今天的写时间，更早的写「昨天」或日期）。0 次的卡变灰，写「24 小时内没有」。点一张卡：下面的流水只看这一类，卡片显示选中；再点一次取消。
- **筛选行**：「只看问题」（默认）/「全部」二选一；两个来源各一个开关，默认全开；iPad 本机只有 hub，就不显示来源开关（按"在 iPad 上且选的是本机"判断，不看回来的数据）。搜索框输入后约 300 毫秒发查询（`q`）。
- **启动输出**：筛选行右边一个「启动输出 ▸」，只在这台机器有 `launchd.log` 时出现（macOS）。点开在流水上方展开一块等宽文本，显示 `launchd.log` 的最后 100 行原文，最新的在下面，带「复制」；再点收起。服务起不来、崩溃时的 panic 输出在这里。
- **流水**：每行是时间（`HH:mm:ss`，不是今天的前面加日期）、来源、有 `kind` 的加 ⚠ 和警告色、中文摘要（`lvl` 是 warn/error 的行即使没有 `kind` 也用警告色）。摘要过长时换行，不截断。滚到底自动加载更早的（`before` = 上一页的 `older`）；`more` 为假时底部写「没有更早的了」。
- **刷新**：⟳ 按钮旁边写「刷新」两个字，重新查一遍；首页还在路上时再按 ⟳ 不再发（换设备、改筛选照常发，那是新的查询）。界面开着时每 5 秒用 `after`（= 最近一次的 `newer`）补新的，按 `at` 去重后插到最上面，`again` 里的行就地替换；如果用户已经往下翻了，就不跳回顶部，只在顶上提示「有 N 条新的」，点了才回到顶部。
- **每 5 秒最多一个请求**：上一个还没回来，这一拍跳过；回复带 `gap` 时这一拍只丢掉游标，下一拍再查首页。补新的或悄悄重查首页**失败一次就停**（对方离线时每次失败都会在本机 `hub.log` 里写连接错误），直到按 ⟳、换设备或改筛选。
- **滚动**：标题行以下（三张卡、筛选行、启动输出、流水）是同一个滚动区，一起滚。
- **打开文件夹**：只在本机时显示，和访问记录的按钮做同一件事。
- **窄窗口 / iPad 竖屏**：三张卡排不下就换成可横滑的一行；筛选行折行。iPad 上可点控件至少 48 高。

### 4.3 点开一条

就地展开，再点一下收起：

```
23:30:11 service ⚠ 拒绝 5.6.7.8 · 密码不对                ▴
    来源地址   5.6.7.8:51022
    路径       直连
    原因       wrong password
    {"ts":"2026-11-17T15:30:11.204Z","ev":"rejected",…}
    [复制]  [看前后 ±1 分钟]
```

- 字段表：已知字段用中文名（`peer` 来源地址、`path` 路径、`reason` 原因、`app`、`sid` 会话、`secs` 时长……），不认识的字段照原名列出。值照原样，不翻译（原因是英文就是英文）。
- 原文就是 `raw`，等宽字体，能选中。
- 「复制」复制原文这一行。
- 「看前后 ±1 分钟」：发 `around` 查询，流水换成这两分钟内所有来源、所有级别的记录（按时间从旧到新），这一条高亮并滚到中间。顶上出现一条「前后 1 分钟 · 23:29:11–23:31:11  × 返回」，点 × 回到原来的流水和滚动位置。

### 4.4 中文摘要

- 放在 Dart 里，和现在 `access_log.dart` 的 `historyRow` 一个思路，扩成一个总的 `logLine(event) → (摘要, 字段表)`。访问记录那几类直接复用现有说法。
- 已知事件给一句中文；不认识的事件写 `<ev>` 加 `msg`（有的话）。
- `route` 失败写「路由失败 <设备名> · <路径> · <原因>」；`id` 能在设备列表里找到名字就用名字。

## 5 改到哪些地方

- `rust/net/src/log.rs`：倒序读、合并两份、`repeat` 归并、游标、`launchd.log` 尾部、归类函数、字节上限、`counts`/`latest`。单元测试。
- `rust/net/src/msg.rs`：`Op::Logs`。
- `rust/service/src/peer.rs`：处理 `Op::Logs`。

## 6 测试

- **`rapp_net::log` 单元测试**：两份合并按时间排序且同一毫秒顺序稳定；跨 `.log` / `.log.1`；游标翻页在一阵同毫秒事件上不漏不重；轮转后游标退回；`repeat` 并到前一条（含跨块、跨文件）且计数加 N；`launchd.log` 尾部 100 行和截短；归类表每一行（含 info 的 `relay`、`relay_revoked`、stderr 里的 panic）；`around`/`q`/`src`/`kind`；字节上限截断后 `more` 为真且回复小于 64 KB；超长单条被截短；24 小时 `counts` 在边界上的取舍；原有 `src`（`host`、`client`）保留在 `from`。
- **service 集成测试**：认证后 `logs` 能返回；没认证发 `logs` 被拒；对一台旧版（假的）设备，hub 把 `unknown op` 原样交给界面。
- **hub 测试**：不带 `id` 读本机日志目录，**service 没在跑时也能读**；带 `id` 转发。
- **全量秘密检查**：测试用的密码、令牌、中继 key 不出现在任何 `logs` 回复里。
- **GUI**：`logLine` 纯函数；卡片计数和点卡片筛选；只看问题 / 全部；来源开关；滚到底加载更早；5 秒补新的且用户翻下去时不跳；展开、复制、看前后和返回；设备是旧版本时的提示；进出（更多、返回、Esc）；iPad 48 高。
- 所有测试只用临时目录和临时端口。

## 7 我（Claude）替用户定的

- 读日志不另加权限，能对设备发 `list_apps` 的就能读（§3.3）。
- 本机日志由 hub 读，而不是 service：服务坏了也能看。
- 三张卡按 24 小时统计。
- 归类初版规则（§3.2）：看事件和字段而不只看级别；`presence` 离线不算问题；子进程 stderr 里含 panic/fatal/error 的算服务出错。
- 重复行并到前一条，计数加上重复次数。
- `launchd.log` 不并进时间线，单独做「启动输出」（最后 100 行），不计数。
- 翻页用不透明游标，不用裸的 `ts`。
- 每 5 秒自动补新的；翻下去时不跳，只提示。
- 每页默认 200 条，上限 500，并受 64 KB 一行的限制。
- 进入日志界面时收起侧栏；出口是「‹ 返回」和 Esc。
