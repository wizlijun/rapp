# 看不见的会话停发画面

日期：2026-11-22。状态：用户确认了 D1–D3，并要求一直做到开发完成；§4.3 的"其他画面状态也限速"和 §6 是我的决定。

改的是 S2 规格 `2026-11-12-rapp-s2-embedded-stage-design.md` 的 R6（"没在舞台上的嵌入会话降到 1 fps"）和 S4 规格 §2 的帧率一条。别的不变。

## 1. 为什么改

同时连着几台设备时，人一次只看一个画面，别的会话还在传。用户的要求（原话大意）：没在看的已连接会话，流量降到最低，只留一张静止画面，基本为零；不浪费视频流量。

现在的做法（代码）：
- `effectiveFps()`（`gui/lib/embed/stream_choice.dart:38`）：在舞台上或已分离按所选帧率，其余 1 fps；`_applyFps()`（`gui/lib/ui/main_state.dart:845`）在切换、全景、日志页时发 `set_stream`。
- A 端只发变了的瓦片，所以后台画面不动时已接近 0；**后台画面一直在变**（Agent 出字、光标闪、网页动画、视频）时，每秒发一次变化。这些画面没有地方显示（全景只写窗口数），是纯浪费。
- 桌面端不管 rapp 窗口看不看得见：最小化、被挡住时，舞台上的会话照样满帧率发。iPad 进后台会断开所有会话，已经是 0。
- 1 fps 有一个用处：会话列表、全景、顶栏的「活动 / 空闲」灯。它靠 `TrafficEvent.frames`（`gui/lib/embed/remote_session.dart:381`）：有帧就清零，连续 10 秒（`idleAfter`）没帧算空闲。

## 2. 用户定下的

| # | 决定 |
|---|---|
| D1 | 不在看的会话停发画面，但**保留活动信号**：A 照常判断画面变没变，只发几个字节的「变了」，活动 / 空闲灯照常工作 |
| D2 | 桌面端窗口**最小化、被完全挡住、在别的桌面空间**时，当前会话和分离窗口也停；只是切到别的 app、窗口还露在屏幕上时照常发 |
| D3 | 做法选甲：A 端加"暂停"档（见 §4） |

## 3. 目标、非目标、反目标

目标：
- G1 看不见的会话，每个会话的流量在画面持续变化时也不超过约 0.1 KB/s（「变了」消息加上现有的 ping 等）。
- G2 活动 / 空闲灯和现在一样：后台画面在变时是「活动」，停下 10 秒左右变「空闲」。
- G3 切回来时，一个往返加一次编码之内看到当前画面，然后恢复原帧率。这中间显示的是最后一张画面，不黑、不闪。

非目标：
- 文字终端会话（只发文字，流量本来就小）。
- 实时缩略图（S4 V3 不做，不变）。
- iPad 进后台的做法（已经断开，不变）。iPad 前台时"不在舞台上"的会话照本文暂停。

反目标（做出来了但算失败）：
- 切回来看到的是降过档的画质，或者 A 把暂停当成网络差、进了省流级（这就是不选乙的原因）。
- 后台 Agent 跑完了，灯还一直亮「活动」，或者一直「空闲」看不出它在跑。
- 暂停期间 A 的编码器和 B 的画面对不上，切回来花屏。

## 4. 做法

### 4.1 考虑过的三种

| | 做法 | 结果 |
|---|---|---|
| **甲（选）** | `set_stream` 加一档"暂停"；A 只在本机判断变化，发「变了」；切回时补一帧 | 流量约 0，灯照常；要升协议，五个端都改 |
| 乙 | B 不回确认，让 A 的在途帧上限卡住 | 不改协议，但 A 当成网络差降档（反目标 1），灯没了 |
| 丙 | 离开舞台就断开，切回来重连 | 流量 0，但每次切换都要重连（经中继几百毫秒到几秒），灯没了 |

### 4.2 协议 v15

- `set_stream`（类型 11）的 fps 允许 **0 = 暂停**。hello 里的 fps 不允许 0（新会话总要先有画面，见 4.3）。
- 新的 A→B 消息 **`changed`（类型 42，无负载）**：暂停期间画面变了时发，**每秒最多一条**。不暂停时不发（帧本身就说明了）。
- 升版本要改的所有地方（`merge-gotchas` 的教训，逐个 grep）：Swift `protocolVersion` 和 `knownTypes`（`Sources/RappCore/Protocol.swift`）、Rust `read_message()` 的 A→B 白名单和 `decode()`（`rust/client-core/src/protocol.rs`）、Linux A 端 `rust/host-linux/src/wire.rs`、Dart `sessionProtocolVersion`（`gui/lib/embed/session_protocol.dart`），以及帧率白名单 `[1, 5, 15, 30]`（`host-linux/src/wire.rs:30`、`client-core/src/protocol.rs:131`、`client-core/src/bin/rapp-session.rs:115`、`Sources/RappSession/Channel.swift:325` 的 `allowedFps`、Swift 端 `setStream` 的解码校验）。界面上可选的帧率（设置页、app 配置页、`client-gtk`）**不加** 0：暂停只由界面自动发，人选不到。

### 4.3 A 端行为（macOS `rapp-host`、Linux `host-linux` 一样）

- **进入暂停**：B 那里已经有最后一张画面。A 不再发帧，也不为暂停补发什么。
- **暂停期间**：A 继续以 1 fps 左右的节奏看画面有没有变，不编码、不发。变了就发 `changed`（每秒最多一条）。
  - macOS：ScreenCaptureKit 只在内容变了时交出 `.complete` 帧（`Sources/rapp-host/WindowCapture.swift:230`），收到一帧就算"变了"，把最小帧间隔设为 1 秒。
  - Linux：照常 1 fps 采集，和上一张采集比较；**不能让编码器的参考帧前进**，否则切回时和 B 对不上（`host-linux/src/server.rs` 里采集和编码在同一个 job 里，要拆开或加"只比较"的 job）。
- **退出暂停**（收到 fps > 0）：立刻采集一次，按编码器的参考帧（就是最后发给 B 的那一帧）算差异发出去，然后按新帧率走。现在两个 A 端都只有瓦片帧（运动层还没做），所以总能只发差异；以后加了运动层，最后发出去的是视频帧时退回发一整帧瓦片。
- **暂停期间的其他画面状态也限速**（我的决定，审稿发现）：窗口表（13）里有每个窗口的标题，后台 Agent 常常每秒改终端标题，Linux 每 100 ms 查一次、变了就发，光这一项就能超出 G1 十倍。所以暂停期间：
  - 窗口表变了**最多每 5 秒发一次**（发最新的）。全景里的窗口数、标签最多晚 5 秒，可以接受：它们本来就不在舞台上。
  - 菜单栏（17）、焦点区（36）暂停期间不发，退出暂停时如果变过就先发最新的，再发画面。
  - 其余 A→B 消息（剪贴板、粘贴结果、`pong`、省流级、锁屏、被遮挡、输入法、安全输入框等）照常：它们很少，有的还是人在等的回应。
- **暂停不算网络差**：暂停期间没有在途帧，不能触发省流降级，也不能触发"client stopped acknowledging frames"（Linux 15 秒）之类的超时；退出暂停时省流级沿用暂停前的。
- 新会话 hello 的 fps 总是大于 0；界面想让它一开始就暂停，就在第一帧到了以后再发暂停（见 4.4）。

### 4.4 B 端（界面）

- `effectiveFps()` 把"不在舞台上"的 1 改成 0。判断"看得见"再加一条窗口可见性：
  - **舞台上的会话**：主窗口看得见才按所选帧率，看不见（D2）就 0。全景、日志页时照旧都算不在舞台上。
  - **分离出去的窗口**：按它自己那个窗口看不看得见。
  - **macOS**：用 `NSWindow.occlusionState` 的 `.visible`（最小化、被完全挡住、在别的桌面空间、⌘H 隐藏、屏幕睡眠都会变成不可见）。主窗口在 `gui/macos/Runner/MainFlutterWindow.swift`，分离窗口在 `DetachedWindow.swift`。
  - **Linux**：Wayland 不告诉应用有没有被挡住，只认**最小化**（能拿到时）。拿不到就当看得见。
  - **iPad**：前台时只有舞台规则；进后台照旧断开。
- 还没收到第一帧的会话不暂停（否则 `sawFrame` 一直是 false，灯停在「连接中」），第一帧到了再按规则发。
- 两个 B 端会话库（Swift `RappSession`：macOS 和 iPad；Rust `rapp-session`：Linux）收到 `changed` 时，把它算进 `TrafficEvent` 的 frames 计数（或另加一个字段，由实现决定），保证 `remote_session.dart` 的活动 / 空闲判断**不用改**就照常工作。
- 流量标签、会话列表的流量数字照常显示真实字节数（会接近 0）。暂停的会话状态文字仍按活动 / 空闲显示，不新增"已暂停"字样。

### 4.5 不变的

- 用户选的档位（`session.choice`）不变，暂停只是发给 A 的有效帧率。
- 「智能」、焦点区、`pinned` 的规则不变；暂停期间它们照样随 `set_stream` 发，A 只是不出画面。

## 5. 验收

实机，A 为 macOS 和 Linux 各一台，B 为 macOS：

1. 开三个会话，其中一个不在舞台上、在播视频。它的流量数字 ≤ 0.1 KB/s；灯是「活动」。
2. 停掉视频 10–15 秒后，那个会话的灯变「空闲」。
3. 切回它：一个往返之内画面更新到当前，没有花屏；之后帧率和画质和离开前一样（没有 `省流·N`）。
4. rapp 主窗口最小化，舞台上的会话在播视频：流量 ≤ 0.1 KB/s。还原窗口后画面立刻更新。
5. 窗口被别的窗口完全盖住：同 4。切到别的 app、rapp 窗口还露在副屏上：照常满帧率。
6. 分离窗口最小化：那个会话停；还原后恢复。
7. 全景、日志页：所有会话停；回到窗口模式，当前会话恢复。
8. Linux B 端：最小化主窗口时停（如果当前桌面环境报得出最小化）。
9. iPad：前台时不在舞台上的会话停；切回恢复。

自动化测试：两个 A 端的暂停 / 恢复（暂停期间不发帧、变化时 `changed` 每秒不超过一条、恢复后第一帧和 B 的画面拼起来逐像素等于 A 当前画面、暂停不改省流级）；三个协议实现的 v15 编解码；`effectiveFps` 和 `_applyFps` 的可见性规则。

## 6. 发版和 Linux 端（我的决定）

- 协议要求两端版本完全一致（`Protocol.swift:309`、`host-linux/src/wire.rs`），照这个仓库的惯例**严格升到 v15**，不做兼容 v14 的路。以前升协议时 Linux 晚一步跟上的情况出现过（0.14.7 时 Linux 还是 v13），这期间 macOS 和 Linux 之间连不上，靠自动升级补齐。
- 五个端都在这一个分支里改完。在这台 Mac 上：Swift 两端、Dart、`client-core`、`host-linux` 里不分平台的模块（`wire`、`pacing`、`encode`）跑测试；`host-linux` 里只在 Linux 下编译的部分（`server.rs`、`capture`）和 Linux B 端尽量在 Linux 容器里编译、跑测试，做不到就在交接时写明"Linux 只改了代码，没编译"，由 Linux 那台机器验。

## 7. 留给实现的

- Linux A 端"只比较不编码"的拆法。
