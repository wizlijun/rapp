# rapp 主机（host）与客户端（client）应用规格 · 协议 v3

日期：2026-11-10
依据：已完成并通过 91 个测试的 Swift 实现（`Sources/`），代码与本文不一致时以代码为准，并回头改本文。

供以后在 Windows、Omarchy、手机等平台上重新实现时逐条对照。`2026-11-10-rapp-native-rust-design.md` 是 Rust 实现方案，协议细节以本文为准。

## 0. 目标与读法

### 0.1 你说的

- 每台电脑上都装 host。
- 常用电脑上，以及以后的手机上，装 client。
- 规格要从刚做好的 Swift 实现整理出来，尤其是压缩算法要整理清楚。

### 0.2 本文的假设（请核对）

- 一个 client 一次连一台 host 上的一个 app 窗口；想看几个窗口就开几个 client。
- host 端仍是"独占模式"：远程操作时动的是 A 上真实的鼠标和焦点。
- 安全边界不变：不加密，只有口令；只在可信局域网或 Tailscale 里用。
- 协议保持 v3。凡是愿景需要、但 v3 没有的东西（常驻、列窗口、发现、触摸、跨平台按键），都放在第 9 章"待定"，本文不擅自设计。

### 0.3 用语

| 词 | 含义 |
|---|---|
| A / host | 被控端，app 真正运行的电脑 |
| B / client | 操作端，看画面、发输入 |
| 点（pt） | 与屏幕像素密度无关的逻辑长度。A 的窗口尺寸、Ready/Size/Resize 里的尺寸都用点 |
| 像素（px） | 采集出来的图像像素。Frame 里的宽高用像素 |
| 样本 | 一个像素量化后的值，1 或 2 字节（见 4.2） |
| 内容区 | A 窗口去掉标题栏那一行后的部分。画面、坐标都只针对内容区 |
| 必须 / 应 / 可以 | 必须 = 不这样做就不能互通；应 = 参考实现这样做，改了要有理由；可以 = 自由 |

### 0.4 一致性等级

不同部分对"跟 Swift 一样"的要求不同：

| 部分 | 要求 |
|---|---|
| 线协议（第 3 章） | 必须逐字节一致 |
| 帧体（第 4.7–4.10 节，deflate 之前） | 给定同样的样本画布，必须逐字节一致 |
| 量化（第 4.3–4.6 节） | 给定同样的 BGRA 输入，必须逐字节一致（这样跨实现的测试夹具才能直接比对） |
| deflate 输出（第 4.11 节） | 不要求一致，只要求对方能解。不同 zlib 版本的压缩结果本来就可能不同 |
| 展开为显示像素（第 4.13 节） | 应一致；画面上差 1 级亮度不影响互通 |
| 应用行为（第 5、6 章） | 按"必须/应/可以"逐条看 |

## 1. 整体流程

```
  B: client                                        A: host
  ─────────                                        ───────
  解析地址 rapp://A:47800/<app>?token=…
  TCP 连接 ───────────────────────────────────────▶ 接受（同时只服务一个 client）
  Hello(版本 3, 口令, app, 档位, fps, 密度) ──────▶ 5 秒内必须收到；校验版本、口令
                                                   找到 app 的窗口（最多 10 秒）
                       ◀─────────────────────────── Ready(标题, 内容区宽高 pt)
  窗口按 A 的尺寸打开
                       ◀─────────────────────────── Frame(全帧)
                       ◀─────────────────────────── Frame(增量) …（画面变了才发）
  鼠标/滚轮/文字/按键 ─────────────────────────────▶ 注入到 A 的窗口
  拖边/缩放按钮 → Resize(pt) ─────────────────────▶ 改 A 窗口大小
                       ◀─────────────────────────── Size(A 实际内容区 pt)
  右键流量 → SetStream(档位, fps, 密度) ──────────▶ 换采集参数/编码器
                       ◀─────────────────────────── Title(新标题)（每秒查一次）
  任一方出错 ◀──────── Error(原因) ──────────────── 然后断开
```

## 2. 连接与安全

| 项 | 规定 |
|---|---|
| 传输 | TCP，关闭 Nagle（`TCP_NODELAY`）。必须 |
| 端口 | 默认 47800，可改，不能是 0 |
| 监听 | host 监听所有网卡。必须在文档里提醒"只在可信网络用" |
| 加密 | 没有。口令明文传输 |
| 口令 | host 启动时给定，非空；client 的 Hello 里带上。host 必须用恒定时间比较 |
| 并发 | host 同一时刻只服务一个 client。第二个连接进来时，host 必须发 `Error("busy")` 后关闭它，不影响已有会话 |
| Hello 超时 | 连接建立后 5 秒内没收到 Hello，host 发 `Error("no hello received")` 并断开 |
| 版本 | Hello 的第一个字节是协议版本。不等于 3 时 host 回 `Error("protocol version mismatch: host 3, client N (update both sides)")` |

## 3. 线协议 v3

### 3.1 消息帧

```
u8   type      1…12，其他值直接报错（在读长度之前就判断）
u32  length    负载字节数，小端，最大 64 MiB（67 108 864）
     payload   length 个字节
```

一条 TCP 流里消息首尾相接，没有分隔符。接收方要自己攒字节、切消息（参考：`MessageParser`）。

### 3.2 基本类型

| 写法 | 编码 |
|---|---|
| `u8` `u16` `u32` `u64` | 无符号整数，小端 |
| `f32` | IEEE 754 单精度的位模式，小端。解码时必须是有限数，否则报错 `coordinate is not a finite number` |
| `string` | `u16` 字节数 + 这么多字节的 UTF-8。最长 65535 字节；不是合法 UTF-8 就报错 |
| `rest` | 负载里剩下的全部字节 |

每条消息解码完后不能有多余字节，否则报错 `unexpected bytes after message N`。

### 3.3 消息表

方向：C→H 表示 client 发给 host，H→C 反之。

| type | 名称 | 方向 | 负载 |
|---|---|---|---|
| 1 | Hello | C→H | `u8 version`(=3) · `string token` · `string appID` · `u8 mode` · `u8 fps` · `f32 density` |
| 2 | Ready | H→C | `string title` · `u16 width` · `u16 height`（内容区，pt） |
| 3 | Error | H→C | `string reason` |
| 4 | Frame | H→C | `u8 mode` · `u16 width` · `u16 height`（像素） · `u8 isFull`(0/1) · `rest data`（deflate 数据） |
| 5 | Text | C→H | `rest`：整段 UTF-8（**没有**长度前缀，这是唯一例外） |
| 6 | Key | C→H | `u16 keyCode` · `u64 modifiers` · `u8 down`(0/1) |
| 7 | Mouse | C→H | `u8 kind`(0 按下 / 1 松开 / 2 拖动) · `u8 button`(0 左 / 1 右) · `f32 x` · `f32 y` · `u8 clickCount` |
| 8 | Scroll | C→H | `f32 x` · `f32 y` · `f32 dx` · `f32 dy` |
| 9 | Resize | C→H | `u16 width` · `u16 height`（希望的内容区，pt） |
| 10 | Title | H→C | `string title` |
| 11 | SetStream | C→H | `u8 mode` · `u8 fps` · `f32 density` |
| 12 | Size | H→C | `u16 width` · `u16 height`（A 实际内容区，pt） |

字段取值：

| 字段 | 合法值 | 不合法时 |
|---|---|---|
| `mode` | 0 gray4 · 1 color8 · 2 color16 · 3 duogray · 4 duocolor | `unknown mode` |
| `fps` | 30、15、5 或 1 | `fps must be 30, 15, 5 or 1` |
| `density` | 有限数，且 0 < density ≤ 8 | `density must be in (0, 8]` |
| `isFull` / `down` | 0 或 1 | `bad frame flag` / `bad key state` |
| `kind` / `button` | 见上表 | `unknown mouse event` / `unknown mouse button` |
| `x` `y` | 0…1，内容区左上角为 (0,0)，向右向下增大。超出范围不报错，host 会钳到 0…1 | — |

`appID` 的含义由 host 平台决定：macOS 是 bundle id（如 `com.apple.Safari`），Windows 是 exe 文件名（不区分大小写，已定），Omarchy 见 Rust 方案。

`Key` 的 `keyCode` 和 `modifiers` 目前是 **macOS 专用**的：keyCode 是 macOS 虚拟键码，modifiers 是 `CGEventFlags` 的位。client 实际只会用到下面这些：

| 键 | keyCode | | 修饰键 | 位 |
|---|---|---|---|---|
| Return | 36 | | Shift ⇧ | `0x020000` |
| Delete（退格） | 51 | | Control ⌃ | `0x040000` |
| Tab | 48 | | Option ⌥ | `0x080000` |
| Esc | 53 | | Command ⌘ | `0x100000` |
| ↑ ↓ ← → | 126 125 123 124 | | | |
| ⌘ 组合里的字母、数字、符号键 | macOS 键码（如 A=0、C=8、V=9、Z=6） | | | |

非 macOS 的 host 必须自己把它们翻译成本地按键（Windows 已定：⌘→Ctrl，⌃→Ctrl，⌥→Alt，⇧→Shift，不发 Win 键）。非 macOS 的 client 要发 Key 时也得先翻成 macOS 键码。见 9.5。

### 3.4 消息顺序

- client 连上后第一条必须是 Hello，且只能发一次。第二次发 Hello，host 回 `unexpected hello` 并断开。
- client 只能发 Hello、Text、Key、Mouse、Scroll、Resize、SetStream。发了别的，host 回 `unexpected message from client` 并断开。
- host 先发 Ready，再发第一个 Frame。Ready 之前不会有 Frame、Title、Size。
- 第一个 Frame 必须是全帧（`isFull = 1`）。
- 任一方解析出错（截断、未知类型、取值不合法、多余字节），都按"对方数据有误"处理：host 回 `bad data from client: …` 后断开；client 直接断开并报错退出。

### 3.5 地址格式（client 的输入）

```
rapp://<host>[:<port>]/<appID>?token=<口令>[&mode=gray4|color8|color16|duogray|duocolor][&fps=30|15|5|1]
```

| 部分 | 规则 | 出错提示 |
|---|---|---|
| scheme | 必须是 `rapp` | `address must start with rapp://` |
| host | 不能为空 | `address has no host` |
| port | 省略为 47800；写了就必须是 1…65535 | `bad port N` |
| 路径 | 去掉开头的 `/` 后就是 appID；不能为空，不能再含 `/` | `address has no bundle id` |
| token | 必须有，不能为空 | `address has no token` |
| mode | 省略为 gray4 | `mode must be gray4, color8, color16, duogray or duocolor` |
| fps | 省略为 15 | `fps must be 30, 15, 5 or 1` |
| 其他参数 | 忽略（旧的 `scale` 也被忽略） | — |

## 4. 编码与压缩（核心）

### 4.1 流水线

```
 A 端                                                     B 端
 ────                                                     ────
 窗口内容区，按密度采集（BGRA，预乘 alpha）
   │
   ▼ 4.3 逐行补角落 + 反预乘
   ▼ 4.4 每个像素量化成样本          （duo 档：先补角落得到 RGB，再 4.5 双色化）
   │
 样本画布（宽×高×每样本字节数）
   │
   ▼ 4.7 切 64×64 块，和上一张已发出的画布比，只留变了的块
   ▼ 4.8 每块挑一种编码（单色 / 调色板 / 双色子块 / 原样）
   ▼ 4.9–4.10 拼成帧体
   ▼ 4.11 送进本连接唯一的 deflate 流，同步刷新
   │
 Frame 消息 ───────────── TCP ─────────────▶ 4.11 本连接唯一的 inflate 流
                                             ▼ 4.12 校验并按块写回样本画布
                                             ▼ 4.13 样本展开成 BGRA 显示
```

省流量的手段一共七层，每层管一件事：

| 层 | 手段 | 省在哪 |
|---|---|---|
| 1 | 按 B 上实际显示大小采集（密度，见 5.5、6.8） | B 上画面缩小一半，像素少到四分之一 |
| 2 | 低位深（4 位灰、8 位色、16 位色） | 每像素 0.5–2 字节，原图是 4 字节 |
| 3 | 双色化（duo 档） | 每 16×16 块只剩两种基色加两级边缘过渡，文字边缘仍清晰 |
| 4 | 块差分 | 只发变了的 64×64 块，静止画面一个字节都不发 |
| 5 | 块内调色板 / 双色子块 | 少色块用 1、2、4 位索引或每像素 1 位 |
| 6 | 跨帧的 deflate 流 | 字典跨帧保留，重复出现的图案越来越便宜 |
| 7 | 只发最新帧（见 5.6） | 网络慢时中间帧直接丢掉，不排队 |

### 4.2 五种档位

| mode | 名称 | 每样本字节 | 样本含义 |
|---|---|---|---|
| 0 | gray4 | 1 | 0…15 的灰度级 |
| 1 | color8 | 1 | 固定 256 色：0…215 是 6×6×6 色立方，216…255 是 40 级灰 |
| 2 | color16 | 2 | RGB565，小端存放 |
| 3 | duogray | 1 | 同 gray4，但每个 16×16 块最多四种值（两种基色 + 两级过渡） |
| 4 | duocolor | 2 | 同 color16，但每个 16×16 块最多四种值（两种基色 + 两级过渡） |

客户端菜单里的"最省流"= duogray + 自适应密度 + 1 fps，"最清晰"= color16 + 原画密度 + 15 fps。

下面所有公式里的除法都是**非负整数除法、向下取整**，`>>` 是右移。

### 4.3 输入像素与逐行补角落

输入：宽 `W`、高 `H` 的 BGRA 图，每像素 4 字节，依次是 B、G、R、A；每行 `bytesPerRow ≥ 4W` 字节（行尾可以有填充）。颜色是**预乘过 alpha 的**。

macOS 的窗口有圆角，角落外面是全透明像素。直接量化会在四角留下黑色或白色的缺口，所以每一行先这样处理：

```
对每一行 y = 0 … H-1：
    first = 本行第一个 A ≠ 0 的像素位置
    如果整行都是 A = 0：
        y = 0 时，整行都用白色 (255,255,255) 的样本
        y > 0 时，整行照抄上一行的结果
        继续下一行
    last = 本行最后一个 A ≠ 0 的像素位置
    对 x = first … last：
        A = 255 或 A = 0：  (r,g,b) = (R,G,B)
        否则：              r = min(255, (R*255 + A/2) / A)，g、b 同理
        out[x] = 量化(r,g,b)
    x < first 的像素都复制 out[first]
    x > last  的像素都复制 out[last]
```

注意：

- `first…last` 中间的全透明像素（A = 0）不补，直接按它的 R、G、B 量化（一般是黑）。
- "复制"复制的是量化后的样本；duo 档复制的是 RGB 三元组（见 4.5）。
- 半透明像素（毛玻璃侧栏、抗锯齿的圆角边）保留，只做反预乘。

### 4.4 单像素量化 `store(r, g, b, mode)`

```
luma(r,g,b) = (77*r + 150*g + 29*b) >> 8                       结果 0…255

gray4 / duogray：
    sample = (luma*15 + 127) / 255                             0…15，1 字节

color8：
    如果 max(r,g,b) - min(r,g,b) < 16：                        接近灰色
        sample = 216 + (luma*39 + 127) / 255                   216…255
    否则：
        ri = (r*5 + 127) / 255，gi、bi 同理                     各 0…5
        sample = ri*36 + gi*6 + bi                             0…215

color16 / duocolor：
    v = (r>>3)<<11 | (g>>2)<<5 | (b>>3)                        RGB565
    存成两个字节：v & 0xFF，然后 v >> 8                          小端
```

核对用的例子：

| 输入 (r,g,b) | gray4 | color8 | color16 字节 |
|---|---|---|---|
| (255,255,255) 白 | 15 | 255 | `FF FF` |
| (0,0,0) 黑 | 0 | 216 | `00 00` |
| (255,0,0) 红 | 4 | 180 | `00 F8` |
| (128,128,128) 中灰 | 8 | 236 | `10 84` |

（红：luma = 77*255>>8 = 76，(76*15+127)/255 = 4。中灰：luma = 128，gray4 = (1920+127)/255 = 8，color8 = 216 + (4992+127)/255 = 236，RGB565 = 16<<11 | 32<<5 | 16 = 0x8410。）

### 4.5 双色化（duogray、duocolor）

先按 4.3 补角落，但输出的是每像素 3 字节的 (r,g,b)，还不量化。然后：

```
从图像左上角起，切成 16×16 的块（右边、下边的块保持实际大小，可能更小）。
对每一块：
    对块内每个像素求 l = luma(r,g,b)，lo = 最小 l，hi = 最大 l

    如果 hi - lo < 24：
        整块一种颜色 = 块内 r、g、b 各自的整数平均（和 / 个数），量化成一个样本，写满整块
    否则：
        q = (hi - lo) / 8
        暗色 D = l ≤ lo + q 的像素的 r、g、b 整数平均（笔画本身）
        亮色 L = l ≥ hi - q 的像素的 r、g、b 整数平均（背景本身）
        ld = luma(D)，span = max(1, luma(L) - ld)
        四级颜色 tone[k]，k = 0…3：每个分量 c 取 D.c + ((L.c - D.c)·k·2 + 3) / 6
            （tone[0] = D，tone[3] = L，中间两级是 1/3、2/3 处的过渡色；
              这里的除法向零截断，和 Swift 的 Int 除法一致）
        每个像素：k = clamp(((l - ld)·6 + span) / (span·2), 0, 3)，写入 store(tone[k], mode)
```

只用两端各 1/8 亮度范围内的像素定基色，是为了不让抗锯齿边缘把笔画"冲淡"、把背景"染灰"。
抗锯齿边缘落在中间两级上，所以文字边缘保留了过渡，不会断笔或变成锯齿。

结果：每个 16×16 块里最多四种样本值，通常只有两种（笔画和背景），外加边缘上的一两级过渡。
块里只有两种值时，编码时仍会识别成第 3 种块（4.8），每像素只花 1 位；有过渡级时走调色板块。
同样大小下，码率约是 gray4 的 70–80%（旧的纯双色算法约 35%，但文字会断笔、背景出灰块）。

### 4.6 样本画布

量化结果是一个 `W × H × bps` 字节的数组（`bps` = 每样本字节数），逐行排列，行与行之间没有填充。像素 (x, y) 的样本在偏移 `(y*W + x)*bps`。

2 字节样本在比较、排序时当作 `u16 = 低字节 | 高字节<<8`。

### 4.7 切块与差分

- 块边长 64。块列数 `cols = ⌈W/64⌉`，行数 `rows = ⌈H/64⌉`，块总数不能超过 65535。
- 块编号 `index = ty*cols + tx`，按行从左到右、从上到下。
- 块 (tx, ty) 的左上角是 `(64*tx, 64*ty)`，大小 `tw = min(64, W - 64*tx)`、`th = min(64, H - 64*ty)`。
- 编码器记住**上一次真正产出的那张画布**（不是上一次采集到的）。

一帧是**全帧**的条件（满足任一）：

1. 这是这个编码器的第一帧；
2. 宽或高和上一帧不同；
3. 上一帧之后调用过 `reset()`（host 在 A 窗口尺寸或标题栏高度变化后调用，见 5.7）。

全帧把所有块都编进去。增量帧只编"和上一张画布比，块内任一行有任一字节不同"的块。增量帧里一个变化的块都没有时，编码器什么都不产出，host 也就不发 Frame。

### 4.8 块种类的选择

```
1. 按行扫描块内样本，收集不同的值；收集到第 17 个就停止（count = 17 表示"多于 16"）。
2. 如果 count ≥ 3，且块内每个 16×16 子块（以块的左上角为起点切，边缘子块保持实际大小）
   都最多只有 2 种值 → 种类 3（双色子块）。
3. 否则按 count：
       1        → 种类 0   单色
       2        → 种类 1   调色板，每像素 1 位
       3 或 4   → 种类 2   调色板，每像素 2 位
       5 … 16   → 种类 4   调色板，每像素 4 位
       17       → 种类 255 原样
```

说明：

- 第 2 步对所有档位都适用，不只 duo 档。文字界面在 gray4 下也经常命中种类 3。
- 只有 2 种值的块用种类 1，不用种类 3（种类 1 更省）。
- 块是 64 的倍数对齐，子块是 16 的倍数对齐，所以 duo 档量化时的 16×16 块正好就是这里的子块。

### 4.9 各种块的字节布局

每个块在帧体里都以 3 字节开头：

```
u16 index      块编号，小端
u8  kind       0 / 1 / 2 / 4 / 3 / 255
```

接着按种类：

**种类 0 · 单色**

```
sample         1 个样本（bps 字节）
```

**种类 1、2、4 · 调色板**（`bits` = 种类值，即每像素 1、2 或 4 位）

```
u8  n          调色板长度，1 ≤ n ≤ 2^bits
n 个 sample    按 u16 值从小到大排列
索引位         逐行；每行 tw 个索引，每个 bits 位，
               高位在前紧密排列，每行末尾补 0 到整字节
               每行字节数 = ⌈tw * bits / 8⌉
```

第 x 个像素的索引在本行第 `x*bits/8` 字节里，左移量为 `8 - bits - (x*bits % 8)`。

**种类 3 · 双色子块**

按行从左到右依次写出块内每个 16×16 子块（子块大小 `sw × sh`，边缘的更小）：

```
u8  n          1 或 2
n 个 sample    n = 2 时先小后大（按 u16 值）
如果 n = 2：
    位图       逐行；每行 sw 位，1 表示该像素是较大的那个值，0 表示较小的，
               高位在前，每行补 0 到整字节；每行字节数 = ⌈sw / 8⌉
```

**种类 255 · 原样**

```
tw*th 个 sample，逐行
```

### 4.10 帧体

```
u16 tileCount           本帧里块的个数，小端
tileCount 个块           按块编号从小到大，每个块按 4.9 编码
```

帧体就是 deflate 之前的字节。

**例 1**：gray4，4×1 像素，样本 `0 15 15 0`，全帧。
一个块，2 种值 → 种类 1；调色板 `[0, 15]`；索引 `0 1 1 0` → 二进制 `0110 0000` = `0x60`。

```
01 00   tileCount = 1
00 00   index = 0
01      kind = 1
02      n = 2
00 0F   调色板
60      索引位
```

**例 2**：gray4，20×1 像素，前 16 个样本都是 3，后 4 个是 `5 9 9 5`。
3 种值，两个子块分别是 {3} 和 {5, 9} → 种类 3。

```
01 00   tileCount = 1
00 00   index = 0
03      kind = 3
01 03   子块 1：n = 1，值 3
02 05 09 60   子块 2：n = 2，值 5、9，位图 0110 → 0x60
```

**例 3**：color16，1×1 像素，纯红。种类 0，样本 `0xF800` → 字节 `00 F8`。帧体 `01 00 00 00 00 00 F8`。

### 4.11 deflate 流

| 项 | 规定 |
|---|---|
| 格式 | zlib 格式（带 2 字节 zlib 头和 Adler-32），不是裸 deflate，也不是 gzip |
| 参数 | 压缩级别 6，windowBits 15，memLevel 8，默认策略（即 zlib 的 `deflateInit` 默认值）。级别以外的参数不影响互通；级别影响流量和 CPU |
| 生命周期 | 每个编码器一条压缩流，跨帧连续使用，字典一直保留 |
| 每帧 | 把帧体整个送进去，用 `Z_SYNC_FLUSH` 刷新，得到的全部输出就是这帧 Frame 的 `data`。输出以 `00 00 FF FF` 结尾 |
| 全帧 | 压缩之前先 `deflateReset`，所以全帧的 `data` 以一个新的 zlib 头开始（通常是 `78 9C`） |
| 接收 | 每个连接一条解压流。收到全帧，先 `inflateReset` 再解；收到增量帧，接着上一帧的状态解。解压同样用 `Z_SYNC_FLUSH`，`Z_BUF_ERROR` 和 `Z_STREAM_END` 不算错 |
| 换档位 | host 换一个新的编码器（新的压缩流），它的第一帧必然是全帧，client 随之重置。两边就这样对齐，不需要额外的消息 |

后果：增量帧不能单独解，必须按顺序解完它之前、直到上一个全帧的所有帧。TCP 保证了顺序，所以不需要别的机制。

### 4.12 解码与校验

client 维护一张样本画布（宽、高、档位）。收到 Frame：

**全帧**

1. 宽、高都必须大于 0，否则 `frame has zero size`。
2. 块总数 ≤ 65535，且 `宽 × 高 ≤ 8192 × 8192`，否则 `frame too large`。
3. 重置解压流；画布改用这一帧的档位和尺寸，所有样本清零。

**增量帧**

1. 之前必须收到过全帧，否则 `update frame before any full frame`。
2. 宽高必须等于画布，否则 `update frame size does not match canvas`。
3. 档位必须等于画布，否则 `update frame mode does not match canvas`。

**然后**

1. 解压。输出上限 `2 + cols*rows*(3 + 64*64*bps)` 字节（所有块都按原样编码时的最大可能），超过就报错 `decompressed data is larger than the frame allows`。这防止一小段恶意数据让 client 分配无限内存。
2. 按 4.10 / 4.9 逐块写回画布，过程中：
   - 块编号必须 < `cols*rows`，否则 `tile index out of range`；
   - 调色板 `n` 必须在 `1 … 2^bits`，否则 `bad palette size`；
   - 每个索引必须 < `n`，否则 `palette index out of range`；
   - 双色子块的 `n` 必须是 1 或 2，否则 `bad two-tone sub-block`；
   - 未知种类报错 `unknown tile kind N`；
   - 任何地方数据不够，报错 `frame data is truncated`。
3. 最后一个块读完后不能剩字节，否则 `unexpected data after last tile`。

解码器不要求调色板有序、不要求双色子块先小后大。这些是编码器的义务，不是解码器的检查项。

任何一条出错，client 都报错并断开（参考实现直接退出）。

### 4.13 展开为显示像素

每个样本变成 B、G、R、A=255：

```
gray4 / duogray：  v = (s & 0x0F) * 17                   r = g = b = v
color8：           s ≥ 216：v = ((s-216)*255 + 19) / 39   r = g = b = v
                   s < 216：r = (s/36)*51，g = (s/6 % 6)*51，b = (s % 6)*51
color16 / duocolor：s 为 u16
                   r5 = s>>11，g6 = (s>>5) & 0x3F，b5 = s & 0x1F
                   r = r5<<3 | r5>>2，g = g6<<2 | g6>>4，b = b5<<3 | b5>>2
```

client 把展开后的图按等比缩放画到画面区，开平滑插值，空出来的地方是黑边。

### 4.14 跨实现的测试

新实现至少要过这些对照（夹具从 Swift 版生成，存进仓库）：

1. 量化：几张固定的 BGRA 输入（含圆角透明、半透明、全透明行），五种档位的样本逐字节相等。
2. 帧体：固定样本画布，五种档位、全帧和增量帧，deflate 之前的帧体逐字节相等。覆盖每种块种类和边缘块。
3. 互解：新实现编码 → Swift 解码，Swift 编码 → 新实现解码，画布完全相同。deflate 字节不比。
4. 坏数据：对第 3 章和 4.12 的每条错误，都有一条输入能触发它，且不崩溃、不过量分配。
5. 本文 4.4 的核对表和 4.10 的三个例子。

## 5. host 应用

### 5.1 启动

参考实现是命令行程序：

```
rapp-host --token <口令> [--port 47800]
```

- 口令必须给、不能为空；端口必须是 1…65535。参数不对：打印用法，退出码 2。
- 需要的系统权限（macOS：屏幕录制、辅助功能）缺了：打印缺哪个、去哪开，退出码 2。
- 监听失败：打印 `cannot listen on port N: …`，退出码 1。
- 监听成功：打印 `listening on N`。

host 没有界面，前台运行，日志写到标准输出（按行刷新）。常驻、开机自启见 9.1。

### 5.2 会话

- 一个连接对应一个会话，同时只有一个（第 2 章）。
- 会话结束（任何原因）时打印 `session ended: <原因>`，然后 host 回到等待状态，接受下一个连接。
- 会话结束时必须停止采集、停止注入、丢掉待发帧。

### 5.3 收到 Hello 之后

1. 记下档位、fps、密度，建立一个新的编码器。
2. 打印 `client connected: <appID>, <档位名>, <fps> fps, density <两位小数>`。
3. 找窗口（5.4）。找不到就回 Error 并结束会话。
4. 量出窗口的标题栏高度和内容区（5.5）。
5. 发 Ready：标题（见 5.8 的规则）、内容区宽高（pt，四舍五入，钳到 0…65535）。
6. 开始采集。
7. 启动每秒一次的定时任务（5.7）。

Hello 和找到窗口之间如果收到了 SetStream，找到窗口后按最新的设置采集。

### 5.4 找窗口

平台无关的要求：

- 按 appID 找到那个 app 的**一个**普通窗口作为本会话的目标，会话期间不换。
- 找不到必须给出能看懂的 Error，告诉用户怎么办。
- 整个过程有上限（参考：10 秒），任何卡住的系统调用都不能让会话永远等下去。

macOS 参考实现的具体做法：

| 情况 | 做法 |
|---|---|
| app 没装 | `no app with bundle id X is installed` |
| app 没运行 | 启动它 |
| app 在运行 | 激活它 |
| 选窗口 | 该进程、层级 0、宽高都 ≥ 50pt 的屏上窗口里，面积最大的 |
| 有进程没窗口 | 发一次"重新打开"（等同 `open -b`），每 0.3 秒再找一次 |
| 10 秒仍没有 | `X has no window on screen (open one, and make sure it is not minimized)` |
| 系统列窗口的调用超时 | `timed out asking macOS for windows (check the Screen Recording permission, and look for a permission prompt on A)` |

Windows 已定：appID = exe 文件名（不区分大小写）；取该进程最前面的可见主窗口；进程没运行就报错，不自动启动。

### 5.5 采集

- 只采集内容区：窗口去掉标题栏那一行。没有标题栏、全屏、或量不出来时，标题栏高度为 0。
  macOS 的量法：标题栏高度 = round(2 × (关闭按钮中心 y − 窗口顶边 y))；结果 ≤ 0 或大于窗口高度一半时算 0；全屏时为 0。
- 采集像素尺寸 = round(内容区 pt × f)，至少 1×1，其中 `f = min(密度, 该窗口所在屏幕的像素/点比)`。永远不采得比屏幕实际像素更细。
- 每秒最多采 fps 帧。
- 不画鼠标指针，不带窗口阴影。
- 画面静止时可以不产出新帧（macOS 的 ScreenCaptureKit 就是这样）。
- 交给 4.3 的像素必须是 BGRA、预乘 alpha。别的平台采到的若不是预乘的，必须先换成预乘（或把 A 全部当作 255），否则半透明像素会偏亮。

### 5.6 发送节奏（只发最新帧）

```
采集线程：每来一帧 → 记为"最新采集"，序号 +1 → 按当前档位量化（不在会话线程上做）
                    → 把（样本, 宽, 高, 档位, 序号）交给会话线程

会话线程收到样本：
    档位已经不是当前档位 → 丢弃
    序号比已经交过的还旧 → 丢弃
    正有一帧在发送中     → 放进"待发"槽，覆盖槽里原来的
    否则                 → 编码；编码器说没变化就什么也不做；否则发出，标记"发送中"

一帧发送完成：
    清除"发送中"；待发槽里有东西就取出来编码、发送
```

结果：网络慢时，中间的帧直接被后来的覆盖，不会排队越积越多；编码器总是和上一次真正发出去的画布比，所以被跳过的帧不会造成画面错乱。

### 5.7 每秒任务

每秒执行一次：

1. 打印 `[stats] <千比特每秒，一位小数> kbps <帧数> fps <宽>x<高>`。字节数包括消息头，kbps = 字节 × 8 / 1000；宽高是最后一帧的像素尺寸。然后计数清零。
2. 窗口没了 → Error `the window was closed`，结束会话。
3. 窗口尺寸变化 ≥ 0.5pt，或标题栏高度变了：按新尺寸重设采集，调用编码器 `reset()`（下一帧是全帧），发 Size（新的内容区 pt）。
4. 标题变了 → 发 Title。

### 5.8 标题

标题 = 窗口当前标题；为空时用 app 名；app 名也没有时用 `rapp`；最多取前 200 个字符。Ready 和 Title 都用这个规则。

### 5.9 SetStream

1. 和当前设置完全相同 → 什么都不做。
2. fps 或密度变了 → 按新值重设采集。不重置编码器：像素尺寸真变了的话，编码器自己会出全帧。
3. 打印 `stream -> <档位名>, <fps> fps, density <两位小数>`。
4. 档位变了 → 换一个新的编码器（第一帧必然是全帧，压缩流也随之重来），清空待发槽，并且**立刻用最后一次采集到的画面按新档位重新量化、发送**。因为静止的窗口不会再产生新帧，不这样做 B 上会一直停在旧档位的画面。

### 5.10 Resize

收到 Resize(w, h)：

1. 目标窗口尺寸 = (w, h + 标题栏高度)。
2. 以窗口左上角为准，宽高不超出它所在的屏幕右边和下边，且至少 100×100。
3. 只改尺寸，左上角不动。app 拒绝时打印 `could not resize the window (the app may not allow it)`，不报错、不断开。
4. 0.2 秒后按 5.7 第 3 步检查一次尺寸（app 可能只接受了部分尺寸），这样 client 很快就能收到 Size。

### 5.11 输入注入

注入的是系统级的真实鼠标、键盘事件，app 不需要任何配合。代价是 A 的真鼠标和焦点会被占用。

每次处理 Text、Key、Mouse、Scroll 之前：

- 窗口没了 → 丢弃这条输入。
- 目标 app 不在最前 → 激活它、把目标窗口提到最上，等 50 毫秒。

坐标换算：`(x, y)` 先各自钳到 0…1，再换成屏幕坐标
`X = min(内容区左 + x × 内容区宽, 内容区右 − 1)`，`Y` 同理。

| 消息 | 注入 |
|---|---|
| Mouse 按下 | 先把指针移到该点，再发按下；点击次数 = max(1, clickCount)，用来区分单击、双击、三击 |
| Mouse 拖动 / 松开 | 在该点发拖动 / 松开 |
| Scroll | 先把指针移到该点，再发一次按像素计的滚动：竖直 = round(dy)，水平 = round(dx)，各自钳到 ±10000。dy > 0 表示内容向下移（看到上面的内容），dx 同理 |
| Text | 按 UTF-16 切成每段最多 20 个码元（不拆代理对），每段发一次"带 Unicode 文字的按下 + 松开"，不带修饰键，段与段之间隔 5 毫秒 |
| Key | 按 keyCode 和 modifiers 发一次按下或松开（macOS 直接用；其他平台按 3.3 翻译） |

### 5.12 出错与结束

- 需要告诉 client 原因时：发 `Error(原因)`，发完或 1 秒后（先到者）断开。
- 连接断了、发送失败：直接结束会话。
- 采集被系统停掉：Error `capture stopped: <原因>`。

## 6. client 应用

### 6.1 启动

参考实现：`rapp-client "<地址>"`，地址格式见 3.5。参数个数不对或地址不合法：打印用法和原因，退出码 2。

### 6.2 连接

- 连上后立刻发 Hello：版本 3、地址里的口令、appID、档位、fps，以及按当前窗口算出的密度（6.8，此时 zoom = 1）。
- 连不上：`cannot reach <host>:<port> (…)`。
- 收到 Error、连接断开、任何解析或解码错误：在标准错误上打印原因，退出（退出码 1）。参考实现不自动重连（见 9.6）。

### 6.3 窗口

```
┌─────────────────────────────────────────────┐
│ ● ● ●       A 窗口的标题           12.3 KB/s │  ← 标题栏，右端是流量
├─────────────────────────────────────────────┤
│                                             │
│            画面区（等比缩放，黑边）              │
│                                             │
├─────────────────────────────────────────────┤
│ 在此输入，回车发送                              │  ← 输入条，高 28pt
└─────────────────────────────────────────────┘
```

- 连上之前：800×600 的画面区，标题 `Connecting to <host>…`。最小画面区 200×150。
- 收到 Ready：标题改为 A 的标题；画面区设为 A 内容区的大小（pt），也就是一开始 1:1；屏幕放不下时系统会缩小窗口，这时 zoom 按实际显示算。显示流量。
- 收到 Title：改标题。
- 收到 Frame：按 4.12 解码，按 4.13 展开并显示。
- 画面不含 A 的标题栏，四角是方的。

### 6.4 鼠标

坐标：画面在画面区里等比居中，`x = (指针 − 画面左) / 画面宽`，`y` 同理，左上为 (0, 0)。

- 按下：只在画面内才发（点在黑边上不发）。记下这个键已按下。
- 拖动、松开：只在之前发过按下的情况下才发；指针出了画面也照发，坐标钳到 0…1。
- 左键、右键各自独立。clickCount 取系统给的点击次数（钳到 0…255）。

### 6.5 滚轮

- 只在画面内才发。
- 精确滚动设备（触控板、妙控鼠标）：用系统给的点数增量。普通滚轮的"行"：×10。
- dx、dy 都是 0 时不发。

### 6.6 输入条与按键

输入条用 B 本地的输入法打字，整段一次发出：

| 情况 | 按键 | 结果 |
|---|---|---|
| 输入法正在组字 | 任何键 | 交给输入法 |
| 输入条为空 | Return、Delete、Tab、Esc、↑↓←→ | 发 Key 按下 + 松开（键码见 3.3，无修饰键） |
| 输入条为空 | 其他编辑命令 | 忽略 |
| 输入条非空 | Return | 发 Text（整段），清空 |
| 输入条非空 | Esc | 清空，不发 |
| 输入条非空 | Tab、Shift-Tab | 忽略（不让焦点离开输入条） |
| 任何时候 | ⌘Q | 退出 client，不发给 A |
| 输入条为空 | 其他 ⌘ 组合 | 发 Key 按下 + 松开，modifiers 只保留 ⇧⌃⌥⌘ |
| 输入条非空 | 其他 ⌘ 组合 | 在输入条里生效（拷贝、粘贴、撤销…） |

输入条一直持有键盘焦点；画面区不接收键盘。

### 6.7 改窗口大小（三种拖法）

开始拖动时就判定拖的是哪里（判定区 16pt）：

```
鼠标键没按住（非拖动）     → 两边
dx = 指针到左右边中较近者的距离，dy = 到上下边中较近者的距离
dx ≤ 16 且 dy ≤ 16         → 角
否则 dx ≤ dy               → 左右边
否则                      → 上下边
```

| 拖法 | B 上 | A 上 |
|---|---|---|
| 角 | 拖动时锁定 A 的宽高比；松手后 zoom = 现在的显示比例，按需发 SetStream | 不变 |
| 左右边 | 自由改 | 松手 0.3 秒后发 Resize(round(画面区宽 / zoom), A 当前高) |
| 上下边 | 自由改 | 松手 0.3 秒后发 Resize(A 当前宽, round(画面区高 / zoom)) |
| 缩放按钮、全屏、系统改尺寸 | — | 0.3 秒后发 Resize(round(宽 / zoom), round(高 / zoom)) |

- `zoom` = B 上每 pt 画面对应多少 A 的 pt。
- 锁比例时，以变化幅度（相对值）更大的那条边为准，另一条边按比例算出并四舍五入。
- 0.3 秒内又改了尺寸，只发最后一次；新的拖动开始时取消还没发的 Resize。
- 算出来的尺寸和 A 当前尺寸一样就不发。
- 收到 Size：更新 A 的尺寸。不在拖动中时，zoom 改为现在的显示比例并按需发 SetStream。**client 窗口不跟着再改一次**，A 不接受请求的尺寸时就留黑边。

### 6.8 密度与 SetStream

```
密度 = zoom × (省流 1x ? 1 : B 屏幕的像素/点比)
       钳到 [0.01, 8]；算出非有限数时取 1
```

client 记住上一次在 Hello 或 SetStream 里发出的（档位, fps, 密度）。下面任何一件事发生后重新算，**档位或 fps 不同，或者密度相对变化超过 1%** 时发 SetStream：

- 收到 Ready（屏幕放不下、窗口被缩小时，密度会比 Hello 里的小）；
- 收到 Size；
- 拖角结束；
- 窗口移到另一块像素密度不同的屏幕；
- 在流量菜单里改了选择。

Ready 之前不发 SetStream。

### 6.9 流量显示与菜单

- 位置：标题栏右端，距右边 8pt，11pt 字，次要颜色，单行。Ready 之前不显示。
- 每秒刷新一次，显示这一秒收到的字节数（含消息头）：
  - 0 → `0 KB/s`
  - 不足 1000 KB → `x.x KB/s`（1 KB = 1024 字节，一位小数）
  - 1000 KB 起 → `x.x MB/s`
- 右键或按住 Control 点击，弹出菜单，当前选择打勾：

```
最省流（双色·灰度 + 自适应 + 1 fps）    ← 两个预设都是动作，本身从不打勾
最清晰（高彩 + 原画 + 15 fps）
──────────
双色·灰度（文本优化）
双色·彩色
高彩（图像优化）
──────────
省流 1x       采集密度 = 缩放 × 1（按 B 的点）
自适应        采集密度 = 缩放 × B 的倍率（按 B 的物理像素，默认）
原画          采集密度发 8，主机压到 A 自己的像素
──────────
1 fps
5 fps
15 fps
30 fps（看视频）    ← 帧率组例外地有四项（用户定）
```

gray4、color8 不在菜单里，但地址里的 `mode=gray4|color8` 和协议照旧接受。
选了和现在一样的就不发。

## 8. 已知限制（v3 就是这样，不是 bug）

- 只有左右两个鼠标键，没有中键、侧键、悬停移动（只在按下前移一次指针）。
- 没有剪贴板同步、没有声音、没有文件传输。
- A 窗口标题栏里的按钮在 B 上点不到。
- 一个会话只对应一个窗口；app 的弹出窗口、菜单、对话框如果是独立窗口，B 上看不到。
- 远程操作时 A 的真鼠标被移走，A 前面有人时会互相抢。
- Key 的键码和修饰键是 macOS 的。

## 9. 和"每台装 host、常用设备和手机装 client"之间的差距（待定，需要你拿主意）

下面每一项都是 v3 没有的。我只列出问题和可能的方向，**都还没设计**。

### 9.1 host 常驻

现在 host 是终端里前台跑的命令行，关了终端就没了，口令写在命令行里。每台电脑都装，就需要：开机或登录后自动启动、后台运行、口令存在配置文件里、崩溃后自动拉起。各平台做法不同（macOS LaunchAgent，Windows 计划任务或服务，Linux systemd user unit）。还要注意：macOS 的屏幕录制、辅助功能权限是给"运行 host 的那个程序"的，常驻后要给 host 本身授权。

### 9.2 选哪个 app、哪个窗口

现在 client 必须事先知道 appID（还得查 bundle id）。host 多了以后，手机上更不可能手打。可能需要一条新消息让 host 列出可共享的 app 和窗口，这要升协议版本。

### 9.3 发现 host

现在要手写地址。可能的方向：mDNS/Bonjour 广播、Tailscale 的设备列表、client 里存一个收藏夹。

### 9.4 一台 host 同时被多台 client 连

现在第二个直接 `busy`。每台都装 host 后，同一台 A 可能有人想同时开两个窗口。独占模式下两个会话会抢同一个鼠标，要不要支持、怎么排队，需要决定。

### 9.5 按键与平台无关

Key 消息用的是 macOS 键码和 `CGEventFlags`。Windows host 已经靠翻译表解决。如果 client 在 Windows、Linux 或手机上，它也得把本地按键翻成 macOS 键码。两种做法：保持 v3，由各 client 维护翻译表；或者在 v4 里改成平台无关的键名（如 USB HID 用法码）。

### 9.6 断线与重连

现在 client 遇到任何错误都退出。手机切到后台、换网络都会断，可能需要自动重连、保留窗口和最后一帧。

### 9.7 手机 client

- 触摸：单击、双击、长按当右键、拖动、双指滚动、双指缩放（对应"拖角"）都要定义映射。
- 没有窗口可以拖：三种改尺寸的拖法要换成别的交互，比如"让 A 适应手机屏幕"一个按钮。
- 屏幕小：密度会自动变小，流量会下降，这部分不用改。
- 输入：输入条 + 系统输入法可以照搬；Return、方向键、⌘ 组合需要一排快捷按钮。
- 流量菜单要换成手机上的设置面板。

### 9.8 安全

每台电脑都开 host、都监听所有网卡，暴露面成倍增加，而协议不加密、口令明文。至少要考虑：只监听 Tailscale 网卡、每台不同的口令、或者加 TLS。这件事我建议在做 9.1 之前先定。
