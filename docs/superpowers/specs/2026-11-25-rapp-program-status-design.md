## 1. 一句话和边界

**`rapp-term run` 回答 CLI 的 7501 探测，从 CLI 的输出里读出状态报告，存成记录，随会话列表送到主控台。CLI 不改，用户不配。**

分四步，每一步单独能用：

| 步 | 做什么 | 本文写到哪 |
|---|---|---|
| S1 状态 | 知道每个会话在干活、在等你、做完了还是出错了；“等你”进“需要你” | 写到可以实施 |
| S2 问答事件 | “等你”的那一刻产生一条事件：哪一类、问了什么、当时的屏幕文字。给主控台，也给本机的其他程序（只读） | 写到接口 |
| S3 人点一下 | 在“需要你”里直接点“允许”或“拒绝”，不用切进会话。每一次回复都是人的一个动作 | 写到接口，按键要先探查 |
| S4 自动回应 | 规则自动回、助理代回、脚本回。默认关，使用者知情后按设备、按 app 打开 | 写到接口 |

不做：

- **伪装和绕过**：把自动输入装成人（随机延时、模拟打字节奏）、碰凭据、切号、多人共用一个订阅。理由见 §7.7。
- 协议道（Agent SDK、app-server、ACP）。理由见调研 §3；另外需求反馈 §0.6 记着 Anthropic 和 Google 的订阅不能用在第三方工具里。
- tmux 后端。tmux 不答探测，维护者已经拒绝加（调研 §4.2）。tmux 会话继续用现在的未读规则。
- 读 CLI 自己的文件、装 hook、改 CLI 的配置。
- 按 app 的屏幕规则。它仍然是 app 配置第二版的事，本文不依赖它。

### 2.1 确切的代码位置

**答探测（gascity）**

- 顺序的道理：`gascity@0997336 internal/runtime/programstatus/relay/doc.go:10-20`。程序通常一口气发出“7501 探测”和“设备属性查询”。中继读到探测，**先把回答排进程序的输入队列，再把这块输出转给外层**。外层对设备属性查询的回答只能排在后面，所以程序先读到 7501 的回答。
- 实现：`relay/bridge.go:70-97`（`Output`），回答的内容在 `relay/bridge.go:15`：`ESC ] 7501 ; ? ESC \`。
- 探测匹配器：`probe.go:13-94`。一个不分配内存的小状态机，认 `ESC ] 7501 ; ?` 加 BEL 或 `ESC \`，跳过 DCS，能跨读取边界。
- 流式扫描器：`scanner.go:46-221`。从任意切分的字节流里拼出完整的 7501 报告、探测和 OSC 133;A；超过 4096 字节的丢弃。

**解析和记录（zellij）**

- 限制常量：`zellij@d73e7d5 zellij-server/src/attention/program_status.rs:8-18`。
- 解析一条报告：同文件 `:99-181`（`parse`）；base64 解码和控制字符检查在 `:70-97`。
- 记录表：同文件 `:185-356`。`apply`（`:251`）处理新报告和 `clear`；`drop_transient`（`:306`）丢掉临时状态；`deciding_record`（`:329`）决定哪条说了算：根记录为准，任何子记录是 `blocked` 或 `error` 时由它顶上来。
- 接进终端解析的地方：`zellij-server/src/panes/grid.rs:5539-5552`。
- 什么时候丢临时记录：`zellij-server/src/attention/tracker.rs:761-764`（出现新的 shell 提示符）和 `:909`（程序退出）。
- 把状态再报给外层终端：`zellij-client/src/host_status.rs:1-47`。rapp 第一版用不到（§5.8）。

**核对用**

- kitty：`kitty@a6e966b kitty/program_status.py:15-59`，`kitty/window.py:1722-1733`。`program_status.py:25-26` 指出规范写的 id 总长 128 字节和“每段 32、最多 8 段”对不上，它取了后者算出来的 263。zellij 和 ghostty 取 128。rapp 取 128【我定的】，和多数一致。
- ghostty：`ghostty@10473f6 src/terminal/osc/parsers/program_status.zig:58-104`。
- gascity 清除不可见字符：`parse.go:271-286`。

## 4. 做法的选择

要在 `rapp-term run` 里认出 7501，有三种做法：

| | A. 手写扫描器，再移植 zellij 的解析（**选这个**） | B. 再开一个 `vte` 解析器，只接 OSC | C. 改仿真器 |
|---|---|---|---|
| 做法 | 照 gascity 的 `Scanner` 写一个小状态机，只认 7501 和 133;A；认出的报告交给照 zellij 写的 `parse` | `alacritty_terminal` 带着 `vte` 0.15，另起一个 `Parser`，在 `osc_dispatch` 里接 7501（zellij 的接法） | 让 `Emu` 里的 `Term` 把未知 OSC 交出来 |
| 好处 | 不依赖仿真器；可以放在“写窗口之前”；不会 panic；和 `fit.rs` 里的 `SeqTracker` 是同一种写法 | 代码最少 | 只解析一遍 |
| 代价 | 约 200 行状态机，要自己测切分边界 | 全部输出解析两遍；`vte` 的 OSC 行为要逐条核对 | `alacritty_terminal` 的 `Handler` 不暴露未知 OSC，要 fork |

选 A 的理由【我定的】：答探测必须发生在把输出写给窗口之前（§5.3），而仿真器在 `guarded` 里跑，是允许 panic 后重建的（`rust/term/src/pty/holder.rs:298-312`）。状态这条线不应该跟着仿真器一起坏。

## 5. S1：状态

### 5.1 数据怎么走

```
CLI（claude / codex / agy）
   │ 输出字节
   ▼
pump_output（holder.rs:267）
   ├─ ① ps.feed(字节)  ──► 有探测：把回答送进 shared.input（排在键盘输入的同一个队列里）
   │                   └─► 有报告：解析 → 记录表 → 说了算的那条变了就改 shared.ps、rev 加一
   ├─ ② 原样写给窗口（现有）
   └─ ③ 喂给仿真器（现有）
```

①必须在②之前。这就是 gascity 的顺序。`shared.input` 是键盘输入用的同一个通道（`rust/term/src/pty/mod.rs:29`），由 `pump_input` 一个线程按顺序写进伪终端，所以外层窗口后来的回答一定排在后面。

### 5.2 新文件 `rust/term/src/pty/ps.rs`

三样东西，都不碰仿真器：

1. **`Scanner`**：照 `gascity scanner.go:46-221`。输入任意切分的字节，输出三种事件：探测、报告（正文字符串）、新提示符（OSC 133;A）。BEL 和 `ESC \` 都认；序列中途来了 ESC、CAN、SUB 就作废；DCS 整段跳过（不拆 tmux 的包裹【我定的】，`rapp-term run` 外面不是 tmux）；一条序列超过 4096 字节就丢掉，缓冲不超过这个数。
2. **`parse(正文) -> Option<Message>`**：照 `zellij program_status.rs:99-181`，去掉 `vte` 参数那一层。规则照规范：不认识的键忽略；键重复取最后一个；`state` 不认识、`id` 不合法、超限、base64 解不开、解出来有控制字符，整条丢弃。解出来的 `msg`、`title` 再去掉双向控制符和不可见字符（照 `gascity parse.go:271-286`）。
3. **`Records`**：照 `zellij program_status.rs:185-356`。最多 256 条，满了丢最久没更新的；每条报告整条替换；`clear` 带 `id` 清这一枝，不带清全部；`deciding()` 给出说了算的那条。

依赖：`base64`（工作区的 `Cargo.lock` 里已有 0.22.1，`rust/term/Cargo.toml` 里加上）。

### 5.3 答探测

- 回答固定是 `ESC ] 7501 ; ? ESC \`【我定的】，和 gascity 一样。理由：这是唯一一个有人对着真的 Claude Code 跑通并留了测试的回答。zellij 会跟着探测的结尾用 BEL，还附上状态列表；规范说这两样都是可选的。
- 一块输出里有几个探测就答几次。排着队还没写进伪终端的回答最多 64 条，多出来的丢掉（`gascity relay/bridge.go:21-24` 的上限），免得一个只发探测、不读输入的程序把队列撑大。
- 配置关掉时（§5.9）不答、不解析，行为和现在完全一样。

### 5.4 记录什么时候没

| 时机 | 做什么 | 依据 |
|---|---|---|
| 收到 `state=clear` | 照 `id` 清 | 规范；Claude Code 和 Codex 退出时都发 |
| 出现新的 shell 提示符（OSC 133;A） | 丢掉 `working`、`blocked`、`idle` | 规范；`zellij tracker.rs:761-764`；kitty 的 `TRANSIENT_STATES` |
| `rapp-term run` 里的程序结束 | 会话本身就结束了，不用另做 | |

已知的缺口：CLI 被强杀、没来得及发 `clear`，而 shell 又没有开 133 提示符标记时，旧状态会留着。规范没有心跳。第一版接受它；主控台上能看到屏幕已经回到 shell。

### 5.5 送出去的数据

`Shared`（`rust/term/src/pty/mod.rs:23-38`）加一个 `ps: Mutex<Option<Ps>>`。`Status`（`rust/term/src/pty/local.rs:95-112`）和 `TermRow`（`rust/term/src/list.rs:7-17`）各加一个可选字段 `ps`，没有就不发，写法照 `Status.key`：

```rust
pub struct Ps {
    pub state: String,            // idle | working | done | blocked | error
    pub kind: Option<String>,     // permission | question | auth，只在 blocked 时有
    pub app: Option<String>,      // claude-code | codex | …
    pub msg: Option<String>,      // 已清洗；列表里最多 200 个字符，超出截断加 …
    pub progress: Option<u8>,
    pub since: u64,               // 进入这个状态的 Unix 秒
    pub stopped: u64,             // 最近一次从 working 或 blocked 变成 done、error、idle 的 Unix 秒；没有过是 0
    pub seq: u64,                 // 说了算的那条每变一次加一
}
```

- 旧版的 `rapp-term run` 不发 `ps`，新版的服务读到没有就按现在的规则走。两边谁先升级都不坏。`LOCAL_V` **不加一**（review 定）：`Status` 没有 `deny_unknown_fields`，`ps` 是带 `#[serde(default)]` 的可选字段，旧服务读新 `Status` 会忽略它，新服务读旧的得到 `None`。
- 服务和 hub 原样转这个字段：hub 把 `r["terms"]` 整个当 JSON 转（`rust/hub/src/terms.rs:92`、`:185`），不用改。主控台要改解析（§5.6）。
- testkit 里有断言整行会话列表的测试，加字段后跑 `cargo test --workspace`，不要只跑 `rapp-term` 一个 crate。

### 5.6 未读和“需要你”

`pty_rows`（`rust/term/src/serve.rs:529-546`）里这样算：

| `ps` | `unread` | 进“需要你” |
|---|---|---|
| 没有 | 现在的规则：有输出，然后安静 3 秒 | 否（和现在一样：终端会话现在不进“需要你”） |
| `working` | 否 | 否 |
| `done`、`error`、`idle` | `stopped` 晚于上次看过就算未读，不再等 3 秒安静 | 否【我定的】 |
| `blocked` | 是 | **是**，看过也不清，直到状态离开 `blocked` |

- “看过”的记法不变（`serve.rs:479-481`）。
- **“需要你”在主控台算，不在服务里算**（review 补）。现在“需要你”只有两类：断开的 app 会话和离线的设备（`gui/lib/ui/main_state.dart:1049-1061`），终端会话一条都不进。服务只送 `ps`；主控台加一类 `NeedKind.terminal`，凡是 `ps.state == "blocked"` 的会话进这一类，离开 `blocked` 就自动出去。`TermRow` 的 `unread` 仍由服务按上表算。主控台解析会话行的地方是 `gui/lib/hub_client.dart:171-181`（`_termList`），要加读 `ps`。
- 主控台只认 `pty` 的行（`hub_client.dart:178`），tmux 的行本来就不显示，所以 §1 “tmux 不做”在主控台上没有可见的差别。
- 这也回答了终端会话设计 §18 第 2 条留着的问题（“未读算不算进需要你的数字，数字可能一直不为 0”）：有 7501 的会话只有 `blocked` 才进数字，回合结束只亮未读灯。
- Agent 安静地想了很久不会再被误判成“停下来了”，因为 `working` 期间不看安静时长。

### 5.7 主控台上看到什么

守设计语言 §0：平时只改灯，不弹窗、不抢焦点。

| 状态 | 灯 | 列表和全景里的一行字 |
|---|---|---|
| `working` | 活动 | 有 `progress` 就带百分比 |
| `blocked` | 等你 | “等确认”“在提问”“要登录”加 `msg`。例：`等确认 · approve Bash: touch /tmp/…` |
| `done` | 未读 | 无 |
| `error` | 未读，错误色 | `msg` |
| `idle` | 无 | 无 |

`msg` 是程序给的文字，只当纯文字显示，不当标记解析。

### 5.8 外层的终端窗口

第一版**原样转发**，探测和报告都不动【我定的】。

- 外层是 Terminal.app 这类不支持的：它不认识 7501，忽略。
- 外层是 iTerm2 3.7.5、kitty 0.50.0 这类支持的：报告到了外层，标签页上自己会显示状态，这是白得的好处。但外层也会回答探测，程序会收到两次回答。有没有副作用未实测，列在 §9 第 3 条。有的话，第二步改成把探测从转给窗口的字节里拿掉。

### 5.9 开关

`term.json`（`rust/term/src/config.rs:11-15`）加 `programStatus`，默认 `true`【我定的】。写进《配置规范总览》。

### 5.10 安全和日志

- `msg` 里可能有命令和路径。它和屏幕文字走同一条设备间加密隧道，**不进日志**（照终端会话设计 §14：不记屏幕内容和输入内容）。
- rapp 写回给程序的只有那一条固定的探测回答，记录的内容从不回写。这是规范的要求。
- 状态变化合并后才通知：同一块输出里连着几条报告，只按最后的结果加一次 `rev`。

## 6. S2：问答事件

**事件**：说了算的那条记录进入 `blocked`，或者从 `working`、`blocked` 变成 `done`、`error`、`idle` 时，产生一条：

`session` 用会话行的 `id`（`pty_id`，按 `key` 算，形如 `term:pty:<key>`，`serve.rs:515`），不用 pid。

```json
{"t":"ask","session":"term:pty:9f2c…","key":"9f2c…","app":"claude-code",
 "kind":"permission","msg":"approve Bash: touch /tmp/x","seq":12,"at":1764054000,
 "tail":["屏幕上的每一行，去掉颜色转义的纯文字"]}
```

- `t` 是 `ask`（在等你）或 `rest`（回合结束，带 `state`）。
- `tail` 是那一刻整屏的纯文字【我定的】，用现成的 `strip_escapes`（`rust/term/src/screen.rs`）。Codex 没有 `msg`，内容靠它；Claude Code 有 `msg`，它是补充。
- `seq` 用来对上“是不是同一次提问”，S3 发按键前靠它核对。

**去处**

1. 主控台的“需要你”：显示类别和 `msg`；没有 `msg` 时显示 `tail` 里光标附近的几行。
2. 本机的其他程序：服务加一个订阅请求，逐行吐 JSON，写法照现有的会话列表监视流。这就是 PS1 说的“捕获到，并做其他处理”的出口。**这个出口默认只读**：通知、记录、汇总、起草回复给人看，都可以拿它做。往会话里送输入的入口只在这个会话开了自动回应以后才有（§7.7）。

事件带屏幕内容，所以不进日志；接不接进全局的记录，等记录那份规格（路线图 D1）。

## 7. 合规、S3 和 S4

我不是律师。下面是按各家公开的条款、文档和官方答复整理的，其中一部分是别人的转述（都标了）。默认状态（什么都不开）把风险降到和“在普通终端里手动用这三家 CLI”同一个水平；它不能替厂商做保证。打开自动回应以后的风险由使用者承担（§7.7）。各家条款这一年改过多次，每次发版前照 §7.6 重查。

### 7.1 三家各自划的线

| | 明确允许的 | 明确不允许的 |
|---|---|---|
| **Anthropic** | 订阅登录用于 Claude Code 和 Anthropic 自己的应用的普通、个人使用。Claude Code 自己的权限模式和放行规则 | 消费者条款第 3 条：除了用 API key 或另有明确许可，不得通过机器人、脚本等自动或非人工的方式访问服务。不得共享账号登录 |
| **Google** | 交互式的 App、IDE、CLI 会话；自己直接写的脚本和 CI 里用 `agy -p`；官方扩展和支持 ACP 的编辑器。跑未改动的官方程序、由人直接驾驶 | 用第三方软件访问服务；把 agy 包进第三方 Agent 或应用；自动循环；无人值守的后台使用；自动切换账号；让别的 Agent 把活转给 agy，即使每一步有人批准。后果是停号 |
| **OpenAI** | 用 ChatGPT 登录 Codex；Codex 自己的审批策略和自动审查 | 共用、转让额度；用一个人的订阅替另一个人服务 |

- Anthropic 那一栏：消费者条款的原句经多个来源引用，我没有读到条款原页；“普通、个人使用”出自 Claude Code 的法律与合规页，同样是经引用。
- Google 那一栏：常见问题页和论坛上的官方答复（2026-10-23）我读了；“无人值守不支持”“别的 Agent 转活不允许”来自一篇整理官方答复的文章（2026-11-16），没有核对原帖。
- OpenAI 对“自动往官方 TUI 里按键”没有查到条文。

**三家里 Google 最严，Anthropic 的条文最宽泛。** rapp 的默认状态对三家一律按最严的来。

### 7.2 默认状态下 rapp 守的七条线

第 2、3、4 条是默认。使用者可以照 §7.7 自己打开自动回应，打开以后这三条对那个会话不再成立，责任在使用者。第 1、5、6、7 条不随任何开关变。

1. **官方原版程序，用户自己的原生登录。** rapp 不碰凭据，不读登录文件，不代理请求，不改程序，不往里注入东西。
2. **人直接驾驶。** 进到 CLI 里的每一次输入，都来自一个人当下的一个动作：打字、粘贴、点一下。一个动作对应一次输入。
3. **rapp 自己不产生输入。** 不按规则自动回，不定时发，不循环，不重试，不用模型起草了直接发。唯一的例外是 7501 探测的那条固定回答：它是终端对程序的回答，到不了模型，也不是替人做决定。
4. **不把 CLI 接到别的 Agent 下面。** rapp 不派任务（已有的决定），这一版**新加的**口子（S2 的订阅、S4 的输入入口）在没开自动回应时都不能往会话里送输入。
   - 已有的情况照实写（review 补）：`rapp-term run` 的本机 socket 现在就有 `view` 请求，它收 `keys` 和 `text` 并写进伪终端（`rust/term/src/pty/view.rs:213-222`、`:252`、`:304-307`），本机任何拿得到 `term` 目录 token 的程序都能用。这是主控台看和回会话的通路，本文不改它，也不把它当成给助理的入口来宣传；“合规使用”说明里写明：拿 token 自己往 `view` 里送按键，和 S4 一样是使用者自己的自动化，责任在使用者。
5. **一个订阅一个人。** 不切号，不轮换，不共享。使用说明里写明：rapp 的 key 意味着互信，带着订阅 CLI 的设备不要把 key 分给别人。
6. **不伪装。** 不改 CLI 的环境变量和配置（PS2），不冒充别的终端。答 7501 探测是如实回答：`rapp-term run` 确实支持它。
7. **可以整个关掉**（§5.9）。

### 7.3 这些线落在设计上

| 部分 | 结论 | 说明 |
|---|---|---|
| S1 状态 | 照做 | 答探测、读报告是终端的本分，厂商发这个探测就是给终端答的。它不产生任何发往厂商的请求，不改变 CLI 的行为，只是多知道一个状态 |
| S2 事件 | 照做，出口默认只读 | 事件只往外给；输入入口要开了自动回应才有 |
| S3 人点一下 | 照做，默认开 | 每次回复都是人的一个动作 |
| S4 自动回应 | 做，默认关 | 落在 §7.1 不允许的那一栏里。由使用者知情后自己开，后果自担（§7.7、§7.8） |
| 远程看和回 | 照做 | 人在主控台上打字，和 SSH、tmux 一样是人在用 |
| 协议道 | 不做 | Anthropic、Google 对第三方产品用订阅登录都有限制（调研 §3.1） |

封号依据的是厂商在服务端看得见的行为：凭据被别的程序拿去用、无人值守的循环、异常的用量、切号（我的分析，厂商没有公布检测办法）。S1、S2 在服务端看不出和普通终端有任何差别。

**它改了一条已有的界线吗。** app 配置设计第 127 行写的是：“在等你”的判断只观察、不替用户点。默认状态仍然守着它：rapp 不替用户点，是用户自己点。使用者打开自动回应以后，这条界线对那个会话就改了，那是使用者自己的选择（PS6）。

### 7.4 S3：人点一下

“需要你”里，`blocked` 的那一行除了显示问的内容，再给两三个按钮：

| `kind` | 按钮 | 点了以后 |
|---|---|---|
| `permission` | 允许、拒绝、打开 | 发这个 app 配置里写的那组按键 |
| `question` | 打开 | 进会话自己选。选项的按键因题而异，第一版不做快捷回答【我定的】 |
| `auth` | 打开 | 永远由人进去处理 |

规矩：

1. **一次点击只回一个提问。** 没有“全部允许”【我定的】。
2. **发之前核对。** 再读一次这个会话的 `seq` 和状态，已经不是同一次提问就不发，提示“已经变了”。
3. **发之后确认。** 限定时间内状态离开了 `blocked` 才算成功；没离开就提示“没成功，打开看看”，不重试。
4. **按键写在 app 配置里**，按 `ps.app` 匹配，例如 `"reply": {"allow": ["Enter"], "deny": ["Escape"]}`（键名是示意，未实测）。这个 app 没有配，就只有“打开”一个按钮。
5. **只发按键，不发文字。**
6. 日志照现有规定：记谁在什么时候对哪个会话点了允许或拒绝，不记内容。
7. **这些按钮只接受人的操作。** 用户问过（2026-11-25，原话）：“我有在 pad 上，由我的助理机器人替我回复一下、点一下，有没有问题。”有问题：点的是不是人，和在哪台设备上点没有关系，助理代点就是非人工的自动输入，落在 §7.1 不允许的那一栏里。所以助理代点不走 S3，走 S4（§7.7），由使用者自己打开。
8. **通路**（review 补）：主控台不开 `view` 也要能发，所以是一个新的设备请求，例如 `reply_term`（会话 id、`seq`、`allow` 或 `deny`），走 hub → 服务 → `rapp-term serve` → 那个 `run` 的本机 socket 上一个新的本机请求。按键由跑 CLI 的那一端照 app 配置换成字节，主控台只送“允许 / 拒绝”。要动的地方：服务的 `Op` 和它的请求允许列表（`rust/service/src/term.rs`，有两处允许列表，见合并时的教训）、hub 的命令分发（`rust/hub/src/lib.rs:433`）、协议版本照新加请求的惯例定。
9. **不碰“窗口跟谁的尺寸”**：`view` 的输入会把窗口尺寸交给最近打字的那个看的人（`view.rs:222`，`fit.input`）。S3、S4 的按键直接送进 `shared.input`，不经过 `view`，不改 `fit`，也不算进会话结束时上报的 `inputs` 数。

**不开 S4 时助理可以做的**（都不往 CLI 里送输入）：读 S2 的事件；把好几个会话的提问排好先后；说明这条命令要干什么、有没有风险；给出“建议允许”或“建议拒绝”和理由；提问是文字题时起草一段回复放进输入区，由人看过再发。人用语音说“允许”算人的动作。

### 7.5 自动放行交给 CLI 自己

想少被问，合规的办法是用各家自己提供的设置。它们是厂商为这件事做的，不涉及第三方。rapp 只在使用说明里指路，**不替用户写这些配置**（PS2）。

| CLI | 官方的办法 |
|---|---|
| Claude Code | 权限模式：2.1.283 起交互会话默认就是 auto 模式，由一个分类器在后台审每个动作。会话里按 Shift+Tab 切换。再细的用放行、询问、拒绝规则。提问（`AskUserQuestion`）任何模式都不会自动回答，这是它自己的设计 |
| Codex | 审批策略 `approval_policy`（`untrusted`、`on-request`、`never`）配合沙箱；`approvals_reviewer = "auto_review"` 让一个审查 Agent 代替人批越界请求。会话里用 `/permissions` 切换 |
| agy | 放行、询问、拒绝规则，以及它自己的 Auto 模式（来自第三方介绍，没有读官方文档） |

用了这些以后，rapp 这边剩下要人点的就是 CLI 自己认为必须问人的那些。

### 7.6 还留着的风险，和每次发版前要做的

1. **agy 的边界不清楚。** Google 的常见问题说“把 agy 包进第三方应用”不受个人套餐支持，没有说终端模拟器、tmux、远程会话算不算。那篇整理文章还转述了一条答复：从一个第三方的 Agent 管理工具里启动 agy 不在支持范围内，那个帖子问的是多 Agent 工作流。rapp 的情况是人自己在 shell 里敲 `agy`、自己驾驶，我的判断是它属于“交互式 CLI 会话”，但 Google 没有就这种情况表过态。**最稳妥的做法是去 Google 的开发者论坛要一份书面答复**，已有好几个工具的作者这么做了。用户决定不起草询问帖（§10 第 2 条），这条不确定照实写进“合规使用”说明。
2. **条款会变。** 发版前重查三处：Anthropic 的消费者条款和 Claude Code 法律与合规页；Antigravity 的附加条款和常见问题；Codex 的条款。结论记进产品决策。
3. **想要自动化又不担条款的风险**，有两条路：用 CLI 自己的自动审批（§7.5）；或者那个会话改用 API key 登录。Anthropic 的条文把 API key 列为自动访问的例外，Google 给第三方 Agent 指的正路也是 API key。按量付费，不走订阅。

### 7.7 S4 自动回应：功能都给，默认关，使用者自己开

依据是 PS6。PS1 要的自动化都做，放在一个默认关着的开关后面。开不开、对哪家开，由使用者决定，后果由使用者承担。

**三种形式，共用一个输入入口**

| 形式 | 谁决定回什么 | 说明 |
|---|---|---|
| 规则自动回 | 使用者事先写的规则 | 规则写明：哪个 app、哪一类、`msg` 或 `tail` 匹配什么、回哪组按键或哪段文字 |
| 助理代回 | 使用者的助理程序 | 助理订阅 S2 的事件，经输入入口发按键或文字。“pad 上由助理替我点一下”就是这一种 |
| 脚本回 | 使用者自己的程序 | 同一个输入入口 |

输入入口：服务加一个本机请求，参数是会话、`seq`、按键或文字。这个会话没开自动回应就拒绝。助理本身（用哪个模型、跑在哪）不在本文范围内，这里只定它能用的入口。

**怎么打开**

1. 默认关。开关在跑 CLI 的那台设备自己的 `term.json` 里（`autoReply`），不同步【我定的】。
2. 可以按 app 开。比如只对 `codex` 开，`claude-code` 和 `agy` 不开。
3. 第一次打开时显示一段说明，使用者确认后才生效。确认记在本机：时间和说明的版本号。说明的文字改了，下次要重新确认。
4. 说明要讲清五件事（逐字的文本在写计划时定稿，放进附录）：
   - 打开以后，程序会代替你往 CLI 里输入。
   - 三家的条款现在怎么写（§7.1 的要点，带查的日期和链接）。
   - 可能的后果是订阅账号被暂停或终止。这个后果由你承担，rapp 的作者不承担。
   - 用 API key 登录的会话不受订阅条款这一条的限制。
   - 随时可以关。

**开着的时候**

- 会话在列表、全景和舞台上都带一个一直在的“自动”标记。
- 每次自动回应记一条：时间、会话、app、类别、`msg`、命中的规则或发起的程序、回了什么。记在单独一个只在本机的文件里，可以设保留天数【我定的】。它是给使用者自己查“当时放行的是什么”的，不是 rapp 的运行日志，所以带内容；它不出本机。
- 主控台上有一个“全部停下”，一下关掉这台设备上所有的自动回应。

**不随开关变的规矩**（防的是出事，和条款无关）

1. 发之前核对 `seq`；发之后确认状态离开了 `blocked`。不成功不重试，交给人。
2. `kind=auth` 不自动回。
3. 限速：每个会话每分钟最多 6 次【我定的】，超了就停下交给人。这是防回应和提问互相触发成死循环。
4. 按 `tail`（屏幕文字）匹配的规则在界面上单独标出“按屏幕匹配，可能认错”。Codex 现在没有 `msg`，对它写规则只能按类别或按屏幕。

**我建议不做，也没有写进规格的**

- **伪装成人**：随机延时、模拟打字节奏、挑时间段。它不是功能，是为了躲检测，还会让使用者以为“这样就安全了”。
- **碰凭据、切号、多人共用一个订阅。**

这两样不属于“把选择交给使用者”，而是帮使用者绕过厂商。你要是不同意，告诉我。

### 7.8 责任怎么交给使用者

| 做法 | 放在哪 |
|---|---|
| 默认关；打开之前知情确认；确认有记录 | §7.7 |
| “合规使用”一节：rapp 是通用的终端工具，怎么用、用在哪个账号上，由使用者决定并负责；列出三家条款的链接和查的日期 | README；每次发版的说明 |
| 无担保、不承担责任 | GPL-3.0 第 15、16 条本来就有；README 里点一句 |
| 开着时一直有标记；每次自动回应都有本机记录 | §7.7 |

这些做到的是：rapp 把选择和后果讲清楚，交到使用者手里。有两件事它做不到（我的分析，不是法律意见）：

1. **使用者的账号该被停还是会被停。** 声明改变不了厂商怎么执行条款。你自己也是使用者：在订阅登录的会话上打开自动回应，风险和别的使用者一样。
2. **声明能不能免掉 rapp 的作者和以后的商业主体的责任**，要看法域和怎么卖。rapp 以后要随硬件商业化，这一条建议发布前请律师看一次。

| 步 | 做什么 | 验收 |
