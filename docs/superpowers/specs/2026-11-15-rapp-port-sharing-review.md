# rapp 端口分享设计：评审记录（企业安全管理员的视角）

日期：2026-11-15。状态：**§5.1 的 6 处已并入规格第 2 稿（L4、L5 按操作评审改过），用户已确认（U141）；§5.2 组织模式另立规格，未开始。** 本文不改代码。

被评审的：`2026-11-15-rapp-port-sharing-design.md` 第 1 稿（下称"规格"），连同它依赖的 relay 规格（`2026-11-13-rapp-relay-design.md`）和换 key（`2026-11-14-relay-device-2c-design.md`，下称"2c"）。

用户的要求（2026-11-15，原话，反馈文档 U138）："现在请企业级安全管理员，评审下方案；确保能合规进入企业使用"。

评审的立场：我是一家企业里负责审批"员工电脑和服务器上能装什么远程访问工具"的人。我要回答的是：这个东西装进来以后，出了事我能不能查清、能不能止损、审计来了能不能交代。

三点说明：

- **"合规"不是一份设计文档能保证的。** 它取决于那家企业按哪套标准被审、在哪个国家、审计的人怎么判。本文能做的是指出按常见标准一定会被问到的地方。我不是律师，也不是审计师；§6 的条款对照是我的理解，条款号没有逐条对原文。
- 标"查过"的是这次检索到资料的；标"仓库里"的是在代码或已有文档里看到的；其余是凭经验说的。
- 规格的 §16 已经列了 11 条没验证的，本文不重复，只补新的。

## 0. 结论

**给个人和几个人的小团队用：可以通过。** 公网上没有服务端口、relay 看不到内容、默认什么都不交出、服务器只能被访问，这几条比 frp 和手工端口映射强得多，也比多数人自己搭的方案规矩。

**作为企业的正式工具：现在不能通过。** 有 5 条阻断项（§3）。它们不是这份规格新带来的毛病，而是同一个根上长出来的：**"有 key 就互信"**（relay 规格 R10、R11）。这条规则对个人是优点，一把 key 管到底；对企业是缺点，因为它意味着没有个人身份、没有权限区分、离职要全员换 key。端口分享把这个缺点放大了：以前拿到 key 的人能远程操作桌面；现在还能直接连上每一台机器分享的数据库、管理页面和 SSH。

**我的建议分两层：**

1. **这份规格现在就加 6 处"留位置"**（§5）。每一处都小，不改变个人使用时的体验，但以后做企业版时不用推翻重来。
2. **企业要的那一整套（身份、权限、集中策略、集中审计）单独立一份规格**，叫它"组织模式"（§5.2）。它和现在的"一把 key"并存：个人用 key，企业用组织模式。不建议塞进这一份。

另外，评审时查到两件会直接影响规格 §9 的事（§1 的 C3、C4），和企业无关，个人使用也会碰到。

## 2. 做对了的

站在审批的人的角度，这些是加分项，不要在后面的修改里丢掉：

- **公网上没有任何服务端口**，设备只向外连一个地址、一个端口。防火墙规则写得出来，也查得到。
- **relay 拿不到 key，看不到内容和名字。** 托管 relay 的那台机器被攻破，损失是服务中断和"谁连过谁"，不是数据。
- **默认拒绝**：没注册的端口访问不到，SSH 也不例外。
- **只接到分享方自己的 `127.0.0.1`，不转发到它所在的网段。** 这一条请一直守住：一旦能转发到别的地址，每台装了 rapp 的机器都成了进入那个网段的网关。
- **服务器只能被访问**，并且带公钥的做法挡住了"一台服务器失守后横向进入别的服务器"。
- **入口只在本机回环地址上听。**
- **名字钉在设备密钥上**，换了设备要人确认。
- relay 的限速、锁定、审计、非 root、只读文件系统；日志里不记 key、口令、内容。
- 不自己发明加密算法；握手和证明绑在一起。

## 3. 阻断项（企业使用前必须解决）

### B1 一把共享的 key，没有"谁"

所有设备填同一把主 key。拿到 key 的人和合法员工在系统里没有区别；日志里只有设备指纹和"自称"的名字（规格 §14.2 自己写了名字不可信）。

审批的人会问三个问题，现在都答不上来：

1. 这次访问是哪个员工做的？
2. 张三离职了，怎么收回他的访问权？按 2c，只能换 key，然后**每一台设备**上有人重新输入一遍。一百台设备的公司，每走一个人做一次，没有人会真的执行。
3. key 是谁发的、发给了谁、有没有被转发到聊天群里？key 是一串可以复制的字符，设置里点一下就显示（relay 规格 §6.2）。

企业的普遍要求是：每个人、每台设备有自己的身份，可以单独开通、单独收回，最好接公司已有的登录系统。

### B2 没有权限区分：进来了就哪都能去

任何一台持主 key 的设备，能访问**所有**设备分享的**所有**端口。没有"这个端口只给这几台设备"的说法。

后果是横向移动：一台员工笔记本中了木马，木马能连入口（入口对本机任何进程开放，规格 T7、T8），于是公司里每一台机器分享出来的数据库、Jupyter、模型服务、SSH 都在它面前。企业的要求是最小权限：默认不通，按人按组开。

### B3 安全团队管不了它

规格里，分享哪个端口完全由那台机器的使用者决定（`rapp share`）。对企业来说，这是一个能穿透 NAT 和防火墙、内容还解不开的通道，而且开关在每个员工手里。

具体缺的是：

- 不能统一禁止分享，或者只允许分享某些端口。
- 不能禁止某类机器（比如生产服务器）装了以后分享 22。
- 不能规定只许连公司自己的 relay。员工可以填一个自己在外面架的 relay，把公司内网的服务带出去。
- 没有办法通过设备管理系统下发这些规定，并且不让使用者改。

没有这些，安全团队唯一的选择是在防火墙上封掉它的端口。

### B4 日志达不到审计的要求

| 审计要什么 | 现在是什么 |
|---|---|
| 谁（到人） | 设备指纹加自称的名字 |
| 做了什么、什么时候 | 分享方每 10 分钟合并一行（规格 §14.2）；一次具体的连接查不到 |
| 日志不能被当事人改 | 分享方的记录就存在那台机器上，机器的主人或者攻破它的人都能改、能删 |
| 集中保存、能检索、能告警 | relay 的审计可以经 Docker 送走；**设备这一侧的记录没有任何外送的办法**，而"谁访问了哪个端口"恰恰只有设备知道 |
| 保留期限符合规定 | relay 默认 180 天，够得上常见的"不少于六个月"；设备这一侧没有规定 |
| 管理操作是谁做的 | relay 的管理命令经 `docker exec` 执行，日志里没有操作人 |

### B5 收回权限收不干净

- 在 relay 上吊销一台设备以后，同一个局域网里认识它的设备照样接受它（2c §6 自己列的缺口）。办公室正是"同一个局域网"。
- relay 的"入网"开关默认是开的，并且 2c 砍掉了设备端的"接受新设备"开关。所以 key 一旦泄露，对方随时能加一台新设备进来，没有人会收到通知，也不需要任何人批准。
- 设备密钥长期不变，没有有效期。丢了一台没人注意到的旧设备，它永远有效。

## 4. 应该改的（不阻断，但审批时会被逐条问到）

| # | 问题 | 建议 |
|---|---|---|
| S1 | key 和设备私钥是磁盘上的普通文件（C1）。能读这个用户文件的任何程序都能拿走总钥匙 | 桌面上放进系统钥匙串；有安全芯片的机器上设备私钥不出芯片。显示 key 之前要过一次本机验证（指纹、密码） |
| S2 | 服务器 key 所有服务器共用一把。一台失守，对方能不断加入冒充的服务器、抢注名字 | 改成每台服务器一个一次性的入网凭据，用完作废；新设备入网要管理员批准。组织模式里做 |
| S3 | HTTP 适配（规格 §10）替本机服务关掉了它们自己的防护。很多本机服务把"来自 localhost"当成"可信"：模型服务没有登录，开发服务器没有登录，MCP 服务器能执行工具。分享这样的端口，等于把它不设防地交给所有持 key 的设备 | 注册这类端口时明确提示"这个服务没有自己的登录"；策略里可以强制原样转发或禁用适配；改写头部用成熟的 HTTP 库，不自己写解析（请求走私是这类代码最常见的漏洞）；做模糊测试 |
| S4 | 分享 22，或者分享一个本机代理的端口，实际上是把那台机器能到达的整个网段交出去（SSH 自带转发）。规格"不转发到本机以外"的保证在这里被绕过 | 给一张敏感端口的清单（22、3389、5900、常见数据库、Docker 的接口、本机代理），注册时要二次确认；策略里默认禁止；文档里写明"分享 SSH 等于分享网络" |
| S5 | `http://名字.rapp` 是明文，而且名字解析完全依赖本机那一处设置。解析被绕过（C3、C4）时，浏览器会把请求连同其中的登录凭据发给一个不相干的地址，没有任何东西能发现。`.rapp` 是自己造的后缀，不在任何保留名单里 | **https 从"以后"提到企业使用的必要条件**：有了证书，解析错了浏览器会报错而不是照发。后缀是否改用 ICANN 保留的 `.internal`（如 `gpu1.rapp.internal`），是好记和规范之间的取舍，用户定；C3 显示保留后缀同样会碰到 macOS 的那个问题，所以它不解决技术问题，只解决"将来会不会和公共域名撞车" |
| S6 | 算法本身没有问题（TLS 1.3、P-256、HKDF、HMAC、Ed25519 都是标准的）。问题在三处：加密库没有经过 FIPS 验证（C6）；有些行业和地区要求本国的算法，这里没有；互信证明、来访签名、服务器 key 的推导是自己组合出来的协议，没有第三方看过 | 留一个换加密库的构建选项；面向有本国算法要求的客户时另议；**在对外说"企业级安全"之前，请独立的第三方做一次协议评审和渗透测试**，并把威胁模型写成一份可以交给客户的文档 |
| S7 | 入口对本机所有进程、所有用户开放（规格 T7） | 多人共用的机器上不启用入口，做成策略而不是建议；文档里写明"入口等于把访问权交给这台机器上的每个程序" |
| S8 | 生产环境通常要求特权访问走堡垒机：先审批、全程录像、事后可查。`ssh 服务器.rapp` 绕过了这一切 | 规格里写明适用范围：不用于生产环境的特权访问，除非堡垒机本身作为分享方。或者以后提供会话记录 |
| S9 | 只走 UDP。不少企业的出口只放行 TCP 80/443，UDP 除了域名解析一律不通。relay 只有一个节点，它停了全公司都断 | relay 规格 §14 已经留了 TCP 入口和多节点的位置；企业使用时要先把 TCP 443 的入口做出来，并给出 relay 数据卷的备份和恢复流程 |
| S10 | 安装包没有公证（C2）；没有软件成分清单；没有公开的漏洞报告渠道和修复时限；整体是 GPL-3.0 | 用 Developer ID 签名并公证；每个版本出成分清单和哈希；定一个安全问题的联系方式和响应承诺。GPL-3.0 对内部使用通常不是障碍，但有些公司有自己的规定，要过他们的法务 |
| S11 | relay 上的"谁在什么时候从哪个地址连了谁"是个人信息；relay 架在境外时，这些数据在境外。有些国家对跨境的隧道类服务有电信方面的规定 | 这是法务问题，不是技术问题。企业自己托管 relay、放在自己的法域里，是最省事的答案 |
| S12 | 入网、换名字、新增分享这些事件，没有人会被通知 | 新设备入网、服务器角色入网、名字换了设备、分享了敏感端口、被拒绝的访问达到一定次数：这几类事件要能送到集中的地方并触发告警 |
| S13 | 需要管理员权限的安装步骤（规格 §9.2）没有清单 | 列出写了哪些文件、起了哪些系统级的东西、怎么完整卸载；不留常驻的高权限进程；能由设备管理系统统一安装 |

## 5. 给规格的改动建议

### 5.1 现在就加进这份规格的 6 处（都是留位置）

| # | 加什么 | 个人使用时的样子 | 为的是 |
|---|---|---|---|
| L1 | **每个分享多一项"允许谁"**，并且 `forward` 在受理之前统一过一个检查点（来的是谁、什么角色、要哪个端口、策略许不许） | 默认"所有持 key 的设备"，和现在一样；想收紧时可以写几台设备的 ID | B2。以后按人按组授权时，只是往这个检查点里加规则 |
| L2 | **托管策略文件**：系统级的只读位置，优先于使用者的设置。第一版只要这几项：禁用分享、禁用入口、允许或禁止的端口、只许连指定的接入点、强制原样转发、日志送到哪 | 没有这个文件就什么都不限制 | B3。可以由设备管理系统下发 |
| L3 | **访问记录可以每条连接一行**，格式固定（一行一条 JSON），可以同时写到系统日志或者指定的目录 | 默认仍是 10 分钟一行 | B4。企业的日志采集程序能直接收走 |
| L4 | **敏感端口清单**：注册时提示并要确认一次 | 多按一次回车 | S4 |
| L5 | **key 放进系统钥匙串**（桌面）；显示 key 之前过本机验证 | 多一次指纹 | S1。这一条动的是 relay 规格 §6.2 和数据目录规格 |
| L6 | **macOS 的解析做法先实测再定**（C3）；浏览器开着加密 DNS 的情况加进验证清单（C4）；https 在分期里写明"企业使用的前提" | — | S5，以及规格 §9 本身能不能成立 |

这 6 处我估计让第 1 到 5 步各多出一小块工作，不改变分期的顺序。

### 5.2 另立一份规格的：组织模式

和"一把 key"并存，企业用它，个人不用。要点（只列方向，不是设计）：

- **身份**：管理员手里有一把组织的签名密钥，不放在 relay 上。每台设备的凭证由它签发，写明是谁的、什么角色、属于哪些组、到什么时候过期。设备之间验的是这个签名，不再是共同的口令。设备上不再有总钥匙。可以接公司的登录系统来决定"发不发"。
- **入网**：一次性的入网凭据，用完作废；新设备要批准。
- **权限**：管理员签发的策略，写明哪些组能访问哪些分享。由分享方执行，relay 只负责分发、看不懂内容。
- **收回**：凭证短期有效、自动续期；停掉一个人就是不再给他续。局域网里同样生效。
- **审计**：设备的访问记录加密后送到指定的收集点；管理操作带操作人。
- **可用性**：TCP 443 入口、多节点、备份恢复。
- **合规构建**：可选的经验证的加密库。

relay 规格 §14"往 SaaS 扩"已经给其中几项留了接口（准入、登记簿、传输）。组织模式基本就是把那张表里"SaaS 时"的一列做出来，再加上设备之间的授权。

| 供应链 | A.5.19–A.5.22 | CC9.2 | 不满足 | S10 |

其他会被问到的（同样没有逐条对原文）：

- 有等级保护要求的环境：身份鉴别、访问控制、安全审计三项对应 B1、B2、B4；日志留存不少于六个月；部分行业要求本国的密码算法（S6）。
- 支付行业：按人授权、所有访问可追溯到人、日志保留一年，对应 B1、B2、B4。
- 面向美国政府的客户：经验证的加密模块（C6、S6）。

## 7. 要用户定的

1. **"企业使用"具体指谁。** 这决定后面做多少：
   - 你自己的团队或公司内部用，自己说了算：做完 §5.1 的 6 处，加上 https，大致就能交代。
   - 提供给别的企业，对方的安全团队会来审：§5.2 的组织模式必须做，§4 的 S6（第三方评审）、S10（签名、成分清单）也必须做。
   - 对方在哪个国家、哪个行业，决定加密算法（S6）和日志（B4）的具体要求。
2. **§5.1 的 6 处要不要并进规格，出第 2 稿。** 我的建议是要。
3. **组织模式另立规格**，排在端口分享的第 3 步之后还是之前。我的建议是之后：先把个人版做通，组织模式的设计才有东西可以对照。
4. **后缀**：保持 `.rapp`，还是改成带保留后缀的写法（S5）。你定过 `.rapp`（U132），我只是把风险摆出来。
