## 1. 一句话

每台设备的 `rapp-service` 里有一个发件箱，把本机会话的状态变化单向发给网里的 `rapp-state`；各个 rapp app 从 `rapp-state` 读同一份队列和“需要你”，并把“看过了”写回去。网里没有 `rapp-state` 时，一切和今天一样。

## 2. 现状（代码）

| 东西 | 现在在哪 | 换一台设备操作时 |
|---|---|---|
| 终端程序状态 `ps`（干活、等确认、完成、出错、空闲） | 被控设备的 `rapp-term serve`，随会话行发出（`rust/term/src/list.rs` 的 `TermRow.ps`） | 新设备连上就能看到。已经是全局的 |
| 终端“未读”和“看过” | 被控设备，内存里（`rust/term/src/unread.rs`） | 同上 |
| 状态队列（最近 50 条） | 操作端 GUI 的内存里，不存盘（`gui/lib/ui/main_state.dart:619-655`，`_trackPrograms`） | 丢了 |
| “需要你”的内容和先后 | 操作端 GUI 现算（`main_state.dart:1148`，`needs`），先后靠本机的计数 | 内容能重算，先后不一样；别的设备观察到的看不到 |
| GUI 客户端的推断状态（Claude、ChatGPT 等） | 操作端开着这个会话时，被控端才识别并沿这条连接报回（`main_state.dart:1686-1775`） | 新设备没打开的会话看不到 |
| 开着哪些会话 | 操作端 GUI 的记录 | 不带过去 |

另外两个事实：

- 程序状态设计 §6（S2 问答事件）已经定了一个“给本机其他程序的只读出口”，还没实现。本设计的发件箱是它的第一个使用者，事件格式沿用它（§6）。
- 端口分享主规格的第 3 步（服务器 key：只能被访问）**还没实现**。今天所有设备用同一把 key，都能主动访问别的设备。本设计要和第 3 步相容（§13），但第一版不依赖它。

## 3. 目标、不做、反目标

**目标**

- T1 在任何一台 rapp app 上，状态队列和“需要你”是同一份：内容相同，先后相同。
- T2 没有 rapp app 开着的时候，状态变化仍然被记下来。
- T3 在一台 app 上看过的，在另一台上不再算新的。
- T4 换设备后能看到“别处开着哪些会话”，点一下在这台上打开。不自动连画面。
- T5 设备不用逐台配置：网里出现状态服务，设备自己接上；服务没了，自己停。
- T6 服务不可用时不丢当前状态；历史尽力补。
- T7 本机的任何程序都能交一条事件进来（G8）。

**不做**

- 推送通知（G3 选了甲）。服务的形状不挡以后加。
- 在“需要你”里直接答复。回程不走这条路；它属于程序状态设计的 S3、S4。
- 把断开的会话、离线的设备做成全局的。那是“我这台到它的连接怎么了”，每台 app 各算各的。
- 让服务判断设备在不在线。在线与否仍由 app 自己的探测决定。
- 多个状态服务并存、互相同步。

**反目标（做到了也算失败）**

- 没开状态服务的用户，行为、流量、内存有任何变化。
- 本体的 crate 依赖 `rapp-state` 的代码，或者 `rapp-state` 依赖 `rapp-service`、`rapp-hub`。
- 服务连不上时 app 报错、卡住，或者“需要你”少了本来能算出来的项。
- 事件里的文字（命令、路径）进了任何日志。

## 4. 考虑过的做法

| 做法 | 是什么 | 结论 |
|---|---|---|
| 一、常驻采集 | 服务像一个没有界面的主控台，自己去盯每台设备 | 不用。它要持有一把能访问所有设备的 key，和本体缠得深，不符合 G5 |
| **二、设备上报** | 每台设备把自己的状态变化发给服务，服务只收、存、给查询 | **采用（G4、G8、G9）** |
| 三、主控台之间同步 | 只把 Mac 上 app 的队列存到服务，pad 打开时取 | 不用。Mac 合上以后没人记，T2 做不到 |

没列入的：放进 relay（relay 要保持不懂业务）；用 git 同步（iPad 没有 git，状态是秒级变化）；并进 rapp-llm（它是 Node 的模型网关，而且还在试验）。

发送放在哪一层（G8）：

| 候选 | 结论 |
|---|---|
| 命令行自己发 | 不用。命令跑完就退出，服务不可用时没有进程留下来缓存和重试 |
| `rapp-term` | 不用。它只管终端，别的来源走不了它；它也不碰网络 |
| hub | 不用。没人操作时不在运行；iPad 上才有内嵌的 hub |
| **`rapp-service`** | **采用**。每台设备常驻一个；relay 连接、分享表、本机 IPC 都在它手里；`rapp` 命令行只和它说话（`rust/cli/src/main.rs:1`） |

## 5. 结构

```
来源                         发件箱（rapp-service）            rapp-state                 读的人
──────────────             ───────────────────────          ───────────────           ─────────
终端程序状态（rapp-term）┐                                    收：POST /v1/events        Mac 上的 rapp
GUI 客户端状态（以后）   ├─ 本机 ─► 排队、补发、重试 ─ 单向 ─►  存：当前状态 + 队列    ◄─►  pad 上的 rapp
rapp emit（G8）          ┘                                    给：/v1/state /v1/queue    Duo 上的 rapp
                                                                  /v1/watch /v1/seen     进阶用户的脚本
```

三块，各管各的：

1. **来源**只管把一条事件交给本机的发件箱，交完就返回。
2. **发件箱**只管送，不看事件内容。加新来源不动它。
3. **`rapp-state`** 只认 §6 的事件格式和 §8 的接口，不认识 rapp 的设备协议。进阶用户可以换成自己的实现（G6）。

本体为它加的东西只有四样：事件格式、分享的一个标记、发件箱、app 的接入点。relay、串流协议、key 规则不动。

## 6. 事件

一行一个 JSON。字段照程序状态设计 §6 的写法，外面加一层信封。

```json
{"v":1,"fp":"<设备指纹>","id":"686712053","device":"MacBook-M4-Pro",
 "epoch":"c41f9a","n":1042,"at":1764130000,
 "src":"term","t":"state","session":"term:pty:9f2c…","name":"rapp","title":"~/git/rapp","fg":"claude",
 "state":"blocked","kind":"permission","app":"claude-code","msg":"approve Bash: touch /tmp/x","seq":12}
```

**信封**（发件箱填）

| 字段 | 含义 |
|---|---|
| `v` | 格式版本，现在是 1。不认识的字段忽略 |
| `fp`、`id`、`device` | 设备指纹、9 位 ID（没有 relay 时可以缺）、设备名。app 用 `id` 对上自己的设备表，对不上再用 `fp`【我定的】。设备名不叫 `name`，因为 `name` 留给会话自己的名字 |
| `epoch` | 发件箱这一次启动的随机标记。`rapp-service` 重启就换 |
| `n` | 这个 `epoch` 里的序号，从 1 递增。（发送者、`epoch`、`n`）用来去重；发送者是 `via`，没有 `via` 时是 `fp` |
| `at` | 事件发生时设备上的 Unix 秒 |
| `src` | 来源：`term`、`app`（GUI 客户端，推断）、`emit` |
| `via` | 只在代报时有：替它报的那台设备的 `fp`（§9.2 第 4 条） |

**种类**（`t`）

| `t` | 什么时候发 | 内容 |
|---|---|---|
| `state` | 一个会话的状态换了，或者等你时换了一个新问题（`seq` 变了）。只是进度数字变不发。规则和现在 GUI 的 `_trackPrograms` 相同 | `session`、会话行里起名用的字段原样带上（`name`、`title`、`fg`、`host`，见 `rust/term/src/list.rs`）、`state`（`working`、`blocked`、`done`、`error`、`idle`）；`blocked` 时带 `kind`；有就带 `app`、`msg`、`seq` |
| `gone` | 会话结束或者不见了 | `session` |
| `snap` | 发件箱刚连上服务、断了以后恢复、缓存丢过东西：这个发送者此刻知道的所有会话的状态。服务用它整份替换**这个发送者**报过的会话，别的发送者替这台设备报的不动 | `sessions`：一个数组，每项是 `state` 的那几个字段加 `since`（进入这个状态的时间） |
| `emit` | 本机程序交来的一条（§11） | `level`（`done`、`ask`、`info`、`clear`）、`text`；可选 `key`（以后用同一个 `key` 清掉）、`session` |

- 会话显示成什么名字由 app 拼，办法和现在一样（`gui/lib/term/term_id.dart:32` 的 `termDisplayName` 和总览用的那一套）。发件箱不拼名字，免得同一条规则写两份【我定的】。
- `msg`、`text` 只当纯文字，收的一方不当标记解析。长度上限 500 个字符，超出截断【我定的】。
- 程序状态设计 §6 的 `tail`（整屏文字）第一版不带【我定的】：它大，而且内容更敏感。等 S2 实现时再定。
- 事件格式的定义和样例文件放在 `services/state/api/`（§12），发件箱和 `rapp-state` 的测试读同一批样例。

## 7. 发件箱（`rapp-service`）

新文件 `rust/service/src/outbox.rs`。

### 7.1 什么时候工作

- **网里没有状态服务**：不收集、不缓存、不开任何连接。本机 IPC 的 `emit` 回 `ok`，带一个 `sink:false`。
- **有**：开始收集和发送。
- 状态服务没了（分享取消，或者那台设备从设备表里删了）：停下来，清空缓存。

### 7.2 怎么找到状态服务（T5）

- `Share`（`rust/service/src/shares.rs:84`）加一个可选字段 `kind`，状态服务的分享写 `"kind":"state"`。`Op::Shares`、`Op::ListShares` 的回复和本机 IPC 的 `shares`、`hosts` 每项带上它。只加可选字段，旧设备忽略（`Share` 从全局分享号那一版起就不拒绝不认识的字段）。
- ~~`rapp-service` 本来就定期问各设备分享了什么~~：**不对**。`rapp-service` 只在启动时（而且只在有分享缺号时）、`rapp hosts` 和 GUI 打开某台设备的分享页时问；纯服务器上没有 `hosts.json`，不知道该问谁。改成**知道的告诉别人**（用户 2026-11-26 选定）：
  - 设备之间加一个请求 `StateSink{id,port,on}`：“设备 `id` 的端口 `port` 上有（`on:false`：没了）状态服务”。
  - 谁会知道：开状态服务的那台自己；任何一台在分享表的回复里（`rapp hosts`、分享页、启动时问号）看到 `kind:"state"` 的；收到 `StateSink` 的。
  - 知道了（或者知道的变了）就告诉自己 `hosts.json` 里的每台设备，已经告诉过的不再说；有状态服务的时候每 5 分钟看一次 `hosts.json`，新加的、上次没告诉成的补上。收到的记进 `local/state-sinks.json`，重启后还认。
  - 忘掉：收到 `on:false`；再看到那台的分享表里没有它了；连过去被回“没有分享”；那台从 `hosts.json` 里删了（有这个文件时）。
  - 网里没有状态服务时，这些都不发生，流量不变。纯服务器上开的状态服务，要等一台有 GUI 的设备看过一次它的分享表（`rapp hosts` 或分享页）才传开；P2 做 app 接入时再看要不要借 `list_apps` 的回复带出来。
- 发件箱不经本机的 `localhost:<分享号>`，直接用 `Op::Forward` 连那台设备的真实端口（和 `rapp pipe` 同一条路），所以纯服务器上不需要端口映射。状态服务在本机时，直接连它的真实端口。
- 看到两个以上：用设备 ID 最小的那个（各台算出的是同一个；`StateSink` 里没有指纹），日志里记一行，`rapp state` 里列出来【我定的】。

### 7.3 来源怎么接进来

| 来源 | 怎么接 | 哪一步 |
|---|---|---|
| 终端程序状态 | 发件箱向本机的终端工作进程开一个 `watch_terms`（和别的设备来问时走的是同一个请求，`rust/service/src/term.rs`），比较前后两份会话表，按 §6 的规则出事件。第一份表不算变化，进 `snap`。终端会话关着（`term.json`）时没有这个来源 | P1 |
| 本机程序 | 本机 IPC 加一个命令 `emit`（§11） | P4 |
| GUI 客户端的推断状态 | 现在只有操作端开着会话时才有，由 app 代报（§9.2 第 4 条）。被控端自己识别、自己交给发件箱，要等 GUI 客户端状态规则那份设计的后续 | P3 代报；自己报另立 |

### 7.4 发送（G8：单向持续发）

- 用 HTTP：`POST /v1/events`，正文是一行一个事件，一次最多 50 条。只看状态码：2xx 算收到，从缓存里去掉；别的都算没收到。回应的正文不读。
- 第一次连上、失败之后恢复、缓存丢过东西：按 `n` 的顺序先补发缓存，最后发一条 `snap`（它的 `n` 最大，是此刻的实情。先发 `snap` 的话，后补的旧事件要么被去重丢掉，要么把当前状态改回旧的）。
- 服务回 4xx（不认这批）：这一批丢掉，日志记条数和状态码，不重试；回 5xx 或连不上才重试。
- 连不上：2 秒后重试，每次翻倍，最长 60 秒。
- 同一时刻只有一个请求在路上，保证顺序。

### 7.5 缓存还是丢弃（G4、G8）

| 数据 | 处理 |
|---|---|
| 当前状态 | 不缓存，也不会丢。它本来就在设备上，恢复时用 `snap` 重报 |
| 历史 | 内存里最多留 200 条【我定的】。满了丢最旧的，并记下“丢过”；恢复后的 `snap` 带 `gap:true`，服务在队列里放一行“<设备> 有一段没记下来” |
| `rapp-service` 重启 | 缓存没了，`epoch` 换了。服务看到新 `epoch`，等它的 `snap` |

不落盘【我定的】：事件里带命令和路径，程序状态设计 §5.10 要求这类内容不进日志。

### 7.6 日志

只记条数和结果：连上、断开、补发了几条、丢了几条。不记事件内容。

## 8. `rapp-state` 服务

### 8.1 是什么

- 一个没有界面的程序，Rust，和 `rapp-service` 同一套技术（tokio），macOS、Windows、Linux 都能跑（G7）。源码在 `services/state/`（§12）。
- 只监听回环地址上的一个端口，默认 8102（rapp-llm 的 8101 的下一个，用户 2026-11-26 定）。别的设备经端口分享访问它；路上的加密和“谁能访问”都由端口分享负责，它自己不做认证【我定的】。
- HTTP 库用 hyper 1.x【我定的】。工作区现在没有 HTTP 库，这是新增依赖；发件箱的那个小客户端也用它。

### 8.2 存什么

| 内容 | 上限 |
|---|---|
| 每台设备每个会话的当前状态 | 设备 30 天没消息就清掉【我定的】 |
| 队列：`state`、`gone`、`emit` 事件，按 `at` 排，同一秒按到达先后 | 最近 1000 条，且不超过 7 天【我定的】 |
| 每个会话、每条 `emit` 的“看过”时间 | 跟着它的对象清 |
| 桌面：各 app 开着的会话清单（§9.2 第 5 条） | 每台 app 一份，30 天没更新就清掉 |

- **存盘**：数据目录下 `local/state/`，权限 0600，重启后还在【我定的，要你确认，§17 第 1 条】。配置里可以改成只放内存。
- “需要你”不单独存：它是“当前状态里 `blocked` 的会话”加“没清掉的 `ask`”，每项带第一次出现的时间，各 app 按这个时间排，所以先后到处一样（T1）。
- 一个会话的状态一直留到有人报新的为止，不因为“报它的那台 app 走了”而过期【我定的】：Mac 合上以后，那台设备上的 Claude 多半还在等。每项带着“谁在什么时候看到的”，app 显示出来；别的 app 打开这个会话后会重新报一次，把它纠正过来。

### 8.3 接口

| 接口 | 做什么 |
|---|---|
| `GET /v1/health` | `{"name":"rapp-state","v":1}`。发件箱和 app 用它确认对面真是状态服务 |
| `POST /v1/events` | 收事件（§7.4）。重复的（发送者、`epoch`、`n`）丢掉。204 |
| `GET /v1/state` | 当前全貌：设备、各会话的状态和“看过”时间、`needs`、桌面 |
| `GET /v1/queue?before=<游标>&limit=<n>` | 队列，新的在前，最多 200 条一页。每条带一个标识 `eid`（`<发送者>:<epoch>:<n>`） |
| `GET /v1/watch` | 长连接（SSE）。有变化就推一条：`what`（`session`、`queue`、`need`、`seen`、`desk`）加变了的那一项。app 在前台时开着 |
| `PUT /v1/seen` | `{"fp","session"}` 或 `{"eid":"…"}`：记成此刻看过。带 `"handled":true` 时把一条 `ask` 清出“需要你” |
| `PUT /v1/desk/<app 的设备指纹>` | 这台 app 现在开着的会话清单，整份替换。每项：被控设备的 `fp` 和 `id`、app 标识（终端是会话 id）、显示名 |

- 都是 JSON，UTF-8。出错回 `{"error":"…"}` 和合适的状态码。
- 接口的定义放 `services/state/api/`，和事件格式在一起。进阶用户照着它就能写自己的服务，或者写脚本去读（G6）。

### 8.4 配置

放在 `local/services.json` 里 `state` 那一项下面（§10），和“开没开”在一起：`port`、`store`（`disk` 或 `memory`）、`keep_days`、`keep_events`。都有默认值。`rapp-service` 启动它时用命令行参数传过去，所以 `rapp-state` 单独跑时不需要这个文件。写进《配置规范总览》。

app 的接入点是另一个文件 `local/state.json`（§9.1）。同一台设备可以两个都有：它既跑服务，又开着 app。

## 9. app 一侧

### 9.1 接入点

- 设置里加一块“状态服务”，三个选项：**自动**（默认：在设备分享的端口里找 `kind` 是 `state` 的，找到就用 `http://localhost:<号>`）、**关**、**手填地址**（给用自己实现的人）。存 `local/state.json`（app 所在设备）。
- iOS 上没有后台服务，`localhost:<号>` 由内嵌的 hub 开（app 端口映射设计），所以 pad 和 Duo 走同一个地址。hub 的 `ports` 事件每项带上 `kind`。
- 连上以后先取 `/v1/state` 和一页 `/v1/queue`，再开 `/v1/watch`。回到前台时重取一次。

### 9.2 连上以后变什么

1. **状态队列**：rApp 自己说的话（提示历史）仍然是这台 app 自己的。程序状态的变化改成从服务来；`_trackPrograms` 不再往队列里加行，免得同一件事出现两次【我定的】。两种按时间排在一起，还是一个列表。
2. **需要你**：
   - 这台 app 自己连着的设备上的终端，仍然照现在的办法现算（它最新）。
   - 服务的 `needs` 里有而这台没算出来的（`emit` 的 `ask`、别的 app 代报的 GUI 客户端），加进来。
   - 先后：服务里有这一项，就用服务记的第一次出现的时间；没有才用本机的计数。
   - 断开的会话、离线的设备：照旧，本机的。离线设备上的终端不算等你，这条规则不变，用的是 app 自己的探测结果。
3. **看过**：用户看了一个会话，app 发 `PUT /v1/seen`。队列里“上次看过之后的新行”和 `emit` 的未读靠它。终端自己的未读规则不动。
4. **代报 GUI 客户端状态**：这台 app 开着的会话里，被控端报回的推断状态变了，app 向服务发一条 `src:"app"` 的事件，`fp` 写被控设备，`via` 写自己。别的 app 上显示时照旧标“推断”。会话关掉时发 `gone`。
5. **别处开着的会话**（T4）：app 每次开、关会话后把自己的清单发给服务。会话面板里多一组“别处开着”，列出别的 app 清单里有、这台没开的会话，灯用“未打开”，旁边写在哪台上开着；点一下在这台打开。不自动打开。

### 9.3 连不上时

- 一切退回今天的做法：队列、需要你都用本机算的。不弹窗，不报错。
- 设置里那一块写“连不上”。状态队列里记一行“状态服务连不上，先用本机的”，一次中断只记一行【我定的】。
- 这段时间的“看过”攒在内存里（最多 200 条），连上以后补发。

## 10. 开启和关闭（G4：在 app 里方便地开）

- `rapp-state` 随安装包装好，默认不启动（§12）。
- `rapp-service` 加一个“附带服务”的小管理器：一张表，每项是名字、程序名、默认端口、分享时的 `kind`。第一版表里只有 `state` 一项。开了的写进 `local/services.json`；管理器负责启动它、挂了重启、把端口分享出去、关的时候取消分享。以后别的服务（比如并进来的 rapp-llm）加一行就行。
- 本机：`rapp state on`、`rapp state off`、`rapp state`（看状态：开没开、端口、分享号、存了多少、最近一次收到谁的事件）。
- 远程：设备之间加一个请求 `SetService{name,on}`，谁能发照现在 `Op::Share`（替另一台设备改分享，`rust/net/src/msg.rs:56`）的规则。app 的设备页上，每台设备的分享那一段加一行“状态服务”开关。旧设备回 `unknown op`，开关不显示。
- 网里已经有一个状态服务时再开第二个：照开，但面板上提示“已经有一个在 <设备> 上”【我定的】。

和我在讨论里说的不同：当时说“生成一行安装命令、不加远程启动的请求”。既然它随安装包带着（G7），开启就只是打开一个开关，所以改成一个通用的请求。

## 11. `rapp emit`（G8）

```
rapp emit done  "构建完成"
rapp emit ask   "要不要部署到生产？" --key deploy-123
rapp emit clear --key deploy-123
rapp emit info  "开始跑第 3 轮"
```

- 命令行经本机 IPC 把事件交给发件箱，马上返回。网里没有状态服务时也返回 0，不打印东西；`--json` 时输出 `{"sink":false}`【我定的】。这样脚本不会因为没开状态服务而失败。
- `ask` 进“需要你”，直到同一个 `key` 的 `clear`，或者用户在 app 里点“已处理”。
- 在 rapp 的终端会话里运行时，事件带上这个会话，点它就切到这个会话。做法：`rapp-term run` 给里面的程序设一个环境变量 `RAPP_TERM=<会话 id>`【我定的；现在没有这个变量】。不在终端里运行的，点它去设备页。
- 跑在 rapp 终端里的 Agent，优先用 OSC 7501：`rapp-term` 已经在解析它，不用调这个命令。`rapp emit` 是给不在终端里的东西用的（定时任务、脚本、后台服务）。

## 12. 目录、构建、打包（G7）

```
services/
  README.md          这一类是什么、进来的条件
  state/             rapp-state
    Cargo.toml       package.workspace = "../../rust"
    src/
    tests/
    api/             事件格式、接口定义、样例文件
    README.md        怎么单独跑、配置、接口
  llm/               以后并进来的 rapp-llm（位置先留着）
```

- 放在顶层而不是 `rust/` 里：`rust/` 是平铺的本体 crate，放进去看不出“可选”；rapp-llm 是 Node 的，放不进 `rust/`。
- `services/state` 仍然是 `rust/` 这个 workspace 的成员（`rust/Cargo.toml` 的 `members` 加 `"../services/state"`），共用版本号、`Cargo.lock`、`target`。我用一个临时工程验证过（cargo 1.97）：成员放在 workspace 目录外可以编译，`cargo test --workspace` 会带上它。发版的门禁不用改。
- 安装包：`scripts/package-macos.sh:34` 的构建和 `:44` 的拷贝各加一个 `rapp-state`；`scripts/package-linux.sh` 同理。Windows 跟着 `rapp-service` 在 Windows 上的进度。
- **进 `services/` 的条件**（写进 `services/README.md`）：
  1. 本体不依赖它，没有它 rapp 照常工作；
  2. 它不引用 `rapp-service`、`rapp-hub`、`rapp-conn` 这些本体 crate，只通过端口分享和 `api/` 里的接口打交道；
  3. 两边各自用 `api/` 里的同一批样例做测试，接口改了两边都会挂。
- relay 不搬：它是本体的基础设施，不是可选服务。
- 容器部署（`docker/state/`）第一版不做【我定的】：状态服务要靠同一台机器上的 `rapp-service` 把端口分享出去，单独一个容器接不进网。
- rapp-llm 并进来时要先定：保持 Node 就进不了安装包（要带 Node 运行时）；要进安装包就得改写成 Rust。

## 13. 和服务器 key 的关系（端口分享第 3 步，未实现）

- 今天所有设备都能主动访问别的设备，发件箱在每台设备上都能自己发。
- 第 3 步做完以后，用服务器 key 的设备发起的访问一律被拒，它的发件箱发不出去。到时候加第二个出口：设备之间加一个请求，让普通设备把服务器发件箱里的事件**取走**再转交。由谁去取：跑状态服务的那台设备的 `rapp-service`（它是普通设备时）；它也是服务器 key 时，只有开着的 rapp app 去取。
- 所以状态服务放在哪有区别：放在普通 key 的常开机器上，全程不断；放在服务器 key 的机器上，别的服务器的事件只在有 app 开着时才到。
- 这一条写进第 3 步的实现计划，本设计的 P1–P4 不做。发件箱的缓存和 `snap` 已经够它用，不用改格式。

## 14. 安全和隐私

- 事件里可能有命令和路径（`msg`、`text`）。路上：走端口分享，设备之间全程加密，relay 看不到内容。
- 落地：只有 `rapp-state` 那一台存盘（§8.2），0600，7 天。别的设备只在内存里。
- 谁能读写：能访问这个分享端口的设备。默认是所有持 key 的设备；要收紧，用分享的“只给谁”。
- 本机：回环端口，本机的任何程序都能读写。这和别的分享端口一样。
- 伪造：持 key 的设备可以冒别的设备的名义发事件。这在“有 key 即互信”的范围内，不另外防。
- 日志：两边都不记事件内容（§7.6）。`rapp-state` 的日志只记条数、设备、状态码。
