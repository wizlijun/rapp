# 调研：macOS、iPadOS 自带 app 里，哪些是刚需、值得改成多设备读写

日期：2026-11-13。状态：**调研，不是确定的需求**。和 `2026-11-13-rapp-agentos-ideas.md` 一样属于阶段性脑暴的材料。

用户的话：

> 根据 macos、ipados 的默认自带 app 的设计，哪些组件（例如备忘录）是刚需的，只是我们把他改为多设备可以读写的设计。请帮我自己研究一下，给出列表。

## 怎么做的

- 自带 app 的名单取自苹果官方的使用手册（2026-11-13 查看）：Mac 手册"Apps included on your Mac"（macOS 27）列了 72 个；iPad 手册（iPadOS 27）的 app 章节有 38 个。
- "刚需"是我的判断，不是数据。我用的标准有三条：
  1. 干活时一天要用很多次，不是娱乐。
  2. 里面的内容是"我的"，不属于某一个 app（笔记、待办、剪贴板、文件、截图）。
  3. 苹果自己已经让它在多台设备之间同步。这说明多设备是真需求；而苹果的同步到不了 Windows 和 Omarchy，那正是空档。
- rapp 的现状取自仓库里的规格（S3–S6 已实现、实机检查待做；沟通机制在设计中）。

## 第三档：不需要

这些是内容或娱乐类的 app，要用的话它们本身就是被远程打开的 app，不是主控台的组成部分：

Safari、邮件、日历以外的沟通类（FaceTime、电话）、地图、音乐、播客、TV、图书、新闻、股市、天气、家庭、健康、游戏、国际象棋、Photo Booth、Pages、Numbers、Keynote、GarageBand、iMovie、计算器、词典、翻译、测距仪、放大器、时钟（并入提醒事项）、文本编辑、终端（它是最常被远程的 app 之一）。

系统工具类（磁盘工具、字体册、色彩同步、迁移助理、蓝牙文件交换、打印中心、AirPort 实用工具等）和 rapp 无关。

## 看出来的三件事（我的分析）

1. **刚需的那一档很短，而且有共同点：里面的东西是人的，不是哪个 app 的。** 笔记、待办、剪贴板、文件、截图、搜索、通知。其余的 app 要么是内容，要么是工具。
2. **第一档 14 项里，rapp 已经有 8 项或一半。** 完全没有的是五项：备忘录、便笺、提醒事项、聚焦搜索、活动监视器。前三项合起来就是 inbox。
3. **聚焦搜索是清单里之前没提过的一项。** 设备、员工、笔记、记录越多，越需要一个输入框找到一切。它也最符合"不记位置不常用的操作，说一句就行"（U11）。

## 按用户的设想重新看这张表（U45）

写这份调研的同时，用户说了他设想的工作台（原话在需求反馈文档的 U45）：不同物理机、虚拟机、不同系统上开的 app，都在一个平台上灵活切换，按项目分类；人只要切换项目，就切到不同的工具里，但始终在同一个思维空间中，忽略操作系统和电脑的细节。

按这个设想，上面的组件可以分成三类（我的分析）：

| 类别 | 是什么 | 哪些组件 |
|---|---|---|
| 思维空间里不变的东西 | 换项目、换机器都跟着人走 | 备忘录、便笺、提醒事项、剪贴板、文件、聚焦搜索、通知、截图和记录 |
| 随项目切换的东西 | 换一个项目就换一套 | 工具，也就是被远程打开的那些 app；程序坞和启动台里摆的是"这个项目的工具" |
| 应该被藏起来的东西 | 机器和系统的细节，平时不该看到 | 查找、活动监视器、系统设置 |

由此对第一档的两点修正：

- **查找、活动监视器、系统设置仍然要有，但要退到后面。** 平时不显示，只在出了问题时露出来（哪台机器掉线了、哪台吃紧了）。这正是企业资源管理里的"例外管理"。
- **刚需的核心就是第一类那八项。** 它们构成用户说的"同一个思维空间"。

和现状的出入：现在的主界面是以设备为先的。会话列表默认按设备分组，全景模式是一面设备墙，面板里有单独的"设备"标签。按 U45，项目应该排在最前，设备退到后面。这一条如果要改，会动到已经实现的 S4、S5，需要用户确认，这里只记录。

## 用户对每个插件的计划（逐个问、逐个记）

用户要求一个个地问他计划怎么做。下面按问答的顺序记，原话在需求反馈文档里。

### 1. 备忘（U48）

用户的计划：

- 不另做一个备忘 app。用户自己有一个项目 note.md，专门做 vault 的多设备同步和管理，就用它，作为一个应用在本机使用。
- 其他设备通过"系统提供的资源共享机制"来读、写这份 vault。

我查到的相关现状：

- note.md（`~/git/note.md`）：vault 是一个装着普通 `.md` 文件的文件夹，自带 git 同步、命令行和 MCP 接口；它的原则之一是"一个 vault，多个 agent"。
- rapp 现在的资源共享（S6）只有两样：一份剪贴板列表，和一次传一个文件的传输。没有"把一个文件夹共享给别的设备"这种能力，S6 还把"把条目发到另一台设备"列为非目标。
- 所以"其他设备读写 vault"如果走 rapp，需要给资源共享加新的能力；如果走 note.md 自己的 git 同步或操作系统的文件共享，则不用。用户说的"系统"指哪一个，待问。

追问后用户的回答（U49）：

- 别的设备上如果在做项目，一般有项目自己的 git。只有长期思考的东西才会并进 vault。所以不用担心别的设备需要整个 vault。
- 用户只在主控的那一个 rapp 里用它。顶多偶尔在另一台电脑上用；需要的话，由用户自己挑几台必要的机器，在上面配好 note.md 的 vault。

由此定下来的范围：

- vault 在主控机上。别的机器要不要有，靠 note.md 自己的同步，由用户逐台配置。
- **rapp 不需要把 vault 共享给远端设备**，资源共享（S6）不用为这件事加新能力。
- 员工干活的上下文在各自项目的 git 里，不在 vault 里。

我的两点补充（待用户确认）：

- rapp 这边"一下就记"的那个动作，可以是往 vault 里一个固定的文件追加一行，note.md 打开就能看到。两个程序之间只靠文件，不用互相调用。
- note.md 现在没有手机和平板版（它的 README 写着移动端没有发布）。用户自己的主控是装了 Omarchy 的平板，note.md 有 Linux 版，可以用；将来用 iPad 或 Android 平板当主控时，这个插件用不了，要另想办法。

#### 补充：用 Sumi 做全局的备忘编辑器（U51）

用户的补充：

- note.md 里有一个插件 Sumi write，可以独立出来，做成原生体验的书写模块。
- 它做了输入法适配，适合沉浸式地把想法写出来，也适合将来的语音输入。
- 拿它来做全局的备忘编辑器。
- 文件仍然存在 vault 里，多台机器可以同步。

我查到的相关现状（note.md 的 `docs/superpowers/specs/2026-11-07-immersive-write-design.md` 和 `plugins-src/write`）：

- Sumi（中文名"玄霜打字机"）是一页纸、下一页纸式的写作空间：打开就写，自动保存，没有文件名和文件夹这些概念。
- 编辑区用的是本机原生的文字控件，专门做了输入法适配（有单独的输入法桥规格）。
- 纸页存成 Markdown，默认放在 vault 的 `inbox/writings/` 下面。**vault 里本来就有一个叫 inbox 的目录**，和用户前面说的"自留地叫 inbox"对上了。
- 它有自己的同步服务，只同步纸页，不上传整个 vault。
- 规划里桌面是 note.md 的插件，iOS、Android 是独立的客户端；目前公开的只有 macOS 版。Linux 以 Omarchy 为首要目标。

由此对第 1 个插件的理解更新为：

- 备忘 = 用 Sumi 写 + 存在 vault 里。写的时候是一页纸，不用起名字、不用选位置。
- 之前我提的"往 vault 里一个固定文件追加一行"不需要了，Sumi 自己就会把纸页写进 `inbox/writings/`。
- 之前我担心的"将来用 iPad 当主控时 note.md 用不了"，Sumi 的规划里有独立的 iOS、Android 客户端，方向上解决了；但它们还没做出来。

两点要知道的（我的分析）：

- 现在 Sumi 的原生编辑部分是和 note.md 宿主一起编译的。要让它"独立出来"给 rapp 用，是一块要做的工作。怎么做等用户说明。
- 用户最在意的是书写流畅（U3）。rapp 的输入区也是"在本机写好再发过去"。同一个书写模块将来也可以用在输入区上。这只是我的一个想法，没有定。

#### 编辑器可以换（U52）

用户的话："是可以独立成插件，用户按需使用哪种编辑器。"

- Sumi 独立成一个插件。
- 编辑器是可以选的：用户按自己的需要决定用哪一种，Sumi 是其中一种，不是唯一的一种。
- 所以"备忘"这个插件要分成两层：存放（vault）是固定的，编辑器是可换的。除了 Sumi 还有哪些编辑器可选，用户没有说。

#### 沉浸式书写和语音输入是 rapp 的特色能力（U53）

用户的话："这块沉浸式的 write 体验和语音输入，可以作为一个特色组件，作为 rapp app 的特色能力。"

- 沉浸式书写（Sumi）加语音输入，不只是备忘的一个编辑器选项，而是 rapp 对外的一项特色能力。

这个服务跑在哪台机器上：用户在 U59 里回答了，三种都可以（本机；自己的服务器配地址；经 relay 中转），见后面"数据服务跑在哪里（U59）"。

### 3. 提醒（U54）

用户的计划：

|---|---|---|---|
| 便签 | 最重要的几件大事 | 很少 | 用户自己；状态在 NEXT 里管 |

我查到的相关现状（note.md 的 `plugins-src/next` 和几份规格）：

- **这条链已经通了一部分**：vault 里有一个规程（`skills/proactive-reminder-push`）会把 NEXT 的任务提醒推到 xiaobucubic 的显示服务里，消息 ID 是 `xiaobu-task-<任务的 UUID>`。也就是说，现在小屏上的便签，有一部分本来就是 NEXT 的任务。

由此的理解（待用户确认）：

- rapp 不自己管任务状态。任务在 vault 里、由 NEXT 管；rapp 的便签只是把服务里的消息显示出来。这样主界面规格里"rapp 不做任务模型"那条非目标不用改。

#### 提醒区域和"需要你"的关系（U66）

用户的话："数据上 需要你是 提醒的一个子集。提醒区另开一个。需要你为特殊的优先级类别。"

- **数据上是一份**：所有提醒是一个集合，"需要你"是其中的一个子集。
- **界面上是两个地方**：提醒区域另开一个；"需要你"留在原处。
- **"需要你"是一个特殊的优先级类别**：一条提醒的优先级是这一类时，它出现在"需要你"里。

| | 提醒区域 | 需要你 |
|---|---|---|
| 装什么 | 全部提醒 | 优先级是"需要你"这一类的提醒 |
| 数量 | 可能很多 | 很少 |
| 样子 | 不闪，不用强调色（我的提议，用户没有反对） | 会闪，用强调色（现有设计语言不变） |
| 谁决定进来 | 各个来源 | 现在是"员工停下来等你"；将来助理也可以把重要的提醒升到这一类 |

对现有设计的影响：

- 设计语言里"颜色只表示要你处理""只有等你会闪"两条不用改。
- 现在的"需要你"是会话上的一个标记（S3 已实现）。按 U66，它在数据上要变成"提醒"这个集合里的一类。实现时是把现有的标记并进提醒的数据里，还是两边各存一份再合起来显示，留到设计时定。
- 第 5 条专注（U56）里"专注时等你还亮不亮"的问题，现在可以这样问：专注时，"需要你"这一类还打不打断。用户没有说。
- （第 7 条资源监控里"数值吃紧时提不提醒"，用户在 U69 里回答了：不提醒，在便签里用颜色区分，更不进"需要你"。我在这里原先写的"吃紧是一条提醒，进提醒区域"作废。）

这一条的范围比"快照"大：用户说的是 rapp 要有一个自己的、用 git 同步的目录，快照和关键配置都放在里面。

我查到的相关现状：

| 文件 | 在哪一侧 | 有没有机密 |
|---|---|---|
| `service.json` | 被控端 | 有（设备的密钥、密码） |

| `workspace.json`（常用和项目） | 操作端 | 无 |

## 数据服务跑在哪里（U59）

这一条回答了第 2 条里搁置的"便签服务跑在哪台机器上"，并且推广到所有同类服务（便签、提醒、资源监控的数值……）。

用户的计划：

- 只需要自己的 rapp 查看的数据服务，可以跑在本机。
- 也可以自己部署在某台服务器上，通过配置地址（IP 或 URL）来用，或者通过 relay 来用。relay 可以做中转。
- 这类应用服务可以算作 rapp 核心的一部分。
- 目的：数据服务只在自己的安全环境里（局域网，或者经 relay 中转），把安全风险降到最小。

三种部署方式：

| 方式 | 服务在哪 | rapp 怎么连 | 暴露在公网的 |
|---|---|---|---|
| 本机 | 和 rapp 同一台机器 | 直接连本机 | 没有 |
| 自己的服务器，局域网内 | 局域网里的某台机器 | 配置它的地址 | 没有 |
| 自己的服务器，不在同一个局域网 | 别处的某台机器 | 经 relay 中转 | 只有 relay |

和已有决定的关系：

- 和 relay 安全要求（`2026-11-12-rapp-relay-security-requirements.md`）的 R2 一致："relay 是唯一暴露在公网的服务"。数据服务自己不开公网端口，就不会多出第二个暴露面。
- **relay 现在不能中转这类数据。** 现状是 relay 只帮两台 rapp 设备之间牵线和中继远程会话的流量，没有"替 rapp 转发到某个数据服务"的功能。用户说的"relay 可以作为中转"是要新加的能力，会让 relay 多做一件事；按 R2，relay 上每多一样功能都要过安全要求那份清单。
- xiaobucubic 的显示服务现在是独立的服务，有自己的访问口令。"算作 rapp 核心的一部分"是指把它搬进 rapp，还是 rapp 把它当作一个受管的服务来启动和连接，用户没有说。

用户没有说的（不替用户定）：

- （外部小屏怎么连，用户在 U60 里回答了，见下面"外部小屏怎么连"。）
- （relay 能不能看到内容，用户在 U62 里回答了：不能。见下面"relay 中转的两条要求"。）
- 服务跑在本机时，另一台 rapp 设备（比如平板）要不要也能读到。如果要，就是经过设备之间已有的连接去读，不需要服务自己开端口。

### 外部小屏怎么连（U60）

用户的话："外部小屏可以走 usb,或接入 relay 的 ip, 是可以访问到的。"

两条路：

| 路 | 怎么走 | 现状 |
|---|---|---|
| USB | 小屏插在一台电脑上，电脑上的桥接程序去读数据服务，再通过串口把同样的数据传给小屏 | xiaobucubic 已经有（`apps/xiaobucubic/API.md` 的"USB 串口传输"；还有"优先 USB，超时后用备用 Wi-Fi"的自动模式） |
| relay 的地址 | 小屏通过 Wi-Fi 连 relay 的 IP，读到数据 | relay 现在没有这个功能 |

所以我在上一条里写的"小屏不是 rapp 设备，不能经 relay"要更正：用户的意思是让小屏直接访问 relay 的地址。

USB 这条路不需要 rapp 或 relay 新做任何事，也没有新的暴露面：数据只在那台电脑和小屏之间走。

走 relay 这条路，要提醒用户一点（是我的看法）：

- relay 现在只开一个端口（`22026/udp`），说的是 rapp 设备之间的协议。小屏在 Wi-Fi 模式下是用普通的网页请求方式读数据的，说不了这个协议。要让小屏连 relay，relay 就得再开一个给网页请求用的入口。
- 这等于在唯一的公网门禁上多开一个口子，而且对面是一个口令存在固件里的小设备。按 relay 安全要求的 R2，这个口子要单独过一遍清单：只读、只给便签和数值这类数据、口令可以单独吊销、限速。
- 相比之下，USB 那条路零风险。如果小屏平时就摆在主控电脑旁边，USB 就够了；relay 那条路只在小屏要放在别处（比如另一个房间、另一个地方）时才需要。

用户没有说的（不替用户定）：两条路是都做，还是先做 USB、relay 的以后再说。

#### 更正：USB 不用特别处理（U61）

用户的话："usb 也只是联网接入互联网，不用特别处理"。

我在上面把 USB 和 relay 的地址写成了两条要分别设计的路，这不对。用户的意思是：USB 只是小屏上网的一种方式，和 Wi-Fi 一样。对 rapp 来说，小屏就是一个能联网的客户端，按配置好的地址（局域网里的地址，或者 relay 的地址）去读数据服务；它是插着 USB 还是连着 Wi-Fi，rapp 不用管，也不用为 USB 做任何设计。

所以：

- 上面表格里"USB / relay 的地址"两条路的分法作废。小屏怎么连，只有一个问题：它读的那个地址是什么（和 U59 的三种部署方式对应）。
- 上面"两条路是都做，还是先做 USB"这个待定项作废。
- 仍然成立的一点：如果小屏读的是 relay 的地址，relay 要有一个它读得到的入口，这个入口要过 relay 安全要求。

### relay 中转的两条要求（U62）

用户的话："经 relay 中转时，relay 不能看到任何内容。有点向 frpc 之类的能力，但是非统一认证（设备注册或其他）是访问不到的"。

两条要求：

1. **relay 看不到任何内容。** 中转的数据在两头加密，relay 只搬运，解不开。
2. **没有经过统一认证的访问不到。** 能力上像 frp 那类内网穿透工具（把内网里的一个服务通过公网上的一台机器转出去），但不是谁知道地址就能连：只有经过统一认证的一方（注册过的设备，或者别的认证方式）才连得上。

**这和已有的一条决定冲突，需要用户知道：**

- 平台规格（`2026-11-11-rapp-platform-design.md`）的 D8 写的是"性能优先于安全；唯一的门禁是 relay，其余连接一律从简"，并且明确接受了一个代价："拿到 VPS 的人能冒充任何设备，也能看到中继流量。"证书校验和端到端密钥被列在"不做"里。
- 也就是说，**现在经 relay 中继的远程会话，relay 是看得到内容的。** relay 安全要求草稿里也记着这一条。
- U62 要求的"relay 不能看到任何内容"，比 D8 严。要做到，两头的设备得各自有密钥、互相认得对方，加密在设备之间完成，relay 手里没有钥匙。这正是 D8 里说不做的"端到端密钥"。

两种读法，用户没有说是哪一种（不替用户定）：

| 读法 | 含义 | 影响 |
|---|---|---|
| 只管数据服务 | 新加的数据中转做到 relay 看不到；远程会话维持 D8 现状 | 两套做法并存；远程画面和键盘输入仍然能被拿到 VPS 的人看到 |
| 全部都管 | 远程会话的中继也改成 relay 看不到 | 要改 D8，是平台层面的改动；好处是只有一套做法 |

我的看法（不是用户说的）：键盘输入和画面比便签敏感得多。如果便签都要求 relay 看不到，远程会话没有理由更松。所以第二种读法更说得通，但它要改已定的 D8，得由用户明确说。

"统一认证"和现状的关系：

- 现在的认证是一个共享的 relay key，加每台设备的密码。设备第一次启动时自己生成 `id` 和 `secret`，向 relay 登记。
- 用户说的"设备注册或其他"和这个方向一致：以注册过的设备为准。
- 外部小屏不是 rapp 设备。按 U62，它要读 relay 上的数据，也得先经过统一认证，比如作为一种设备注册进来、拿到自己的凭据。这同时要求小屏自己能解密，因为 relay 解不开。小屏的固件做不做得到，没有核对。

#### 这是对 relay 整体的要求（U63）

用户的话："这是 relay 的设计规格，我希望在不消耗额外资源、更流畅轻量化的中转服务上，保持必要的安全性。避免被攻破后劫持数据。"

读到的三点：

1. 这是对 relay 整体的要求，写进 relay 的设计规格，不是只针对数据服务。
2. 前提：relay 不多消耗资源，保持流畅、轻量。
3. 目标：relay 被攻破后，数据不被劫持。也就是拿到 VPS 的人既看不到中转的内容，也不能冒充设备去接管。

这改了 D8 接受的那个代价（"拿到 VPS 的人能冒充任何设备，也能看到中继流量"）。D8 的另一半"性能优先、从简"用户保留了，就是第 2 点。

我核对了现在的代码（`rust/relay/src/server.rs` 的 `relay` 函数）：

- 现在 relay 是把两条连接接在一起：从一头收到的数据先解开，再加密发给另一头。所以它看得到内容，而且每份数据在 relay 上要做一次解密、一次加密。
- 要做到"relay 看不到"，是两头的设备之间自己再加密一层，relay 收到的就是解不开的数据，原样转发。**relay 上不增加任何工作**，和第 2 点不矛盾。多出来的一次加密在两头的设备上，开销很小。
- "不能冒充"需要设备之间互相认得对方的密钥，不靠 relay 担保。现在设备的身份（密码的校验）是 relay 说了算，所以拿到 relay 就能冒充。

以上是方向上的判断，具体做法（密钥怎么生成、第一次怎么互相认识、性能实测）要在 relay 的设计里定，没有做。

用户没有说的（不替用户定）：

- 设备第一次怎么互相认识（比如配对时在两台设备上核对一串码）。这是"relay 被攻破也不能冒充"绕不开的一步，会多一个用户动作。
- 已经配好的设备怎么过渡。

#### relay 与业务无关，选最成熟的（U64）

用户的话："relay 功能尽量与业务无关，纯技术方案，尽量选最成熟的"。

读到的三点：

1. **relay 与业务无关。** relay 不知道经过它的是远程画面、便签还是数值，也不为某一种数据做专门的功能。它只做一件事：让经过认证的两方连上，搬运它解不开的数据。
2. **纯技术方案。** 安全靠协议本身保证，不靠业务上的约定。
3. **选最成熟的。** 用已经被广泛使用、检验过的做法，不自己发明。

这一条顺带回答了前面的几个问题：

- U59 说的"relay 可以中转数据服务"，不是给 relay 加一个"数据服务转发"功能，而是 relay 提供一条通用的通道，数据服务和远程会话都走它。relay 上不会因为多一种业务而多一样功能。
- 小屏要读 relay 那边的数据，也不是 relay 给它开一个专门的入口，而是小屏作为通道的一方接进来。

成熟做法的候选（是我列的，不是用户说的；选哪个在 relay 的设计里定）：

| 做法 | 是什么 | 成熟度 | 对 rapp 的改动 |
|---|---|---|---|
| 设备之间直接用 TLS 1.3 互相验证 | 每台设备有自己的证书，配对时记住对方证书的指纹；加密在两台设备之间建立，relay 只转发 | TLS 是用得最广的加密协议；rapp 现在的连接（QUIC）里用的就是它，只是没有校验证书 | 最小：把现在"不校验证书"改成"校验配对时记下的指纹"，加密的两端从"设备到 relay"改成"设备到设备" |
| Noise 协议 | WireGuard 用的那套密钥交换 | 成熟，WireGuard 已进 Linux 内核 | 要新引入一套库，新写握手 |
| 直接用现成的组网工具（WireGuard、Tailscale 一类） | 不自己做中转，设备之间先组成一个私有网络 | 很成熟 | 最大：每台设备多装一样东西，平板上的安装和权限更麻烦；rapp 的 relay 基本就不需要了 |

我的看法：第一种最贴合"最成熟、改动最小、relay 不多干活"。它用的是 rapp 已经在用的东西，relay 的代码反而会更少。

#### 用户的答复（U65）

我把上面的理解、三个候选做法和"倾向第一种（设备之间直接用 TLS 1.3 互相验证）"发给用户，用户回："行"。

我的读法：理解没有错；relay 的设计以第一种做法为首选来展开。这只是方向上的认可，不是对一份设计的批准：relay 的设计还没有写，配对时设备怎么互相认识、已配好的设备怎么过渡、性能实测，都留到那份设计里，写出来再请用户看。
