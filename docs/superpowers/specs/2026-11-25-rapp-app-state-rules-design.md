## 1. 一句话和边界

**被控端有一个通用的小引擎，只认四样东西：去哪看、怎么认、认出来算什么、什么条件下换一套。这四样全写在规则里。换 app、app 改版、换主题、换语言，改的都是规则，不改 rapp。**

- 只看画面，不碰 app（守 K2）。
- 只观察。认出来的状态不触发任何自动点击或输入。
- 认出来的状态是**推断**的，界面上和 CLI 自己报的状态分开标。

不做：规则里带图片或脚本；读 app 的本地文件；Antigravity IDE 和并进 Gemini app 的那一版（默认规则只管 Antigravity App）。

## 2. 第 2 稿改了什么

**按 AS6 重做了规则的模型**：第 1 稿把“去哪看”写死成三处、“怎么认”写死成四种，换一个布局不同的 app 就要改代码。第 2 稿把这两样都放进规则（§4），加了变体、继承、补丁和能力声明（§5），加了一包谁都能用的通用规则（§6.1）。

**更正了第 1 稿和调研里的两处错**，都是读了代码才发现的：

1. 第 1 稿说“输入区沿用焦点面板的规则找”。**对这三家不成立。** 焦点面板靠读控件树，而这三家都是 Electron 做的，默认不给控件树；rapp 现在也没有去打开它（焦点面板规格 §3）。所以输入区和侧栏要**从画面上找**，办法写在 §4.2。
2. 调研里说“被控端已有文字识别”。**代码里没有。** 沟通机制设计规划了它，还没有实现。所以“按文字认”在本文里是一项要新做的能力，没有它时规则照样能用，只是少几个标志（§5.4）。

## 3. “灵活”具体指什么

要适配的变化有八种。每一种对应一个机制，都不用改代码：

| 会变的东西 | 靠什么适配 | 在哪 |
|---|---|---|
| 换一个 app | 规则是数据，一个 app 一包；没有专门规则的聊天类 app 可以先用通用包 | §4、§6.1 |
| app 改版 | 一包里可以有按版本区分的变体；规则自检发现对不上就自动试别的变体；新修订导入就生效，不用等 rapp 发版（规则源第一阶段不做，§9） | §5.1、§7 |
| 浅色深色、缩放、窗口大小 | 区域用“相对窗口的位置加搜索”来定，不用固定坐标；认法用形状、色相、动没动，不用图片模板；主题自动判断 | §4.2、§4.3 |
| 界面语言 | 优先用不靠文字的标志；要靠文字的，词表按语言写在变体里 | §5.1 |
| 布局不同（侧栏收起了、换了页签） | 区域找不到时，只是用到它的标志不作数，别的照常；也可以为这种布局写变体 | §4.2、§5.1 |
| 被控端能力不同（没有文字识别、读不到版本、系统不同） | 每个标志声明它要什么能力；缺了就只跳过这个标志 | §5.4 |
| 以后有新的信号来源（控件树、系统通知） | 标志可以写几种取法，按顺序试。格式里留了位置，第一阶段只实现“看画面” | §4.1 |
| 用户想微调一个数 | “我的”可以只写一小块补丁，不用抄整包 | §5.3 |

## 4. 模型：四层

```
来源（画面、瓦片变化、文字识别…）
   ▼
区域：去哪看        例：主栏底部那一条里，最靠右的小圆按钮
   ▼
标志：怎么认        例：按钮里的图标是实心方块
   ▼
状态：算什么        例：这个标志成立 → 在干活
```

### 4.1 来源和能力

| 来源 | 给什么 | 现在有没有 |
|---|---|---|
| `pixels` | 窗口的原始画面 | 有（`WindowCapture.swift`） |
| `tiles` | 这一帧哪些小块变了 | 有，在编码器里（`TileCodec.swift`），要报出来 |
| `text` | 一小块画面里识别出的文字 | **没有，要新做**。macOS 用系统自带的识别，只在本机跑 |
| `tree` | 控件树里某个控件的角色和位置 | 预留。这三家默认不给；要用得先定要不要打开 Electron 的开关 |
| `notice` | 系统通知 | 预留 |

被控端在会话开始时报出自己有哪些能力，还有 app 的版本号（§8）。

### 4.2 区域：去哪看

区域是一步步收窄出来的，每一步都写在规则里。单位是窗口的逻辑点，和屏幕缩放无关。四种写法：

| 写法 | 含义 | 例 |
|---|---|---|
| `box` | 相对窗口或另一个区域的一块：贴哪条边、多宽多高，可以写点数或百分比 | 主栏最下面 160 点高的一条 |
| `edge` | 找一条分界线：从某一边往里，背景色第一次明显变化的地方 | 侧栏的右边界，在 160 到 420 点之间找 |
| `blob` | 在一块里找小图形：大小范围、圆不圆，取最右的、最下的或全部 | 底部那一条里最靠右的、24 到 48 点的圆形 |
| `strip` | 沿一条边切出一窄条 | 侧栏靠右 40 点宽的一条，圆点都在这里 |

区域找不到是正常情况（侧栏收起了），不是错误：用到它的标志这一轮不作数。

### 4.3 标志：怎么认

每个标志是“在某个区域里，认某一样东西”。五种认法，都带可调的参数：

| 认法 | 认什么 | 参数 | 要的能力 |
|---|---|---|---|
| `shape` | 小图形的形状：实心方块、箭头、圆点、圆环、其他 | 形状名；最低相似度 | `pixels` |
| `color` | 颜色落在哪一段：可以写颜色名，也可以写色相、饱和度、明度的范围 | 范围 | `pixels` |
| `motion` | 这一块在一小段时间里变没变 | 时间窗；变了多少算变 | `tiles` 或 `pixels` |
| `text` | 这一块识别出的文字里有没有某些词 | 词表，可以用通配 | `text` |
| `present` | 这个区域找没找到 | 无 | `pixels` |

一个标志可以同时写几项，要都成立才算（“绿色的圆点”是 `shape` 加 `color`）。区域里有多个图形时（侧栏的一串圆点），标志给出**命中了几个**。

### 4.4 状态：算什么

状态是一张有先后的表，从上往下，第一条成立的就是结果：

```json
"states": [
  {"state": "blocked", "kind": "permission", "when": {"any": ["ask"]}},
  {"state": "working", "when": {"any": ["stop", "rowBusy"]}, "hold": 0.6, "release": 2.0},
  {"state": "done",    "when": {"any": ["rowDot", "workedFor"]}},
  {"state": "idle"}
]
```

- `when` 里可以用 `any`、`all`、`not` 组合标志。
- `hold` 是进入这个状态前条件要连续成立多少秒，`release` 是离开前要连续不成立多少秒。防止图标一闪就跳状态。
- 状态用和终端那边同一套词：`working`、`done`、`blocked`（可带 `kind`）、`idle`。

### 4.5 报出来什么

- 当前窗口的状态；各个“数个数”的标志的结果（比如“在跑的 2 个，做完没看的 3 个”）；一个 `inferred: true`。
- 这一包规则的健康情况（§7）。
- **不报**画面和识别出的文字。侧栏每一行的标题第一阶段不取【我定的】，只报个数。

## 5. 让规则灵活的四样东西

### 5.1 变体：什么条件下换一套

一包规则里可以有若干变体。每个变体是“条件加一块补丁”，条件成立就把补丁盖上去；几个变体可以同时成立，按书写顺序依次盖。

可以写的条件：

| 条件 | 含义 |
|---|---|
| `appVersion` | 版本范围，`min`、`max` |
| `os` | `macos`、`windows`、`linux` |
| `theme` | `light`、`dark`。被控端按主栏背景的明暗自己判断 |
| `locale` | 被控端系统的界面语言 |
| `windowWidth` | 窗口宽度的范围 |
| `found`、`missing` | 某个区域找到了、没找到 |

例：深色主题下圆点的绿色偏暗，只改一个参数：

```json
{"when": {"theme": "dark"}, "patch": {"signals": {"rowDot": {"detect": {"color": {"h": [100, 160], "l": [35, 70]}}}}}}
```

### 5.2 继承：只写不一样的地方

`"extends": "generic-chat"` 表示先拿通用包，再把自己写的盖上去。三家的默认规则都是这么写的（§6），每包只有几行。

### 5.3 补丁：用户只改一个数

“我的”这一层既可以放整包，也可以只放一块补丁，指明盖在哪一包上。上游那一包升级了，补丁继续有效。

补丁的规则（变体、继承、“我的”都用同一种）：对象按键合并；写 `null` 是删掉；数组整个替换。

### 5.4 能力声明：缺什么就少认什么

- 标志可以写 `needs`，列出它要的能力。被控端没有这项能力，这个标志就跳过，状态表里当它不成立。
- 引擎遇到不认识的认法或区域写法，同样只跳过用到它的标志，不丢整包。
- `format` 分大小版本。小版本只加东西，旧引擎照常能读；大版本不一样才整包跳过。

所以一包新规则放到旧版 rapp 上，或者放到没有文字识别的机器上，是“少认几样”，不是“不能用”。

## 6. 默认规则

### 6.1 通用包 `generic-chat`

给“下面一个输入区、左边可能有一列会话”的聊天类 app 用。它只用不靠颜色、不靠文字的标志：

```json
{
  "format": "1.0", "id": "generic-chat", "name": "聊天类通用", "rev": 1, "updated": "2026-11-25",
  "ids": [],
  "regions": {
    "sidebar": {"edge": {"from": "left", "min": 160, "max": 420}},
    "main":    {"box": {"rightOf": "sidebar", "top": 0, "right": 0, "bottom": 0}},
    "bottom":  {"box": {"in": "main", "bottom": 0, "height": 160}},
    "button":  {"blob": {"in": "bottom", "round": true, "size": [24, 48], "pick": "rightmost"}},
    "markers": {"blob": {"in": {"strip": {"of": "sidebar", "side": "right", "width": 40}}, "size": [6, 20], "pick": "all"}},
    "tail":    {"box": {"in": "main", "above": "bottom", "height": 240}}
  },
  "signals": {
    "stop":    {"in": "button",  "detect": {"shape": "square"}, "status": "untested"},
    "rowBusy": {"in": "markers", "detect": {"motion": {"window": 0.4}}, "count": true, "status": "untested"}
  },
  "states": [
    {"state": "working", "when": {"any": ["stop", "rowBusy"]}, "hold": 0.6, "release": 2.0},
    {"state": "idle"}
  ],
  "require": ["bottom"]
}
```

- `ids` 是空的：它不会自动套到任何 app 上。哪个 app 要用，在它的 app 配置里写 `"stateRules": "generic-chat"`【我定的】。
- 没有侧栏时 `sidebar` 找不到，`main` 就是整个窗口。
- `require` 列出必须找得到的区域，规则自检看它（§7）。
- 这一包里的数（160、24 到 48 这些）是照 ChatGPT 桌面端那一张画面估的，是起步值。

### 6.2 ChatGPT 桌面端

app 标识 `com.openai.codex` 是在用户的 Mac 上核对的。旧版 ChatGPT Classic 是另一个 app，不在这包里。

```json
{
  "format": "1.0", "id": "chatgpt-desktop", "name": "ChatGPT", "rev": 1, "updated": "2026-11-25",
  "extends": "generic-chat",
  "ids": ["com.openai.codex"],
  "signals": {
    "rowDot":    {"in": "markers", "detect": {"shape": "dot", "color": "green"}, "count": true, "status": "seen"},
    "workedFor": {"in": "tail", "detect": {"text": ["Worked for*"]}, "needs": ["text"], "status": "seen"},
    "ask":       {"in": "tail", "detect": {"text": ["Allow", "Deny", "允许", "拒绝"]}, "needs": ["text"], "status": "untested"}
  },
  "states": [
    {"state": "blocked", "kind": "permission", "when": {"any": ["ask"]}},
    {"state": "working", "when": {"any": ["stop", "rowBusy"]}, "hold": 0.6, "release": 2.0},
    {"state": "done", "when": {"any": ["rowDot", "workedFor"]}},
    {"state": "idle"}
  ]
}
```

- 绿点的意思用户确认了（2026-11-25，原话：“一般绿点表示ready有信息提示”）：做完了、有新结果。所以 `rowDot` 算 `done`。第一次探查时有一行带着另一种圆形图标，后来重截复现不了，用户也不知道指什么。按“不认识的就忽略”，不写，也不报。
- 最左一列“主页”图标右上角也有一个绿点（调研 §5.2），按同样的意思，是“有任务有新结果”的汇总。它在 `sidebar` 左边，现在的区域里没有它；要用时加一个区域和一个标志，等标注时定。
- `ask` 特意不认“Approve”，也只看 `tail`、不看输入区：这个 app 的输入区里常驻着一个“Approve for me”。

### 6.3 Claude 桌面端

app 标识 `com.anthropic.claudefordesktop` 在用户的机器上核对过（版本 7.37095.0，Electron 做的；调研 §5.2）。Chat、Cowork、Code 三个页签先用同一包。

```json
{
  "format": "1.0", "id": "claude-desktop", "name": "Claude", "rev": 1, "updated": "2026-11-25",
  "extends": "generic-chat",
  "ids": ["com.anthropic.claudefordesktop"],
  "signals": {
    "stop":    {"status": "seen"},
    "rowDot":  {"in": "markers", "detect": {"shape": "dot", "color": "green"}, "count": true, "status": "reported"},
    "rowGray": {"in": "markers", "detect": {"shape": "dot", "color": "gray"}, "count": true, "status": "reported"},
    "ask":     {"in": "tail", "detect": {"text": ["Allow", "Deny", "允许", "拒绝"]}, "needs": ["text"], "status": "untested"}
  },
  "states": [
    {"state": "blocked", "kind": "permission", "when": {"any": ["ask"]}},
    {"state": "working", "when": {"any": ["stop", "rowBusy", "rowGray"]}, "hold": 0.6, "release": 2.0},
    {"state": "done", "when": {"any": ["rowDot"]}},
    {"state": "idle"}
  ]
}
```

圆点的意思用户说了（2026-11-25，原话：“一般绿点表示ready有信息提示，claude session 正在工作时灰点”）：**绿点是做完了、有新结果，灰点是正在工作**。所以分成 `rowDot`（绿）和 `rowGray`（灰）。“灰”是饱和度低的那一段，靠明度和侧栏底色分开；灰点和底色很近，明度的范围等标注时量出来再写，现在用颜色名起步。探查时有任务在跑，侧栏却一行标记都没有（调研 §5.2）：在跑的那一行正好是选中的，可能选中时不显示灰点，也可能灰点太淡没看出来。所以两个都还是 `reported`。

`stop` 沿用通用包的认法（实心方块），真机上见过：在跑时输入区右边是一个黑色实心方块，所以改成 `seen`。回复下面还有一行“三个橙色点 + 动词 + 计时”（`Weighing 6m 22s`），也是“在干活”的好标志；要不要加成一个标志，等 R5 标注时定。

### 6.4 Antigravity App

app 标识 `com.google.antigravity` 来自公开资料。用户用的就是 Antigravity App（2026-11-25 确认）。Antigravity IDE（`com.google.antigravity-ide`）不在这包里。

```json
{
  "format": "1.0", "id": "antigravity-app", "name": "Antigravity", "rev": 1, "updated": "2026-11-25",
  "extends": "generic-chat",
  "ids": ["com.google.antigravity"]
}
```

这一包完全没有验过，所以它就是通用包，一个字没加。

### 6.5 哪些是验过的

| app | 真机上见过的 | 用户说有、我没看到的 | 没见过的 |
|---|---|---|---|
| ChatGPT | 侧栏行尾的绿色圆点；最左一列“主页”图标右上角的绿点（调研 §5.2）；“Worked for …”一行；输入区里常驻的“Approve for me” | — | 停止按钮；进行中的标记；等确认的样子 |
| Claude | 输入区右边的停止按钮（黑色实心方块）；回复下面的进行行（三个橙色点 + 动词 + 计时）（调研 §5.2，有任务在跑时） | 侧栏圆点：绿点是做完了，灰点是在工作（探查时侧栏一行标记都没有） | 做完时的样子；等确认的样子；圆点在画面上的位置和颜色 |
| Antigravity | — | — | 全部。这台机器上没装 |

每个标志的 `status`：`tested`（两头都在真机验过）、`seen`（在真机画面上见过）、`reported`（用户说有）、`untested`。**只有 `tested` 的标志能让会话进“需要你”，其余只改灯**【我定的】。转正靠 §10 的标注。

## 7. 挑哪一包、自检、退回

**挑**：

1. 这个 app 的 app 配置里写了 `stateRules`：`off` 就不用；写了包名就用那一包；没写就按 `ids` 找。
2. 各层里同一个 `id` 取层最高、`rev` 最大的；解开 `extends`；把条件成立的变体依次盖上。
3. 被控端没报版本时，带 `appVersion` 条件的变体里取版本最新的那个。

**自检**：窗口看得见时，`require` 里的区域连着 5 轮都找不到，就判定当前这一套“对不上”。

**退回的顺序**：

1. 换变体：把别的版本变体一个个试一遍，哪个能让 `require` 的区域都找到就用哪个，并标“自动换了变体”。
2. 重读一次版本号（app 可能刚自动更新过），再挑一次。
3. 还不行：这包标“不适用”，退回没有规则时的做法，不报推断的状态。
4. 在会话菜单和 app 配置页里安静地标一句“状态规则可能过期”。不弹窗、不抢焦点（设计语言 §0）。

没有规则、或者规则不适用时，行为和现在完全一样。

## 8. 版本号读不读得到

| 系统 | 怎么读 | 结论 |
|---|---|---|
| macOS | app 包里 `Info.plist` 的 `CFBundleShortVersionString` 和 `CFBundleVersion`；从正在运行的进程拿包的路径 | **读得到**。这是 app 公开的包信息。Claude 桌面端的 `Info.plist` 有公开的样例，两个字段都有；另两家未在真机核对 |
| Windows | exe 的版本资源 | 一般读得到。商店版路径不同，未实测 |
| Linux | 没有统一的办法：按 deb、rpm、Flatpak、AppImage 依次试 | 可能读不到，读不到就留空 |

被控端现在不读 app 的版本（查过 `Sources/` 和 `rust/host-linux/`），要加一个可选字段 `appVersion`。

**版本号只是条件之一，不是主要依据。** 这三家更新很快；界面是网页技术做的，可能由服务端下发，版本号没变界面也会变；自动更新后磁盘上的版本可能比正在运行的新。所以真正兜底的是 §7 的自检。

## 9. 升级和分享

**第一阶段两层，后面的盖前面的**（用户 2026-11-25 定：先不要规则源）：

| 层 | 从哪来 | 能不能改 |
|---|---|---|
| 内置 | 随 GUI 发布（`gui/assets/state_rules.json`） | 只读 |
| 我的 | 自己写的、标注出来的、导入的；整包或补丁 | 能改 |

- **动态升级**：导入一包 `rev` 更大的就生效，不用等 rapp 发版。内置的那一份跟着 rapp 发版更新。
- **分享**：导出一包成文件，对方导入。
- **规则源以后再做**：从 HTTPS 地址自动取规则，放在内置和“我的”中间当第三层。规则的格式现在就按三层留好（`id`、`rev`、来源），以后加不用改格式。
- **谁来算**【我定的】：规则存在操作端；打开会话时，操作端把解开后的一包发给被控端，被控端在本机算，只把结果发回来。
- **安全**：规则是纯数据，没有脚本、没有图片、不许带要去取的地址；一包不超过 64 KB；最坏的结果是灯亮错，发不出任何输入。从别人那里来的包一直标着来源。
- **隐私**：rapp 不上传任何东西。导出的包里只有参数，没有画面、没有文字。

这改了 app 配置设计的两条决定（§13 第 4 条，用户 2026-11-25 同意）：D1“配置只在操作端、被控端不用改”；D5“第一版不做导入、分享”。

## 10. 标注：让规则自己长出来

会话菜单里加“标注状态”。用户在 app 正在干活、刚做完、在等确认的时候各点一下。被控端当场把规则里每个区域、每种认法量一遍，记下结果：找到了哪些区域；按钮里的图形最像哪种形状；每个小图形的色相、动没动；认出了哪些词。

- 只记量出来的特征，**不存画面，不存文字内容**。
- 操作端对比几次标注，做三件事：
  1. 已有的标志和标的状态对得上的，`status` 改成 `tested`。
  2. 对不上的，给出改法。例：“圆点的色相量到的是 205，规则写的是绿色，建议改成蓝色”。
  3. 找出规则里没写、但在不同状态下明显不一样的特征，建议加成新标志。
- 结果写成一块补丁，放进“我的”。可以导出。

给一个没有规则的 app 做适配，就是：套上通用包，标注三次，存下补丁。不用手写 JSON。

三家的默认规则靠这一步转正。Claude 那一包只能由用户或别的 agent 在真机上做。

### 10.1 会话开着时不断确认

用户的要求（2026-11-25，原话）：“应该保持会话时，不断确认。”所以不另开一轮探查等结论，规则在平时用的时候一边用一边验。

- **互证**：会话开着时被控端本来就一直在算状态。同一轮里，两个不同的标志指向同一个状态（例：Claude 的停止按钮和侧栏灰点同时出现），两个标志各记一次“对上了”；指向互相冲突的状态（一个说在干活、一个说做完了），各记一次“打架”。
- **前后印证**：在干活的标志消失后 10 秒内，做完的标志出现了（例：停止按钮没了，接着侧栏出现绿点），两个都记一次“对上了”【我定的，10 秒】。
- 只记次数和量到的特征（同 §10），**不存画面，不存文字内容**。
- **自动转正**：一个标志对上 5 次、一次没打架，`status` 自动升成 `tested`【我定的】。只限“在干活”“做完了”这两类，它们只改灯，不进“需要你”，认错了代价小。
- **不自动转正的**：认“在等确认”的标志（`ask` 这类）会让会话进“需要你”，要人在 §10 里标注一次才转正。
- **打架多了**：同一个标志打架 3 次，就当它对不上，按 §7 的自检处理，并在 app 配置页标出来【我定的】。
- **不认识的就忽略**（用户 2026-11-25 原话）：画面上出现规则里没写的图形、颜色，不报、不提示、不影响状态。不断确认只验规则里已有的标志；要加新标志，只在用户手动标注（§10 第 3 条）时提建议。
- 结果和 §10 一样写成补丁进“我的”；手动标注仍然保留，用来纠正。

这样 §6.5 表里“用户说有、我没看到”的标志可以直接带着 `reported` 发出去，用着用着就转正，不再挡在编码前面。

## 11. 分步和验收

| 步 | 做什么 | 验收 |
|---|---|---|
| R0 探查 | 不再单独做（§10.1）。只在开发时用录下来的画面核对 §6 的标志 | 不挡后面的步骤 |
| R1 引擎 | 纯逻辑的一个模块：区域的四种写法、`shape`、`color`、`motion`、`present`、状态表、`hold` 和 `release`、补丁的合并。不碰系统接口 | 用合成的小图和录下来的画面序列做单元测试 |
| R2 被控端 | 报能力和 `appVersion`；把瓦片变化报给引擎；收规则、报结果 | ChatGPT 做完一轮后报 `done`；没有规则时输出和现在逐项相同 |
| R3 操作端 | 两层（内置、我的）、继承、变体、挑包；灯和“推断”标记；app 配置页显示用的哪一包、哪个修订、验到什么程度、健康情况 | `untested` 的标志只改灯；`stateRules: off` 生效 |
| R4 自检和退回 | §7 | 故意给一包对不上的规则，5 轮之后自动换变体或退回，并标出来 |
| R5 标注和互证 | §10、§10.1 | 对 ChatGPT 标三种状态后，`stop` 变成 `tested`，补丁进“我的”；Claude 的停止按钮和灰点同时出现 5 次后，两个都自动变成 `tested`；`ask` 不会自动转正 |
| R6 文字识别 | macOS 被控端的 `text` 能力，只识别规则指定的小块，只在那一块变了时跑 | `workedFor` 和 `ask` 开始作数；没有这项能力的被控端照常工作 |
| R7 升级和分享 | 导出、导入（规则源以后再做，§9） | 不升级 rapp，导入一个 `rev` 更大的包就生效；导出的文件里没有画面和文字 |

R1 到 R4 是能用的最小一套。没有 R6 时认不出“在等确认”，只有“在干活”和“做完了”。

## 12. 测试要求

- 引擎：每种区域写法、每种认法各一组；浅色和深色背景各一遍；一倍和两倍缩放各一遍；窗口宽窄各一遍。
- 补丁：合并、删除、数组替换；继承加变体加“我的”三重叠加。
- 向前兼容：带了不认识的认法、不认识的字段、更新的小版本、更新的大版本、超过大小、坏的 JSON，都不能让会话出错。
- 能力：去掉 `text`，带 `needs` 的标志被跳过，其余结果不变。
- 挑包：版本在范围内、超出范围、读不到版本、两层互相盖。
- 录下来的三家窗口画面只留在本机的测试目录，不进仓库。
