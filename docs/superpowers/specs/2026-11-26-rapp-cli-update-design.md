## 1. 为什么做

用户原话（2026-11-26）：

> 这个工具主要是给 agent 自动化使用。
> 我其实最缺的是自动升级，现在每次要手工点升级很麻烦。请优先实现升级的cli
> 如果是手动执行，应该立即安装

用户的选择：

- 升级 CLI 和放宽自动升级**两个都做**，共用一个新机制：服务先让 GUI 退出，装好后再打开它。
- 自动升级在**没人操作时**装：本机键盘鼠标 10 分钟没动，并且远程会话 10 分钟没有输入。
- 手动执行（`rapp update`）**立即安装**，不等空闲。

## 2. 现在为什么总要手工点（按代码，2026-11-26 在本机核对）

自动升级每 60 秒（`idle_poll`）试一次。版本已下好（`ready`）、开着自动升级、服务由 launchd 启动、不用确认签名、不用管理员密码，并且「没人在用」，它才会装。「没人在用」（`update.rs` 的 `in_use`）由两部分组成：

1. `sessions_in_use`：只要有一个远程会话，或者有会话正在连进来，就算在用。
2. `procs_in_use`：`rapp.app/Contents/` 下有任何进程，只要它不是服务自己、也不是服务的子进程，就算在用；从 `/usr/local/bin/rapp` 启动的进程也算。

本机实况：有 6 个远程会话一直连着（MacBook-M4-Pro 在看终端），还有 6 个 `rapp-term run`（每个文本终端窗口一个，父进程是 shell）。两条都满足，所以自动升级永远等不到「没人在用」。

由此还暴露出两个现成的毛病：

- **文本终端会挡住升级，手工升级也一样。** 手工升级在 GUI 退出后，还要等 `procs_in_use` 变成空，最多等 `gui_wait`（10 秒），等不到就报「rApp 还开着」。而 `rapp-term run` 只要窗口开着就一直在。文本终端设计原本写明「升级时终端照样跑」：`run` 不是服务的子孙，替换 `.app` 碰不到它。
- **`rapp` 命令自己也算在用。** 一个 CLI 进程不可能在升级时把自己排除掉。

现在的手工升级流程：GUI 发 `update_apply`，然后自己退出（`global_sections.dart` 的 `_thenQuit`）。服务等这条 IPC 连接断开（最多 10 秒），再等 app 里没有别的进程（最多 10 秒），然后替换 app、写下标记、重启。新服务起来后读标记，标记里记着 GUI 原来开着，就重新打开 GUI。`update_check` 只是起一个后台任务，马上返回；状态依次是 `checking`、`downloading`，最后变成 `ready`、`up_to_date` 或 `failed`。

## 3. 目标、非目标、反目标

**目标**

1. `rapp update` 一条命令做完：检查、下载、立即装、等新版本跑起来、报告结果。agent 直接能用：有 JSON 输出，有固定的退出码，从不等人输入，有超时。
2. 自动升级真的会在没人操作时发生，不用再点。
3. 两种升级都不打断文本终端里的程序。

**非目标**

- Linux 的自动升级。Linux 上服务不是由 launchd 启动的，现在会回 `NOT_LAUNCHD`，CLI 照实报告就行。
- `rapp status`、`doctor`、`version`，以及给 `share`、`unshare`、`hosts`、`pipe` 补 `--json`。这些放下一份设计。
- 定时升级。需要的话由 agent 用 cron 跑 `rapp update`。

**反目标**（技术上能用，但发生了就算失败）

- 用户正在本机或远程打字、点鼠标时自动装。
- 升级结束了文本终端里的程序。
- 用「杀进程」的方式让 GUI 退出，丢掉没保存的状态。
- CLI 一直挂着不返回。
- CLI 输出 key 或密码。

## 4. 做法的选择

| | 做法 | 结论 |
|---|---|---|
| **A（选定）** | 服务在 `update_status` 里亮一个「请 GUI 退出」的标志。GUI 看到后自己正常退出（不弹 ⌘Q 确认）。自动升级、CLI 升级、CLI 回滚、GUI 升级都走这一条 | 唯一干净的路。GUI 只改一小处 |
| B | 服务用 AppleScript 让 GUI 退出 | 不行：⌘Q 会弹「确认退出」（0.14.14 加的），会卡在那个对话框上 |
| C | 服务直接杀掉 GUI 进程 | 不行：会丢掉没发出去的输入这类状态 |

## 5. 设计

### 5.1 「在用」的新规则

**进程**（`procs_in_use` 改为）：

- **不算在用**：`rapp-term`（`serve` 本来就是服务的子进程；`run` 持有终端，本来就该活过升级），以及 `rapp-cli`（不管从 app 里的路径启动，还是从 `/usr/local/bin/rapp` 启动）。
- **还算在用，要等它退出**：GUI（`rapp`）、`rapp-hub`、`rapp-client`、`rapp-host`，只要它们不是服务的子进程。

**管道**：以前靠在进程表里找 `rapp` 来发现 `rapp pipe`，现在改成服务自己记：数一数开着的 `pipe` 连接，并记下每条最后一次有流量的时间。

**两种场合，两套判断**：

| | 连进本机的远程会话 | 本机连出去的远程窗口 | 管道、端口分享、本机端口映射 | 本机操作 | GUI 等 app 内进程 |
|---|---|---|---|---|---|
| 自动升级 | 10 分钟内有输入、或 10 分钟内刚连进来，才挡 | 有一个不是文本终端的就挡 | 10 分钟内有流量才挡 | 10 分钟内有键盘鼠标才挡 | 先请它们退出（§5.2），退不了就放弃这一次 |
| 手动（`rapp update`、`rapp update rollback`、GUI 的「立即升级」） | 不管 | 不管（GUI 自己点的照旧先问） | 不管（会随重启断开）【我定的】 | 不管 | 先请它们退出（§5.2），退不了就失败 |

审阅后补定的几条（2026-11-26，用户说「全部做完，中途不用问我」，以下都是【我定的】）：

- **本机连出去的远程窗口**：本机正在看别的设备、没碰键盘鼠标时，本机空闲时间照样会到 10 分钟，挡不住。GUI 退出时这些窗口会断开，重开后也不会恢复（只有文本终端的标签页会恢复）。所以有这种窗口就不自动装。GUI 通过 IPC 告诉服务：`{"cmd":"gui_windows","count":N}`，N 是 hub 里**不算文本终端标签页**的远程窗口数；数目一变就发。服务按连接记，连接断开就当作 0。文本终端标签页会恢复，不算。
- **端口分享、本机端口映射也算流量**（连进来的转发 `forward.rs`、本机 `localhost:28000+` 的映射 `maps.rs`，比如 llmapi 网关）：它们和管道一样，会随服务重启断开。服务只记一个「最后一次远程活动」的时间：远程输入、会话开始、管道、转发、映射的流量，都更新这一个时间。
- **会话刚连进来、还没输入**：会话开始时也更新「最后一次远程活动」。不用现有的 `opening` 计数，因为它在整个会话期间都占着，用了的话自动升级还是永远不发生。
- **`rapp-term serve` 不复用 `input` 事件**：`input` 会让别的会话给打字的设备让路（`tell_others`）。终端输入另发 `{"event":"activity"}`，服务只用它记时间。

需要的信号：

- **本机空闲时间**：读 `ioreg -c IOHIDSystem` 里的 `HIDIdleTime`（单位纳秒），用升级模块现有的命令执行器（`Runner`）跑。读不到或看不懂，就算有人在操作，不装。
- **远程输入**：`rapp-host` 遇到输入时已经会发 `{"event":"input"}`（`WorkerCLI.swift:244`），服务在 `workers.rs` 里收到。现在要在这里更新「最后一次远程活动」的时间。`rapp-term serve` 改发 `{"event":"activity"}`（见上），服务收到后只更新时间。
- 10 分钟是常量【我定的】。仍然每 `idle_poll`（60 秒）判断一次。

实现时补定的几条（2026-11-26，都是【我定的】）：

- **自动升级退不掉 GUI 就退避 30 分钟**：请 GUI 退出、等满 `gui_wait` 还在，这一次放弃，30 分钟内不再试，免得每分钟都把 GUI 关一次又打开。
- **`update_check` 可以带 `"wait": true`**：等这次检查（和下载）做完再回复，CLI 用它避免读到检查前的旧状态。已有别的检查或下载在跑时立即回复，CLI 接着轮询状态，直到不再是 checking/downloading。
- **`update_status` 新增字段**：`launchd`（服务是不是 launchd 启动的，不是就不能在线升级）、`error_code`（`still_open`、`needs_admin`、`not_launchd`、`failed`，给 CLI 定退出码）、`auto_wait`（自动升级正在等什么，比如「最近本机有人操作」；日志 `update_auto_wait` 在原因变化时记一条）、`quit_gui`。
- **IPC 失败回复带 `code`**（`needs_confirm`、`needs_admin`、`not_launchd`、`nothing_to_install`、`busy`、`no_previous`、`failed`），需要页面时带 `page`。
- **手动安装等 GUI 期间版本被忽略或换掉**：失败，`nothing_to_install`，不让 CLI 空等。
- **本机自己的端口分享上的流量不算**活动；只有连进本机的转发、管道、映射、远程输入和会话开始算。
- **`--cm` 小窗也是 GUI 进程**：看到 `quit_gui` 一样关掉，不然安装会一直等它。
- **安装记号（marker）记下是谁发起的**（`by`：gui、cli、auto），`update_applied` 日志带上它。

### 5.2 退出 GUI、安装、再打开（四种入口共用）

1. 服务把 `update_status` 的 `quit_gui` 设为 `true`，然后调用 `notify()`。订阅了变化的 GUI 收到 `changed`，重新取状态，看到 `quit_gui`，就直接退出：调用现有的 `hooks.quitNow()`，不弹 ⌘Q 确认。由 GUI 自己发起的升级照旧是 GUI 先退出，不受影响。
2. 服务在第 1 步时看一眼进程表，记下 GUI 原来开没开，把这个结果写进标记的 `gui_was_open`。现在自动升级时这一项总是写 `false`，要改成写实际看到的结果。
3. 等 app 里需要等的进程（§5.1）都退出，最多等 `gui_wait`。等不到：清掉 `quit_gui`；GUI 原来开着的话把它打开；然后失败（手动）或放弃这一次、等下一轮（自动）。
4. 替换 app，写标记，重启。新服务读到标记后打开 GUI（现有逻辑）。

版本差：做替换的是旧服务，被请退出的是同一个 app 里的旧 GUI，两者版本相同。所以从带这个功能的版本往后升级都没有问题。从 0.15.35 升级到带这个功能的第一个版本时，用的还是旧逻辑，只能照旧手工点一次。

### 5.3 命令

所有命令都通过本机 IPC 和服务说话，和现在一样。服务每次启动都会换 `ipc.token`，所以 CLI 每次重连都要重新读一次。

**`rapp update [--yes] [--timeout 秒] [--json]`**：立即升级。

1. 取 `update_status`。服务不是由 launchd 启动的，或者需要重装 pkg（`needs_reinstall`），就报「要手动处理」并给出页面链接。
2. 发 `update_check`，然后每 0.5 秒取一次状态，直到它变成 `ready`、`up_to_date` 或 `failed`。
3. `up_to_date`：报告「已是最新」，退出码 0。`failed`：报告服务给的原因。
4. `needs_confirm`（签名变了）并且没写 `--yes`：报告「要确认」，退出码 6。`needs_admin`：报告「要手动处理」，给出页面链接。
5. 发 `update_apply`，`confirm_signature_change` 跟着 `--yes` 走。收到 ok 后**马上关掉这条连接**，因为服务要等它断开才开始。
6. 每 0.5 秒重连一次，直到服务回答、`update.current` 等于目标版本、状态不再是 `installing`。服务回报失败（`state` 为 `failed`，或者版本没变却有 `error`）就报失败。
7. 报告「已升级到 X（原来 Y）」。

默认超时 900 秒，包含下载时间【我定的】。CLI 自己也会被替换，但正在运行的进程不受影响，和 `rapp-term run` 一样。

**`rapp update check [--timeout 秒] [--json]`**：做第 1–3 步，不安装。因为开着自动下载，结果是 `ready` 时新版本已经下好了。默认超时 300 秒。

**`rapp update status [--json]`**：取一次 `update_status`，把当前版本、最新版本、状态、进度、自动升级开没开、能不能回滚、错误印出来。

**`rapp update rollback [--timeout 秒] [--json]`**：发 `update_rollback`，再按第 5–7 步等版本变成上一版。不要求 `--yes`：明确敲下这条命令本身就是确认【我定的】。默认超时 120 秒。

### 5.4 全局约定（这次落在 update 命令上；退出码同时用到老命令）

**`--json`**：成功和失败都只在**标准输出**的最后打一个 JSON 对象，这样 `rapp update --json | jq` 总能拿到结果，退出码另外说明成没成。例如：

```
{"ok":true,"result":"updated","from":"0.15.35","to":"0.15.36"}
{"ok":true,"result":"up_to_date","current":"0.15.35"}
{"ok":false,"error":"needs_confirm","message":"新版本换了签名，确认后加 --yes 再运行"}
```

不加 `--json` 时，过程中的提示（「检查中」「下载中 45%」「安装中」「等新版本起来」）写到标准错误，结果写到标准输出。

**退出码**（所有命令都用）：

| 码 | 意思 | `error` 代码 |
|---|---|---|
| 0 | 成功，包括「已是最新」 | — |
| 1 | 失败 | `failed`、`busy`、`still_open`、`nothing_to_install`、`no_previous` |
| 2 | 用法错 | `usage` |
| 3 | 本机服务没有在运行 | `not_running` |
| 4 | 对端不在线（老命令以后用） | `offline` |
| 5 | 超时 | `timeout` |
| 6 | 要确认，加 `--yes` 再来 | `needs_confirm` |
| 7 | 要人手动处理（管理员密码、不是 launchd 启动、要重装 pkg） | `needs_admin`、`not_launchd`、`needs_reinstall` |

老命令在服务没运行时，现在的退出码是 1，改成 3；其余不变。

**错误**：加了 `--json` 时，错误以 `{"ok":false,"error":"<代码>","message":"<中文>","page":<链接或 null>}` 写到标准输出（同上）；不加时只把那句中文写到标准错误。`error` 代码用英文，是给 agent 判断用的，以后不改。

**服务端配合**：现在升级相关的错误回复只有一句中文。给它们加一个 `code` 字段，取值就是上表里的代码【我定的】。这是加字段，GUI 不认识会忽略。CLI 按 `code` 判断，不去对中文句子。

**从不交互**：除了 `pipe`，所有命令都不读标准输入。

### 5.5 GUI

- 认识 `update_status.quit_gui`：看到就调用 `hooks.quitNow()`。
- 告诉服务不算文本终端的远程窗口有几个（`gui_windows`，§5.1）。
- 「更新」那一栏里的说明「没人在用时会自动装好」改成「10 分钟没人操作时会自动装好」。具体措辞由实现的人定，意思要准。

### 5.6 日志

`update_applied` 现有的 `mode` 字段取 `auto`、`manual`、`rollback`。新增 `by` 字段，取 `gui`、`cli` 或 `auto`【我定的】。CLI 发的 `update_apply` 和 `update_rollback` 带上 `"by":"cli"`，GUI 不带，服务就当作 `gui`。

### 5.7 测试

- 单元测试：进程表规则（用 ps 的样例数据，包括 `rapp-term run`、`rapp-cli`、链接启动的 `rapp`、从 Dock 打开的 GUI、服务子进程里的 GUI）；自动升级的判断表（§5.1 的每一格）；`HIDIdleTime` 的解析，包括读不到的情况。
- 服务测试：`quit_gui` 会亮起，等不到 GUI 退出会熄灭并失败；手动升级不管远程会话；自动升级在会话空闲时会装，有输入时不装。用 `update/src/fake.rs` 的假执行器。
- CLI：参数解析；退出码和 `error` 代码的对应；`--json` 的输出；对着一个假的服务（`RAPP_LOCAL`）走完整流程，包括服务中途断开、换了 token 再起来、超时。
- 跑测试用 `cargo test --workspace --no-fail-fast`（老教训：只跑单个 crate，testkit 的断言不会编译）。

### 5.8 实机检查（要等一个比当前更新的版本发布出来才能做）

1. 开着几个文本终端，里面跑着 claude，执行 `rapp update`：升级完成，终端里的程序照样跑，窗口照样能用。
2. GUI 开着时执行 `rapp update`：GUI 退出，装好后重新打开，没有弹 ⌘Q 确认。
3. MacBook-M4-Pro 连着在看终端，但两边都 10 分钟不碰：自动装上，M4-Pro 那边断开几秒后自己重连。
4. 本机一直在打字：不自动装。
5. M4-Pro 一直往终端里输入：不自动装。
5a. 本机开着一个看别的设备桌面的远程窗口：不自动装；只开着文本终端标签页：照样自动装，重开后标签页恢复。
6. `rapp update --json`、`rapp update check --json`、`rapp update status --json` 的输出可以被 `jq` 解析，退出码符合 §5.4。
7. `rapp update --timeout 1`：退出码 5。
