U1 和 U3 是读这份文档的前提：rapp 要解决的是用户自己用 Claude 时的注意力瓶颈，不是 Agent 怎么执行、怎么编排。

U3 把"注意力瓶颈"说具体了，是三件事：

1. **书写要流畅**：瓶颈在输入法和编辑器。
2. **一个主控制台**：最常用的那套键盘和显示屏（也就是 B）。
3. **减少多设备的切换成本**：别的电脑上跑着的任务，偶尔去确认一下、回复一下。

## 0.1 理论依据（U4）

出处：Mark Weiser、John Seely Brown，*The Coming Age of Calm Technology*，Xerox PARC，1996 年。
原文 <https://calmtech.com/papers/coming-age-calm-technology>；用户的摘要在 sotvault 的 `youtube-summaries/2026-07-14-coming-age-calm-technology-summary.md`，原文归档在 `ssot/papers/1996-weiser-brown-coming-age-calm-technology/`。

下面三条论点取自那份摘要，右边一列是我做的对应。

| 论点 | 在 rapp 里指什么 |
|---|---|
| **许多计算机共享一个人。** 计算机到处都是以后，问题不再是能不能把信息送到人面前，而是谁有资格占据人的中心注意力 | 多台设备、多个 Agent、多个项目共享用户一个人（U5）。这就是 U1 说的注意力瓶颈 |
| **信息默认待在边缘注意力，需要时进入中心，处理完退回边缘。** 边缘不是不重要，而是容量更大、负担更低的通道 | 边缘：状态灯、全景模式、流量标签（主界面规格 D6、D13）。中心：舞台里那一个远程 app 和底部编辑器（D10、D12）。按 U5，主项目 1–2 个在中心，探索项目和后台任务在边缘 |
| **控制权留给人。** 系统不能强行占据中心；人要始终知道自己在哪、能做什么 | 设计语言第 3 条"只有'等你'会闪"；关掉 B 的窗口只断开会话，不动 A 上的 app |

**这个理论管到哪里（我的分析）**

- 它解释的是主界面为什么长成这样：状态灯、全景、一次只嵌一个窗口。
- 它不解释为什么要远程用真的 GUI、为什么要在本地写字。那两点的依据是 U3，不是这篇文章。回应 F1、F2 时不要把两者混在一起。
- 原文写于 1996 年，"许多计算机"指的是嵌在环境里的设备。把它用到多个 Agent 上是我们的延伸，不是原文的结论。

**由它得出的三条检查（用户已确认采用，正式条文在设计语言 §0，以那边为准）**

1. 每一类信息都要指定它平时待在哪一层。说不清在哪一层的，先不显示。
2. 能自己从边缘进入中心的只有"等你"。其他状态变化只改灯，不弹窗、不抢焦点。
3. 处理完要能退回边缘、不留痕迹：回复发出去以后，那盏灯应该自己变回去，不需要用户再做一步。
   这一条和现状有差距：主界面规格 §3 里"Agent 等你"的提示靠「已处理」按钮手动清除，自动退回要等 S8 有信号来源。

## 0.2 为什么是专用平板或 PC，而不是手机（U6）

用户原话：

> 我认为专注工作时，一个手机是不行的，一是屏幕小，对于视力不好的人是灾难。2 是混合了娱乐沟通等使用，会让人无心专注工作，现在的 pad 市场主要是服务娱乐，生产力方面反而被厂家忽视了价值。第 3 是远程电脑上需要确认事情的交互，往往要滚动、要点击输入、要输入一些文字，这些在手机上做不仅麻烦，阅读也很吃力，虽然有了手机语音输入法，但很少有人为远程终端做优化。我个人使用体验是觉得语音输入和好反馈的机械键盘输入都很重要，一个可交互式 13 寸–16 寸屏幕也很重要，兼顾了便携性和可视范围。

下面是 2026-11-12 在欧美互联网上找到的相关讨论。左边是用户的论点，中间是支持它的，右边是不支持或要小心的。链接见 §5。

| 用户的论点 | 支持 | 反面或要小心的 |
|---|---|---|
| **1. 屏幕小，阅读吃力** | Singh 等 2011 年的研究：同样的文本，理解测验得分桌面约 39%，手机约 19%（UX Magazine 2026-02 转引）。Builder.io《Claude Code on Your Phone》（2026-03）：约 6 寸、390 像素宽，虚拟键盘盖住大半屏，200 行的 diff 很难审；结论是手机终端只是起点，细看 diff、同时照看多个 Agent 需要更大的面。HN 上多人说手机只适合批准、看状态、回一句"继续"，复杂的事要回到大屏和键盘；有人提到没有语法高亮、长时间低头伤颈椎 | 那项研究是 2011 年的手机，读的是隐私条款，只此一项。没有找到专门讨论视力不好的人远程管 Agent 的内容；HN 上只有人建议用墨水屏护眼 |
| **2a. 手机混着娱乐和沟通，没法专注** | "专用设备"是一股看得见的风气：reMarkable、Daylight、Freewrite 都以"只做一件事、没有通知"为卖点。HN 上有人担心手机遥控 Agent 会变成一种强迫行为 | 常被引用的"手机放在旁边就会降低认知能力"（Ward 等 2017）**没有复现**：2022 年的预注册直接复现失败，伯尔尼大学 302 人的研究也没发现总体效应。不要拿它当论据 |
| **2b. 平板市场服务娱乐，生产力被忽视** | Hackaday《Do You Need A Tablet?》（2026-04）及评论：多数人把平板当消费设备；Android 平板的系统和应用支持比手机差；iPad 对编程锁得太死；实体键盘是必需品。也有人正拿平板当远程客户端用（iPad 上的远程桌面、RustDesk）。HN 上有人希望 iPad 能当通用瘦客户端 | 同一篇文章的作者自己买了几台平板都闲置，认为平板只是大一号的手机；有评论说平板加键盘是"多绕几步的笔记本"。这是对"为什么是平板而不是笔记本"的直接质疑 |
| **3. 远程确认要滚动、点击、打字；语音输入没人为远程终端优化** | Claude Code 官方文档写明：语音听写需要本机麦克风，SSH 会话和云端会话里不能用；支持的 20 种语言里有日语，没有中文。有人给 Remote Control 提需求，标题就是"没有听写，手机上没法用"（只看到标题，页面没打开）。Ask HN 上有人说终端界面在手机上"远谈不上舒服"。想用语音的人都在自己搭桥：有人写了手表 app，有人用 Telegram 语音加转写再转给 VPS 上的 Agent | 自己搭桥的人也说明这条路走得通：有人同时跑 3–8 个会话，全靠语音 |
| **4. 语音和机械键盘都重要** | 语音一侧：Wispr 的 CTO 说瓶颈是键盘（厂商立场）；有人实测说话 179 词/分、打字 90。键盘一侧：HN 上有人说光靠说话想不清楚，宁可打字；有人在手机上最想念实体键盘；有人拿十年前的 Surface Pro 3 配机械键盘当终端；用语音的人也承认口述精确的代码很别扭 | — |
| **5. 13–16 寸可交互屏** | Builder.io 那篇的结论（要更大的面）和 Hackaday 评论里对 10–13 寸的偏好，方向一致 | 没有找到专门论证"13–16 寸触屏当 Agent 主控台"的讨论。这一条目前只有用户自己的体验 |

**怎么看这些材料（我的分析）**

- 论点 1 和 3 的外部支持最扎实，而且讨论的共识和用户的说法基本一样：手机管批准、看状态、回一句短话，重活回到大屏和键盘。这也正是 U5 里"手机上也只是做一些辅助"。
- 论点 2a 不要引那项心理学研究。能站住的是专用设备的风气和用户自己的体验。
- 论点 2b 要先回答"为什么不是笔记本"。用户的回答是触屏加便携（论点 5），但外部没有现成的论证，得靠自己的实测。
- 论点 3 对 rapp 有一条直接的设计含义：底部编辑器是 B 上的本地输入框，B 上任何语音输入法都能直接往里说，正好绕过"语音在远程会话里不能用"这个限制。编辑器要不要专门为语音做优化（比如说完自动成段、不自动发送），由用户定。

## 0.4 主控台论点与发散（U5、U7）

用户的论点（U5、U7）：一个人注意力有限，大部分工作放在一台主战电脑上，手机只做辅助；用这台电脑掌控多个 Agent、多个项目和还在跑的任务。既然如此，下一台主电脑不必是 Mac。

以下都是我的发散和分析，供用户取舍，没有一条是已定的。

**核心：主控台和算力分家。** 主电脑只需要输入、显示、网络和一个 rapp；干活的机器在别处。"何必是 Mac"是它的推论。

1. **Mac 从主机变成机房。** Mac mini 无头跑只有 macOS 才有的东西，Omarchy 做前台。DHH 的旧 mini PC 是同一个思路。
2. **三层注意力。** 主项目 1–2 个常驻舞台；探索项目只占一盏灯；后台任务只在"等你"时出现。对应 §0.1 的中心和边缘。
3. **手工操作是 rapp 的独占地带。** 登录、授权弹窗、验证码、没有接口的软件，Agent 和聊天都代劳不了。聊天管大部分，rapp 管必须动手的那部分。
4. **手机和主控台分工。** 手机负责通知和一句话批准，主控台负责成段书写。Boris 那条路和用户这条路是互补的。
5. **键盘即身份。** 机械键盘、输入法词库、编辑器习惯只留在主控台，所有远端 app 自动继承。可以说成"一套输入环境，N 台机器"。
6. **触屏对应全景模式。** 点一盏灯就进去，比鼠标直接。
7. **主控台可替换。** 推到底，结论是"何必是固定的一台"。

**macOS 还剩什么优势**

- 当被控端：Xcode 和签名、Apple 生态、只有 macOS 版的 app。据我所知 Claude 桌面版没有官方 Linux 版（没有核对）。这些理由都支持 Mac 留在机房，而 rapp 正是让它们能留在机房的东西。
- 当主控台：要紧的是输入法。用户的瓶颈是书写（U3），而 Hyprland 上 fcitx5 的候选窗定位、Electron 应用兼容，据我所知是 Linux 桌面的老问题，需要实测。
- 硬件成熟度：用户自己在 sotvault 的调研（`research/2026-10-22-omarchy-xiaomi-tablet-support.md`）写着，小米 Pad 9 Pro 的原生移植只验证过 2 台，深度休眠不可用，温控缺实测。
- rapp 的现状：底部编辑器只在 macOS 客户端有（协议 v5），Windows 和 Omarchy 上的 host、client 还是 v3（README）。要让 Omarchy 当主控台，得先把编辑器移植过去。这是最大的一笔成本。

**最该先验证的一件事**：在 Omarchy 上用自己的键盘和输入法，在 4K 下写一段 500 字的中日文。这一步不顺，整个论点不成立；顺了，剩下的只是移植工作量。

## 0.5 复杂交互在减少，交互以人的注意力为界（U9、U10）

用户的判断（U9）：人和软件之间的复杂操作一路在变少。Office 的复杂操作被云文档取代；现在连云文档上也很少有人亲手操作，复杂的事是跟 Agent 聊，由 Agent 去批量做。

这是用户的观察，我没有数据去证实或否定"没人在云文档上交互"这个程度。下面是它对 rapp 意味着什么，都是我的分析。

**它支持 rapp 的地方**

- **剩下要人亲手做的交互很简单：看、滚动、点一下、写一段话。** rapp 只要把这四件事做好，不必做成完整的远程桌面。原型规格的取向（双色档、低帧率、画面不变不发数据、底部编辑器）正好对着这四件事。
- **这是对 F1 最直接的回答。** UU 的强项是 4K、144 帧、低延迟、手柄，服务的是高强度的实时操作，也就是 U9 说的正在减少的那一类。rapp 服务的是留下来的那一类。
- **聊天发生在各家自己的 GUI 里。** Claude 桌面版、Codex、Cursor 各有各的界面和远程方式。rapp 只处理窗口里的像素（原型规格的第一条原则），所以对哪一家都一样，不用逐家对接。

**它不利于 rapp 的地方**

- **U9 和 F2 是同一个前提。** 反馈者说"Raft 大部分时候就差不多了"，依据正是"复杂交互都变成跟 Agent 聊天"。如果交互只剩聊天，一个原生的聊天客户端（各家的手机 app、remote control、Raft）传的是文字，比传像素更省、更清楚。
- 所以 rapp 的理由不能是"还有很多 GUI 要操作"，那和 U9 矛盾。能站住的是三条：书写在本地（U3）；一套主控台对所有厂商的界面通用；以及聊天代劳不了的那点手工操作（§0.4 第 3 条）。

**对需求的影响**

- 可以把"看、滚动、点、写"明确成 rapp 必须做好的最小交互集，其余交互（拖拽、精细绘图、游戏、视频）明确为不追求。见 §4 第 10 条。
- 介绍 rapp 时，U9 可以放在最前面当背景：不是"远程控制电脑"，而是"交互已经简单到只剩看和写，所以一个省流的窗口加一个好用的输入框就够了"。

### U10：AI native 的交互以人的认知负荷和注意力为界

用户的判断（U10）：留给人的交互，应该只是人的认知负荷和注意力承受得了的那部分；复杂的操作通过语音和写作交给 Agent。

U10 是 U9 的结论，也把前面几条串了起来（以下是我的分析）：

| 前面的哪一条 | 在 U10 里的位置 |
|---|---|
| U1 注意力瓶颈、§0.1 理论依据 | 界线画在哪：人的注意力 |
| U3 书写要流畅、U6 语音和机械键盘都重要 | 人这一侧的出口：说和写 |
| U9 复杂交互在减少 | 界线另一侧的东西去哪了：交给 Agent |

**它给 rapp 的一条判据**：rapp 要支持的每一种交互都问一句，这是不是人的注意力承受得了、而且必须由人来做的？是，就做好；不是，就不做，留给 Agent。§4 第 10 条的最小交互集可以用这条判据来定。

**它带来的三点提醒**

- **人剩下的活是"读和判断"加"说和写"，不是"操作"。** 所以显示这一侧和输入这一侧同样重要：文字要清楚、状态要一眼看得出，判断的成本才低。只把编辑器做好是不够的。
- **"手工操作是 rapp 的独占地带"（§0.4 第 3 条）是一项会贬值的理由。** 按 U10 的方向，登录、授权这类事迟早也会交给 Agent。rapp 长期能站住的是主控台本身：读得清、写得顺、看得过来。手工操作只能算眼下的附带好处。
- 和 §0.5 前面说的一样，U10 也是 F2 的前提。区别仍然在于：rapp 不换掉各家为人设计的界面，只是把它们收到一套主控台上。

### U11：专业工具的复杂界面也不再需要

用户的判断（U11）：专业的生产力工作也不再需要 VS Code、Xcode 那样极其复杂的操作界面。人没空去学、去记那些不常用的操作在哪里；记住它，不如跟 AI 说一句来得快。

以下是我的分析。

**这句话的边界**：用户说的是"用得频率不高的操作"。常用的操作，直接动手和快捷键仍然比说一句快。所以分界线是频率：常用的留给手，不常用的交给语言。

**对 rapp 要远程的那些 app**

- 被远程使用的 app 会越来越像 Agent 的前台（对话、diff、确认），而不是布满工具栏的 IDE。这类界面以文字为主、变化少，正是双色档和按块编码最省的画面。
- Xcode 这类工具不会消失，但会变成没人看的后台：构建和签名还得在 Mac 上跑，只是不再由人去点。这和 §0.4 第 1 条"Mac 从主机变成机房"是一回事。

**对 rapp 自己的界面：同一条标准也要用在自己身上**

- rapp 也不该要求用户记住不常用操作的位置。现在有几处是藏起来的：流量标签上的右键菜单（档位、采集密度、帧率）、按住 ⌥ 点剪贴板历史。
- 已有的做法里有符合 U11 的先例："最省流""最清晰"两个预设，一个词代替三组设置；设计语言 §6 也规定"不依赖悬停、右键、长按才能完成的操作"。
- 一个可以考虑的方向：不常用的设置不做成菜单，而是在底部编辑器里说一句就行。这只是想法，没有定。见 §4 第 11 条。

## 0.6 封闭 app 是必然（U12）

用户原话：

> 我有一个洞察，各家 app 厂家，都会把用户限制在自己的 app 里，作为流量入口和产品粘性可能。好用的模型厂家都会出自己的客户端和订阅包，为了这份收入，会越做越封闭，虽然海外有数据保护法的要求反垄断，但产品经理会把很多产品特性和服务端的工具调用等都放在云端，只能 app 内使用。导致用户想用最好的效果，但必须使用对方提供的 app。官方说法也是安全的考量，不允许其他形式使用。顺着这样发展下去，开源阵营和商业 app 的阵营将会持续的对立。而我们工作，没有必要只用开源软件，而是要用最有成效 ROI 最高的软件解决问题。因此使用各种封闭的 app 成为必然。即使是 ai native 也将会是这样。因此 rapp 必然有需求。

**外部事实（2026-11-12 检索，链接见 §5）**

| 厂商 | 订阅能不能在第三方工具里用 | 时间 |
|---|---|---|
| Anthropic | 不能。订阅的登录只用于 Claude Code 和 Claude.ai；第三方工具要用 API key 另外计费。OpenCode 因此移除了订阅登录；OpenClaw 等第三方工具被移出订阅覆盖范围 | 2026-02 条款澄清；2026-04-04 生效 |
| Google | 不能。AI Pro、Ultra 订阅不再能用于 Gemini CLI；条款禁止用第三方工具走它的登录，有封号报道 | 2026-06-18 起 |
| OpenAI | 能，但限于合作方。订阅可用于 Codex 和"用 ChatGPT 登录"的合作应用 | 2026 年 |
| xAI | 部分能。订阅可登录 Grok Build CLI 和几款第三方工具 | 2026-05-25 起 |

各家的规则这一年里改过几次，上表是媒体和第三方博客的转述，其中一篇的发布方自己卖相关产品。用之前要看各家当时的条款。

**和用户说法的出入**

- "各家都越做越封闭"只对了一半：四家里两家在收紧，两家在放开。但放开的两家也只放给自己指定的合作方和登录方式，入口仍在厂商手里。
- 报道里厂商给出的理由主要是成本和用量（订阅不是为第三方工具的用法设计的、第三方流量缺少遥测难以排查），不是安全。

**它回答了哪条质疑（我的分析）**

- **回答了 F2、F3。** 旁边团队的方案"只能用 API 和无头模式"（F3），正好撞上这道墙：API 另外计费，app 里才有的功能和云端工具也拿不到。U12 解释了为什么必须用厂商自己的 app，也就解释了为什么要远程用真的 GUI。
- **没有回答 F1。** UU 同样能把封闭 app 的画面传过来。"为什么是 rapp 而不是 UU"仍然靠 U3 和 §0.5。
- 两套理由要分开说：**U12 说明为什么是 GUI 而不是 API；U3 和 §0.5 说明为什么是 rapp 而不是通用远程桌面。**

**它加强了哪一点**

- 封闭的 app 越多，一套对各家通用的主控台越有用。每家都会给自己的 app 配远程办法（Claude 的 remote control、ChatGPT app 里的 Codex），但都只管自己那一个。rapp 只处理窗口里的像素，不关心 app 是谁的。
- 需求大小跟着"同时用几家"走。只用一家的人，厂商自己的手机 app 可能就够了。

**要守的一条界线**

rapp 现在做的事是：用户本人在官方 app 里操作，rapp 只把画面和输入搬到另一台机器上。这和远程桌面是同一类用法。
被厂商禁止的是另一类：第三方程序拿着订阅的登录去自动访问。如果将来让 Agent 通过 rapp 去操作厂商的 app（主界面规格 D14 的方向里有这种可能），就可能落到后一类里。
各家条款以现行文本为准，我不是律师，这里只是提醒有这条线。见 §4 第 12 条。

## 0.7 订阅是理性选择，多家订阅是常态（U13）

用户的判断（U13，原话见 §0）：按理性人假设，个人会选固定价格的订阅，API 只有企业用得起；所以一个人订阅几家是常态，最好用的那家买高档，其他家买基础档；走正式 API 的第三方工具基本用不起；灰产 token 有安全风险，而且违法。

**外部材料（2026-11-12 检索，链接见 §5）**

| 用户的说法 | 找到的材料 | 要小心的 |
|---|---|---|
| 一个人用几家是常态 | Pragmatic Engineer 2026 年初的调查（906 人）：70% 同时用 2–4 个 AI 工具，15% 用 5 个以上，只用 1 个的占 15% | 受访者是这份通讯的读者，都是软件工程师；统计的是"在用"，不是"自己掏钱订阅"，谁付费没有说 |
| 订阅比 API 便宜得多 | Anthropic 把 OpenClaw 移出订阅时的报道：Max 订阅最高每月 200 美元，重度用户按 API 价折算一天就有 1000–5000 美元（一位市场人士的估算） | 这是重度使用的情况。用得少的人，API 按量付费反而可能比订阅便宜。"API 只有企业用得起"对重度使用成立 |
| 走正式 API 的第三方工具基本用不起 | 同上；Anthropic、Google 的订阅不能用于第三方工具（§0.6） | OpenAI、xAI 的订阅可以用于部分第三方工具；有报道说 Anthropic 的 Max、Team 套餐从 10 月起附带每月的 API 额度。所以这句话对 Anthropic 和 Google 的重度使用成立，不是对所有厂商都成立 |
| 灰产 token 有风险、违法 | 没有专门检索 | 安全风险是实在的：账号和对话内容都经过来路不明的中间人；违反厂商条款也是确定的。是否违法取决于所在地和具体做法，我不是律师，文档里按用户的判断记录 |

"最好用的那家买高档，其他家买基础档"这个分布，没有找到调查数据。

**它补上了哪一环（我的分析）**

§0.6 说"需求大小跟着同时用几家走"，当时没有依据。U13 加上那份调查补上了这一环：同时用两家以上是多数情况。

**到这里为止的整条论证链**

1. 留给人的交互在变简单，人只需要读和判断、说和写（U9、U10、U11）。
2. 重度使用的个人会选订阅，而且会订几家（U13）。
3. 每份订阅都绑在厂商自己的 app 上，最好的效果只能在 app 里拿到（U12）。
4. 所以一个人手上会有好几个封闭的 app，分散在几台机器上，每个都时不时要人看一眼、回一句（U5）。
5. 人的注意力有限，需要一套主控台把它们收拢，信息平时待在边缘（U1、U4）。
6. 主控台应该是一套顺手的键盘、语音和 13–16 寸屏幕，不是手机（U6）。
7. 在主控台上写字必须流畅，所以输入要在本地完成（U3）。

**这条链证明了什么、没证明什么**

- 第 1–6 步证明了"需要一个跨厂商、以 GUI 为对象的主控台"。
- 第 7 步加上 §0.5 的"只需要看和写"，是 rapp 区别于通用远程桌面的理由。**这一步目前只有推理，没有实测**，仍然要靠 §4 第 2 条的对比实验。
- 第 2 步的调查样本是软件工程师。这条链对别的人群成不成立，没有材料。

## 0.8 目标用户和平台（U14）

用户的决定（U14）：主打 Omarchy 用户和机械键盘用户里做生产力工作的人（不是游戏用户）。也会出 macOS 和 Windows 版本。

**Omarchy 这群人有多大、是什么样的人（2026-11-12 检索，链接见 §5）**

- Omarchy Quattro（4.0）发布后 18 天 ISO 下载 20 万次（官方 2026-09-02 的数字，是下载数，不是活跃用户数）。GitHub 约 3.9 万星，Discord 约 3.5 万人，插件市场 8 月时约 500 个插件。
- 官方口号是"为 Agent 时代准备的可塑操作系统"。系统自带各家的 Agent 命令行工具（Claude Code、Codex、OpenCode、Copilot CLI、Grok CLI 等）。
- 以键盘为中心：窗口自动平铺，常驻界面只有顶栏。面向开发者和整天待在终端里的人。

**为什么对得上（我的分析）**

- 这群人键盘优先、重度用 Agent、常有多台机器（DHH 自己就是，见 §0.3），和 U3、U5、U6 描述的是同一种人。
- "非游戏"正好和 UU 错开。UU 的主场是游戏串流（F1）。
- Omarchy 上跑不了只有 macOS、Windows 版的封闭 app（U12）。要用这些 app，就得另有一台 Mac 或 Windows，再远程过去。这是 rapp 在这群人里最具体的用处。
- Omarchy 的常驻界面只有顶栏，其余靠键盘呼出，和主界面规格 D12"最大程度给远程使用留空间"是同一个取向。

**要正视的矛盾（我的分析）**

- 这群人也是最习惯命令行和 SSH 的人。系统已经自带各家 Agent 的命令行版，他们的 Agent 多半就跑在终端里，tmux 加 SSH 就够了。DHH 本人在访谈里说的做法是终端加 Claude 手机 app（§0.3）。
- 所以对他们来说，rapp 的用处只在命令行版给不了的地方：桌面 app 独有的功能、Xcode 这类只有图形界面的工具、Windows 或 macOS 独占的软件。介绍 rapp 时要直接说这一点，不要泛泛地说"远程用 app"。

**和现状的差距（来自仓库里的 README、`tasks/todo.md`、Rust 版规格）**

| 平台 | 现在有什么 | 要"主打"还缺什么 |
|---|---|---|
| Omarchy | 被控端和操作端的 Rust 方案，协议 v3，只支持 x86_64 | 升到 v4（多窗口）、v5（剪贴板和编辑器）；底部编辑器和输入法；Flutter 主界面的 Linux 构建；嵌入舞台现在靠 macOS 的 IOSurface 把画面送进 GUI，Linux 上要另找办法；Linux 上的服务 |
| macOS | 最完整，协议 v5，主界面 S1 已实现、S2 在做 | — |
| Windows | 被控端的 Rust 方案，协议 v3 | 升到 v4、v5；操作端目前没有方案；Windows 上的服务 |

现在的开发顺序是 macOS 先行。"主打 Omarchy"意味着优先级要调：Omarchy 的操作端至少要追平 macOS 的操作端，否则主打的平台反而是功能最少的。

**"机械键盘用户"对需求意味着什么（我的分析）**

- 按键要原样、可靠地传过去：自定义键位和层、长按重复、修饰键映射。Rust 版规格里已经定了"Super 归 Omarchy，⌘ → Ctrl"。
- 这群人对输入延迟和手感敏感，所以"本地写完再发"（U3）对他们是卖点，不只是用户个人的偏好。

**从个人工具变成给别人用的产品**

之前的前提是"个人使用、独占模式"（原型规格），U14 说的是目标用户和多平台版本，前提变了。平台规格 D8"性能优先于安全，relay 是唯一门禁"是在个人使用的前提下接受的；发布给别人以后这条要不要重新看，由用户定（§4 第 15 条）。

### U15 补充：平台排序和 Omarchy 的角色

用户的判断（U15）：开发者里用 macOS 的最多，其次是 Windows。Omarchy 的意义在于它让 AI native 的用法成为可能，也可以作为初期的流量来源。用户自己是在 Windows 平板上装 Omarchy 用。

**外部数据（2026-11-12 检索，链接见 §5）**

| 来源 | 样本 | macOS | Windows | Linux |
|---|---|---|---|---|
| Stack Overflow 2025 开发者调查（职业开发者，可多选） | 大范围 | 32.9% | 49.5% | Ubuntu 27.7%，WSL 另计 16.8% |
| Pragmatic Engineer 作者在 X 上的投票（约 4000 人，单选） | 创业公司和大厂的开发者，作者自己说是他的"圈子" | 61.6% | 12.8% | 24.2% |
| 同一作者在 LinkedIn 上的投票（约 6000 人） | 同上 | 66% | 12% | 20% |

**和用户判断的出入（我的分析）**

- 放到全体开发者里看，排第一的是 Windows，不是 macOS。
- 放到创业公司和大厂这个圈子里看，macOS 第一是对的，但第二是 Linux，Windows 排第三，只有一成多。
- rapp 早期的用户（重度用 Agent、愿意折腾）更像后一个圈子。按这组数字，先后顺序是 macOS、Linux、Windows。这支持"macOS 为主、Omarchy 引流"，同时说明 Windows 版可以排在后面。
- 两组数字的问法不同（一个可多选，一个单选），不能直接相减，只能看排序。

**这条补充改变了什么**

- §0.8 前面说"主打 Omarchy 意味着优先级要调"，按 U15 要改：macOS 仍是用户最多的平台，现有的 macOS 先行是对的。Omarchy 的角色是早期引流和 AI native 用法的样板，不是最大的用户群。
- 所以问题不再是"要不要让 Omarchy 先行"，而是"Omarchy 版要做到什么程度才拿得出手"。引流用的版本如果缺编辑器和输入法（U3 的核心），第一印象会是反的。见 §4 第 13 条。
- 用户自己的主控台是装了 Omarchy 的 x86 Windows 平板。这正好落在 Rust 版规格支持的范围里（只支持 x86_64），也是 §0.4"先验证输入法书写"最现成的一台机器。§0.4 里引的小米平板调研说的是 ARM 平板，不适用于这台。
- 用户库里另有一篇 Surface Book 的调研（`research/2026-10-20-github-omarchy-surface-book-driver-support.md`），结论是触控要补装驱动。用户用的是哪一款平板我不知道，这条只是提醒触屏可能要单独验证。

### U16 补充：选 Flutter 是为了将来的 Android 平板和 iPad

用户的说明（U16）：GUI 选 Flutter（平台规格 D6），看重的是将来用 Android 平板、iPad 当主控平板的可能性。

这和已有的决策是一条线：主界面规格 D8"要能在平板上操作"，界面的基准尺寸是 11 寸平板横屏，控件高度不小于 48px，不依赖悬停和右键，还留了一排给没有实体键盘的平板用的按键。平板端排在 S7，方式待定。

**现状离平板还有多远（来自仓库，以下是我的分析）**

| 环节 | 现在怎么做 | 到平板上会怎样 |
|---|---|---|
| 构建目标 | `gui/` 下只有 macos、linux、windows | 要新增 ios、android 两个目标 |
| B 端中枢 `rapp-hub` | 是 GUI 拉起的子进程，用标准输入输出通信（平台规格 §4 的默认选择：子进程，不用 FFI） | iOS 上的 app 不能拉起子进程。hub 要改成链进 app 的库。Android 上能跑子进程，但也不顺 |
| 画面进 GUI | Swift 的连接和解码库链进 runner，解码到 IOSurface 的像素缓冲，再交给 Flutter 纹理（S2） | iPad 和 macOS 用的是同一套 Swift 和像素缓冲接口，这条路大概率能直接搬过去。Android 要另写一套；Rust 版的核心库（`rapp-core`）可以是共用的起点 |
| 被控端 | macOS、Windows、Omarchy | 平板只当操作端，不需要被控端 |

- 按这张表，**iPad 可能是除 macOS 外最省事的第二个操作端**，比 Omarchy 和 Android 都近，因为解码和显示那一半可以复用。这是推断，没有试过。
- 最大的一处返工是 hub 从子进程改成库。这件事越晚做，依赖子进程通信的代码越多。要不要现在就为它留口子，见 §4 第 16 条。

**和前面几条的关系**

- §0.2 里外部讨论对平板的看法是：Android 平板系统支持差；iPad 对编程锁得太死，但有人正拿它当远程客户端用，也有人希望它能当通用瘦客户端。rapp 在 iPad 上正好是瘦客户端这个用法，绕开了"锁得太死"。
- U6 说手机不行的理由之一是"混合了娱乐沟通"。iPad 和 Android 平板同样是什么都能装的设备，这一条对它们也成立，除非那台平板专门拿来干活。这一点由用户自己把握，文档只记一笔。
- 机械键盘和语音在 iPad 上都现成可用，输入法也成熟。U3 最担心的书写问题，在 iPad 上的风险比在 Omarchy 上小。

### U17 补充：出差时用平板完成全部工作

用户的场景（U17）：出差在外时，拿出平板就能完成全部工作。

**这个场景让哪些已有的设计变得要紧（我的分析）**

- **省流终于有了明确的用处。** §3 里写过"U3 没有提带宽"。出差用的是酒店、车上、手机热点的网络，双色档和"画面不变不发数据"正是为这种网络准备的。
- **公网可达是前提。** 平台规格 D3、D4 定了自建 relay、先局域网再打洞最后中继。但 `tasks/todo.md` 里写着跨 NAT 打洞和 VPS 上的 relay 都还没有实机验证过。出差用的正是这条没验证的路。

**"全部工作"现在还做不到的地方**

"全部"意味着家里或办公室那几台机器没人照看，也得一直连得上。现状有几处靠不住：

| 情况 | 现状 |
|---|---|
| 被控的 Mac 睡眠、锁屏、关了显示器 | README 的前提是"保持登录、不锁屏、显示器开着"。人不在的时候，这几条一旦不成立就连不上，而且没法从远处恢复 |
| 被控的机器重启或 rapp 的服务挂了 | 服务有开机自启和崩溃重启（LaunchAgent）。但重启后要先登录系统，远程登不了 |
| 被控的机器关机了 | 没有远程开机。UU 远程有这个功能（§1 的 F1） |
| 网络断了又恢复 | 原型规格把自动重连列为不做；主界面的 S3 会话生命周期设计了断开后保留条目和重连 |
| 被控端弹出权限确认 | 第一次采集时 macOS 可能弹窗要在本机点"允许"。人不在就点不了 |

这几条在家里用的时候都不是问题，走过去按一下就行。出差时每一条都会让"全部工作"变成"连不上"。要不要把"无人值守也连得上"列成一组正式需求，见 §4 第 17 条。

### U18 补充：平板基本只当操作端

用户的说明（U18）：不用担心平板上的被控端（rapp-server）能力。大多数情况下不会拿平板来跑 Agent，干活主要靠远端的 PC。

**由此定下来的范围**

- iPad 和 Android 平板只做操作端。被控端的两个程序（`rapp-service`、`rapp-host`）不需要上平板。这和 U16 小节表格最后一行一致，现在由用户确认了。
- 这也和 §0.4 的核心一致：主控台和算力分家，平板是主控台。

**要分清的一点（我的说明）**

U16 小节里说的"hub 要从子进程改成库"，说的不是被控端，而是操作端自己的中枢 `rapp-hub`：它负责已存的主机、选路和隧道，平板当操作端时也要用到它。所以 U18 不影响那一条，§4 第 16 条仍然要定。

**顺带的推论（我的分析，待用户确认）**

用户自己的主控台是装了 Omarchy 的平板。按 U18，Omarchy 上也是操作端更要紧。Rust 版规格里 Omarchy 的被控端和操作端是并列的，可以把被控端排到操作端后面。用户说的是"大多数情况下"，所以被控端不是取消，只是靠后。

### U19 补充：无人值守靠使用说明和现成方案，公网安全放在 relay

用户的决定（U19），回答的是 U17 小节里列的那几处"连不上"：

| U17 小节里的问题 | 用户的决定 |
|---|---|
| 被控的机器睡眠、锁屏、熄屏 | 不由 rapp 解决。在使用说明里强调：PC 不关机、不熄屏 |
| 重启、停电 | 已有现成方案，不用 rapp 操心 |
| 没人照看的机器放在哪 | 可以放到云主机上，用虚拟化的 PC 开发机 |
| 公网连接 | 有安全上的考量，放在 relay 里做（原话说的是 router 服务，U20 更正为 relay） |

**已经照做的**

README"A 上的前提"下新增一段"A 没人照看时"，写了不关机不睡眠不熄屏、重启和停电用现成办法、可以用云上的开发机、公网连接和安全放在 relay 这一层。

**两处我的理解**

- "router 服务"就是 `rapp-relay`（平台规格里公网上唯一的门禁）。用户已确认是记错了名字（U20）。README 里写的也是 relay。
- U19 同时回答了 §4 第 15 条的一半：公网上的安全考量放在 relay 这一层，其余连接从简（平台规格 D8）不变。具体在 relay 里做哪些，还没有定。

**一处没有验证的**

rapp 没有在云上的虚拟机里实测过。被控端在 macOS 上靠屏幕录制和辅助功能两项权限，在没有物理显示器的虚拟机里能不能正常采集，要试了才知道。README 里也注明了没实测。

## 0.9 按常用 app 优化，做成可配置的能力（U23）

用户的要求（U23）：针对常用 app 做优化，并且把它做成产品的一项可配置能力。发布时给常用 app 带上默认好用的配置，例如 Chrome、终端、Claude、ChatGPT、grokbot；没适配的 app 用默认配置。

以下是我的分析，供用户取舍。

**它和前面几条的关系**

- **符合 U11。** 每个 app 开箱就是合适的设置，用户就不用去记流量标签右键菜单里的档位、密度、帧率。§4 第 11 条要清理的隐藏操作，有一部分可以靠它消掉。
- **是 UU 做法的生产力版本。** UU 自带三百多套按游戏定制的按键方案（§1 的 F1）。rapp 按生产力 app 带配置，定位正好对上"非游戏的生产力用户"（U14）。
- **不改变"不关心 app 是用什么技术开发的"这条原则**（原型规格）。配置只是给已知的 app 挑一组更合适的参数，底层仍然只处理像素和系统级输入。

**哪些东西可以按 app 配置（候选，来自现有实现里已经因 app 而异的地方）**

| 类别 | 可配置的项 | 现在的情况 |
|---|---|---|
| 画面 | 档位、采集密度、帧率 | 用户在右键菜单里手选；重连时沿用上次的（S3）。原型规格把"记住上次的选择"列为不做 |
| 窗口 | 标题栏裁不裁 | 自动判断：自绘标题栏的 app（Chrome、Electron 应用）整窗传。原型规格风险 5 提过可以加"不裁标题栏"的开关 |
| 文字输入 | 文字是直接注入还是走粘贴；发送后要不要补一个回车；多行怎么送 | 编辑器把文字和块逐个贴到 A 上。个别 app 不接受直接注入的文字（原型规格风险 2） |
| 按键 | 修饰键映射、哪些快捷键留给本机 | Windows、Omarchy 上有固定的映射表（⌘ → Ctrl 等） |
| 滚动 | 方向、速度 | 统一处理 |
| 状态 | 怎么判断这个 app"在等你" | 没有。"等你"的信号要等 S8（设计语言 §0 第 3 条的差距） |

**最后一行可能是这项能力里价值最大的一块。** 如果配置里能写明"这个 app 出现什么迹象就是在等你"（比如窗口标题变了、出现了某个提示），"等你"的灯就不必等 S8，全景模式和设计语言 §0 的第 3 条也有了信号来源。
但它只能是观察，不能替用户去点。这条界线见 §0.6 最后一段。能不能可靠地判断，要逐个 app 试过才知道。

**首批 app 的默认配置（都是我的猜测，没有一条测过）**

| app | 画面 | 输入 | 备注 |
|---|---|---|---|
| 终端 | 双色·灰度，低帧率 | 回车就是执行；多行粘贴要小心逐行执行 | 文字为主，最省流 |
| Claude、ChatGPT、grokbot | 双色·彩色 | 回车是发送，⇧回车是换行，要和编辑器自己的回车规则对齐 | 文字为主，带代码高亮；"等你"的判断最值得先做 |
| Chrome | 高彩 | 网页里的输入框各不相同，用通用方式 | 有图片和视频，流量最大；自绘标题栏，整窗传 |
| 未适配的 app | 现在的默认 | 现在的默认 | — |

**做成"可配置"时要先想清楚的几件事**

- **同一个 app 在不同系统上标识不一样。** macOS 用包名，Windows 用 exe 文件名，Omarchy 用窗口的 class（主机与客户端规格 §7）。一份配置要能对上三种标识。
- **配置分两头。** 档位、密度、帧率是操作端提出的；裁不裁标题栏是被控端的事。一份配置两边都要读得到。
- **谁盖过谁。** 内置默认、用户自己改过的、上次用过的，三者的先后要定。我的建议是：用户明确改过的最优先，其次是内置的 app 配置，最后是通用默认。
- **配置文件要不要开放给用户自己写、互相分享。** Omarchy 社区有插件市场的习惯（§0.8）。开放的话，没适配的 app 可以靠用户补。

## 0.10 固定位置、自留地、聊天窗口、借鉴企业资源管理、AgentOS（U35–U40）

**定性（U43）：这一节整节是阶段性脑暴，不是确定的需求。** 用户的六条想法（U35–U40）、我做的对照、"把六条合成一张图"的提议、固定格子等做法，都只是记录。其中只有一条是用户明确选过的：inbox 只放自己的东西（U41）；它也跟着这一节一起，等真要做 inbox 时再确认。

2026-11-13 用户一次说了六条想法，原话见 §0 的 U35–U40。下面逐条记下它碰到了现有设计的哪里。都是我的分析，没有一条是已定的。

### U35 固定位置比写进 git 好回忆

- 这和 Tower.md 自己的一条原则是同一件事：`~/git/tower.md` 的 README 里写着"位置是记忆的锚。画布上的位置只由人改变；Agent 的进展只改颜色和角标，不移动任何东西"。
- 落到 rapp 上的含义：用户放下的东西，位置只由用户动。程序和 Agent 只能改它上面的灯，不能给它重新排序、把它顶上去或挤下去。
- 现状：会话列表和全景的设备墙，顺序是按设备、按打开先后排的，基本稳定；但没有"我把它放在这里"这个动作。
- 没有查过相关的研究，这里只按用户的体验记录。

### U36、U37 项目是逐步长出来的；要一块叫 inbox 的自留地

- 现状（S5 已实现）：项目要先建好，再把（设备, app）加进去。没归到项目里的会话，在按项目分组时显示成"未归类"。
- U36 的意思是反过来：东西先随手放下，攒多了、看出是一回事了，再变成项目。inbox 就是先放下的那个地方。
- **和已有的"收件箱"重名，而且行为相反。** 沟通机制规格 §3.1 里的"收件箱"指的是未读的员工：谁来消息了就出现，回复或看过就自动消失。U37 的 inbox 是用户自己的地，东西放进去是为了留着、长大。一个是来了就清掉，一个是放下不走。两者要么分开、各起一个名字，要么得说清楚怎么放在一起。
- **和一条非目标有冲突。** 主界面规格 §1 写着"rapp 不做自己的任务模型，任务、放行、注意力编排归 Tower.md"，S5 的 P3 也是这一条。U35 说的"临时想法或任务"如果放进 rapp 的 inbox，rapp 就开始有自己的任务了。这条非目标要不要改，由用户定。

### U38 聊天窗口留给智能助理

- 和已定的顺序一致：U34 把智能助理放在第三阶段，沟通机制规格 §4 只记了方向。U38 给它加了形态（聊天窗口）和用途（确认数据、警告、避免错过提醒）。
- 也回答了沟通机制规格 §9 第 6 条的一半（出差时怎么知道有人需要自己）：通过助理的这个窗口。
- 要小心的一点：本文 §1 分析 F2 时写过，聊天是一条串行的文字流，信息密度低，逐条读很费注意力。所以这个窗口里应该只有助理筛过的少数几条（要确认的、警告、提醒），不是所有员工的全部动态。全部动态仍然归时间线（沟通机制规格 §3.2）。
- 设计语言 §0 的检查第 2 条"能自己从边缘进入中心的只有'等你'"在这里仍然适用：助理的警告算不算"等你"，要定。

### U39 借鉴企业资源管理

用户没有说借鉴哪一部分。下面是我能想到的对应，供用户取舍：

| 企业资源管理里的做法 | 在 rapp 里可以对应什么 |
|---|---|
| 资源主数据：有哪些资源、各自的状态 | 设备、app、订阅的台账。前两样已经有了；订阅（U13 说的"几家各买一档"）还没有 |
| 例外管理：正常的不报，只报偏离计划的 | 设计语言"只有'等你'会闪"；U38 的警告 |
| 审批流：到了某一步要人批 | Agent 等你放行；沟通机制的 K3"每一句都由用户触发" |

## 1. 反馈逐条

### F1 "不如用 UU"

指的是网易 UU 远程：网易的免费远程控制软件，闭源，要网易账号。

**说得对的地方（我的分析）**

- UU 远程很成熟：免费版就有 4K/144Hz、不限时长和设备数，Mac 被控也已支持。
- 只说"远程用 A 上的 Mac"，rapp 讲不出区别，自己做也不划算。别人看不懂价值，是 rapp 的介绍方式有问题。
- 视频类内容 rapp 确实不占优：高彩 15 fps 播视频实测约 14.7 MB/s（README）。硬件编码在 `tasks/todo.md` 里，暂不排期。

**没打中的地方（我的分析）**

| | UU 远程 | rapp（现状） |
|---|---|---|
| 传什么 | 整个桌面（小窗模式也是整块远端屏幕） | 一个 app 的窗口，A 的每个窗口在 B 上各是一个窗口，嵌在主界面的舞台里 |
| 画质取向 | 高画质高码率：4:4:4 真彩、HDR、最高 500 Mbps | 省流、文字清楚、可以牺牲颜色：双色档，画面不变时不发数据 |
| 打字 | 逐键发到远端，用远端的输入法 | 底部编辑器用 B 的输入法组字，回车整段发过去 |
| 多个会话 | 设备列表 | 主界面按设备、App、项目看会话，状态灯，全景模式 |
| 掌控 | 闭源，网易账号和服务器 | 自己的 relay，放在自己的 VPS 上 |

**对需求的影响**

- rapp 不能介绍成"远程控制"。要讲的是上表这五行。
- 这五行要拿得出演示，见 §4 第 2 条。

### F2 "Raft / Slock 大部分时候就差不多了"

指的是 Raft（原名 Slock，Botiverse 出品）：人和 AI Agent 在频道、线程、任务里一起干活的聊天式工作区。
Agent 由守护进程跑在用户自己的机器上，可以分布在多台机器。不是 Raft 共识算法。

**这句话的意思（我的分析）**

想用 A 上的东西，多数时候不用看 A 的画面，给跑在 A 上的 Agent 发消息派活就够了。
它质疑的不是 rapp 做得好不好，而是"远程操作 GUI"这个需求本身。比 F1 更尖锐。

**说得对的地方（我的分析）**

写代码、跑命令、改文件、查日志，Agent 加聊天确实够用，流量只有文字。

**没打中的地方（我的分析）**

- 它解决的是 harness。按 U1，瓶颈在人这头：Agent 越多，要人过目的输出越多。
- 聊天是一条串行的文字流，信息密度低。diff、产物、等人确认的地方、多个会话的状态都要逐条读，不能一眼扫。
- 没有命令行或接口的软件、要靠眼睛判断的活、用户想自己动手而不是交出去的事，它够不着。

**对需求的影响**

- rapp 不做"派任务"。这和主界面规格 §1 的非目标一致：rapp 没有自己的任务模型，任务、放行、注意力编排归 Tower.md。
- rapp 的位置是"人回到现场亲眼看、亲手做"的那部分。纯终端的活、能交给 Agent 的活，不在 rapp 要覆盖的范围里。

### F3 旁边团队的"完全聊天控制"

形态：全部用聊天控制，只走 API 和无头模式，没有 GUI。

**为什么解决不了（我的分析）**

无头模式丢掉的正是 GUI 里为人的注意力做的那部分：会话列表、看得见的变更、能直接点的确认。
这些东西到了聊天里又变回一条文字流，问题和 F2 一样。

**对需求的影响**

- 要远程用的 app 明确包括 Claude 桌面版本身。原型规格 §12 的风险 5、6 已经把它当作实测对象。
- 需求是把那个为人设计的界面原样带到人所在的地方，不是换一个界面。

## 2. 替代方案对照

| 方案 | 形态 | 它解决什么 | 和 rapp 的需求对不上的地方 | 开源 |
|---|---|---|---|---|
| 网易 UU 远程 | 整桌面远程控制 | 远程办公、游戏串流 | 见 F1 的表 | 否 |
| RustDesk | 整桌面远程控制，可自建服务器 | 自己掌控的远程桌面 | 整桌面；不为弱网下看文字设计；用远端输入法。rapp 的组件划分和 ID + 密码认证照的就是它（平台规格 D2、D5） | 是（AGPL-3.0） |

## 3. 由反馈得出的定位

用户已经用 U3 说了要什么（原话见 §0）。下面这句是我的归纳，措辞待用户确认：

> 一套最常用的键盘和显示屏当主控制台。别的电脑上跑着的任务，在这里看一眼、流畅地写一段回复，不用换设备。

**按 U3 重新看三条反馈（我的分析）**

- F1（UU）："一套键盘和显示屏操作多台电脑"，UU 和 RustDesk 也做得到，这一点不是 rapp 独有的。
  差别收窄到两处：打字（UU 逐键发到远端、用远端的输入法；rapp 在 B 上用自己的输入法写完再发），
  以及不用点开就知道哪台机器上的任务在等人。
- F2、F3（Raft、全聊天控制）：聊天框本来就在本机，用的是本机的输入法，"书写流畅"这一条它们是满足的。
  它们缺的是 Claude 的界面本身（F3 原话：只能用 API 和无头模式）。
- 所以 rapp 要同时做到两件事：看到的是 A 上那个真的 app 的界面，写字却在 B 本地。两类替代方案各只占一头。

**和现有设计的对应**

| U3 的哪件事 | 现有设计 |
|---|---|
| 书写要流畅 | 底部编辑器：用 B 的输入法，多行，长文字、图片、文件变成块（协议 v5） |
| 一个主控制台 | 主窗口是装下所有设备和 app 窗口的唯一 dashboard（主界面规格 D1）；点开的远程 app 嵌在主界面里（D10、D12） |
| 偶尔确认、回复，少切换 | 按设备、App、项目看会话（D2）；状态灯（D6，设计语言"只有'等你'会闪"）；全景模式（D13） |

U3 没有提带宽。省流、文字清楚是之前定的（原型规格修订 2），这里不动。

## 4. 待确认和待验证

1. **注意力瓶颈是哪一种：已回答（U3）。** 不是我给的两个选项里的任何一个，而是书写流畅、一个主控制台、少切换设备这三件事。
   它带出两个新问题，由用户定：
   - "偶尔确认一下、回复一下"是短进短出。从主界面切到某个会话、看清状态、写完回复、离开，这一趟多快才算够？现在没有这个指标。
   - README 的前提里有"A 当前输入源设为英文键盘"，每台被控的机器都要手动设一次。这算不算 U3 说的运维成本，要不要由 rapp 代劳？
2. **和 UU 的同条件对比（没做过）。** rapp 自己的码率有实测（README）：文本编辑整帧双色·灰度 1x 约 1.5 KB，Safari 网页约 7.5 KB（这两个数是旧的纯双色算法测的，README 注明新算法约为 2 倍多），画面静止时是 0。
   但没有和 UU、或 H.264/HEVC 在同样限速下比过。低码率下视频编码有可能比按块降色更省，这一点不能凭推断下结论。
   建议的做法：同一个 app（Claude 桌面版），把带宽限到约 200 kbps，UU 调到最低画质，rapp 用"最省流"，比三样：文字看不看得清；写一段中文或日文顺不顺；在两台机器的任务之间各确认、回复一次要多久。
   后两样对应 U3，比第一样重要。
   UU 也够用，就接受 F1；rapp 明显更好，这段对比录屏就是价值说明。
3. **"看不懂价值"本身是一条需求。** README 第一句现在讲的是机制（低位深按块编码串流）。要不要换成 §3 那样先讲解决什么问题，由用户定。
4. **不覆盖的范围要不要写明。** 纯终端的活、能交给 Agent 的活不归 rapp（见 F2）。要不要写进主界面规格的非目标，由用户定。
5. **「已处理」按钮怎么办（待用户定）。** 设计语言 §0 第 3 条要求处理完自己退回边缘，主界面规格 §3 现在靠「已处理」按钮手动清除。两个走法：S8 之前保留按钮当过渡；或者现在就改成"切到那个会话并发出回复后自动清除"。
6. **编辑器要不要专门为语音优化（待用户定）。** 比如说完自动成段、不自动发送。背景见 §0.2 论点 3。
7. **为什么是平板而不是笔记本（待实测）。** 外部对平板的质疑正是这一条（§0.2 论点 2b），13–16 寸触屏也没有外部论证可借（论点 5），只能靠用户自己的实测来回答。
8. **Omarchy 当主控台的两个前置条件（待实测、待排期）。** 一是输入法书写是否流畅（§0.4 最后一段）；二是把底部编辑器移植到 Omarchy 客户端。
9. **§0.4 的七条发散哪些要采纳（待用户定）。** 现在全部只是记录。
10. **要不要把最小交互集写成正式需求（待用户定）。** 即"看、滚动、点、写"必须做好，拖拽、精细绘图、游戏、视频不追求。背景见 §0.5。
11. **用 U11 的标准检查 rapp 自己的界面（待用户定）。** 把现有的隐藏操作列出来，逐个决定：常用的摆到明面上，不常用的改成说一句就能做，或者干脆去掉。
12. **要不要把"rapp 只搬运人的操作，不让 Agent 经它去操作厂商的 app"写成原则（待用户定）。** 背景见 §0.6 最后一段。
