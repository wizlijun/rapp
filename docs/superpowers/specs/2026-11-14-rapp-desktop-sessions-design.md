## 0. 用户的要求

| # | 要求 | 出处 |
|---|---|---|
| DK1 | 加全桌面的远程控制，方便偶尔的全屏操作：屏幕解锁密码、安全弹框、系统升级。原因：“经常有系统的弹出窗口看不到，得且过来点” | 2026-11-14 |
| DK2 | 桌面和 app 的远程不同。会话种类从此有三种：app、终端、桌面 | 2026-11-14 |
| DK3 | 多块屏时以开子窗口的方式打开，且“不响应子窗口”（A 上的单个窗口不单独跟踪，见 §3） | 2026-11-14 |
| DK4 | 设备上“用屏幕共享打开”的按钮去掉，用 rapp 自己的机制重做一遍；入口挪到下面的应用列表里，成为一个叫“桌面”的应用，也可以设为常用 | 2026-11-14 |
| DK5 | 锁屏时鼠标操作无效，要识别出来，提醒用户解锁 | 2026-11-14 |
| DK6 | 参考 RustDesk 记住密码、自动输入密码的做法 | 2026-11-14，第 1 件的回答 |

用户逐件定下的三件事：

1. 解锁做到“锁屏解锁＋记住密码”。开机后的登录窗口不做。
2. 多块屏时，主屏显示在主窗口里，其余每块屏各开一个子窗口。
3. 实现方式选“每块屏一条会话”。

## 1. 一句话和边界

**桌面会话是第三种会话：传 A 一整块屏的像素，不跟踪单个窗口。每块屏一条会话，复用 app 会话的抓屏、编码、限速和输入通道。**

目标：

- 在 rapp 里看到并操作 A 的整块屏，包括系统弹窗、权限框、升级提示，以及别的 app 盖在上面的东西。
- A 锁屏时，B 能看出来，并且能把 A 的系统密码输进去解锁。密码可以记住，可以一键输入，也可以在连上时自动输入。
- 走 rapp 现有的通道（局域网、直连、中继都行），不再依赖苹果的“屏幕共享”和局域网 IP。

不做：

- 开机后、还没有人登录时的登录窗口。那需要一个跑在登录窗口里的 root 进程，安装时要管理员密码，工作量大很多。A 开了 FileVault 的话，开机后第一个解锁界面在系统启动之前，任何远程软件都碰不到。
- 自动登录、远程唤醒睡眠中的 A。README 里“A 不关机、不睡眠、不熄屏”的前提不变，只有锁屏这一条放宽。
- Linux、Windows 被控端。被控端目前只有 macOS 有 `rapp-host`，桌面会话也只在 macOS 被控端上提供。
- A 上“正在被远程控制”的提示。【我定的】沿用“只靠中继把关，其余从简”的原则。会话照常记进访问日志，`rapp --cm` 里照常能看到。

反目标（技术上能跑但算失败）：

- 用户在 B 上点了半天，A 其实是锁着的，B 却没有任何提示。
- 系统密码被敲进了不是锁屏密码框的地方（比如一个打开着的聊天窗口）。

## 2. 现状（2b4bf20）

- **“用屏幕共享打开”**（`gui/lib/ui/devices_tab.dart:192-228`、`gui/lib/ui/main_window.dart:204-206`）只在 macOS 上有。它取 hub 记下的 A 的第一个局域网 IP，执行 `open vnc://<ip>`，调起苹果自带的“屏幕共享”，完全不经过 rapp 的通道，跨网络就用不了。
- **app 会话的抓屏**（`Sources/rapp-host/WindowCapture.swift`）用 ScreenCaptureKit。过滤器是“某块屏上的某个 app”，画布就是那块屏（窗口中心在哪块屏就用哪块，`:77-82`）。窗口表来自 `CGWindowListCopyWindowInfo`，每秒刷新 10 次（`WindowTracker.swift`）。
- **编码**是量化加 64 像素分块，只传有变化的块，再压缩（`RappCore/TileCodec.swift`），没有视频编码。
- **输入注入**（`Sources/rapp-host/InputInjector.swift`）：
  - 事件来源是 `CGEventSource(stateID: .hidSystemState)`（`:13`），投递到 `.cghidEventTap`，作用于整个系统。
  - 按键前会先 `app.activate()`。
  - 鼠标按下前会先检查目标窗口是不是被别的窗口盖住，盖住就先把它提到最前，还盖着就丢掉这次点击。
  - 坐标限制在画布那块屏内。
- **锁屏判断**：`screenLocked()`（`RappCore/Clipboard.swift:148`）读 `CGSSessionScreenIsLocked`，目前只用来改日志和粘贴报错的文字。
- **进程形态**：`rapp-service` 是用户会话里的 LaunchAgent，`rapp-host` 是它的子进程，一个 app 一个进程，一个进程同一时间只服务一条会话（新连接会顶掉旧的）。没有 root 进程。
- **终端会话的先例**：应用 id `term:…` 被当成不透明的字符串，设备、常用（`AppRef(device, bundle, name)`）、会话的键都没改结构；`rapp-service/peer.rs` 按前缀分流。
- **子窗口的先例**：macOS 版 GUI 已经能把一条会话里的 A 窗口拆到独立的 NSWindow（`gui/macos/Runner/DetachedWindow.swift`，⌃⌘D）。Linux 版 GUI 不支持拆分（`linux_session_port.dart:75`）。
- **协议**：v8（`Sources/RappCore/Protocol.swift`），类型号用到 30。还没合并的 `feat/scroll-copy` 分支会把协议升到 v9。

## 3. RustDesk 的做法（为什么锁屏能输密码）

调研用的是 rustdesk master fc9713c，结论如下：

- 锁屏（用户已登录、屏幕锁了）时，处理输入的就是普通的用户会话进程，没有 root 参与。它能把密码输进去，靠的是两点：
  - 事件来源用 `CombinedSessionState`。
  - 每个事件都主动设置修饰键（`event.set_flags(...)`）。锁屏时系统会残留 ⌃⌘ 标志，导致后面的鼠标、键盘都失效（rustdesk issue #11802，PR #11808 修复）。
- 记住密码：密码存在控制端，按设备加密，实际上只是混淆。点“输入系统密码”时：
  1. 先晃一下鼠标、点一下，把密码框唤出来。
  2. 等约 1.2 秒。
  3. 发一条专门的“系统登录”消息。
  4. 被控端先确认“现在确实在锁屏或登录界面”，是才把密码当按键敲进去并回车，否则丢弃。
  
  勾了“自动登录”的话，连上时会自动做一遍。
- 开机后的登录窗口靠一个由 launchd 放进登录窗口会话的 root 进程。本文不做。
- 已知问题：快速切换用户后停在登录界面时控制不了（rustdesk issue #2357，至今未解决）。

## 4. 设计

### 4.1 应用 id 和入口

- 设备的应用列表里多一项“桌面”。它的应用 id 是 `desktop:`，作为不透明字符串放进 `AppRef.bundle`，所以常用、项目、会话列表都不改结构，可以设为常用（DK4）。
- 每块屏的会话 id 是 `desktop:<CGDirectDisplayID>`，只在内部使用，不进常用。CGDirectDisplayID 重启后可能会变，所以常用里只存 `desktop:`。
- `rapp-host list-apps --json` 的输出多一个 `displays` 字段，每块屏一项：`{id, name, main, width, height}`。字段为空或没有这个字段（老版本 A）时不显示“桌面”这一项。【我定的】
- 设备行上的“用屏幕共享打开”按钮删掉，连同 `main_window.dart` 里的 `vnc://` 回调。hub 的 `lan` 字段还要用来拨号，保留。

### 4.2 被控端：整屏模式

- `rapp-host serve` 新增 `--display <CGDirectDisplayID>`，和 `--app` 二选一。`rapp-service` 在 `peer.rs` 里按 `desktop:` 前缀分流，每块屏一个 worker，键是完整的会话 id。worker 的启动、闲置停止、权限检查都沿用 app 的流程。
- 抓屏用 `SCContentFilter(display:excludingWindows: [])`，抓整块屏，包括菜单栏、Dock、系统弹窗。画布就是这块屏。
- 窗口表固定只有一项：一个铺满整屏的窗口，id 固定，类型 normal，没有标题栏，不可移动、不可缩放、不可关闭。这就是“不响应子窗口”（DK3）：A 上开关窗口、移动窗口都不影响 B 这边的布局。
- 菜单栏镜像不发，因为画面里已经有真的菜单栏。`resize`、`move`、`close` 这三类消息直接忽略。
- 输入：
  - 按键前不 `activate` 任何 app。
  - 点击前不做“被盖住”检查。
  - 坐标限制在这块屏内。
  - 剪贴板、粘贴、文件传输只在主屏的会话里开，和 app 会话一样；副屏的会话关掉剪贴板监听和文件传输，否则 A 上复制一次，B 会收到 N 份。【我定的】`rapp-host serve` 加一个开关（如 `--no-clipboard`）。
  - 输入源（v8 的 29/30）照常发。
- 让出输入：沿用现有规则。同一台 A 上，谁在操作，其他会话（包括别的桌面会话、app 会话）就让出输入，B 上显示“远端正在被 X 操作”。
- 防睡眠（`PowerHold`）照常持有。

### 4.3 输入注入修正（对 app 会话也生效）

照 RustDesk 的办法改 `InputInjector`：

- 事件来源改成 `CGEventSource(stateID: .combinedSessionState)`。
- 每个键盘、鼠标、滚轮事件都显式设置修饰键。鼠标和滚轮设成空，按键用消息里带的修饰键。现在 `:50`、`:114` 有一部分已经这样做了，要补齐到所有事件。

这一改同时影响 app 会话，回归测试要覆盖 app 会话的打字、快捷键和拖拽。

### 4.4 锁屏识别、提醒和解锁

- 被控端每秒检查一次锁屏状态（`screenLocked()`），状态变化时发一条新消息 `screenLocked(Bool)`（类型 31，host → client）。会话开始时也发一次当前状态。
- 31 和 32 加进合并时的下一个协议版本：`feat/scroll-copy` 还没合并就一起进 v9，已经合并了就是 v10。【我定的】现在的解析器（`MessageParser.next()`）遇到不认识的类型会断开连接，所以被控端只对报告了新版本的客户端发 31。桌面会话只有新版 GUI 才开得了，天然满足这个条件。
- 锁屏时 B 的桌面画面上方显示一条提示：“A 已锁屏，鼠标和键盘操作不会生效。请先解锁。”旁边有一个“输入系统密码”按钮。所有显示这块屏的窗口都显示这条提示，包括主窗口和子窗口。
- app 会话也发 31（同样按版本判断），B 上提示“A 已锁屏，操作不会生效”，并给一个打开“桌面”的入口。【我定的】用户看到“锁屏时鼠标无效”很可能就是在 app 会话里，所以 app 会话也要提示。老版本客户端收不到这条提示，行为和现在一样。
- 输入系统密码：
  1. B 发新消息 `unlock(password)`（类型 32，client → host）。
  2. 被控端先检查 `screenLocked()`，不是锁屏就丢弃，回一条 `error("A 没有锁屏，没有输入密码")`。这一步是为了满足 §1 的第二条反目标。
  3. 是锁屏的话：唤出密码框（移动鼠标加一次点击），等 1 秒左右，按字符逐个注入密码（`keyboardSetUnicodeString`），再按回车。
  4. 不管成功与否，被控端都不保存密码，也不写进日志。
- 记住密码：
  - 密码只存在 B 上，按设备（A 的 id）存，放在 B 的数据目录里的本机私有部分，文件权限 0600，不同步，不经过中继。存储形式只做简单混淆，不当安全措施（和 RustDesk 一样）。具体文件位置由实现者定，但不能放进会被同步的 `shared/` 目录。
  - “输入系统密码”的对话框里有：密码框、“记住密码”、“连上时自动输入”。
  - 勾了“连上时自动输入”且记住了密码时，只在桌面会话刚连上（包括断线重连）、A 报告正处于锁屏的那一刻自动输入一次。【我定的】会话进行中 A 上有人主动锁屏，不自动解锁，只显示提示条，免得 A 前的人刚锁上就被 B 解开。
  - 多块屏时每条会话都会收到 31，自动输入按设备只做一次，走主屏的会话。
  - 输错了不再重试，提示“密码可能不对”。判断方法：输入后 5 秒仍是锁屏。
- 锁屏时能不能抓到画面，要实测（§6 第 1 步）。如果抓到的是黑屏或旧画面，提示和解锁照样能用，只是 B 看不见锁屏界面。提示里要写明这一点。

### 4.5 B 端：主屏在主窗口，其余开子窗口

- 点“桌面”时，GUI 先拿到 A 的 `displays`：
  - 主屏（`main: true`，有菜单栏的那块）开一条会话，像 app 一样显示在主窗口的舞台里。
  - 其余每块屏各开一条会话，显示在独立的 NSWindow 里，标题是“<设备名> · 屏幕 N”。
- 子窗口复用 `DetachedWindow` 的窗口外壳。它装的是一条独立会话的整屏窗口，不是同一会话里拆出来的 A 窗口。和现有拆分窗口不同，它一开始就是独立窗口，关掉它就结束这条会话，不会“回到舞台”。
- 子窗口只有画面、锁屏提示条和“输入系统密码”按钮（点了在主窗口里弹对话框），没有自己的画质菜单、流量显示、输入框、剪贴板和传输界面。【我定的】画质和帧率跟着主屏会话走，在主窗口里改就同时改所有屏。桌面是偶尔用的，不值得把舞台的整套界面移植到原生窗口里。
- 关闭和断线：
  - 关掉某个子窗口，只结束那块屏的会话。
  - 在主窗口里关掉“桌面”，就结束这台 A 上的全部桌面会话，子窗口一起关。
  - 某条会话断线重连时，只影响它自己的窗口。
- 会话列表和概览里，一台 A 的桌面只显示成一项：“桌面”，后面写屏幕数。
- A 中途接上或拔掉显示器时（桌面打开期间 GUI 每 30 秒重新拉一次 `displays`，不加新消息）【我定的】：
  - 新出现的屏不自动打开。【我定的】桌面这一项上提示“A 多了一块屏”，点一下再开。
  - 消失的屏，它的会话结束，窗口关闭。
- Linux 版 GUI 不支持子窗口。【我定的】在 Linux 上只开主屏，舞台上方给一排“屏幕 1 / 屏幕 2”按钮，点哪块就切到哪块（关掉当前会话，开新会话）。
- 画质和帧率沿用用户在 app 会话里的设置。整屏的分辨率一般比单个 app 大，编码不改（只传变化的块），实测里要看看 4K 屏的流量和卡顿。

### 4.6 访问日志

桌面会话的开始和结束照常记录，应用名写“桌面（屏幕 N）”。“输入系统密码”记一条“输入了系统密码”，不带密码本身。

## 5. 实现方式的比较

| 方式 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| 每块屏一条会话 | `rapp-host` 加整屏模式，一块屏一个进程、一条连接 | 几乎不改协议，复用全部编码和弱网处理；屏多时进程和连接也多 | **用户选定** |
| 一条会话带所有屏 | 几块屏拼成一张大画布，用“拆分窗口”显示各屏 | 要升协议，和 `feat/scroll-copy` 的 v9 冲突；混合 DPI 很别扭 | 不选 |
| 单独的 `rapp-desktop` | 像终端那样单独一个程序 | 抓屏、编码、输入要重写一遍 | 不选 |

## 6. 建议的顺序

1. **实测（一次性，代码不留）**：在一台 A 上改好输入注入（§4.3），然后锁屏，确认三件事：
   - 整屏抓取在锁屏时能不能抓到锁屏界面；
   - 注入的鼠标能不能唤出密码框；
   - 注入的字符加回车能不能解锁。

   结果写进本文，决定 §4.4 的提示文字。如果画面能看到但输不进密码：桌面照常做，§4.4 里的密码部分（32、对话框、记住密码）先不做，提示条改成“请到 A 前解锁”，README 不改锁屏那句；回来告诉用户，再决定要不要另起一份 root 辅助进程的规格。【我定的】
2. 输入注入修正，加上 app 会话的回归测试。
3. 被控端整屏模式、`displays` 列表、`desktop:` 分流。
4. 锁屏消息（31）和解锁消息（32）。
5. GUI：应用列表里的“桌面”和常用、主屏嵌入、子窗口、提示条、密码对话框、删除屏幕共享按钮。
6. Linux 版 GUI 的屏幕切换。
7. README：把“A 不能锁屏”改成“锁屏后可以在‘桌面’里输入密码解锁；睡眠、关机、开机后的登录窗口仍然不行”。

## 7. 留给实现者

- 密码文件放在 B 数据目录里的具体位置，以及混淆方式（不进 `shared/`）。
- 唤出密码框的具体动作和等待时间，以实测为准。
- 子窗口的初始位置和大小（建议放到 B 的副屏上，没有副屏就和主窗口错开）。
- 显示器名字从哪里取（`NSScreen.localizedName` 或 `CGDisplay` 系列）。
