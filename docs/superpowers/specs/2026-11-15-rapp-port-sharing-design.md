## 1. 一句话和边界

**一台设备把本机的某个端口注册成"分享"，其他持 key 的设备就能用 `名字.rapp:端口` 访问它。** 路上走的是 rapp 已有的设备连接：同一个 key、设备之间 TLS 1.3 互相验证、局域网优先、不通时经 relay。公网上不出现任何服务端口。

用户要懂的词只有两个：**分享**、**名字**。

本文的用词（后三个只在本文里用，不出现在界面的正常路径上）：

| 词 | 意思 |
|---|---|
| 分享方 | 注册了端口、让别人访问的设备 |
| 访问方 | 去访问别人端口的设备 |
| 普通设备 | 填了主 key 的设备。能分享，也能访问 |
| 服务器设备 | 用服务器 key 接入的设备。只能分享，只能被访问 |
| 入口 | 访问方机器上，让 `名字.rapp:端口` 生效的那一部分 |

各类设备的角色（S7、S8、S11）：

| 设备 | 分享端口 | 访问别人 | 用哪把 key |
|---|---|---|---|
| Mac、Windows、Linux 桌面、PC 平板 | 能 | 能，系统里任何程序 | 主 key |
| 无界面 Linux | 能 | 不做 | 服务器 key |
| iPad、Android 平板、手机 | 不能 | 能，只在 rapp 内置浏览器里 | 主 key |

不做（第一版）：

- 公网入口：没装 rapp 的一方（手机浏览器、云端的 AI 产品、外部 webhook）访问不到（S3）。
- 企业的整套能力（个人身份、按组授权、集中审计）。另立规格"组织模式"（§4.4）。
- UDP。只转发 TCP。
- 把端口转发到分享方本机以外的地址（比如它局域网里的 NAS、路由器）。只接到分享方自己的 `127.0.0.1`。这一条要一直守住：一旦能转发到别的地址，每台装了 rapp 的机器都成了进入那个网段的网关。
- 访问方自己起别名、自己指定本机端口（`ssh -L` 那种）。
- 无界面 Linux 上的入口、终端和画面。
- iPad、Android 上系统层的 `.rapp` 域名（要靠 VPN 类型的系统扩展，用户没选，U133）。
- 打洞。照 2c §6，放到以后。所以不在同一个局域网的两台设备，流量都经 relay。

不能出现的结果（做成了也算失败）：

- 公网上多出任何一个服务端口；relay 上出现 HTTP 入口。
- relay 看到设备名、端口号或者任何内容。
- 用户需要知道、输入或维护任何 IP；出现虚拟网卡、路由、要用户理解的地址段（S10）。
- 没注册的端口被访问到。
- 一台服务器被攻破以后，对方能借它的 key 进入别的设备。
- 每加一个服务，要在访问方再配一次。
- 转发大流量时，远程会话明显变卡。
- 为了安全或合规，个人用户在正常的路上多出一步操作（S15）。

## 2. 用户看到的

全部操作只有三件事。

**分享**（在有服务的机器上）：

```
$ rapp share 8000
已分享：http://gpu1.rapp:8000
```

或者在"本机"面板里：面板列出这台机器上正在监听的端口，每行一个开关，拨一下就是分享。不用输数字。

```
本机正在监听的端口          分享
8000    python            [开]   http://gpu1.rapp:8000   [复制]
11434   ollama            [关]
22      sshd              [关]
```

**访问**（在任何一台装了 rapp 的桌面机上）：直接用，不用配置。

```
http://gpu1.rapp:8000/           浏览器、curl、MCP 客户端
ssh gpu1.rapp                    scp、rsync、git 一样
```

或者在设备面板里点一下 gpu1 的 8000。平板和手机上只有这一种，点开是 rapp 内置的浏览器。

```
设备            域名                       分享的端口（点一下打开）
gpu1            gpu1.rapp                  8000  11434  22
mini            mini.rapp                  8888
书房的 Mac      bruces-macbook-pro.rapp    （没有分享）
```

**加一台无界面的服务器**：在桌面机的设备面板上点"添加服务器"，复制它给的那一行，到服务器上粘贴运行。

```
curl -fsSL https://rapphub.com/install.sh | sh -s -- <入网串> --share 22,8000
```

（安装脚本的地址是举例。`--share` 可以不写，之后在服务器上 `rapp share`。）

**名字是自动的**。三种都作数（S12）：

```
123456789.rapp             9 位 ID，永远可用
bruces-macbook-pro.rapp    机器名的小写，自动有；重名时自动加序号
gpu1.rapp                  短名。想要更好记的名字时才起：rapp name gpu1
```

**用户不需要做的**：启用域名（装 rapp 时已经做了）、配 SSH、记端口号、知道服务器 key 是什么、处理重名。

## 3. 做法的选择

要解决的核心问题：让"另一台设备上的端口"在访问方看起来就是一个普通的地址，同时不开公网端口、不让 relay 看到内容。

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | **在已有的设备连接上加一种请求"接到你本机的某个端口"；访问方本机有一个入口，把 `名字.rapp:端口` 接到这种请求上** | 信任、加密、选路、relay 全部沿用，relay 几乎不改；没有虚拟网卡和路由；一个 key 管到底 | 桌面上启用域名要管理员权限（并进安装）；很多本机服务只认 `localhost`，要做 HTTP 适配（§10） |
| 乙 | 虚拟网卡加虚拟 IP（Tailscale、WireGuard 的模式） | 任何协议都通，包括 UDP | 就是用户嫌麻烦的那种：多一层网络要维护；平板上占 VPN 位置；和 S10 相悖 |
| 丙 | 在 relay 的公网 IP 上开入口（frp 的模式） | 没装 rapp 的也能访问 | relay 会看到内容，没认证的人能敲门，和 relay 规格的 R1、R3 相悖；每个服务仍要配端口 |
| 丁 | 只做本机代理，浏览器和各个程序各自配代理 | 不要管理员权限 | 做不到"任何程序直接用"；SSH、curl、MCP 客户端都要单独配 |
| 戊 | frp 的点对点模式，或 SSH 反向隧道 | 现成 | 另一套认证、另一个守护进程；每个服务仍要配端口 |

**选甲**（用户已定：U130 定了不做公网入口，U132 定了域名形式，U134 定了注册端口和不要虚拟网）。丁在平板的内置浏览器内部被用到，那里不需要用户配置（§12）。

入口这一层还有一个选择：

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| A | **每台设备在访问方本机对应一个回环地址**（127 开头，只在本机有效） | 几台 host 用同一个端口也不冲突；任何 TCP 协议都行 | 多一张内部的"设备 → 回环地址"表（用户看不到）；macOS 上开机时要加地址 |
| B | 所有 `.rapp` 名字都指向 `127.0.0.1` | 更小，没有地址表 | 本机自己占着 11434 时，`gpu1.rapp:11434` 没地方接；非 HTTP 协议下两台设备分享同一个端口时分不清 |

**选 A**（我定的，待用户确认，§17）。理由是 S8：几台 host 分享计算能力，很可能跑同一种服务、用同一个端口。回环地址不是虚拟网：没有网卡，没有路由，别的机器看不到，用户从不输入。

## 4. 安全

### 4.1 安全靠什么

1. **公网上没有服务端口。** 每台设备只向外连 relay。NAT 后面的机器不开任何入站端口。对外开着的仍然只有 relay 的那一个 UDP 端口。
2. **只有持 key 的设备能连。** 沿用 relay 规格 §6、§7：入网、设备密钥、端到端 TLS 1.3。relay 被攻破也看不到内容、冒充不了设备。
3. **只交出注册过的端口。** 默认什么都不交出，SSH 也要注册一次（我定的）。每个分享还可以写明只给哪几台设备（§6）。
4. **服务器只能被访问**（§8，S13）。
5. **入口只在本机回环地址上监听。** 同一个局域网里的其他机器用不了。
6. **留记录**（§14.3）。
7. **管理员可以用一个文件统一限制**（§14.2）。

### 4.2 威胁表（接在 relay 规格 §4 后面）

| 代号 | 是谁 | 能做什么 |
|---|---|---|
| T5 | 拿到主 key 的人 | 和以前一样：是自己人。现在还能访问所有设备分享的端口（没有写明"只给谁"的那些）。（面板增补，2026-11-16）还能远程在任何一台普通设备或服务器设备上打开新的端口、改"只给谁"（面板增补 §3） |
| T6 | 拿到服务器 key 的人（比如攻破了一台服务器） | 能作为一台新的服务器设备入网、分享端口、占用还没人用的名字；在 relay 同时被攻破时，还能冒充一台重装过的服务器（§7.3）。**不能**访问任何设备分享的端口，不能远程操作任何设备，不能抢已经有主的名字和 ID |
| T7 | 访问方机器上的其他本机用户和程序 | 能连入口，也就能访问别的设备分享的端口。入口只该开在自己一个人用的机器上；这也是无界面 Linux 不带入口的原因之一 |
| T8 | 访问方浏览器里的恶意网页 | 被 §10.3 的检查挡住；挡不住的部分和这些服务在自己机器上面对的一样 |
| T9 | 让访问方把 `.rapp` 的名字解析到别处的人或软件（§16 第 1、2 条的情况） | 浏览器会把明文的 http 请求发到错的地址。https（§15 第 6 步）之后，解析错了浏览器会报错而不是照发 |

### 4.3 已知的缺口

- 主 key 仍然是总钥匙（relay 规格 §4.2 的 T5）。
- （面板增补，2026-11-16）**"只给谁"挡不住持主 key 的设备**：它可以远程把自己加进去。"只给谁"是防误用的默认范围，不是限制。要让服务器的端口只由服务器自己决定，等托管策略文件的"不接受远程设置"（§14.2）。
- 被吊销的设备在同一个局域网里仍然被认识它的设备接受（2c §6）。
- **分享 SSH，或者分享一个本机代理的端口，等于把那台机器能到达的网络也交了出去**（SSH 自带转发）。"只接到本机"的保证在这里挡不住。注册这类端口时提醒一句（§6）。
- 分享的服务如果自己没有登录（很多模型服务、开发服务器、MCP 服务器都没有），所有能访问它的设备都能直接用。

### 4.4 适用范围和企业使用（S14）

安全评审的结论：**个人和小团队使用可以通过；作为企业的正式工具，现在不能通过。** 五条阻断项（没有个人身份、没有权限区分、安全团队管不了、日志达不到审计要求、权限收不干净）都来自"有 key 就互信"这一条，它是用户为个人使用定的（relay 规格 R10、R11）。

这一稿做的：

- **留了四处位置**，个人使用时都不出现：每个分享的"只给谁"和统一的授权检查点（§5.1、§6）；托管策略文件（§14.2）；访问记录的逐条模式和外送（§14.3）；https 作为企业使用的前提（§15）。
- **不做**：个人身份、接公司的登录系统、按组授权、短期凭证、集中审计、一次性入网凭据、多节点。这些归"组织模式"，另立规格，和"一把 key"并存：个人用 key，企业用组织模式。排在本文第 3 步之后（我定的）。

本文的适用范围，写进使用说明：

- 给个人和互相信任的小团队用。
- 不用于必须经过堡垒机（先审批、全程记录）的生产环境特权访问。
- 一份设计文档保证不了合规；那取决于企业按哪套标准、在哪个国家被审。

## 5. 结构

只有三样东西：

| | 在哪 | 是什么 |
|---|---|---|
| 分享表 | 分享方的 `rapp-service` | 这台设备交出哪些本机端口（§6） |
| 名字 | relay 登记，访问方查询 | 短名、机器名各对应哪台设备（§7） |
| 入口 | 访问方的 `rapp-service`（桌面）；app 内（平板、手机） | 把 `名字.rapp:端口` 上的连接接到对方的端口（§9、§12） |

入口放在 `rapp-service` 里，不放在 `rapp-hub` 里（我定的）：服务一直在跑，界面关着的时候 host 之间也要通。现在向外拨号的代码在 hub（`rust/hub/src/link.rs` 的 `Dialer`），要挪成 service 和 hub 共用。（实现注，2026-11-16）第 1 步（上）没有挪：hub 的拨号和主机列表、在线探测、升级调度缠在一起，又有几个分支同时在改 hub，所以在 `rapp-conn` 里新写了一个小的 `Outbound`（`rust/conn/src/dial.rs`），只有"局域网 → relay"两档；service 用它，hub 还用自己的。让 hub 也改用它，是以后单独的一次重构。见计划 `docs/superpowers/plans/2026-11-15-port-sharing-1a-base.md` 的"计划定的"第 1 条。

### 5.1 设备之间新增的请求

走 relay 规格的 L4（设备请求），一条流一个请求，一行 JSON。

| 请求 | 内容 | 回复 |
|---|---|---|
| `list_shares` | `{"op":"list_shares"}` | `{"ok":true,"shares":[{"port":8000,"note":"…"}],"short":"gpu1","machine":"ubuntu-gpu"}`。只列出问的这台设备有权访问的 |
| `forward` | `{"op":"forward","port":8000}` | `{"ok":true}`，此后这条流就是那个端口上的字节；错误 `not shared`、`not allowed`、`refused`（端口上没有服务在听）、`limit` |

**一个授权检查点**（安全评审 L1）。分享方受理 `forward` 和 `list_shares` 之前，按这个顺序过一遍，全在一个函数里：

1. 这条连接是按 key 互信的吗（`rapp/2` 直连，或经 relay 的端到端流）。旧的密码认证连接上一律回 `not supported`。
2. 来的是普通设备吗（服务器设备发来的一律拒绝，§8.3）。
3. 托管策略许不许（§14.2）。
4. 这个端口分享了吗。
5. 这个分享给不给这台设备（§6 的"只给谁"）。

以后组织模式按人、按组授权，只是往这个函数里加规则，别处不用动。

（面板增补，2026-11-16）远程设置的三个请求 `shares`（整张表和目标设备认识的设备）、`share`、`unshare` 也走这个检查点，只过前三步。格式和规则见面板增补 §5。

其他规则：

- 分享方连本机的 `127.0.0.1:端口`；连不上再试 `[::1]:端口`。
- 半关闭要保留（一头写完、另一头还在写），否则 SSH、HTTP 的某些用法会断。
- 每台来访设备同时转发的连接有上限（默认 256，我定的），超了回 `limit`。

### 5.2 经 relay 时不能每条连接各握一次手

relay 规格里，经中继的每一条流都要在里面再做一次 TLS 握手。远程会话一个会话一条流，这没问题。网页不一样：打开一个页面就是几十条 TCP 连接。

要求（我定的）：**一对设备之间经 relay 只建一条长开的加密通道，转发的连接在它里面复用。** 通道建好以后，每新开一条转发连接，额外的耗时不超过两台设备经 relay 的一个往返。用什么复用、要不要先量一量"每条各握一次手"到底多慢，留给实现计划。

局域网直连时不需要：一条 QUIC 连接上本来就能开很多条流。

（实现注，2026-11-16）通道是 `rapp-conn` 里自己写的复用层（`rust/conn/src/mux.rs`），帧格式和窗口照实现计划"计划定的"第 1、2 条。第一条连接和建通道一起发（两个往返），之后每条一个往返。旧分享方对 `mux` 回 `unknown op` 时，访问方退回每条一流，记 10 分钟。通道开着时不再试局域网，空闲 5 分钟关。本机加了 25 ms 单向延迟的测量：旧式 `open_seq` 中位数约 117 ms，通道约 57 ms，见 `docs/superpowers/measurements/2026-11-16-port-sharing-mux.md`。

### 5.3 不拖慢远程会话

转发的流和远程会话的流走同一条设备连接。要求：同一对设备之间有大流量转发时，远程会话的输入和画面延迟不明显变差。做法（流的优先级，或限制转发占的份额）和验收的数字留给实现计划，用流畅串流规格 §4.1 的工具量。

（实现注，2026-11-16）优先级只在分享方的 relay 连接上起作用：分享方的通道和旧式单条 `forward` 流读到请求后降到 `-1`，会话流保持默认 `0`；访问方建通道的 relay 流开的时候就设 `-1`。局域网上转发和会话是两条不同的 QUIC 连接，访问方这边会话走 hub 自己的连接，都管不到也不挤在一起，真正挤在一起的只有分享方的 relay 连接（画面和转发下载同向）。quinn 的优先级只决定自己发送缓冲里谁先走，管不到瓶颈上的排队。测量（20 Mbit/s、单向 15 ms、队列 100 ms 的进程内弱网）结果：大转发时会话往返 p50 增加约 80 ms、p95 约 95 ms，不达标（规则 20/40 ms），优先级开和关看不出差别，增加量约等于瓶颈队列的深度；限速或换拥塞控制要用户定。数字和结论见 `docs/superpowers/measurements/2026-11-16-port-sharing-mux.md`。（实现注，2026-11-16）补做了自动让路（用户定的：限速、上限自动探、只在分享方 relay 连接上有会话时生效），设计见 `docs/superpowers/specs/2026-11-16-port-sharing-forward-pacing-design.md`；重测结果见同一份测量文档的"自动让路（§5.3 补做）"一节。

## 6. 分享端口（S9）

- **注册**：`rapp share <端口>…`，或"本机"面板里拨开关（§2）。立刻生效，不用重启。执行完直接打印地址。
- **面板里列出本机正在监听的端口**，带上是哪个程序，每行一个开关（操作评审 M5）。用户不用输数字，也不会输错。
- `rapp share` 不带端口：列出本机的分享、本机的名字、和 relay 连没连上。
- `rapp unshare <端口>`：取消。已经接着的连接立刻断开。
- **注册时那个端口上不必有服务在听。** 服务后启动也行。
- **只给谁**（可选，安全评审 L1）：默认给所有持 key 的普通设备，和不写一样。想收紧时：`rapp share 8000 --allow mini,123456789`，或面板里那一行展开后勾选。存下来的是对方的设备指纹，不是名字。（面板增补，2026-11-16）它是一个默认范围，防误用，不防持主 key 的设备（§4.3）；面板里可以远程改它，候选是目标设备认识的设备加本机。（实现注，2026-11-16）第 1 步（上）里只能写这台设备已经认识的设备：`paired.json` 里对方自报的名字，或者指纹的前几位（至少 8 个十六进制字符），要正好对上一台；对不上回 `unknown device`，对上几台回 `ambiguous device`。上面例子里的 `123456789` 这样的 ID 还不能用（9 位数字会被当成指纹前缀去找）：对方连上来时不带 ID，分享方只能凭指纹认人。
- **提醒，不拦**（安全评审 L4，操作评审 M8）：注册 22、3389、5900、常见的数据库端口、Docker 的接口、本机代理这类端口时，打印一句"分享这个端口，等于把这台机器能到的网络也交出去"。不要求确认。
- **存在哪**：设备数据目录 `local/shares.json`（0600，不进 git）。每项：端口、备注、只给谁、是否原样转发（§10.4）、是否放开公网网页（§10.3）。
- 上限：一台设备最多分享 64 个端口（我定的）。

**命令只有四个**（操作评审 M6）：

| 命令 | 做什么 |
|---|---|
| `rapp share [端口…]` | 分享；不带端口时是列表和状态 |
| `rapp unshare <端口>` | 取消 |
| `rapp hosts` | 别的设备、它们的域名和分享的端口 |
| `rapp add-server` | 打印加服务器的那一行（§11） |

另有两个写在文档"进阶"一节里的：`rapp name <短名>`（§7）、`rapp pipe`（§9.4）。

`rapp` 这个命令名是我定的。现在 `rapp` 是界面程序的名字，`rapp-service` 不接受参数（`rust/service/src/main.rs`），所以要有一个和服务说话的命令行。是给界面程序加子命令，还是另做一个小程序，留给实现计划；无界面的机器上没有界面程序，那里必须有它。

## 7. 名字（S6、S12）

### 7.1 三种名字，一个名字空间

| 名字 | 从哪来 | 规则 |
|---|---|---|
| ID | 现有的 9 位数字 | 永远可用，relay 已经保证不重复 |
| 机器名 | 系统主机名（现有的 `rapp_net::config::hostname()`） | 自动。转小写；其他字符换成连字符；首尾的连字符去掉；结果是纯数字或者空的，就没有机器名 |
| 短名 | 用户想要更好记的名字时，在设备自己身上起 | 小写字母、数字、连字符；字母开头；2 到 32 个字符（长度我定的） |

- 地址是 `<名字>.rapp:<端口>`。`<名字>` 前面还可以有别的层（`a.b.gpu1.rapp`），都算 gpu1：有些网页服务靠子域名区分站点（我定的）。
- 现有的"设备名"（显示用，可以是中文、可以很长）不变。
- 名字在设备自己身上设一次，所有访问方看到的都一样。所以写着 `gpu1.rapp` 的配置可以原样拷到另一台机器上用。没选"访问方各自起别名"，理由是那样每台都要配，而且同一台设备在不同机器上名字不一样。

### 7.2 全局不冲突，由 relay 把关（S12）

只有 relay 知道所有设备，包括当时不在线的。设备之间互相问，问不到离线的那台。

- 设备向 relay 登记自己的名字。relay 把名字绑到这台设备的密钥上，和现在绑 ID 是同一个做法。别的设备再登记同一个名字，被拒绝。
- **relay 存的是名字的指纹，不是名字。** 指纹 = 用 key 推出的一个密值对名字算的消息认证码。relay 没有 key，算不出、也猜不出原名。relay 规格 §4.3 的"relay 不知道设备名"仍然成立。
- 短名和机器名在同一个名字空间里：你的短名不能和别人的机器名一样，反过来也是。
- **提交短名时当场检查**（用户定的，U136）：被占了就拒绝，不存下来，提示"已被占用"。
- **机器名重名时自动加序号**（操作评审 M4，我定的）：`ubuntu` 被占了，这台就登记 `ubuntu-2`，再被占就 `-3`，依此类推。登记上以后不再变，在 `rapp share` 和面板里告诉用户它叫什么。用户什么都不用做。
- **改短名**：旧名字立刻释放。界面提醒：用旧名字写的配置会失效。
- 设备被吊销或者 `unbind`：它的名字一起释放。

### 7.3 访问方怎么查

1. 名字是 9 位数字：就是 ID。
2. 否则算出指纹，问 relay 是哪个 ID（§13 的 `resolve`）。结果在本机缓存。
3. 和那台设备连一次，按现有的办法互信，取它的 `list_shares`。

所以一台新设备填好接入点和 key 以后，直接写 `http://gpu1.rapp:8000` 就能用，不需要先和 gpu1 连过。

**名字换了设备：自动接受并提示**（操作评审 M7，我定的）。访问方记着每个名字对应的设备指纹。以后 relay 说这个名字换了一台设备（比如服务器重装过），只要新设备能给出对的互信证明，就自动重新认识，界面上留一条提示。这和 relay 规格 §7.2 对"对方的指纹变了"的处理一致。

第 1 稿定的是"拒绝，用户确认一次"。改掉的原因是服务器重装一次，每一台访问过它的设备都要确认一次。代价写在 §4.2 的 T6：relay 被攻破、同时有人拿到服务器 key 时，对方能冒充一台已有的服务器。SSH 自己的 `known_hosts` 检查不受影响，照样会报。严格的做法留给组织模式。

### 7.4 没有 relay 时

只在局域网里用 `ID@地址` 直连、没有 relay 的时候，没有全局的裁判。退回到每台访问方各自先到先得：先认识的那台占着名字，后来的重名设备只能用 ID。

## 8. 服务器 key（S13）

### 8.1 用户看到的

用户平时看不到它。加服务器时点"添加服务器"，得到一行命令（§11），服务器 key 包在那一行的入网串里。

要点：

- 它由主 key 单向推出来，普通设备上不存，需要时当场算。不用另外保管。
- 用它接入的设备：能入网、能登记名字、能分享端口、能被普通设备访问。**它发起的任何访问，所有设备都不接受；它也访问不了别的服务器。**
- 从它推不回主 key。
- 换 key（2c）时它跟着变，每台服务器上要重新运行一次 `rapp add-server` 给的那一行。

用户已接受（U138："行吧"）。

### 8.2 构成

主 key 的"根"（relay 规格 §6.2）用现有的单向推导再推出三样：

| 值 | 谁知道 | 用来做什么 |
|---|---|---|
| 服务器根 | 普通设备、服务器设备 | 像主 key 的"根"一样，再推出服务器的入网口令、服务器的信任口令、名字指纹用的密值 |
| 来访签名的私钥 | 只有普通设备 | 普通设备访问服务器时，对这一次握手签名 |
| 来访签名的公钥 | 都知道 | 服务器用它验证"来的是持主 key 的设备" |

服务器 key = relay 指纹的前 16 字节 + 服务器根 + 来访签名的公钥。大约 110 个字符（主 key 是 56 个）。

为什么要多一把公钥：如果服务器和访问方只共用一个口令（现在普通设备之间就是这样），那么拿到服务器 key 的人也有这个口令，就能冒充访问方去敲别的服务器。用签名以后，服务器只能验证、不能伪造。

**入网串** = 接入点 + 服务器 key，编成一串。它是"添加服务器"那一行里唯一必须的参数。

### 8.3 谁接受谁

| 发起方 → 接受方 | 发起方出示什么 | 结果 |
|---|---|---|
| 普通 → 普通 | 现有的互信证明（主 key 的信任口令） | 和现在一样 |
| 普通 → 服务器 | 来访签名，绑在这一次握手上 | 接受。服务器用服务器的信任口令回一个证明，访问方把它记成"服务器" |
| 服务器 → 普通 | 它没有主 key 的信任口令 | 拒绝。已经记成"服务器"的设备，它发来的请求也一律拒绝 |
| 服务器 → 服务器 | 它没有签名私钥 | 拒绝 |

- `paired.json` 的每一项多一个角色：普通或服务器。
- 签名和证明都绑在当次握手上，做法照 relay 规格 §7.2。签名算法用 Ed25519（我定的：现有的库能从一个种子直接得到密钥对）。不自己设计算法。
- relay 那一侧也拦一道（§13）：服务器设备发的 `connect`、`relay`、`resolve` 被拒绝。这只是多一层；真正的门在设备上，因为 relay 本身不被信任。

## 9. 入口：桌面（Mac、Linux 桌面、Windows、PC 平板）

### 9.1 三件事

1. **回答 `.rapp` 的域名查询。** `rapp-service` 里有一个只回答 `.rapp` 的小解析器，只在本机回环地址上听。查到的名字回它对应的回环地址；不认识的回"没有这个名字"；IPv6 的查询立刻回"没有"，不让程序干等。
2. **每台设备一个回环地址。** 从一段固定的回环地址里分配（比如 `127.77.0.x`，具体哪一段留给实现计划），存在 `local/` 下，分配以后不变。同一个名字今天和明天指向同一个地址。
3. **在那个地址上、对方分享的每个端口上监听，22 也一样。** 有连接进来，就向对方发 `forward`，两头对接。

对方分享的端口从 `list_shares` 得到，缓存在本机；对方的分享有变化时要跟上（怎么得知变化留给实现计划）。对方不在线时：监听照旧，连接进来后立刻断开。

第一次查一个从没用过的名字时，解析器要等监听准备好了再回答（问 relay、连上对方、取到分享的端口），否则程序拿到地址马上去连会扑空。最多等几秒，超时就照常回答；具体多久留给实现计划。

### 9.2 系统层怎么生效：并进安装（操作评审 M1）

`.rapp` 不是系统认识的域名，没有不要管理员权限的做法。要做的事只有一次："告诉系统 `.rapp` 结尾的名字去问本机的 rapp"，外加 macOS 上开机时加回环地址、允许在 1024 以下的端口上监听。之后设备增减都不再需要管理员权限。

**这些事放进安装包的安装脚本里做，用户装完就能用，不单独点"启用"。**

| 系统 | 安装包 | 打算怎么做 | 验证过吗 |
|---|---|---|---|
| macOS | `.pkg`，已经带以管理员身份运行的安装脚本（`scripts/pkg/postinstall`） | `/etc/resolver/rapp` 指向本机的解析器；一个系统启动项在开机时给回环口加上那一段地址 | **有风险**：有报告说新版 macOS 上这个机制对自造的后缀失效（§16 第 1 条）。必须先实测；不成立的话换做法 |
| Linux 桌面 | Arch 的包（`scripts/package-linux.sh`），可以带安装钩子 | 回环地址不用加（整个 127 段本来就在本机）。域名交给本机解析器的办法要先验证 | 未验证 |
| Windows | 安装程序 | 系统自带的"某个后缀交给某个解析器"的规则；回环地址不用加 | 未验证 |

两种人装完不会自动生效，界面上给他们留一个"启用 `.rapp` 域名"的按钮（点一次，输一次管理员密码）：

- 从老版本自动升级上来的（自动升级不经过安装包）。
- 用免安装的压缩包的（Linux 的 portable 包）。

没启用时：设备面板里点端口仍然能打开（走 §9.4 的后备），`rapp pipe` 可用。

安装脚本写了哪些文件、起了哪些系统级的东西，要列成清单写进文档；卸载时全部还原；不留常驻的高权限进程（安全评审 S13）。

### 9.3 会碰到的冲突，和提示（操作评审 M9）

每一种都要告诉用户现在该做什么。

| 情况 | 提示 |
|---|---|
| 对方没分享这个端口 | "gpu1 没有分享 8000。在 gpu1 上运行 rapp share 8000" |
| 这个分享不给这台设备 | "gpu1 的 8000 没有分享给这台设备" |
| 对方不在线 | "gpu1 不在线" |
| 本机有服务占着同一个端口（Linux 上监听"所有地址"时尤其会） | "本机的 8000 被 xxx 占着，gpu1.rapp:8000 接不了。可以用 rapp pipe gpu1 8000" |
| 1024 以下的端口监听不了 | "需要权限，点这里启用"；SSH 可以改走 §9.4 的后备 |
| 域名没启用 | "还没有启用 .rapp 域名。点这里启用（需要管理员密码）" |
| 设备太多，回环地址用完（macOS 上开机时加的地址数固定，默认 64，我定的） | 超了的设备只能在面板里点开，或用 `rapp pipe` |

提示出现在三个地方：`rapp hosts`、设备面板里那个端口旁边、以及（是 HTTP 时）浏览器里的一页说明，而不是一个空白的错误页。

### 9.4 后备：`rapp pipe`

`rapp pipe <名字> <端口>`：把标准输入输出接到那台设备的那个端口。名字带不带 `.rapp` 都认。它只和本机的 `rapp-service` 说话，不需要域名解析、不需要监听、不需要管理员权限。

它不出现在正常的路上（操作评审 M2）。用在两处：

- 入口监听不了的时候（§9.3 的几种情况），手动用。
- SSH 的后备：22 端口监听不了、或者域名没启用时，在 `~/.ssh/config` 里加这两行，`ssh gpu1.rapp` 照样通。写在文档里，rapp 不替用户改这个文件，也不问。

```
Host *.rapp
    ProxyCommand rapp pipe %h %p
```

SSH 自己的登录验证（密钥、`known_hosts`）不变，rapp 不碰。


## 10. HTTP 适配

### 10.1 为什么需要

很多跑在本机的服务会检查请求里的 `Host`，只认 `localhost` 和 `127.0.0.1`，别的一律拒绝。这是它们防"恶意网页借浏览器访问本机服务"的办法。据我所知，Ollama、Jupyter、Vite 这类开发服务器、新版的 MCP 服务器框架都有这种检查（没有逐个实测，§16）。浏览器访问 `http://gpu1.rapp:8000` 时，请求里写的是 `Host: gpu1.rapp:8000`，会被这些服务拒绝。

不处理的话，用户得去改每一个服务的配置，和 S15 相悖。

### 10.2 做法

分享方的 `rapp-service` 在把连接接到本机端口之前，看一眼开头的字节：

- **是 HTTP/1.x 的请求**：把请求里的 `Host` 换成 `localhost:端口`；`Origin`、`Referer` 里如果是这台设备自己的 `.rapp` 名字，也换成 `localhost:端口`。响应里 `Location`、`Access-Control-Allow-Origin` 出现的 `localhost:端口`，换回访问方用的那个名字。同一条连接上后面的每个请求同样处理。WebSocket 和流式响应（MCP 用的那种）原样通过。
- **不是**（SSH、数据库、TLS、HTTP/2）：原样转发，一个字节不动。

放在分享方做（我定的）：它知道本机服务认什么；平板的内置浏览器过来也用得上；"要不要适配"这个开关跟着分享的端口走。

改写的范围就是上面列的这几个头。正文里写死的地址不改。

**用成熟的 HTTP 库来解析和重写，不自己写解析器**（安全评审 S3）。这类代码最常见的漏洞是请求走私，自己写最容易出。要做模糊测试，并且拿几个真的服务来验（§19）。

### 10.3 顺带的两条检查

因为适配等于替服务关掉了它自己的那道检查，要补上同样的防护：

1. **`Host` 不是这台设备的 `.rapp` 名字（或 ID）的请求，拒绝。** 防的是恶意网站把自己的域名解析到入口的回环地址上。
2. **公网网页发起的请求，拒绝。** 判断办法：浏览器会标明请求是不是跨站发起的，以及发起的页面是谁。发起页面不是 `.rapp`、不是 `localhost`，而且不是用户自己在地址栏打开或点链接过来的，就拒绝。`mini.rapp` 上的网页调 `gpu1.rapp` 上的接口，放行；之后服务自己的跨域设置照常生效。

第 2 条的精确规则留给实现计划。某个端口确实要让公网网页调用时，注册时加一个选项放开（我定的）。

### 10.4 关掉适配

`rapp share 8000 --raw`：这个端口原样转发，不看内容。给"服务自己已经配好了认 `.rapp` 域名"或者"适配把它弄坏了"的情况用。正常情况下用不到。

## 11. 无界面 Linux（S4、S11）

**这推翻了终端会话规格 §1 的"不做 Linux 无界面的安装包"。** 当时的理由是服务器上已经有 sshd，不想再装一个能给出 shell 的守护进程；并且留了一个例外：服务器在 NAT 后面、谁也 SSH 不到。用户说他的无桌面机器多数在 NAT 后面（U131），正是那个例外。

### 11.1 加一台服务器：一行（操作评审 M3）

在任何一台普通设备上：设备面板点"添加服务器"，或者运行 `rapp add-server`。得到一行，复制到服务器上运行：

```
curl -fsSL https://rapphub.com/install.sh | sh -s -- <入网串> --share 22,8000
```

这一行做完的事：下载并校验程序、装成 systemd 服务、用入网串接入 relay、用机器名登记名字（重名自动加序号）、分享写明的端口、打印这台服务器的域名。

- 名字不用填。服务器的机器名通常本来就起得像样；想改，`rapp name`。
- `--share` 可以不写，之后 `rapp share`。
- 安装脚本要短、读得懂，只做上面这几件事；下载的程序核对哈希。地址是举例，实际放在哪由实现计划定。

**入网串写在命令行里**（我定的，待用户确认，§17）。第 1 稿定的是"key 不从命令行参数传"，因为它会留在 shell 历史和进程列表里。这里反过来的理由：入网串留下的地方和 rapp 自己存 key 的地方是同一台机器、同一个用户；而服务器 key 本来就是为"丢了损失也有限"设计的。更稳的做法保留为第二种用法：命令里不带入网串，脚本运行后问一句"粘贴入网串"。

### 11.2 这个安装包是什么

发布物：`rapp-service` 一个程序、命令行、一个 systemd 单元。`rapp-service` 现在就不依赖任何图形库（`rust/service/Cargo.toml`）。

- **只做分享**：没有入口，不碰系统的域名解析，不需要回环地址，用普通用户身份运行。
- **不给终端、不给画面**：`list_apps` 回空；终端会话默认关（它本来就有开关，`local/term.json`）。它自己不给出 shell；`ssh gpu1.rapp` 的登录仍然由服务器的 sshd 把关。
- **状态和排错**：`rapp share`（不带参数）一条命令看全：连没连上 relay、ID、名字、角色、分享了什么。
- **升级**：第一版重新运行那一行。现有的自动更新只管 `.app`。
- 架构：x86_64 和 arm64。

以后真有服务器要访问别人，入口的代码和 Linux 桌面是同一份，那时它需要主 key。

终端会话规格里"服务器上不装东西、由一台代管设备 SSH 过去"的那条路不变。经它转发端口（用 SSH 自带的转发）排在 §15 的"以后"。

## 12. 平板和手机（S7）

- 只当访问方。不分享端口（iPad、Android 上本来也没有 `rapp-service`，反馈文档 U18）。
- **rapp 内置一个浏览器**。平时不用输地址：在设备面板里点一个分享的端口就打开。也可以在地址栏里写 `http://gpu1.rapp:8000/`。页面的请求不出 app：交给 app 里的同一份底座代码，查名字、连设备、发 `forward`。没有 VPN，没有系统设置要改。
- Safari 和其他 app 用不了 `.rapp`。平板上的终端需求由 rapp 已有的终端会话承担。
- 它跟着平板主控台一起做。现在 `gui/` 下只有 macos、linux、windows 三个目标；平板上要先把 hub 从子进程改成库（反馈文档 U16 小节已经记了这一条）。
- 内置浏览器怎么把请求交给 app（两个系统各自的网页控件支不支持、Flutter 这边用什么）未验证，留到做平板的时候。

## 13. relay 的改动

relay 规格说 relay 只做登记、牵线、接流。这次加的两处都属于"登记"，relay 仍然不知道任何业务，也不知道任何名字。

**一、名字指纹**

| 请求 | 内容 | 回复 |
|---|---|---|
| `register` 多一个字段 | `"names":["<指纹>", …]`（最多 2 个：短名、机器名） | 回复里多 `"names":{"<指纹>":"ok" 或 "taken"}` |
| `claim`（新） | `{"op":"claim","name":"<指纹>","release":"<旧指纹>"}` | `{"ok":true}`；错误 `name taken`。占新的和放旧的是一步完成的 |
| `resolve`（新） | `{"op":"resolve","name":"<指纹>"}` | `{"ok":true,"id":"123456789"}`；错误 `unknown name` |

- 登记簿的设备记录多一项：这台设备占着的指纹。
- 机器名自动加序号（§7.2）由设备来做：`taken` 了就换下一个序号的指纹再试，有次数上限。relay 不知道这些指纹之间有关系。
- `resolve` 和 `connect` 一样限速，防止有人拿它来试名字。
- 审计多一种事件 `name`（占用、释放、被拒，只记指纹）。
- 请求的名字和字段是我的提议，最后以实现计划为准。

**二、设备的角色**

- `rapp-relay key` 生成 key 时，除了主 key 的入网口令的哈希，再存一份服务器入网口令的哈希。入网时对上哪一个，这台设备就是哪种角色，记在登记簿里。
- 服务器角色的设备：可以 `register`、`claim`，可以被 `connect`、`relay`；它自己发的 `connect`、`relay`、`resolve` 回 `host only`。
- `rapp-relay rotate-key` 同时换掉两份哈希；2c 里"所有设备要重新输入 key"对服务器设备同样成立。
- `rapp-relay devices` 多一栏角色；审计的 `enroll` 多记角色。
- **已经在跑的 relay** 没有第二份哈希。怎么补上，留给实现计划。我的提议：由任意一台已入网的普通设备提交一次，relay 只接受第一次；不用换 key。

relay 规格 §4.3 的"relay 知道什么"多两行：每台设备占着几个名字的指纹；每台设备是哪种角色。

## 14. 配置、策略和记录

### 14.1 设备这一侧新增的文件

都在设备数据目录的 `local/` 下，0600，不进 git。

| 文件 | 内容 |
|---|---|
| `service.json` 多两项 | `short`（短名）；`forward_log`（访问记录的模式，§14.3）。key 的种类由 key 自己的写法区分，不另存 |
| `shares.json` | 分享的端口：端口、备注、只给谁、是否原样转发、是否放开公网网页 |
| `names.json` | 访问方：名字 → 设备指纹、设备 → 回环地址、对方分享的端口的缓存 |
| `paired.json` 每项多一个角色 | 普通、服务器 |

**key 放进系统钥匙串**（安全评审 L5，只取前一半）：桌面设备上，主 key 和设备私钥从普通文件挪进系统自带的钥匙串；没有钥匙串的环境（无界面 Linux）仍然是 0600 的文件。用户看不出区别，不多任何操作。这一条动的是 relay 规格 §10.3 和数据目录规格，随第 4 步一起做。

### 14.2 托管策略文件（安全评审 L2）

**没有这个文件，就什么都不限制**，个人用户永远碰不到它。

一个系统级的只读位置上的文件，只有管理员能写，优先于使用者的一切设置。公司可以用设备管理系统下发它。第一版只有这几项：

| 项 | 意思 |
|---|---|
| 分享 | 允许；禁止；只允许这些端口；禁止这些端口 |
| 入口 | 允许；禁止 |
| 接入点 | 只许连这些 relay |
| 适配 | 强制原样转发 |
| 记录 | 强制逐条记录；送到哪（§14.3） |
| 远程设置 | 接受（默认）；不接受。（面板增补，2026-11-16）不接受时，别的设备发来的 `share`、`unshare` 回 `policy`，`shares` 仍然可以看 |

规则（我定的）：

- 文件存在但读不懂（格式错、有不认识的项）：按最严的处理，分享和入口都关，并在界面和日志里说明。
- 被策略关掉的功能，界面上显示"由管理员管理"，开关是灰的。
- 文件放在哪（各系统的惯例位置）留给实现计划。

### 14.3 记录

- **分享方的访问记录**（可观测性规格）多一种事件"转发"：谁（指纹、自报的名字）访问了哪个端口、走的哪条路、多少字节、多久。
  - 默认按"来访设备 + 端口"合并，每 10 分钟一行，带连接数；一个来访设备第一次访问某个端口立刻记一行（我定的）。网页会开很多连接，逐条记对个人用户没有用。
  - **可以改成每条连接一行**（安全评审 L3）：`forward_log` 设成逐条，或者由策略强制。格式固定，一行一条 JSON。
  - **可以同时写到系统日志或指定的目录**，让企业的日志采集程序直接收走。默认不开。
  - 被拒绝的（没分享、不给这台设备、角色不对、策略不许、§10.3 的两条检查）每次都记，同一原因有限速。
  - 新增分享、取消分享、改名字、名字换了设备，各记一行。（面板增补，2026-11-16）新增分享、取消分享带"谁设的"：本机设的写 `local`，远程设的写那台设备的指纹前 8 位和名字；远程设置被检查点拒绝时也记一行。
- **relay 的审计**：`relayed` 照旧（一条长开的通道一行）；新增 `name`；`enroll` 带角色。
- **永远不记**：两种 key、入网串、任何口令和私钥、流里的内容、请求的网址。

### 14.4 界面

- **本机面板**：正在监听的端口和分享的开关（§2）；这台设备的域名；短名（可选，提交时检查重名）；"启用 `.rapp` 域名"只在没启用时出现。
- **设备面板**：每台设备的域名和分享的端口，点一下打开，长按或右键复制地址；"添加服务器"。（面板增补，2026-11-16）分享端口那一段的样子、远程开关端口、各种状态下显示的字，以面板增补 §6 为准；"本机"面板的监听端口列表仍然在第 4 步。设备的角色是服务器时标出来；它没有 app 列表。
- 界面的正常路径上不出现：回环地址、指纹、角色的解释、HTTP 适配、服务器 key、入网串的内容。
- 视觉上的细节照设计语言，留给界面那一步的计划。

## 19. 测试要求

- **操作步数**（操作评审 §0）：按下表各走一遍，实际动手的次数不超过表里的数。

  | 事 | 最多几步 |
  |---|---|
  | 桌面机上分享一个服务 | 1 |
  | 新装了 rapp 的桌面机第一次用域名访问 | 0 |
  | 加一台无界面服务器并分享端口 | 1（复制并运行一行） |
  | 机器名重名 | 0 |
  | 服务器重装后别的设备继续访问 | 0 |

- **分享**：没分享的端口回 `not shared`；"只给谁"以外的设备回 `not allowed`，并且在它的 `list_shares` 里看不到这一项；取消分享后已有连接断开；端口上没有服务时回 `refused`；半关闭保留；并发上限。
- **授权检查点**：五步各有一个被拒的测试；旧的密码认证连接上发 `forward` 被拒。
- **名字**：三种名字都能解析到同一台设备；短名重名当场被拒；机器名重名时自动得到带序号的名字，并且重启后不变；改名后旧名字释放；relay 的数据卷和日志里搜不到任何名字的原文；名字换了设备时自动重新认识并留下提示和记录。
- **服务器 key**：用服务器 key 入网的设备，角色是服务器；它向普通设备、向另一台服务器发起的连接都被拒；普通设备能访问它；只拿到服务器 key 的进程冒充访问方失败；中间插一个转发的进程时签名验证失败；从服务器 key 的所有字节里推不出主 key 的任何口令（按构造检查）。
- **relay**：服务器角色发 `connect`、`relay`、`resolve` 被拒；`resolve` 的限速；审计里有 `name` 和带角色的 `enroll`。
- **入口**：两台设备分享同一个端口，各自的域名各通各的；`ssh 名字.rapp` 不加任何配置能通；§9.3 每一种情况的提示都出现并且写着下一步；没启用域名时面板里点端口和 `rapp pipe` 可用；卸载后系统的解析设置、启动项、证书全部还原。
- **托管策略**：没有文件时不限制；每一项各一个测试；文件读不懂时分享和入口都关；使用者改不了被策略关掉的开关。
- **HTTP 适配**：拿真的 Ollama、Jupyter、一个 Vite 开发服务器、一个 MCP 服务器（含流式响应）、一个 WebSocket 服务各跑一遍，不改它们的配置；`Host` 不对的请求被拒；公网网页发起的请求被拒，`.rapp` 之间的放行；`--raw` 时一个字节不动；请求走私的常见写法被拒；模糊测试。
- **记录**：默认模式和逐条模式各自的内容；外送到系统日志；被拒的都有记录。
- **性能**：经 relay 打开一个有 50 个请求的页面的时间；复用通道建好后新开一条连接的额外耗时（§5.2）；一条大流量转发进行时，远程会话的延迟（§5.3）。
- **机密全量检查**：所有测试结束后，各处的日志和 relay 的数据卷里搜不到两种 key、入网串、任何口令和私钥。
- **无界面**：在一台没有图形环境的 Linux 上，运行那一行以后能从桌面 `ssh` 上去；非 root 运行；重启后自己恢复。
