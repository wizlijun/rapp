# 设备这一侧的收尾（2c）：吊销、换 key 传下去、"接受新设备"、访问记录、跟着 redirect 走

日期：2026-11-14。上级规格：`docs/superpowers/specs/2026-11-13-rapp-relay-design.md`（下称"relay 规格"）。本文不改 relay 规格的任何决定，只把 2a 计划留给 2c 的几件事落到具体做法上。

## 1. 意图

relay 规格 §7.3、§7.4、§11.2 的设备一侧还没做：

- relay 已经会吊销设备、发吊销名单，但设备收到名单只记一行日志，被吊销的设备拿着 key 仍能被其他设备认。
- `rapp-relay rotate-key` 已经能换 key，但新 key 只能一台一台手填。
- 没有"接受新设备"开关：key 一旦泄露，任何拿着 key 的设备都能被认识。
- 被控端的访问记录里看不到"认识了谁、取消了谁、key 换了"。

2c 把这些补齐，让 relay 规格 §2 的两行成立："要踢掉一台设备 → 在 relay 上吊销它"；"丢了一台设备 → 先吊销它，再换 key"。

## 2. 范围

做：

1. 吊销名单：设备记住、去掉认识、以后两个方向都不认。
2. 换 key 传下去：在一台设备上填新 key，它认识的设备自动换上，再往下传；不在线的上线后拿到。
3. "接受新设备"开关（每台设备的设置里，默认开）。
4. relay 规格 §11.2 的访问记录事件。
5. 设备跟着 relay 的 `redirect` 走（relay 规格 §8、§19.9；第一版 relay 不会发）。
6. 2a 留下的两件小事：设备端口不收单向流；"信任被拒"的日志按来源限速。

不做（用户 2026-11-14 定："打洞那些优化工作，安全性我不确定。请放到以后做"）：

- **打洞**以及别的"少走中继"的优化。跨网连接照旧走中继。`incoming` 照旧只回 `{"ok":true}`，`connect` 回复里的 `public` 照旧不用。见 §9。

不改 relay 服务端，不发版，不改版本号。

## 3. 吊销名单

- relay 每次推 `revoked`（连上时一次、名单变了再一次），设备把名单**并进**本地的 `local/revoked.json`。只加不减（relay 规格 R12 的要求：relay 最多骗设备少信几台）。换了 relay 也不清。
- 文件由被控的一侧（rapp-service）写，操作的一侧（rapp-hub）只读，和 `service.json` 的分工一样。
- 新名单里每一个本来在 `paired.json` 里的指纹：从 `paired.json` 去掉，访问记录记一条"已吊销，不再认识"。
- 以后：
  - 被控的一侧：对方指纹在名单里 → 拒绝，原因 `revoked`，不管它给不给得出对的证明（被吊销的设备手里还有旧 key，所以必须单独拦）。
  - 操作的一侧：主机出示的指纹在名单里 → 不连，错误 `revoked`，GUI 写"已吊销"。
- 名单里有本机自己的指纹不用特别处理：relay 会以关闭码 2 断开本机，2a 已经处理（状态"出错：已吊销"）。

## 4. 换 key 传下去

### 4.1 "谁的 key 更新"

`service.json` 多一个 `key_gen`（整数，没有就是 0）。

- 在设置里填了一个**不同的** key：`key_gen = max(旧 key_gen + 1, 当前 Unix 秒)`。
- 从别的设备那里换上 key：`key_gen` 用对方的。
- 比较：`(key_gen, key 文本)` 大的新。相等就是同一个 key。

为什么不用单纯的时间：一台时钟快了的设备会让它那把旧 key 永远"更新"。为什么不用单纯的计数：一台很久没上线的设备手填了新 key，计数可能比别人小，会被旧 key 盖掉。两者取大：每台设备上单调增加，大体按时间先后，只有时钟错得比两次换 key 的间隔还多时才会选错。（我定的）

### 4.2 只接受同一个 relay 的 key

只换成 relay 那一半和本机现在的 key 一样的 key（都没有 relay 那一半也算一样）。`rotate-key` 不换 relay 的身份，所以正常的换 key 都满足；换 relay 要用户在每台设备上自己填（relay 地址本来也不传）。（我定的）

### 4.3 怎么传：搭在每次握手的 hello 上

不新开请求，也不新开连接。2b 以后 hub 每 30 秒探一次每台主机，每次都握手，所以在线的设备 30 秒内就能换上。

- B（操作的一侧）发 hello 时，如果这条连接对方出示的指纹**等于** `hosts.json` 里存的这台主机的指纹，就带上 `key` 和 `key_gen`。只对认得的主机发：TLS 已经证明了对方是它。
- A（被控的一侧）读 hello：确认信任 B 之后（认识的指纹、或者证明对上，并且不在吊销名单里），B 的更新 → A 换上，记"key 已更换（来自 B 的名字）"。A 的更新 → 在回复里带上 `key` 和 `key_gen`。
- B 读回复：验过 A 之后，A 的更新 → B 换上，同样记一条。
- 换上之后，这台设备再和别的设备握手时又会带上新 key，所以一层一层传下去。不在线的设备下次被连上、或者下次去连别人时拿到。
- 老版本设备不认识这两个字段，忽略它们，什么都不会变。

### 4.4 换 key 不断开任何东西

- 从别人那里换上 key：只存文件，**不**重连 relay（relay 靠指纹认已入网的设备，入网口令只在第一次入网时用），开着的会话不受影响。
- hub 缓存的 relay 连接现在按完整的 key 文本判断要不要重连；改成按 relay 地址、relay 那一半和本机指纹判断，否则 key 一换，B 这边经中继开着的会话会全断。
- 用户自己在设置里改 key：和现在一样，被控的一侧会重连 relay（用户主动的操作）。

### 4.5 B 怎么把 key 存下来

`service.json` 只有 rapp-service 写。hub 换 key 时通过本机 IPC 告诉 service（新命令 `adopt_key`，带 key、`key_gen`、对方的名字），由 service 按 §4.1 的规则决定换不换、存文件、记访问记录。hub 读 `ipc.token` 和 `service.json` 里的 IPC 端口，和 GUI 一样。service 没在运行时，这次就不换，下次握手再说。

### 4.6 安全上的考虑

- key 只在端到端 TLS 里走，只发给 TLS 证明过身份、并且本机信任的设备。日志、事件、错误文本里照旧不出现 key。
- 被吊销的设备连不上任何人，所以拿不到新 key，也推不了 key——这就是"先吊销，再换 key"。
- 一台拿着旧 key 的陌生设备：换 key 之前它本来就能被认识（这是 key 的本义）；换 key 之后，已换上新 key 的设备用新 key 核对证明，它就进不来了。它推来的"更新"的 key 也只会让设备换成它的 key——它本来就有同等的能力。真正的门禁仍是 relay（入网和吊销），符合"relay 是唯一的门"的取舍。

## 5. "接受新设备"开关

- `service.json` 的 `accept_new`，不写就是开（relay 规格 §10.3、§20.3）。
- 关上以后，被控的一侧只认 `paired.json` 里的指纹；不认识的设备即使证明对上也拒绝，原因 `not accepting new devices`，GUI 写"对方不接受新设备"。
- 只管被控的一侧。B 在自己这边加主机是用户本人的操作，不受这个开关影响。
- 换 key 的传递不受影响（只在已经信任的设备之间走）。
- GUI：本机一节里，设了 key 时显示一行"接受新设备"和一个开关。IPC `set_accept_new {"on": bool}`，`status` 多一个 `accept_new`。

## 6. 访问记录（relay 规格 §11.2）

被控端的访问记录（`history`）里新增：

| 事件 | 什么时候 | GUI 的结果一栏 |
|---|---|---|
| `trust`，`result: "paired"` | 认识了一台新设备 | 认识了这台设备 |
| `trust`，`result: "refused"` | 一台设备没被认（原因：证明不对、已吊销、不接受新设备、超时…） | 拒绝认识：原因（警示色） |
| `unpaired` | 因为吊销名单取消了认识 | 已吊销，不再认识（警示色） |
| `accept_new` | 开关被打开或关上 | 开始接受新设备 / 不再接受新设备 |
| `peer_key_changed` | 一台自称同一个 ID 的设备换了指纹（重装过）并被重新认识 | 对方的密钥变了（警示色） |
| `relay`，`error: "relay identity mismatch"` | relay 的身份对不上 | 中继身份对不上（警示色） |
| `key_changed` | key 被换了（`by: "settings"` 或 `by: "peer"`，后者带对方名字），**不记 key** | key 已更换（本机设置）/ key 已更换（来自 X） |

`trust` 的 `result: "known"`（认识的设备每次连上）不进访问记录，否则 30 秒一次的探测会把它刷满。

"对方的密钥变了"要知道对方是谁：B 的 hello 多带本机 ID（自报，不验证），A 在 `paired.json` 里多存这个 ID。新认识的设备自报的 ID 和一个已认识、但指纹不同的设备一样时，记 `peer_key_changed`。只记一条，不去掉旧的那项（ID 是自报的，不能凭它删别人）。（我定的）

"信任被拒"的日志按来源地址限速：同一个来源每分钟最多一行，后面的合进下一行的 `count`。（我定的；防止有人对着公网端口刷日志）

## 7. 跟着 `redirect` 走

relay 对任何请求都可能回 `{"ok":false,"error":"redirect","relay":"主机:端口"}`。设备：

- 在一条 relay 连接的**第一个**请求上收到时（被控的一侧是 `register`，操作的一侧是第一次 `connect`），用同一个 key 去连那个地址，同样核对 relay 的身份，再发一遍这个请求。
- 最多跳一次；第二次再被 redirect，报错 `too many redirects`。
- 跳过去的地址只用于这条连接，不存进设置。下次重连仍从设置里的地址开始。

第一版 relay 不会发 `redirect`，所以这只能用一个假 relay 测。

## 8. 两件小事

- 设备端口（`rapp/2`）不收单向流：服务端的单向流上限设为 0（现在是 quinn 的默认值）。
- "信任被拒"日志限速，见 §6。

## 9. 留到以后的：打洞

用户定了放到以后。留下这些问题给那时的设计：

- 打洞要让被控的一侧向 relay 告诉它的任意公网地址发包。要防的是 relay 或冒充的 `connect` 拿设备当跳板去敲别人（反射、放大）。
- 打通以后走的是公网直连：设备端口在公网可达，要确认"不认识的连接只能发证明、10 秒断开、按来源限速"（relay 规格 §7.3）都已生效。
- NAT 的种类多，本机测不到真实效果，要在 VPS 和两个不同网络下实测。

## 10. 我替你定的

1. `key_gen = max(旧值 + 1, 当前 Unix 秒)`，`(key_gen, key 文本)` 大的新（§4.1）。
2. 只换成同一个 relay 的 key（§4.2）。
3. key 搭在 hello 上传，B 只发给指纹对得上的主机（§4.3）。
4. 从别人那里换 key 不重连 relay；hub 的 relay 连接缓存不再因为 key 变了就重连（§4.4）。
5. hub 通过 IPC 让 service 存 key（§4.5）。
6. "接受新设备"只管被控的一侧（§5）。
7. hello 带自报的 ID，用来发现"对方的密钥变了"，只记不删（§6）。
8. "信任被拒"日志每个来源每分钟一行（§6）。
9. redirect 只在一条连接的第一个请求上跟，最多一次，不存地址（§7）。
